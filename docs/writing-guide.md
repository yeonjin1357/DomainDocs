# 글쓰기 가이드

이 사이트의 글은 읽혀야 해요. 이 가이드는 읽히는 글을 쓰는 규칙이에요. 글을 쓰거나 고치기 전에 끝까지 읽어요.

## 1. 목적

독자는 모니터링 제품을 만드는 개발자예요. 코드는 AI가 쓰고, 독자는 그 결과가 맞는지 판단해요.

판단하려면 도메인 지식이 필요해요. 이 사이트는 그 지식을 쉽고 분명하게 전해요.

최우선 가치는 가독성과 쉬운 이해예요. 읽혀야 머리에 들어오고, 이해돼야 남아요.

### 기초가 먼저, 모니터링은 그 위에

글은 그 도메인이 무엇이고 어떻게 동작하는지부터 다뤄요. 네트워크라면 장비, 인터페이스, 스위치, SNMP가 무엇인지가 먼저예요.

모니터링 관점(화면에 무엇을 보여 주고, 어떤 숫자를 조심할지)은 그 위에 얹어요. 한 글 안에서는 `## 모니터링에서는` 소제목으로, 영역 안에서는 기초 글 뒤에 이어지는 모니터링 글로 얹어요.

기초 글은 처음 보는 사람 기준으로 써요. 같은 영역의 다른 기초 글 말고는 아는 것을 가정하지 않아요.

분량 제한은 없어요. 설명할 게 많으면 길어져도 괜찮아요. 대신 아래 규칙으로 읽히게 써요.

### 반면교사

이전에 만든 100장짜리 지식서(`BOOK.html`)처럼 만들지 않아요. 내용도 재사용하지 않아요. 읽히지 않았던 이유는 다음과 같아요.

| 구분 | 문제 |
| --- | --- |
| 화면 | 본문 폭이 1000px 이상이라 한 줄에 60~70자 |
| 화면 | 100장을 한 파일에 몰아넣어 진척감이 없음 |
| 화면 | 목차·표가 모두 같은 무게라 핵심이 안 보임 |
| 문장 | 문장마다 면책·단서("~라고 주장하지 않습니다")가 붙어 핵심이 묻힘 |
| 문장 | 결론과 "그래서 무엇을 판단할 수 있는지"가 늦게 나옴 |
| 문장 | 한 단락에 새 개념이 서너 개씩 등장 |
| 문장 | 입문 설명과 커널 소스 줄 번호 수준 근거가 같은 높이에 섞임 |

## 2. 글쓰기 규칙

규칙은 열두 가지예요. 규칙마다 나쁜 예와 좋은 예를 하나씩 달았어요.

### 2.1 해요체로 써요

본문 문장은 "~요"나 "~죠"로 끝내요. "~습니다"(합쇼체)나 "~다"(해라체)로 끝내지 않아요.

- 나쁜 예: 평균 응답시간은 전체 요청의 합을 개수로 나눈 값입니다. (해라체 "값이다."도 같아요.)
- 좋은 예: 평균 응답시간은 전체 요청 시간의 합을 요청 개수로 나눈 값이에요.

### 2.2 결론을 먼저 써요

독자가 가장 알고 싶은 것을 첫 문장에 둬요.

- 나쁜 예: 응답시간을 요약하는 방법은 여러 가지가 있고, 각각 장단점이 있어요. 그중 평균은 극단값에 약해요.
- 좋은 예: 평균은 느린 요청을 숨겨요. 느린 요청을 보려면 p99를 봐요.

### 2.3 한 문장에는 정보 하나, 한 단락은 세 문장 이하로 써요

문장은 80자를 넘기지 않아요. 단락은 3문장을 넘기지 않아요.

- 나쁜 예: p99는 요청을 빠른 순서로 줄 세웠을 때 99번째 위치의 값인데, 평균과 달리 극단값에 덜 흔들리지만 표본이 적으면 불안정해서 보통 1분 이상의 구간으로 집계해요.
- 좋은 예: p99는 요청을 빠른 순서로 줄 세웠을 때 99% 위치의 값이에요. 요청의 99%가 이 값 안에 끝나요. 표본이 적으면 흔들려서, 보통 1분 이상으로 집계해요.

### 2.4 새 용어는 풀어 쓰거나 `<Term>`으로 이어 줘요

처음 나올 때 한 번만 풀어요. 이미 글이 있는 용어는 `<Term slug="foundations/percentiles">백분위수</Term>`처럼 이어요.

- 나쁜 예: 이때 스팬이 샘플링되면 트레이스가 끊겨요.
- 좋은 예: 이때 스팬(span, 요청 한 구간의 기록)이 샘플링되면 트레이스(요청 전체의 기록)가 끊겨요.

### 2.5 업계 영어는 영어로 쓰고, 처음 한 번만 풀어 줘요

p99, rate, span 같은 말은 영어 그대로 써요. 처음 나올 때 한 번 한글로 풀어요.

- 나쁜 예: 아흔아홉 번째 백분위 응답시간이 높아요.
- 좋은 예: p99(느린 쪽 1%의 경계값)가 높아요.

### 2.6 숫자 예시는 구체적으로 들어요

- 나쁜 예: 일부 요청이 오래 걸리면 평균이 실제 체감과 달라질 수 있어요.
- 좋은 예: 요청 100개 중 1개가 3초 걸리고 나머지가 0.1초면, 평균은 0.129초예요. 사용자 100명 중 1명은 3초를 기다려요.

### 2.7 본문에는 면책 문장을 쓰지 않아요

꼭 필요한 예외는 `<Deeper>`에 넣어요.

- 나쁜 예: 본 문서에서는 CPU 사용률을 특정 수집기의 정의라고 주장하지 않습니다.
- 좋은 예: CPU 사용률은 계산식이 제품마다 달라요.

### 2.8 출처는 문장마다 달지 않아요

출처는 머리말 `sources`에 모아요. 본문에는 마크다운 링크를 쓰지 않아요.

- 나쁜 예: p99는 100개 중 99번째 값이에요([Prometheus 문서](https://prometheus.io/docs/)).
- 좋은 예: p99는 100개 중 99번째 값이에요. (출처는 머리말 `sources`에 `Prometheus 문서`로 적어요.)

### 2.9 한 단락에서 새 개념은 하나만 소개해요

- 나쁜 예: p99는 99번째 백분위수예요. 히스토그램은 값을 구간별로 세어요. 샘플링은 일부만 모아요.
- 좋은 예: p99는 99번째 백분위수예요. 요청의 99%가 이 값 안에 끝나요. 나머지 1%가 느린 꼬리예요.

### 2.10 비유를 쓰고, 어디까지 맞는지 밝혀요

낯선 개념은 일상의 비유로 먼저 잡아 줘요. 비유는 틀린 이해도 심을 수 있어서, `<Analogy limit="...">`의 `limit`에 비유가 안 맞는 곳을 꼭 적어요.

- 나쁜 예: 스위치는 우편함 분류실이에요. (어디까지 같은지 말하지 않음)
- 좋은 예: 스위치는 우편함 분류실과 비슷해요. 받는 사람 주소를 보고 맞는 칸에 넣어요. (limit: 실제 스위치는 어느 칸에 누가 사는지 처음엔 몰라서, 오가는 데이터를 보며 스스로 배워요.)

### 2.11 구조·순서·비교는 그림으로 먼저 보여 줘요

여러 부품이 이어진 모습, 주고받는 순서, 쌓인 층, 두 방식의 차이는 글보다 그림이 빨라요. 그림을 먼저 두고, 글은 그림을 읽는 법을 알려 줘요. 그림 컴포넌트는 5장에 있어요.

- 나쁜 예: 관리 서버가 장비에 요청을 보내고, 장비가 응답하고, 장비에 일이 생기면 장비가 먼저 알림을 보내요.
- 좋은 예: `<Sequence>`로 요청·응답·알림을 그리고, "위 두 줄은 관리 서버가 묻는 쪽, 마지막 줄은 장비가 먼저 알리는 쪽이에요."라고 써요.

### 2.12 새 용어는 용어 사전에 올리고 이어 줘요

처음 나오는 업계 용어는 `src/content/terms/{영역}.yaml`에 올리고, 본문에서는 `<Term term="영역/id">`로 이어요. 독자가 누르면 뜻과 비유가 시트로 떠요. 쓰는 법은 10장에 있어요.

- 나쁜 예: OID로 값을 가져와요. (OID가 무엇인지 모름)
- 좋은 예: `<Term term="network/oid">OID</Term>`(값마다 붙은 주소)로 값을 가져와요.

## 3. 개념 글 뼈대

개념 글은 "무엇 → 어떻게 → 모니터링" 순서로 써요. 머리말 `stage`로 층을 정해요.

- `stage: basics`: 도메인 기초. 무엇이고 어떻게 동작하는지가 중심이에요. `##` 본문 설명이 1개 이상 있어야 해요.
- `stage: monitoring`: 모니터링 관점. 화면에서 무엇을 보고 어떻게 판단하는지가 중심이에요. 기존 글은 모두 이쪽이에요.

복사해서 써요. 기초 글의 순서는 `KeyPoints` → `Analogy` → `##` 본문(`Figure`) → `## 모니터링에서는`(`Figure`) → `Checkpoints` → `Deeper`예요.

`## 모니터링에서는` 아래에는 `OnDashboard` 대신 `Figure`로 화면 예시를 그려요. `OnDashboard`는 자체 제목("대시보드에서는 이렇게 보여요")이 있어서 소제목이 두 번 나와요. `OnDashboard`는 모니터링 글의 맨 앞에 써요.

````mdx
---
title: 제목(30자 이하)
summary: 그게 무엇인지 한 문장(15~60자). 앞 25자만 읽어도 알게 써요.
domain: network
type: concept
stage: basics
order: 10
icon: network
keywords: [검색 별칭, 영어 용어]
related: [network/다른-글]
sources:
  - title: 출처 제목
    url: https://...
updated: 2026-10-21
---

<KeyPoints>
  <Point title="결론으로 쓴 핵심 1 (30자 이하)">
    결론만 한두 문장으로 써요. 설명은 아래 본문에 둬요.
  </Point>
</KeyPoints>

<Analogy limit="비유가 안 맞는 곳 한두 문장">
  일상의 비유 한두 문장이에요.
</Analogy>

## 무엇인가요

그림을 먼저 보여 주고, 그림을 읽는 법을 써요.

<Figure caption="그림이 보여 주는 것 1~2문장">
  <Flow ariaLabel="그림 설명" nodes={[{ id: 'sw', label: '스위치', col: 1, row: 0 }, { id: 's1', label: '서버', col: 0, row: 1 }]} edges={[{ from: 's1', to: 'sw' }]} />
</Figure>

## 어떻게 동작하나요

순서가 있으면 `Sequence`로, 층이 있으면 `Layers`로 그려요. 시간이 흐르며 상태가 바뀌면 `Timeline`으로, 번호 붙은 칸의 위치(오프셋, 버킷)를 짚으면 `Strip`으로 그려요.

## 모니터링에서는

<Figure caption="어느 화면의 어떤 예시인지, 그림이 보여 주는 것 1~2문장">
  <MiniLineChart ariaLabel="그래프 설명" series={[{ label: '평균', values: [1, 2, 3], tone: 'sub' }]} />
</Figure>

화면에서 이 개념을 어떻게 만나는지 써요.

<Checkpoints>
  <Check>AI나 동료의 구현에서 의심해야 할 지점이에요.</Check>
</Checkpoints>

<Deeper>
  몰라도 되는 세부만 둬요. 동작 원리는 본문에 써요.
</Deeper>
````

블록 사이 순서는 검사기가 강제하지 않아요. 검사기가 보는 것은 이것뿐이에요.

- `KeyPoints`는 꼭 하나 있어요.
- `Analogy`, `Checkpoints`, `Deeper`는 한 번까지 써요. `Checkpoints` 뒤에는 `Deeper`만, `Deeper`는 맨 끝에 와요.
- 그림 컴포넌트는 `Figure`나 `OnDashboard` 안에 둬요.
- 소제목은 `##`부터 써요.

그래서 기존 모니터링 글(`OnDashboard` → `KeyPoints` → (데모) → `Checkpoints` → (`Deeper`))도 그대로 통과해요.

### `Point` 제목은 결론으로 써요

`Point` 제목은 개념 미리보기 시트에 "핵심" 목록으로 그대로 나와요. 미리보기 시트는 다른 글에서 `<Term>`을 누르면 뜨는 창이에요. 제목만 읽어도 결론이 전해지게, 동작이 아니라 결론으로 써요.

- 나쁜 예: 재시작하면 카운터는 0부터 다시 세요
- 좋은 예: rate는 재시작을 알아서 메워요

가이드의 `Item` 제목도 본문보다 먼저 읽혀요. 무엇을 볼지 한눈에 알게 짧게 써요.

### 블록마다 분량을 지켜요

본문 전체 분량은 제한하지 않아요. 블록마다의 분량은 이 표로 손으로 확인해요.

| 블록 | 분량 |
| --- | --- |
| `Point` | 기초 글은 결론만 한두 문장. 설명은 본문 `##`에 둬요. 모니터링 글은 5문장 안팎, 두 단락 이하 |
| `Analogy` | 비유 한두 문장, `limit` 한두 문장 |
| `caption` | 1~2문장 |
| `summary` | 한 문장. 목록은 두 줄까지만 보여 줘서 좁은 화면에선 뒤가 잘려요. 앞 25자 안팎만 읽어도 뜻이 통하게 써요 |
| `Deeper` | 2,000자 안팎 |
| `sources` | 독자가 볼 출처 15개 안팎. 소스 줄 번호 같은 세부 근거는 `docs/reviews/`의 검토 기록에 남겨요 |

`summary`와 `sources` 기준은 가이드 글에도 똑같아요.

### 머리말의 `order`와 `draft`

두 항목은 가이드 글에도 똑같이 써요.

- `order`: 영역 안에서 추천하는 읽기 순서예요. 영역 페이지와 홈의 "처음이라면 여기부터"가 이 순서로 줄을 세워요. 글 끝 "다음에 읽을 글"도 이 순서를 따라요.
  - 10, 20, 30처럼 10씩 띄워 써요. 그래야 사이에 글을 끼워도 다른 글 번호를 고치지 않아요.
  - 0부터 쓸 수 있고, 값이 같으면 파일 이름 순이에요.
- `draft: true`: 초안이에요. 운영 빌드(`npm run build`)에서 빠지고 개발 서버에서만 보여요. 공개 글은 `<Term>`이나 `related`로 초안을 가리킬 수 없어요. 공개할 때 이 줄을 지워요.
- 영역 페이지와 "다음에 읽을 글"은 한눈에 보기 → 기초(`order` 순) → 나머지(모니터링 글과 가이드를 섞어 `order` 순)로 줄을 세워요.

### 한눈에 보기 글

영역마다 첫 글로 하나 둬요(`type: overview`, `stage`는 쓰지 않아요). 영역의 구성 요소가 어떻게 이어지는지 그림 한 장으로 먼저 보여 주고, 기초 글로 안내해요.

- `Figure`가 1개 이상, `##` 소제목이 1개 이상 있어야 해요.
- `KeyPoints`는 쓰지 않아요.
- 홈의 "처음이라면 여기부터"에 영역 순서대로 나와요.

## 4. 가이드 글 뼈대

순서는 `Situation` → `FirstLook` → 단계별 설명 → `Checkpoints`예요. `FirstLook`에는 `Item`을 1~3개 둬요.

단계는 `##` 소제목으로 나눠요. 소제목은 1개 이상 필요해요. 단계 사이에는 `OnDashboard`, `Figure`, `Analogy`도 둘 수 있어요.

````mdx
---
title: 제목(30자 이하)
summary: 한 문장 요약(15~60자). 이 글로 무엇을 할 수 있는지 앞부분에 써요.
domain: foundations
type: guide
order: 10
sources:
  - title: 출처 제목
    url: https://...
updated: 2026-10-13
---

<Situation>
  두 화면에서 같은 지표의 숫자가 달라요.
</Situation>
````

## 5. 컴포넌트 목록

| 컴포넌트 | 속성 | 쓰는 곳 |
| --- | --- | --- |
| `OnDashboard` | `title`, `caption?` | 대시보드에서 만나는 모습을 작은 그림으로 보여 줘요. 자체 제목이 있어서 모니터링 글의 맨 앞에 써요. 기초 글의 `## 모니터링에서는` 아래에는 `Figure`를 써요 |
| `Analogy` | `limit` | 비유 한두 문장. `limit`에 비유가 안 맞는 곳을 꼭 적어요 |
| `Figure` | `caption?` | 그림 틀. 그림 컴포넌트와 SVG 그림은 이 안(또는 `OnDashboard` 안)에 둬요 |
| `KeyPoints` | 없음 | 개념 글의 핵심. 안에 `Point` 1~3개 |
| `Point` | `title` (30자 이하) | `KeyPoints` 안의 핵심 하나 |
| `Checkpoints` | 없음 | 다시 확인할 지점. 안에 `Check` 1개 이상 |
| `Check` | 없음 | 의심해야 할 지점 하나 |
| `Deeper` | 없음 | 공식, 예외, 세부 동작. 기본으로 접혀요 |
| `Situation` | 없음 | 가이드의 상황 설명 |
| `FirstLook` | 없음 | 가이드의 먼저 볼 것. 안에 `Item` 1~3개 |
| `Item` | `title` (30자 이하) | `FirstLook` 안의 항목 하나 |
| `Term` | `slug` 또는 `term` | `slug`는 다른 글로 잇는 링크(예: `foundations/percentiles`), `term`은 용어 사전의 용어(예: `network/snmp`). 둘 중 하나만 써요 |
| `MiniLineChart` | `series`, `ariaLabel`, `yMax?`, `height?` | 작은 선 그래프. 단위는 범례 `value`에 직접 써요 |
| `StatTile` | `label`, `value`, `unit?`, `tone?`, `note?` | 숫자 하나를 크게 보여 줘요 |
| `Waterfall` | `spans`, `ariaLabel`, `unit?` | 트레이스 워터폴. `spans`는 `{ label, start, duration, depth?, tone? }` 배열이고, 가장 늦게 끝나는 구간이 막대 끝이에요 |
| `Scatter` | `groups`, `ariaLabel`, `xMax`, `yMax`, `yTicks?`, `unit?`, `xLabels?` | 응답시간 분포도. `groups`는 `{ count, x: [시작, 끝], y: [아래, 위], skew?, tone?, label? }` 배열이고, 범위 안에 점을 `count`개 흩뿌려요. 범위의 두 값이 같으면 가로줄·세로줄이 돼요 |
| `ServiceMap` | `nodes`, `edges`, `ariaLabel`, `height?` | 서비스 맵. `nodes`는 `{ id, label, x, y, note?, tone?, virtual? }`(x·y는 %), `edges`는 `{ from, to, label?, tone? }` 배열이에요. 화살표가 없어서 부르는 쪽을 왼쪽에 두고 `caption`에 밝혀요. `virtual`은 점선으로 그려요 |
| `Flow` | `nodes`, `edges`, `ariaLabel`, `groups?` | 구조도(화살표 있는 상자). `nodes`는 `{ id, label, col, row, note?, tone? }`(칸 위치), `edges`는 `{ from, to, label?, tone?, both?, dashed? }`, `groups`는 `{ label, cols: [시작, 끝], rows: [시작, 끝] }` 배열이에요. 한 줄에 3칸까지가 360px에서 읽혀요. 상자 이름은 8자 안팎으로 써요. 글자를 붙인 가로 화살표는 상자 사이에 빈 칸을 하나 둬요. 묶음(groups) 테두리를 지나는 화살표에는 글자를 붙이지 않아요. 테두리 위의 묶음 이름과 겹쳐요 |
| `Sequence` | `participants`, `messages`, `ariaLabel` | 주고받기 순서. 참여자 2~4명, `messages`는 `{ from, to, label, tone?, dashed? }` 배열이고 위에서 아래로 시간 순이에요. 돌아오는 응답은 `dashed`로 그려요 |
| `Layers` | `layers`, `ariaLabel` | 계층도. `layers`는 위층부터 `{ label, note?, tone? }` 배열이에요. 위아래로 기대는 층에만 써요. 나란히 있는 것은 `Flow`로 그려요 |
| `Compare` | `columns`, `rows` | 두 가지 비교. `columns`는 두 열 이름, `rows`는 `{ label, values: [왼쪽, 오른쪽] }` 배열이에요 |
| `Timeline` | `lanes`, `ariaLabel`, `start?`, `end?`, `marks?`, `ticks?` | 시간 띠. `lanes`는 `{ label, segments: [{ start, end, label?, tone? }] }` 배열이고, 줄마다 시간에 비례한 구간을 그려요. `marks`(`{ at, label, tone? }`)는 모든 줄을 가로지르는 세로선, `ticks`(`{ at, label }`)는 아래 시간축 눈금이에요. 줄 이름은 6자 안팎, 구간 글자는 띠 안에 들어갈 만큼 짧게 써요. 같은 줄 이름이나 눈금 글자가 360px에서 겹치지 않는지 확인해요 |
| `Strip` | `rows`, `ariaLabel`, `marks?`, `ranges?` | 칸 띠. `rows`는 `{ label?, cells, heads? }` 배열이고, `cells`는 글자나 `{ label, tone? }`예요. `heads`는 칸마다 위에 붙는 작은 글자(예: 버킷 경계)로, 칸 수와 같아야 해요. 칸은 12개까지예요. `marks`(`{ row?, at, label, tone? }`)는 칸 하나를 위에서 가리키고, `ranges`(`{ row?, from, to, label, tone? }`)는 여러 칸을 아래에서 묶어요. 번호는 모두 0부터예요. 칸 `tone: 'sub'`는 지나간 칸이나 빈자리처럼 흐리게 그려요 |
| SVG 그림 | `aria-label` | 위 그림으로 안 되는 그림은 `src/assets/figures/{domain}/{name}.svg`에 그려 default import해요. `Figure` 안에 두고 `aria-label`을 꼭 붙여요. 색은 `currentColor`나 `var(--color-…)`만 써야 다크 모드에서도 보여요 |
| `PercentileDemo`, `DownsamplingDemo` | 없음 | 직접 만져 보는 데모. default import 후 `client:visible`로 써요 |

`MiniLineChart`, `StatTile`, `Flow` 같은 그림 컴포넌트는 한 줄에 하나씩 써요. 한 줄에 여러 개를 쓰면 단락으로 묶여 배치가 깨져요.

## 6. 검사 규칙과 기준값

`npm run lint:content`가 아래 규칙을 검사해요. 위반이 하나라도 있으면 빌드가 실패해요. 코드 블록, 인라인 코드, 표, 컴포넌트 속성값은 문장 검사에서 빼요.

그래서 머리말 `title`·`summary`, `caption`, `ariaLabel`, `Point`·`Item`의 `title` 같은 값은 문체·문장 길이·금지 표현을 검사하지 않아요. 길이(제목 30자, `summary` 15~60자)만 빌드나 검사기가 봐요. 이 값들은 손으로 확인해요.

| 규칙 | 기준 | 출력 이름 |
| --- | --- | --- |
| 개념·한눈에 보기 글 틀 | 3장. `KeyPoints` 필수(한눈에 보기는 금지), `Analogy`·`Checkpoints`·`Deeper`는 한 번까지, `Checkpoints` 뒤에는 `Deeper`만, `Deeper`는 맨 끝, 기초 글은 `##` 1개 이상, 한눈에 보기는 `Figure`와 `##` 1개 이상, 그림은 `Figure`나 `OnDashboard` 안, `#` 소제목 금지 | `structure` |
| 머리말 `stage` | 개념 글에 `basics`나 `monitoring`. 다른 글에는 쓰지 않아요 | `frontmatter` |
| 가이드 글 블록 순서와 필수 여부 | 4장 순서 | `structure` |
| `KeyPoints` 안 `Point` 개수 | 1~3개 | `block-children` |
| `FirstLook` 안 `Item` 개수 | 1~3개 | `block-children` |
| 문장 길이 | 80자 이하 | `sentence-length` |
| 단락 길이 | 3문장 이하 | `paragraph-length` |
| 문체 | 본문 문장은 "요"나 "죠"로 끝나요. 뒤에 붙는 문장 부호와 닫는 따옴표·괄호는 괜찮아요. "~니다"(합쇼체)와 "~다"(해라체)는 위반 | `formal-ending` |
| 금지 표현 | "주장하지 않", "단정하지 않", "보장하지 않", "일반화하지 않", "이 문서에서는", "이 장에서는" | `banned-phrase` |
| `Term`의 `slug`·`term`과 `related` | 존재하는 글이나 용어. 공개 글은 초안(`draft`)을 가리킬 수 없어요. `slug`와 `term`은 하나만 | `reference` |
| `domain` | 파일이 있는 폴더 이름과 같아요 | `domain-folder` |
| 마크다운 링크 | 본문에 쓰지 않아요 | `markdown-link` |
| `Point`·`Item` 제목 | 30자 이하 | `block-title` |
| `Analogy`의 `limit` | 꼭 있어요 | `analogy-limit` |
| 쓸 수 있는 요소 | 5장의 컴포넌트와 default import한 데모·SVG 그림만 써요. `<a href="/...">`, `<img>` 같은 HTML 요소도 위반. SVG 그림은 `Figure` 안에 `aria-label`과 함께 둬요(어기면 `structure`) | `unknown-component` |
| 데모의 client 지시어 | import한 데모에는 `client:visible`을 붙여요. 없으면 움직이지 않는 그림으로만 보여서 위반 | `demo-hydration` |
| 용어 파일 | 10장 형식. 파일 이름은 영역 id, 필수 필드, `name` 30자·`short` 60자 이하, 같은 id 금지. `short`·`analogy`는 문장 규칙도 봐요. `doc`은 공개 글 | `glossary`(문장 규칙은 각 규칙 이름) |
| 문제 파일 | 11장 형식. 파일 경로는 공개 글과 같아요. 형태별 정답 형식, 객관식 보기 4개(서로 다름), 같은 id 금지. `explain`은 문장 규칙도 봐요. `doc`·`term`은 있는 글·용어 | `quiz`(문장 규칙은 각 규칙 이름), `reference` |

인라인 코드로 끝나는 문장(예: "이렇게 써요: `rate(x[5m])`")은 코드 앞의 마지막 한글로 문체를 판단해요. 코드만 있는 문장은 문체를 보지 않아요.

`Deeper` 안에서는 금지 표현 규칙만 빠져요. 나머지 규칙은 그대로 적용돼요.

기준값은 `scripts/lint-content/config.ts`에 있어요. 값을 바꾸면 이 표도 같이 고쳐요.

## 7. 검토에서 자주 나온 지적

1·2묶음 검토에서 되풀이된 지적이에요. 검사기는 잡지 못하니, 검토를 맡기기 전에 이 표로 다시 봐요.

| 지적 | 이렇게 고쳐요 |
| --- | --- |
| 왜 신경 써야 하는지가 `Deeper`에만 있음 | 무엇이 나빠지는지를 본문에 써요. 예: "새 값마다 시계열이 생기고, 시계열마다 메모리와 디스크를 써요." |
| `Check`가 `Deeper`와 어긋남 | 같은 글의 `Check`와 `Deeper`를 나란히 놓고 읽어요. `Deeper`가 권장 기준(예: 카디널리티 10 아래)을 들면, 본문 예시가 그 기준과 어떻게 맞는지 밝혀요 |
| 조건이 느슨함 | 조건을 정확히 써요. "지표 이름만 쓴 질의"가 아니라 "`[5m]` 같은 구간 없이 쓴 질의"예요 |
| 근거 없는 단정 | "대부분", "늘", "절대"는 근거가 있을 때만 써요 |
| 도구마다 다른 동작을 일반론으로 씀 | 도구, 버전, 설정을 밝혀요. 예: "Prometheus 3에서", "Grafana Stat 패널의 기본 계산 Last *". 숫자 예시는 전제(수집 주기, 패널 폭 등)도 밝혀요 |
| 도구 화면 용어나 설정 키를 풀지 않음 | 처음 나올 때 풀어요. 예: Explore(질의를 따로 열어 고쳐 가며 실행하는 Grafana 화면), Query options(패널의 질의 간격·기간 설정), `$__rate_interval`(rate 구간을 자동으로 잡는 Grafana 변수), OTLP(OpenTelemetry 전송 규약) |
| 사실 검토 수정을 지적받은 곳만 고침 | 같은 주장이 나오는 곳을 모두 찾아 고쳐요. `Point`, `Check`, `caption`, 그림의 글자(`label`, `value`, `ariaLabel`)까지 봐요 |

### 자주 쓰는 용어

같은 것은 모든 글에서 같은 말로 불러요. "라벨", "시리즈"처럼 바꿔 부르지 않아요. 처음 나올 때는 아래 풀이를 써요.

| 용어 | 처음 나올 때 풀이 |
| --- | --- |
| 레이블 | label, 키와 값의 쌍 |
| 시계열 | time series, 값을 시각 순서로 늘어놓은 줄 |
| 샘플 | sample, 수집한 값 하나 |
| 게이지 | gauge, 오르내리는 현재 값 |
| 카운터 | counter, 계속 더하기만 하는 값. 재시작하면 0부터 다시 세요 |
| 수집 주기 | 값을 하나씩 모으는 간격. Prometheus 설정은 `scrape_interval`이에요 |
| 점 간격 | 그래프의 점 사이 간격. Prometheus는 step, Grafana는 interval이라고 불러요 |
| stale 표시 | 더 이상 값이 없다는 표시 |
| `up` | 수집 성공 1, 실패 0. 대상이 수집 목록에서 빠지면 0이 아니라 사라져요 |

영역을 넘나드는 말은 아래처럼 하나로 불러요. 오른쪽 말은 `keywords`나 용어 사전 `aliases`에만 남겨 검색되게 해요.

| 이렇게 써요 | 쓰지 않는 말 | 메모 |
| --- | --- | --- |
| 에러 | 오류 | 에러율, 에러 예산, 에러 로그도 같아요 |
| 레이블 | 라벨 | Loki 레이블도 같아요 |
| Deployment, ReplicaSet | 디플로이먼트, 레플리카셋 | 쿠버네티스 오브젝트는 영어 이름으로 써요. 파드만 한글로 써요 |
| 옵티마이저 | 플래너 | 처음 나올 때 "PostgreSQL은 플래너라고 불러요"를 붙여도 돼요 |
| 주 서버, 복제 서버 | 원본, 복제본, 프라이머리 | DB 복제에서만이에요. Kafka의 복제본, RDS의 읽기 복제본은 그대로 써요 |
| 커넥션 풀 | 연결 풀 | 풀 밖의 연결 하나하나는 "연결"이라고 써요 |
| 스로틀링 | 스로틀 | 동사는 "스로틀링돼요"예요 |
| ISR | 동기화된 복제본 | 처음 나올 때 "따라잡은 복제본"으로 풀어요 |
| 레지스트리 | 이미지 저장소 | "저장소"는 데이터를 담는 스토리지에만 써요 |
| 쓰기 레이어 | 쓰기 층 | 컨테이너가 실행 중에 바꾼 파일이 쌓이는 곳 |
| 관리 서버 | 모니터링 서버 | SNMP로 장비에 묻는 쪽만이에요. 그 밖의 수집 쪽은 모니터링 서버예요 |
| 에이전트 | 수집기 | 서버에서 돌며 지표를 보내는 프로그램. 흐름 기록을 받는 collector와 node_exporter의 collector는 수집기예요 |
| 가용 영역(AZ) | | 글마다 처음엔 가용 영역(AZ)으로 쓰고, 그 뒤엔 AZ도 써요 |
| 비공개 서브넷, 사설 IP | 사설 서브넷 | 서브넷은 공개·비공개, IP 주소는 공인·사설이에요 |
| Metrics Server | metrics-server | 명령이나 저장소 이름을 그대로 옮길 때만 `metrics-server`예요 |
| Tomcat | 톰캣 | 제품 이름은 영어로 써요 |

## 8. 작성 절차

정확도는 중요하지만, 글이 나오지 못할 만큼 무겁게 확인하지 않아요. 한 편씩 써서 바로 공개해요.

1. 공식 문서, 표준, 원 논문을 먼저 보고 초안을 써요. 용어 파일, 그림, 퀴즈 문제(11장)도 함께 써요.
2. 틀리면 위험한 주장만 골라 따로 확인해요. 숫자, 기본값, 버전마다 다른 동작, 명령어·질의, 표준의 정의예요. "스위치는 같은 네트워크 안에서 데이터를 넘겨요" 같은 교과서 내용은 공식 문서를 한 번 훑는 정도면 돼요.
3. 질의와 명령어는 실제로 돌려 봐요(PromQL은 promtool, SQL은 PGlite 같은 로컬 DB, JavaScript 식은 node). 돌리기 어려우면 공식 문서와 대조해요. 띄운 서버는 끝나면 꼭 꺼요.
4. 확인한 주장과 근거를 `docs/reviews/{domain}-{slug}.md`에 몇 줄로 남겨요(9장).
5. 가독성을 스스로 점검해요. 처음 보는 사람이 그림과 비유만 보고도 감을 잡는지, 7장 표의 지적이 없는지 봐요.
6. `npm run lint:content`를 돌리고, 사이트 주인이 화면에서 확인해요.

## 10. 용어 쓰는 법

용어는 영역마다 파일 하나에 모아요: `src/content/terms/{영역}.yaml`. 파일 이름이 영역 id예요.

```yaml
terms:
  - id: snmp                                 # 필수. 소문자·숫자·하이픈
    name: SNMP                               # 필수. 30자 이하. 보여 줄 이름
    en: Simple Network Management Protocol   # 선택. 영어 원말
    aliases: [에스엔엠피]                      # 선택. 검색·퀴즈 채점에 쓰는 다른 이름
    short: 장비의 상태를 묻고 답하는 표준 규약이에요.   # 필수. 60자 이하 해요체 한 문장
    analogy: 관리 서버가 장비마다 놓인 문진표를 돌며 읽는 것과 같아요.   # 선택. 한 줄 비유
    doc: network/snmp                        # 선택. 자세히 설명한 공개 글
```

- 본문에서 처음 나올 때 `<Term term="network/snmp">SNMP</Term>`로 이어요. 누르면 이름, 영어 원말, 뜻, 비유가 시트로 떠요. `doc`이 있으면 "전체 보기"가 그 글로, 없으면 "용어 사전에서 보기"가 용어 사전의 그 위치로 가요.
- `short`는 "그게 무엇인지"만 써요. 동작 설명은 글로 보내요.
- 용어가 있는 영역에는 용어 사전 페이지(`/terms/{영역}/`)가 생기고, 영역 페이지 아래에 줄이 생겨요.

## 11. 퀴즈 문제 쓰는 법

문제는 글마다 파일 하나에 써요: `src/content/quizzes/{영역}/{글 이름}.yaml`. 경로가 글과 같아야 하고, 그 글의 끝에 "이 글 퀴즈" 카드가 생겨요. 문제는 모두 직접 써요. 용어 사전으로 문제를 자동으로 만들지 않아요. 기계로 만든 문제는 뜻이 겹치거나 오답 보기가 엉뚱해지기 쉬워요. 용어를 떠올리는 문제가 필요하면 그 용어를 처음 다룬 글의 문제 파일에 직접 써요.

```yaml
questions:
  - id: trap-direction            # 필수. 소문자·숫자·하이픈. 한 번 정하면 바꾸지 않아요(기록이 이 id로 이어져요)
    type: ox                      # ox | choice | input
    prompt: SNMP Trap은 관리 서버가 장비에 물어봐서 받는 값인가요?
    answer: false                 # ox는 true·false
    explain: Trap은 장비가 먼저 보내요. 관리 서버가 묻는 건 폴링이에요.
  - id: forwarding-device
    type: choice
    prompt: 같은 네트워크 안에서 MAC 주소로 데이터를 넘기는 장비는?
    choices: [스위치, 라우터, 방화벽, 로드 밸런서]   # 정확히 4개, 서로 달라요
    answer: 0                     # 정답 보기의 순서(0부터)
    explain: 스위치는 MAC 주소 표를 보고 같은 네트워크 안에서 넘겨요.
  - id: syslog-name
    type: input
    prompt: 장비가 이벤트를 글로 남겨 보내는 표준 형식은?
    answer: [Syslog, 시스로그]     # 정답 목록. 대소문자·띄어쓰기·하이픈은 무시해요
    term: network/syslog          # 선택. 그 용어의 이름과 별칭도 정답으로 받아요
    explain: Syslog는 장비가 사건을 글로 남겨 보내는 형식이에요.
    doc: network/traps-and-syslog # 선택. 해설 끝 "관련 글"을 다른 글로 바꿀 때
```

- 글마다 3~5문제, 형태를 섞어요. OX는 동작을 제대로 이해했는지, 객관식은 개념을 구분하거나 상황을 해석하는지, 주관식은 용어를 떠올릴 수 있는지 물어요.
- 글의 문장을 그대로 빈칸으로 뚫지 않아요. 같은 내용을 다른 말이나 상황으로 물어요.
- 오답 보기는 그럴듯해야 해요. 같은 글이나 영역의 다른 개념을 써요.
- 객관식 보기는 풀 때마다 섞여서 나와요. 정답을 어느 자리에 써도 돼요. 그래서 "모두 맞아요", "위의 둘 다"처럼 다른 보기의 자리에 기대는 보기는 쓰지 않아요.
- 해설은 왜 그런지를 한두 문장으로 써요(해요체, 문장 규칙 검사). 문제 글은 물음으로 끝나도 돼요.
- 숫자·기본값이 든 문제는 글과 같은 근거로 확인하고, 그 글의 검토 기록에 한 줄 더해요.
- 문제를 고칠 때 `id`는 그대로 둬요. 지운 문제의 기록은 저절로 무시돼요.
- 기록은 사용자 브라우저에만 남아요. 맞히면 상자가 한 칸 오르고(1·3·7·14·30일 뒤에 다시), 틀리면 상자 1(다음 날 다시)로 가요. 때가 되기 전에 다시 풀어 맞힌 문제는 상자가 그대로예요.
