## 반영

- StatTile 에러(오해 소지): 부분 반영. 이름은 그대로 두고 값을 Errors의 정의대로 바꿨어요. `value="4.8" unit="건/초" note="비율 0.4%"`예요. 발표 자료 정의("the number of those requests that are failing")와 맞고, 확인 2처럼 건수와 비율을 함께 보여요. 이름을 "에러 비율(Errors ÷ Rate)"로 바꾸면 좁은 타일에서 줄이 넘쳐서 이렇게 했어요. caption도 "4.8건(0.4%)이 실패하고"로 순서를 맞췄어요.
- 표 메모리 포화(오해 소지): 반영. 칸을 "익명 페이징·스와핑(앱 메모리를 디스크로 내보냈다가 다시 읽는 일)"으로 바꿨어요. Linux 단락에 "메모리 포화는 `vmstat 1`의 `si`·`so`(스왑 입출력)로 봐요."를 더했어요.
- `aqu-sz`(오해 소지): 반영. "평균 대기열 길이" 풀이를 지우고 "`aqu-sz`는 장치에 보낸 요청의 평균 개수라서, 처리 중인 요청도 세요."를 넣었어요. SSD 문장은 "`aqu-sz`가 1을 넘거나 `%util`(바빴던 시간 비율)이 100%여도 한계가 아닐 수 있어요."로 바꿨어요. 근거로 Linux 커널 문서 I/O statistics fields(field 9·11)를 sources에 더했어요.
- `_count`(오해 소지): 반영. "Prometheus 클래식 히스토그램의 `_count`…"로 한정했어요. 선택 제안도 넣었어요: "네이티브 히스토그램(Prometheus의 새 히스토그램 형식)에는 `_count` 시계열이 없어요. 요청 수는 `histogram_count()`로 세요." sources에 Prometheus Query functions를 더하고, Metric types 출처 이름을 "(클래식·네이티브 히스토그램)"으로 바꿨어요.
- Duration 식(오해 소지): 반영. 식을 `histogram_quantile(0.99, sum by (le) (rate(request_duration_seconds_bucket{status_code!~"5.."}[5m])))`로 바꿨어요. 본문에 세 문장을 더했어요: "`le`만 남기고 더하면 응답 코드도 합쳐져서, 빨리 끝난 5xx가 있으면 p99가 실제보다 낮게 나와요." "그래서 이 식은 `status_code!~"5.."`로 에러가 아닌 요청만 골라요." "실패한 요청의 지연은 `=~"5.."`로 따로 구해요." 같은 주장이 나오는 그림도 고쳤어요. Duration 타일에 `note="에러 제외"`를 달고, caption을 "에러를 뺀 요청의 99%가 820ms 안에 끝나요"로 바꿨어요. 골든 시그널 절의 "지연이 좋아 보여요"는 "지연이 실제보다 짧아 보여요"로 바꿨어요.
  - promtool 3.15.0 `test rules`로 다시 확인했어요. 15초 수집, 서버 2대, 15초마다 서버당 200 8,964건과 500 36건을 넣었어요. 500은 모두 0.1초 버킷이에요.
  - 결과: Rate 1,200, Errors 4.8. 새 Duration(5xx 제외)은 0.96795초, 5xx만 구하면 0.099초, 합친 식은 0.9675초예요. 빠른 에러가 p99를 끌어내리는 것도 확인했어요. 띄운 서버는 없어요.
- load average(맞음, 선택 제안): 반영. "Wilkie의 발표 자료는 load average를 CPU 수로 나눠 CPU 포화로 쓰니, 이 차이를 알고 읽어요."를 더했어요. "이 글은" 같은 메타 표현은 쓰지 않았어요.
- 발표 자료 코드의 `route`에 `r.URL.Path`가 들어가는 점(맞음, 참고): 반영 안 함. 글은 발표 자료의 코드를 옮기지 않고 식만 다뤄요. 더 깊이도 약 2,100자로 상한 근처라 더하지 않았어요.
- 더 깊이 분량을 맞추려고, 다른 사실은 그대로 두고 문장만 줄였어요. 골든 시그널의 지연 두 문장을 한 문장으로 합쳤어요. 배치 작업 문장은 한 문장으로 줄였어요. 표 앞 문장과 Linux 체크리스트 도입 문장도 짧게 썼어요.
