| --- | --- |
| 한 해 허용 멈춤: 99% 3.65일, 99.9% 8.76시간, 99.95% 4.38시간, 99.99% 52.6분, 99.999% 5.26분. 30일(한 달) 99.9% 43.2분, 99.99% 4.32분, 99.999% 25.9초 | https://sre.google/sre-book/availability-table/ |
| 가용성 = 쓸 수 있던 시간 ÷ 전체 시간, 9의 개수로 줄여 부름(five nines = 99.999%) | https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html |
| 꼭 필요한 의존(hard dependency)은 가용성을 곱함(99.99% × 99.99% × 99.99% = 99.97%), 없어도 되는 의존(soft)은 앱이 실패를 메움 | 같은 문서 |
| 서로 독립인 중복 부품은 100% − 실패율의 곱(99.9% 둘 → 99.9999%), 9로만 된 값은 9의 개수를 더함 | 같은 문서 |
| 가용성 어림 = MTBF ÷ (MTBF + MTTR), MTBF 150일·MTTR 1시간 → 99.97% | 같은 문서 |
| EC2 인스턴스 한 대(Instance-Level) 월 99.5%, 둘 이상의 AZ에 둔 인스턴스(Region-Level) 월 99.99% | https://aws.amazon.com/compute/sla/ |

- 계산(Python): 0.999³ = 99.7003%(한 해 26.25시간), 0.999¹⁰ = 99.004%(87.2시간), 0.999²⁰ = 98.019%(173.5시간, 7.23일), 99% 둘 병렬 = 99.99%(52.6분), 99.5% 둘 병렬 = 99.9975%, 여기에 DB 99.9%를 곱하면 99.8975%, 웹 서버 셋이어도 99.8999%. 99.9% × 99.95% = 99.85005%, 30일 64.78분.
- 그림의 서비스 구성과 실측 값(결제 API 99.9%, 재고 DB 99.95%)은 설명용 예시예요.
