# 도메인 기초 전환과 퀴즈 설계

- 작성일: 2026-10-21
- 상태: 승인됨 (2026-10-21, 진행 순서는 사이트 주인이 맡김)
- 앞선 설계: `2026-10-13-domaindocs-site-design.md`. 이 문서와 어긋나는 부분은 이 문서를 따른다.

## 1. 왜 바꾸나

사이트 주인이 꼽은 문제는 세 가지다.

1. **기준이 거의 다 모니터링 관점이다.** 지금 개념 글은 "대시보드에서는 이렇게 보여요"로 시작한다. 그래서 그 도메인이 무엇이고 어떻게 동작하는지는 이미 안다고 가정한다. 사이트 주인에게 더 중요한 것은 도메인 자체의 기본 지식이다. 모니터링 관점은 그 위에 얹으면 더 좋은 것이다.
2. **글 한 편이 너무 오래 걸렸다.** 정확도도 중요하지만 적당해야 한다.
3. **글은 잘 읽히는데 내용이 아쉽다.** 설명 자체가 쉽게 이해되어야 한다. 그림, 차트, 비유를 적극적으로 쓴다.

여기에 퀴즈를 더한다. 말해보카처럼 읽은 내용을 다시 꺼내 보는 문제 풀이다.

### 배우는 흐름 (사이트 주인이 든 예)

네트워크 장비 모니터링 화면을 맡게 되었다면, 근본부터 시작한다.

1. 모르는 말이 쏟아진다. 네트워크 장비, 인터페이스, 스위치, 벤더, SNMP, Syslog.
2. 그 말들이 가리키는 실체와 동작을 이해한다.
3. 그 위에 모니터링 관점을 얹는다. 화면에 무엇을 보여 줘야 하고 어떤 숫자를 조심해야 하는지.

사이트는 이 흐름을 그대로 따라간다.

## 2. 목표와 하지 않을 것

### 목표

- 영역마다 "그게 무엇인지"부터 배울 수 있다. 첫 글은 영역 전체를 그림 한 장으로 보여 준다.
- 모르는 용어를 바로 확인할 수 있다. 용어 사전과 미리보기 시트로.
- 읽은 내용을 퀴즈로 다시 꺼내 본다. 틀린 문제는 나중에 다시 나온다.
- 글 한 편을 쓰고 공개하는 시간이 이전보다 크게 줄어든다.

### 하지 않을 것

- 로그인, 기기 간 기록 동기화. 퀴즈 기록은 지금 쓰는 브라우저에만 남는다(사이트 주인 결정).
- 연속 학습일, 순위, 소리 같은 게임 요소.
- 페이지 안에서 AI로 문제를 만들거나 채점하는 기능. 문제와 정답은 빌드할 때 정해져 있다.
- 댓글, 방문자 분석, 영어판(앞선 설계 그대로).
- 디자인 변경. 색, 글꼴, 카드·리스트 모양은 지금 그대로 쓴다(사이트 주인: "전체적인 디자인은 다 괜찮아").

### 실패로 볼 것 (돌아가더라도)

- 비유가 틀린 이해를 심는다. 비유는 어디까지 맞는지 함께 밝힌다.
- 퀴즈가 글의 문장을 그대로 빈칸으로 뚫은 암기 확인이 된다. 문제는 이해를 묻는다.
- 검토 절차가 다시 무거워져서 글이 안 나온다.
- 회사 제품의 내부 정보(화면 이름, 테이블, 코드)가 공개 글에 들어간다.

## 3. 영역 다시 짜기

사이트 주인이 만드는 제품의 화면 목록(`C:\exem\exemone-harness\specs`)을 지도로 삼는다. 제품은 주제를 고르는 데만 쓴다. 글은 SNMP, 쿠버네티스처럼 일반 지식으로 쓴다.

| id | 이름 | 다루는 것 | 지금 글 |
| --- | --- | --- | --- |
| `foundations` | 모니터링 기초 | 백분위수, rate, 알림처럼 어느 영역에서나 쓰는 모니터링 개념 | 16편 |
| `network` | 네트워크 | 장비, 인터페이스, 스위치·라우터, SNMP, Syslog, 트래픽 | 없음 |
| `server` | 서버·OS | CPU, 메모리, 디스크, 프로세스, 리눅스 기본 | 없음 |
| `kubernetes` | 컨테이너·쿠버네티스 | 컨테이너, 파드, 노드, 워크로드, Service | 없음 |
| `cloud` | 클라우드 | AWS·Azure의 주요 서비스와 지표 | 없음 |
| `apm` | 애플리케이션 | WAS, 웹 서버, 트랜잭션, JVM, 브라우저(RUM) | 16편 |
| `database` | 데이터베이스 | 트랜잭션, 인덱스, 잠금, 세션, 실행 계획. Oracle·MySQL·PostgreSQL·SQL Server | 8편 |
| `messaging` | 메시지 큐 | Kafka의 토픽, 파티션, 컨슈머 그룹 | 없음 |

- `infra`는 없앤다. 이 영역에 쓴 글은 없다.
- 기존 id(`foundations`, `apm`, `database`)는 주소가 이미 공개되어 있어 그대로 둔다. 이름만 바꾼다.
- 로그는 따로 영역을 두지 않는다. Syslog는 `network`, 로그·지표·트레이스는 `foundations`에서 다룬다(내 판단).
- 글이 없는 영역은 지금처럼 "준비 중"으로 보인다.

## 4. 글

### 4.1 글 종류

| 종류 | 머리말 `type` | 역할 |
| --- | --- | --- |
| 한눈에 보기 | `overview` (새로 추가) | 영역마다 하나. 영역의 구성 요소가 어떻게 이어지는지 그림으로 보여 주고, 기초 글로 안내한다 |
| 개념 | `concept` | 개념 하나를 "무엇 → 어떻게 → 모니터링" 순으로 설명한다 |
| 가이드 | `guide` | 지금과 같다. 실제 판단 상황 하나를 다룬다 |

개념 글에는 머리말 `stage`를 꼭 둔다. 값은 `basics`(도메인 기초)와 `monitoring`(모니터링 관점)이다. 기존 개념 글 29편은 모두 `monitoring`이다. 한눈에 보기와 가이드에는 두지 않는다. 영역 페이지는 이 값으로 글을 묶는다(4.4).

읽는 순서("다음에 읽을 글")는 한눈에 보기 → 기초 개념(`order` 순) → 나머지(모니터링 개념과 가이드를 `order` 순으로 섞어서)다. 나머지 부분은 지금의 순서를 그대로 지킨다(내 판단).

### 4.2 개념 글 틀

| 순서 | 블록 | 필수 | 내용 |
| --- | --- | --- | --- |
| 1 | 제목 + 한 줄 요약 | 예 | 머리말에서 자동. 요약은 "그게 무엇인지" 한 문장 |
| 2 | 핵심 `<KeyPoints>` | 예 | 결론 1~3개. 미리보기 시트에도 나온다. 기초 글에서는 짧게 쓰고, 설명은 아래 본문에 둔다 |
| 3 | 비유 `<Analogy>` | 아니요 (새 블록) | 일상의 비유 하나. "비유가 안 맞는 곳"을 함께 적는다 |
| 4 | 본문 | 기초 글은 예 | `##` 소제목으로 나눈 설명. 구조, 동작 순서, 비교를 그림과 함께 쓴다. 접지 않는다 |
| 5 | 모니터링에서는 | 아니요 | `##` 소제목 하나 아래에 `<OnDashboard>` 그림과 설명을 둔다 |
| 6 | 다시 확인하세요 `<Checkpoints>` | 아니요 | 지금과 같다 |
| 7 | 더 깊이 `<Deeper>` | 아니요 | 몰라도 되는 세부만. 동작 원리는 여기 두지 않는다 |
| 8 | 퀴즈로 이어지는 카드 | 자동 | 이 글에 딸린 문제가 있으면 "이 글 퀴즈 풀기"를 보여 준다 |

- 기존 개념 글(대시보드 그림이 맨 앞)도 그대로 통과해야 한다. 글 검사의 순서 규칙은 이렇게 느슨하게 바꾼다.
  - `KeyPoints`는 필수다.
  - `Checkpoints` 다음에는 `Deeper`만 온다.
  - 그 밖의 블록, 데모, 그림, `##` 소제목, 단락, 목록, 표는 그 사이 어디에나 둘 수 있다.
- 한눈에 보기 글은 그림 하나 이상과 `##` 소제목 하나 이상이 필수다. `KeyPoints`는 쓰지 않는다.

### 4.3 그림 재료

지금 있는 것: `MiniLineChart`, `StatTile`, `Waterfall`, `Scatter`, `ServiceMap`(화살표 없음).

새로 만드는 것:

| 이름 | 그리는 것 | 쓰는 예 |
| --- | --- | --- |
| 구조도 | 상자와 화살표. 상자를 묶는 테두리(영역) | 스위치 하나에 서버 여럿이 꽂힌 모습, 파드와 노드 |
| 주고받기 | 참여자 2~4개가 시간 순으로 주고받는 메시지 | SNMP 요청·응답, Trap |
| 계층도 | 위아래로 쌓인 층 | OSI·TCP/IP 계층, 커널과 사용자 영역 |
| 비교 | 두 가지를 나란히 놓고 같은 항목끼리 견줌 | 폴링 vs Trap, 스위치 vs 라우터 |

- 모두 지금 그림처럼 정적 SVG로 그리고, 숫자와 글자만 넣어 재사용한다. 다크 모드와 360px 화면에서 읽혀야 한다.
- 위 넷으로 안 되는 그림은 글마다 SVG 파일을 직접 그려 넣을 수 있게 한다. 색은 사이트 색 변수를 따라 다크 모드에서도 보여야 한다. (어떻게 넣을지는 구현할 때 정한다.)
- 컴포넌트 이름과 속성은 구현할 때 정하고 글쓰기 가이드 5장에 적는다.

### 4.4 영역 페이지와 홈

영역 페이지는 위에서부터 이렇게 보인다.

1. 영역 소개
2. 한눈에 보기 (글이 있으면 맨 위 카드)
3. 기초 (`stage: basics` 개념 글, `order` 순)
4. 모니터링에서는 (`stage: monitoring` 개념 글)
5. 상황 가이드
6. 용어 사전과 퀴즈로 가는 줄

홈은 이렇게 바꾼다.

- "처음이라면 여기부터": 영역마다 한눈에 보기 글. 아직 없으면 지금처럼 모니터링 기초 글.
- 퀴즈 카드: "오늘 다시 볼 문제 N개". 브라우저 기록을 읽어 숫자를 채운다. 기록이 없으면 "퀴즈 풀어 보기"로 보인다.

### 4.5 글쓰기 규칙에서 바뀌는 것

- 본문 분량 제한(개념 1,500자, 가이드 4,000자)을 없앤다. 내용이 많으면 많이 써도 된다. 기준은 읽히는가, 쉽게 이해되는가다(사이트 주인 결정).
- `Point`를 "5문장 안팎"으로 쓰라던 기준도 없앤다. 기초 글의 `Point`는 짧게 쓰고, 설명은 본문에 둔다.
- 그대로 두는 것: 해요체, 문장 80자, 단락 3문장, 결론 먼저, 한 단락에 새 개념 하나, 면책 문장 금지, 출처는 머리말에.
- 새로 넣는 것:
  - 처음 보는 사람 기준으로 쓴다. 기초 글에는 그 영역의 다른 기초 글 말고는 아는 것을 가정하지 않는다.
  - 비유는 적극적으로 쓰되, 어디까지 맞는지 밝힌다.
  - 구조, 순서, 비교는 글보다 그림으로 먼저 보여 준다.
  - 새 용어는 용어 사전에 올리고 `<Term>`으로 잇는다.

## 5. 용어 사전

### 5.1 데이터

용어는 글과 따로 관리한다. 영역마다 파일 하나에 모은다(예: `src/content/terms/network.yaml`).

| 필드 | 필수 | 내용 |
| --- | --- | --- |
| `id` | 예 | 영역 안에서 겹치지 않는 이름. 예: `snmp` |
| `name` | 예 | 보여 줄 이름. 예: SNMP |
| `en` | 아니요 | 영어 원말. 예: Simple Network Management Protocol |
| `aliases` | 아니요 | 다른 이름. 검색과 주관식 채점에 쓴다 |
| `short` | 예 | 한 줄 뜻(60자 이하, 해요체) |
| `analogy` | 아니요 | 한 줄 비유 |
| `doc` | 아니요 | 자세히 설명한 글 |

### 5.2 화면

- 영역마다 용어 사전 페이지가 있다. 가나다·ABC 순으로 용어와 한 줄 뜻을 보여 준다. 검색 색인에 들어간다.
- `<Term>`은 글뿐 아니라 용어도 가리킬 수 있다. 글은 지금처럼 `slug`로, 용어는 새 속성 `term`으로 가리킨다(예: `<Term term="network/snmp">`). 글 `network/snmp`와 용어 `snmp`가 함께 있어도 헷갈리지 않게 하려는 것이다(내 판단).
- 용어를 누르면 미리보기 시트에 이름, 영어 원말, 한 줄 뜻, 비유가 나온다. 자세한 글이 있으면 "전체 보기" 버튼이 그 글로 간다. 자바스크립트가 없으면 용어 사전 페이지의 그 용어 위치로 가는 링크로 동작한다.
- 글 검사는 `<Term>`이 존재하는 글이나 용어를 가리키는지 확인한다. 용어의 `doc`도 존재하는 글이어야 한다.
- 용어 사전 주소는 글 주소(`/{domain}/{slug}/`)와 겹치지 않게 잡는다.
- 용어의 `short`와 `analogy`는 해요체와 문장 길이를 검사한다.

## 6. 퀴즈

### 6.1 문제 형태

| 형태 | 언제 쓰나 | 예 |
| --- | --- | --- |
| OX | 동작을 제대로 이해했는지 | "SNMP Trap은 관리 서버가 장비에 물어봐서 받는 값이다." → X. Trap은 장비가 먼저 보낸다 |
| 객관식(4지) | 개념을 구분하는지, 상황을 해석하는지 | "같은 네트워크 안에서 MAC 주소로 데이터를 넘기는 장비는?" |
| 주관식(입력) | 용어를 떠올릴 수 있는지 | "장비가 이벤트를 문자로 남겨 보내는 표준 형식은?" → Syslog |

- 문제마다 해설이 있다. 해설은 왜 그런지를 한두 문장으로 쓰고, 관련 글로 잇는다.
- 주관식은 정답을 여러 개 둘 수 있다. 대소문자, 띄어쓰기, 하이픈은 무시하고 견준다. 용어의 `name`과 `aliases`도 정답으로 받는다.
- 문제는 글의 문장을 그대로 뚫지 않고 이해를 묻는다(2장 실패로 볼 것).
- 처음 버전의 문제는 글자만 쓴다. 그림을 보고 푸는 문제는 나중에 다룬다(내 판단). 숫자나 상황은 문제 글에 직접 쓴다.
- 해설은 해요체와 문장 길이를 검사한다. 문제 글은 물음으로 끝나도 된다.

### 6.2 문제 데이터

- 글마다 문제 파일을 하나 둔다(예: `src/content/quizzes/network/snmp.yaml`). 문제는 글에 딸린다.
- 용어 사전에서 자동으로 만드는 문제도 있다. "뜻 → 용어"(주관식)와 "용어 → 뜻"(객관식, 오답 보기는 같은 영역의 다른 용어 뜻)이다. 사람이 따로 쓰지 않는다. 영역의 용어가 4개보다 적으면 객관식은 만들지 않는다.
- 문제마다 바뀌지 않는 `id`가 있다. 문제를 고쳐도 기록이 이어지게 하려는 것이다. 지운 문제의 기록은 무시한다.
- 문제 파일도 빌드할 때 형식을 검사한다. 보기 개수, 정답이 보기에 있는지, 가리키는 글이 있는지를 본다.

### 6.3 다시 나오는 규칙

말해보카처럼 틀린 문제와 오래된 문제가 다시 나온다. 단순한 상자 방식으로 한다(내 판단).

- 문제마다 상자 1~5가 있다. 맞히면 한 칸 올라가고, 틀리면 1로 돌아간다.
- 상자마다 다시 나오는 간격: 1 → 1일, 2 → 3일, 3 → 7일, 4 → 14일, 5 → 30일.
- "오늘 다시 볼 문제"는 간격이 지난 문제다. 모든 영역에서 모은다.
- 한 번 풀 때는 다시 볼 문제를 먼저 넣고, 남는 자리를 처음 보는 문제로 채운다. 글이나 영역에서 시작하면 그 범위 안에서만 고른다.
- 읽은 글을 따로 기록하지 않는다. 처음 보는 문제는 모든 글에서 나온다.
- 기록은 브라우저 저장소(localStorage)에만 둔다. 저장소를 쓸 수 없는 환경(사생활 보호 모드 등)에서도 문제는 풀리고, 기록만 남지 않는다.

### 6.4 화면

- 퀴즈 홈(`/quiz/`): 오늘 다시 볼 문제, 영역별 풀기, 처음 보는 문제 풀기.
- 글 끝: 그 글의 문제만 푸는 카드.
- 풀이 화면: 한 화면에 한 문제. 위에 진행 막대, 큰 보기 버튼. 고르면 바로 정답·오답과 해설이 나오고 "다음"으로 넘어간다. 한 번에 10문제 안팎.
- 끝 화면: 맞힌 수, 틀린 문제 목록, 관련 글 링크.
- 360px에서 한 손으로 풀 수 있어야 한다. 키보드로도 풀 수 있어야 한다(숫자 키로 보기 고르기, Enter로 다음).
- 퀴즈는 JavaScript가 필요하다. 앞선 설계의 "데모·시트·검색 말고는 JS 없이"에 퀴즈를 더한다. 퀴즈 페이지는 검색 색인에서 뺀다.
- 디자인은 지금 카드·버튼·색을 그대로 쓴다. 정답은 강조색, 오답은 경고색이다.

## 8. 기존 40편

버리지 않는다. 지금 글은 새 틀의 "모니터링에서는" 층에 해당한다.

- 개념 글 29편에 `stage: monitoring`을 붙인다. 내용은 그대로 둔다.
- 영역마다 기초 글을 앞에 깔면, 기존 글이 그 뒤를 잇는다.
- 기존 글에도 퀴즈 문제를 붙인다. 글을 고치지 않고 문제 파일만 더한다.
- 새 틀로 다시 쓰는 것은 고칠 일이 생길 때 한다. 한꺼번에 다시 쓰지 않는다.
- `database`의 기존 글은 PostgreSQL 중심이다. DB 기초 글을 쓸 때 Oracle 등 다른 DB도 다룬다.

## 9. 진행 순서

| 단계 | 하는 일 | 끝나면 볼 수 있는 것 |
| --- | --- | --- |
| 1 | 틀 정비: 영역 다시 짜기, 머리말(`overview`, `stage`), 글 검사 규칙, `Analogy`와 새 그림 4종, 영역 페이지, 문서 고치기 | 바뀐 영역 목록과 영역 페이지 |
| 2 | 용어 사전: 데이터, 페이지, 미리보기 시트 | 용어를 눌러 뜻을 보는 화면 |
| 3 | DB 첫 글: 한눈에 보기 1편 + 기초 글 2편 + 용어 | 사이트 주인이 새 틀을 실제 글로 보고 판단한다 |
| 4 | 퀴즈: 문제 데이터, 풀이 화면, 다시 나오는 규칙, 퀴즈 홈, 글 끝·홈 카드 | DB 글로 퀴즈를 풀어 보는 화면 |
| 5 | DB 나머지 기초 글과 문제 | DB 영역 하나가 기초부터 기존 모니터링 글까지 이어짐 |
| 6 | 기존 40편에 `stage`와 퀴즈 문제 붙이기 | 모든 글에 퀴즈 |
| 7 | 다음 영역들 | 서버·OS → 네트워크 → 애플리케이션 → 컨테이너·쿠버네티스 → 클라우드 → 메시지 큐 |

3단계에서 사이트 주인의 피드백을 받고, 틀과 규칙을 고친 뒤 다음으로 넘어간다.

### 영역 순서 (사이트 주인이 맡긴 판단)

- **DB를 첫 영역으로 한다.** 기존 DB 글 8편(잠금, 버퍼 캐시, 실행 계획, 복제 지연 등)이 기초를 전제하고 있어서, 기초 글을 앞에 깔면 "기초 → 모니터링"이 바로 이어지는 첫 영역이 된다. 제품에서도 DB 화면이 가장 넓다(DB 종류별 화면).
- 그다음은 다른 영역이 기대는 기초부터 놓는다. 서버·OS와 네트워크는 거의 모든 영역의 바탕이다. 쿠버네티스는 OS와 네트워크를 알아야 이해되고, 클라우드는 앞의 것들을 묶은 것이라 뒤에 둔다.

### DB 기초 글 후보 (쓸 때 다시 고른다)

특정 DB에 묶지 않고 쓰고, DB마다 다른 점(Oracle, MySQL, PostgreSQL, SQL Server)은 비교 그림이나 표로 보여 준다.

- 한눈에 보기: 질의 하나가 DB 안에서 지나가는 길 (연결 → 해석 → 실행 계획 → 메모리 → 디스크 → 로그)
- 연결과 세션, 프로세스와 스레드
- 트랜잭션과 커밋
- 인덱스
- 메모리와 디스크 (페이지, 버퍼 캐시)
- 로그와 복구 (WAL, redo)
- 동시에 읽고 쓰기 (잠금, MVCC)
- SQL이 실행되는 과정 (해석, 옵티마이저)
- 복제

## 10. 성공 기준

- 사이트 주인이 네트워크 기초 글을 읽고 "무엇인지 이해된다"고 판단한다.
- 기초 글을 읽은 뒤 그 글의 퀴즈를 대부분 맞힌다. 못 맞힌다면 글이나 문제를 고친다.
- 글 한 편이 이전처럼 여러 차례 검토를 돌지 않고, 한 번 확인한 뒤 공개된다.
- 기존 글과 테스트가 모두 통과한다(`lint:content`, `check`, `test`, `test:e2e`).
- 360px과 1440px에서 가로 스크롤이 없다. 퀴즈와 새 그림 포함.
