# DomainDocs 사이트 설계

- 작성일: 2026-10-13
- 상태: 승인됨 (구현 계획 작성 전)

## 1. 목적

모니터링 도메인 지식을 한글로 정리하는 공개 지식 사이트를 만든다.

- **배경**: AI가 코드를 쓰고 개발자는 그 결과를 판단하는 역할로 옮겨 간다. 판단하려면 도메인 지식이 필요하다.
- **독자**: 1차로 사이트 주인(모니터링 제품을 만드는 프론트엔드 개발자). 2차로 같은 고민을 하는 다른 개발자.
- **최우선 가치**: 가독성. 읽혀야 머리에 들어온다.
- **작성 주체**: 코드와 글은 에이전트가 쓰고, 사람은 결과를 판단한다.

### 반면교사

`C:\project\Domain-Knowledge\BOOK.html`(이전에 만든 100장짜리 지식서)처럼 만들지 않는다. 내용도 재사용하지 않는다. 읽히지 않았던 이유는 다음과 같다.

| 구분 | 문제 |
| --- | --- |
| 화면 | 본문 폭이 1000px 이상이라 한 줄에 60~70자 |
| 화면 | 100장을 한 파일에 몰아넣어 진척감이 없음 |
| 화면 | 목차·표가 모두 같은 무게라 핵심이 안 보임 |
| 문장 | 문장마다 면책·단서("~라고 주장하지 않습니다")가 붙어 핵심이 묻힘 |
| 문장 | 결론과 "그래서 무엇을 판단할 수 있는지"가 늦게 나옴 |
| 문장 | 한 단락에 새 개념이 서너 개씩 등장 |
| 문장 | 입문 설명과 커널 소스 줄 번호 수준 근거가 같은 높이에 섞임 |

## 2. 성공 기준

- 사이트 주인이 1단계 샘플 4편을 읽고 "읽힌다"고 판단한다.
- 개념 한 편은 3~5분 안에 읽힌다.
- 모든 글이 자동 검사를 통과해야만 빌드가 성공한다.
- 모바일(360px)과 데스크톱(1440px) 모두 가로 스크롤이 없다.
- 데모·미리보기 시트·검색을 제외한 페이지는 JavaScript 없이 렌더링된다.

## 3. 결정 사항 요약

| 항목 | 결정 |
| --- | --- |
| 콘텐츠 구조 | 개념 사전 + 가이드 |
| 다룰 영역 | 공통 기초 → APM → DB 모니터링 → 인프라·쿠버네티스 순으로 하나씩 |
| 공개 범위 | 공개 웹사이트. 회사 내부 정보는 다루지 않음 |
| 디자인 | 토스 앱 시각 언어를 따르되 토스 브랜드 자산은 사용하지 않음 |
| 인터랙티브 | 글로만 설명하면 헷갈리는 핵심 개념에만 데모 |
| 기술 | Astro + MDX + React(데모만) |
| 검색 | Pagefind |
| 배포 | GitHub Actions → GitHub Pages |

## 4. 정보 구조

### 4.1 페이지 종류

| 페이지 | 주소 | 내용 |
| --- | --- | --- |
| 홈 | `/` | 큰 제목, 영역 카드 4개, "처음이라면 여기부터" 추천 순서, 최근 추가된 글 |
| 영역 | `/{domain}/` | 영역 소개 2~3줄, 가이드 목록, 개념 목록 |
| 개념 | `/{domain}/{slug}/` | 개념 하나. 3~5분 분량 |
| 가이드 | `/{domain}/{slug}/` | 여러 개념을 엮어 실제 판단 상황 하나를 다룸. 10분 이내 |

- 영역 카드: 글이 하나도 없는 영역은 "준비 중" 배지를 달고 누를 수 없다.
- 목록: 토스 리스트 행 형태(아이콘 · 제목 · 한 줄 요약 · `›`). 오른쪽에 종류와 읽는 시간 배지를 붙인다.

### 4.2 영역

`src/data/domains.ts`에 정의한다.

| slug | 이름 | 1단계 상태 |
| --- | --- | --- |
| `foundations` | 공통 기초 | 샘플 4편 공개 |
| `apm` | APM | 준비 중 |
| `database` | DB 모니터링 | 준비 중 |
| `infra` | 인프라·쿠버네티스 | 준비 중 |

### 4.3 탐색

- 왼쪽 사이드바와 오른쪽 목차를 두지 않는다. 화면 가운데 좁은 칼럼 하나만 쓴다.
- 상단 바(고정, 높이 56px): 뒤로가기(홈 제외) · 페이지 제목(스크롤하면 나타남) · 검색 버튼.
- 글 끝: "다음에 읽을 글" 카드(영역 내 `order` 기준 다음 글)와 "관련 개념" 카드(`related`).
- **개념 미리보기 시트**: 본문의 개념 링크(`<Term>`)를 누르면 아래에서 시트가 올라와 그 개념의 한 줄 요약과 핵심 소제목을 보여준다. "전체 보기" 버튼으로 이동한다.
  - Ctrl/Cmd+클릭, 가운데 클릭은 일반 링크처럼 새 탭으로 연다.
  - JavaScript가 없으면 일반 링크로 동작한다.
  - Esc, 바깥 영역 클릭, 아래로 끌어내리기로 닫는다. 열리면 포커스를 시트 안에 가두고, 닫히면 원래 링크로 포커스를 돌려준다.
  - 요약 데이터는 빌드할 때 페이지에 넣어 둔다. 시트를 열 때 네트워크 요청이 없다.
- **검색**: 상단 검색 버튼 또는 `/` 키로 화면 전체를 덮는 검색 창을 연다. Pagefind JS API로 결과를 받아 토스 리스트 형태로 직접 그린다.

## 5. 페이지 틀

모든 글은 아래 틀을 따른다. 틀은 MDX 컴포넌트로 표현하고 자동 검사로 강제한다(7장).

### 5.1 개념 페이지

| 순서 | 블록 | 컴포넌트 | 필수 | 내용 |
| --- | --- | --- | --- | --- |
| 1 | 제목 + 한 줄 요약 | (머리말에서 자동) | 예 | 이것만 읽어도 무엇인지 알게 |
| 2 | 대시보드에서는 이렇게 보여요 | `<OnDashboard>` | 예 | 모니터링 화면 어디서 이 개념을 만나는지 작은 그림으로 |
| 3 | 핵심 | `<KeyPoints>` 안에 `<Point title>` 1~3개 | 예 | 결론형 소제목 + 5문장 안팎(두 단락 이하) |
| 4 | 이런 걸 보면 다시 확인하세요 | `<Checkpoints>` 안에 `<Check>` 1개 이상 | 예 | AI나 동료의 구현에서 의심해야 할 지점 |
| 5 | 더 깊이 | `<Deeper>` | 아니오 | 기본으로 접힘. 공식, 예외, 세부 동작 |
| 6 | 참고 자료 | (머리말 `sources`에서 자동) | 예 | 출처 목록 |
| 7 | 관련 개념 · 다음 글 | (자동) | — | |

`<Check>` 예시: "서버별 p99를 구한 뒤 평균을 냈다면 틀린 값이에요."

### 5.2 가이드 페이지

| 순서 | 블록 | 컴포넌트 | 필수 |
| --- | --- | --- | --- |
| 1 | 제목 + 한 줄 요약 | (자동) | 예 |
| 2 | 상황 | `<Situation>` | 예 |
| 3 | 먼저 볼 것 | `<FirstLook>` 안에 `<Item>` 1~3개 | 예 |
| 4 | 단계별 설명 | 일반 `##` 소제목 | 예 (1개 이상) |
| 5 | 이런 걸 보면 다시 확인하세요 | `<Checkpoints>` | 예 |
| 6 | 이 글에 쓰인 개념 | (본문의 `<Term>`에서 자동 수집) | — |
| 7 | 참고 자료 · 다음 글 | (자동) | — |

## 6. 글쓰기 규칙

에이전트가 읽을 작성 가이드는 `docs/writing-guide.md`에 두고, 저장소 루트 `CLAUDE.md`에서 반드시 따르도록 지시한다.

- 해요체로 쓴다. 본문 문장을 "~습니다/~ㅂ니다"로 끝내지 않는다.
- 결론을 먼저 쓴다.
- 한 문장에는 정보 하나만 담는다. 한 단락은 세 문장 이하로 쓴다.
- 새 용어는 처음 나올 때 풀어 쓰거나 `<Term>`으로 링크한다.
- 업계에서 영어로 쓰는 말(p99, rate, span)은 영어로 쓰고, 처음 나올 때 한 번 한글로 풀어 준다.
- 숫자 예시는 구체적으로 든다. ("요청 100개 중 1개가 3초 걸리면")
- 본문에는 면책 문장을 쓰지 않는다. 꼭 필요한 예외는 `<Deeper>`에 넣는다.
- 출처는 문장마다 달지 않고 머리말 `sources`에 모은다.
- 한 단락에서 새 개념은 하나만 소개한다.

## 7. 콘텐츠 스키마와 자동 검사

### 7.1 머리말 스키마 (`src/content.config.ts`, zod)

| 필드 | 타입 | 규칙 |
| --- | --- | --- |
| `title` | string | 필수, 30자 이하 |
| `summary` | string | 필수, 15~60자. 한 줄 요약 |
| `domain` | enum | `foundations` \| `apm` \| `database` \| `infra`. 폴더 일치는 글 검사(7.2)에서 확인 |
| `type` | enum | `concept` \| `guide` |
| `order` | number | 영역 내 추천 읽기 순서 |
| `icon` | enum | 선택. `src/data/icons.ts`에 등록된 아이콘 이름 |
| `keywords` | string[] | 선택, 10개 이하. 검색용 별칭(예: "꼬리 지연", "tail latency"). 화면에는 보이지 않음 |
| `related` | reference[] | 0~5개. 존재하는 글이어야 함 |
| `sources` | `{ title, url }[]` | 1개 이상 |
| `updated` | date | 필수 |
| `draft` | boolean | 기본 `false`. `true`면 운영 빌드에서 제외 |

- 글 위치: `src/content/docs/{domain}/{slug}.mdx`. slug는 파일 이름이다.
- 읽는 시간: '더 깊이'를 뺀 본문 글자 수 ÷ 500자/분, 올림.

### 7.2 글 검사 (`npm run lint:content`, 빌드 전에 실행, 위반 시 실패)

MDX를 remark로 파싱해 검사한다. 코드 블록, 인라인 코드, 표, 컴포넌트 속성값은 문장 검사에서 제외한다. 기준값은 `scripts/lint-content/config.ts`에 모아 두고, 샘플을 써 보면서 조정한다.

| 규칙 | 초기 기준 |
| --- | --- |
| 개념 페이지 블록 순서·필수 여부 | 5.1 표. 최상위에는 틀 블록과 데모만 둘 수 있음 |
| 가이드 페이지 블록 순서·필수 여부 | 5.2 표 |
| `<KeyPoints>` 안 `<Point>` 개수 | 1~3 |
| `<FirstLook>` 안 `<Item>` 개수 | 1~3 |
| 문장 길이 | 80자 초과 금지 (링크·용어는 보이는 글자 기준) |
| 단락 길이 | 3문장 초과 금지 |
| 문체 | 본문 문장은 "요" 또는 "죠"로 끝나야 함(해요체). 인라인 코드로 끝나는 문장은 그 앞 한글로 판단 |
| 알 수 없는 컴포넌트 | 등록된 틀·차트 컴포넌트나 import한 데모가 아닌 JSX(예: `<a>`, `<img>`)는 위반 |
| 데모 hydration | import한 데모에 `client:*` 지시어가 없으면 위반 |
| 금지 표현 | "주장하지 않", "단정하지 않", "보장하지 않" 등. 목록은 설정 파일에서 관리 |
| 본문 분량 | 개념 1,500자 이하, 가이드 4,000자 이하 ('더 깊이' 제외) |
| `<Term slug>`, `related` | 존재하는 글을 가리켜야 함. 공개 글은 초안(`draft`) 글을 가리킬 수 없음 |
| `domain` 필드 | 파일이 있는 폴더 이름과 같아야 함 |
| 마크다운 링크 | 본문에 쓰지 않음. 다른 글은 `<Term>`, 출처는 `sources` |
| `<Point>`·`<Item>` 제목 | 30자 이하 |

데모 컴포넌트는 MDX 안에서 default import로 가져와 `client:visible`로 쓴다. 검사기는 import된 이름을 데모로 인정한다.

`<Deeper>` 안의 문장에는 금지 표현 규칙만 적용하지 않는다. 문장 길이·단락 길이·문체 규칙은 그대로 적용한다.

## 8. 디자인 시스템

토스 앱의 시각 언어를 따른다. 토스 로고, Toss Product Sans, 토스페이스 이모지, 토스 일러스트는 쓰지 않는다.

### 8.1 토큰 (`src/styles/tokens.css`, CSS 변수)

| 토큰 | 라이트 | 다크 |
| --- | --- | --- |
| 배경 | `#F2F4F6` | `#101013` |
| 카드 | `#FFFFFF` | `#1C1C21` |
| 본문 글자 | `#191F28` | `#E8E9EC` |
| 보조 글자 | `#6B7684` | `#9EA4AD` |
| 약한 글자 | `#8B95A1` | `#6E747C` |
| 강조 | `#3182F6` | `#4C93FF` |
| 강조 옅은 배경 | `#E8F3FF` | `#1A2A40` |
| 경고(다시 확인하세요) | `#F04452` | `#FF6B76` |
| 경고 옅은 배경 | `#FFF0F1` | `#3A1E22` |
| 구분 | `#E5E8EB` | `#2A2B31` |

- 다크 모드는 `prefers-color-scheme`를 따른다. 수동 전환 버튼은 두지 않는다.

### 8.2 글자

- 본문: Pretendard Variable(웹폰트, 한글 서브셋), 17px, 행간 1.7, 자간 -0.01em.
- 제목: 페이지 제목 28px/700, `##` 22px/700, `###` 19px/600, 자간 -0.02em.
- 코드: 고정폭 폰트, 15px.
- 본문 칼럼 최대 폭 640px → 한 줄 약 35~40자. 모바일 좌우 여백 20px.

### 8.3 모양과 움직임

- 카드 모서리 20px, 리스트 행·버튼 모서리 12~16px. 그림자는 시트와 검색 창에만 쓴다.
- 구분선 대신 여백(섹션 간 40px 이상)으로 나눈다.
- 누를 수 있는 요소는 누르는 동안 `scale(0.98)`과 배경색 변화로 반응한다.
- 시트: 아래에서 올라오는 모달. 데스크톱에서도 가운데 정렬된 최대 640px 폭.
- `prefers-reduced-motion`이면 애니메이션을 끈다.
- 아이콘: 오픈소스 아이콘 세트(Lucide)를 쓴다.

### 9.1 폴더

```text

├─ CLAUDE.md                     # 에이전트 작업 규칙 (작성 가이드 준수 지시)

│  ├─ content.config.ts          # 컬렉션과 머리말 스키마

│  │  │                          # Deeper, Term, Situation, FirstLook, Item
│  │  ├─ viz/                    # MiniLineChart, StatTile (정적 SVG, 숫자만 넣어 재사용)
│  │  └─ demos/                  # PercentileDemo.tsx, DownsamplingDemo.tsx (React)
│  ├─ layouts/                   # BaseLayout, DocLayout

├─ scripts/lint-content/         # 글 검사
├─ tests/

   ├─ writing-guide.md           # 글쓰기 규칙 (6장의 상세판)

   └─ superpowers/specs/
```

### 9.2 동작 원리

- **MDX 처리기**: Astro 7 기본 처리기(Sätteri)는 `1~2초`처럼 물결표 하나로 쓴 한글 숫자 범위를 취소선으로 바꾼다. 그래서 `@astrojs/markdown-remark`의 `unified()` 처리기에 `remark-gfm`을 `{ singleTilde: false }`로 넣어 쓴다. 글 검사기도 같은 설정의 remark로 파싱하므로 화면과 검사가 같은 해석을 공유한다.
- **정적 기본**: Astro가 모든 페이지를 HTML로 만든다. 데모는 `client:visible`로 화면에 보일 때만 불러온다.
- **시트**: `<Term>`은 `<a href data-term>`으로 렌더링한다. 빌드할 때 대상 글의 `summary`와 `<Point title>` 목록을 추출해 페이지 안 JSON에 넣는다. 작은 스크립트 하나가 클릭을 가로채 시트를 연다.
- **대시보드 그림**: `<OnDashboard>` 안에서 `viz/` 컴포넌트에 숫자만 넣어 그린다. 이미지 파일을 만들지 않는다.
- **데모**: 차트 라이브러리 없이 React + SVG로 직접 그린다. 키보드로도 조작할 수 있어야 한다.
- **검색**: 빌드 후 Pagefind가 색인을 만든다. 본문 영역만 색인한다.
- **base 경로**: GitHub Pages 프로젝트 사이트(`/DomainDocs/`)를 기본으로 하되, `astro.config.mjs`의 `site`·`base`만 바꾸면 커스텀 도메인으로 옮길 수 있다. 내부 링크는 모두 base를 거쳐 만든다.

## 10. 정확성 확보

공개 사이트이고 에이전트가 쓰는 글이라 틀린 내용이 가장 위험하다.

1. 작성 에이전트가 글을 쓴다. 공식 문서·명세·원 논문을 우선 근거로 삼는다.
2. 별도의 검토 에이전트가 사실 관계를 출처와 대조한다. 결과는 `docs/reviews/{domain}-{slug}.md`에 남긴다.
3. 지적 사항을 고친 뒤 글 검사를 통과시킨다.
4. 사이트 주인이 화면에서 읽고 최종 판단한다.

검토 기록과 확인 상태는 독자에게 보여주지 않는다.

## 11. 1단계 범위

### 11.1 만드는 것

- 사이트 전체: 홈, 영역 페이지, 개념·가이드 페이지, 검색, 미리보기 시트, 다크 모드
- 글 검사 스크립트와 테스트, `docs/writing-guide.md`, `CLAUDE.md`
- GitHub Actions 빌드·배포 워크플로
- 공통 기초 샘플 4편

| 종류 | slug | 제목(가안) | 데모 |
| --- | --- | --- | --- |
| 개념 | `percentiles` | 평균과 백분위수 | `PercentileDemo`: 슬라이더로 요청 100개 중 느린 요청(3초)을 늘리면, 1개일 때는 p99가 그대로이고 2개가 되는 순간 3초로 튀는 것을 확인. 평균은 아무도 겪지 않은 값(187ms)으로 오름 |
| 개념 | `counters-and-rate` | 카운터와 rate | 없음 (정적 그림) |
| 개념 | `aggregation-and-downsampling` | 집계 구간과 다운샘플링 | `DownsamplingDemo`: 조회 기간을 넓히면 순간 피크가 사라지는 것을 확인 |
| 가이드 | `why-numbers-differ` | 같은 지표가 화면마다 다르게 보이는 이유 | 위 세 개념을 엮어 설명 |

### 11.2 1단계 이후

1. 사이트 주인이 샘플을 보고 피드백 → 글쓰기 규칙·검사 기준·디자인 수정
2. 공통 기초의 나머지 글 목록을 제안하고 승인받아 묶음 단위로 작성
3. APM → DB 모니터링 → 인프라·쿠버네티스 순으로 같은 방식 반복. 영역마다 글 목록을 따로 승인받는다.

### 11.3 하지 않는 것 (1단계 이후에도)

- 댓글, 로그인, 방문자 분석, 영어판
- CMS, 서버, 데이터베이스
- 다크 모드 수동 전환

## 12. 테스트

| 종류 | 도구 | 확인 내용 |
| --- | --- | --- |
| 타입 | `astro check` | 컴포넌트·스키마 타입 |
| 글 검사 규칙 | Vitest | 7.2의 규칙마다 통과 사례와 위반 사례 |
| 글 검사 실행 | `npm run lint:content` | 실제 글 전체 |
| 화면 | Playwright | 홈의 영역 카드 4개와 "준비 중" 상태 / 개념 페이지 필수 블록 / `<Term>` 클릭 → 시트 열림, Esc로 닫힘, 포커스 복귀 / Ctrl+클릭은 시트를 열지 않음 / 검색 "백분위수" → 결과에 `percentiles` / 데모가 마우스와 키보드 조작에 반응 / 다크 모드 색 적용 / 360px에서 가로 스크롤 없음 |

- 화면 테스트는 실제 글이 아니라 테스트 전용 글(`tests/fixtures/docs/`)로 빌드한 사이트에서 돈다. 콘텐츠 폴더는 환경 변수 `DOCS_CONTENT_DIR`로 바꾼다. 실제 글을 고쳐도 화면 테스트가 깨지지 않게 하기 위해서다.
- 빌드 결과는 base 경로(`/DomainDocs/`) 아래에서만 응답하는 작은 정적 서버로 띄운다. base 밖으로 새는 링크가 있으면 404로 드러난다.

CI는 PR과 `main` 푸시마다 위 검사를 모두 실행한다. 배포는 `main`에서만 한다.

## 13. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| Pagefind의 한글 검색 품질 | 사전 실험(Pagefind 1.5.2)에서 앞부분 일치("백분위" → "백분위수")와 조사 붙은 본문("피크가")은 찾았다. 단어 중간("샘플링" → "다운샘플링")과 조사 붙은 검색어("피크를")는 못 찾았다. 그래서 `keywords` 별칭을 `data-pagefind-meta`로 색인하고 `ranking.termSimilarity: 0`을 쓴다 |
| 한글 숫자 범위(`1~2초`)가 취소선이 됨 | 9.2의 MDX 처리기 설정. 화면 테스트로 고정한다 |
| 문장 검사 기준이 너무 엄격하거나 느슨함 | 샘플 4편을 쓰면서 기준값을 조정하고, 바뀐 값을 `writing-guide.md`에 반영한다 |
| 에이전트가 쓴 글의 사실 오류 | 10장 절차. 사이트 주인의 최종 판단 |
| 토스 디자인 유사성 | 색·여백·모양 같은 시각 언어만 차용하고 브랜드 자산은 쓰지 않는다 |
