## 무엇을 잡나요

패킷 캡처는 네트워크 인터페이스를 지나는 <Term term="network/packet">패킷</Term>을 그대로 잡아 두는 일이에요. 리눅스에서는 명령줄 도구 tcpdump를, 화면에서 읽을 때는 Wireshark를 많이 써요. 둘은 같은 pcap 파일 형식을 써서, tcpdump로 잡은 파일을 Wireshark로 열어요.

```text
tcpdump -i eth0 -nn \
  host 10.0.2.9 and port 8080

tcpdump -i eth0 -nn \
  -w cap.pcap port 5432
```

- `-i eth0`: 잡을 인터페이스예요.
- `-nn`: 주소와 포트를 이름으로 바꾸지 않아요. 이름을 찾느라 DNS 질의가 생기지 않아요.
- `host 10.0.2.9 and port 8080`: 잡을 패킷을 고르는 필터예요. `or`, `not`도 써요.
- `-w cap.pcap`: 화면에 찍지 않고 파일로 저장해요.

인터페이스에서 잡으려면 root 같은 특별한 권한이 필요해요. 저장한 파일을 읽을 때(`-r cap.pcap`)는 권한이 필요 없어요.

플래그는 이 패킷이 무슨 일을 하는지 알려 줘요.

- `S`: 연결을 열자는 SYN이에요.
- `.`: 받았다는 ACK예요. `[S.]`는 SYN과 ACK를 함께 보낸 거예요.
- `P`: 데이터를 바로 넘기라는 표시예요. 요청과 응답 본문이 이 패킷에 실려요.
- `F`: 다 보냈으니 닫자는 FIN이에요.
- `R`: 연결을 당장 끊는 RST예요.

## 연결이 안 될 때는 이렇게 보여요

연결이 안 되는 두 경우는 캡처에서 모양이 확연히 달라요. 같은 실험에서 닫힌 포트와, 답을 버리는 포트에 연결해 봤어요.

답이 없을 때 SYN을 다시 보내는 간격은 운영체제마다 달라요. 이 실험의 리눅스(6.18)는 1초 간격으로 다시 보냈어요.

리눅스 6.5부터는 간격이 1, 1, 1, 1, 1, 2, 4초처럼 처음엔 1초씩이다가 두 배씩 늘어요. 이 동작은 `tcp_syn_linear_timeouts`(기본 4)가 정해요.

<Term term="network/retransmission">재전송</Term>은 캡처에서 같은 `seq` 번호의 패킷이 다시 나오는 모습으로 보여요. 연결 실패가 왜 둘로 나뉘는지는 <Term slug="network/tcp-connections">TCP 연결</Term>에서 다뤄요.

## 조심할 것

- **파일이 빨리 커져요**: 바쁜 서버는 몇 초 만에 수백 MB를 잡아요. 필터로 좁히고, `-c 1000`(1,000개만)이나 `-C 100 -W 5`(100MB씩 5개를 돌려 씀)로 크기를 묶어요.
- **내용이 함께 잡혀요**: 기본으로 패킷마다 262,144바이트까지 잡아서, 암호화하지 않은 요청 본문이 그대로 담겨요. 파일을 넘기기 전에 <Term slug="logs/sensitive-data">민감 정보</Term>를 생각해요.
- **TLS 내용은 안 보여요**: 암호화된 연결은 주소, 포트, 크기, 시각만 보여요. 연결을 여는 단계(TLS 핸드셰이크)의 서버 이름(SNI)은 대개 그대로 보여요.
- **컨테이너는 그 안에서 잡아요**: 파드는 자기 네트워크 네임스페이스가 있어서, 노드의 `eth0`에서는 파드끼리의 패킷이 안 보일 수 있어요.

## 모니터링에서는

모니터링은 패킷을 모두 잡지 않아요. 대신 운영체제가 세어 둔 수를 모아요. 리눅스에서는 `nstat`이나 `netstat -s`로 그 수를 봐요.

- `TcpRetransSegs`: 다시 보낸 세그먼트 수예요.
- `TcpExtTCPSynRetrans`: 다시 보낸 SYN 수예요. 연결이 잘 안 열린다는 신호예요.
- `TcpOutRsts`: 보낸 RST 수예요. 닫힌 포트로 오는 연결이 많으면 늘어요.

이 수가 튀면 그때 캡처로 내려가요. 지표가 어디가 이상한지 알려 주면, 캡처가 무슨 일이 있었는지 보여 줘요.
