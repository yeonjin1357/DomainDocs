TCP 표준은 이 과정을 <Term term="network/three-way-handshake">3방향 핸드셰이크</Term>라고 불러요. 양쪽은 이 과정에서 데이터에 붙일 번호(순서 번호)의 시작값을 서로 알려 줘요.

연결을 맺는 데 왕복 한 번이 더 들어서, 서버가 멀수록 연결 맺기가 오래 걸려요. 그래서 앱은 연결을 매번 새로 맺기보다 열어 둔 연결을 돌려 써요. 이 방식이 <Term slug="apm/connection-pool">커넥션 풀</Term>이에요.

## 받았다는 답이 없으면 다시 보내요

TCP는 데이터를 보낸 뒤 받았다는 답(ACK)을 기다려요. 정한 시간 안에 답이 없으면 같은 데이터를 다시 보내요. 이를 <Term term="network/retransmission">재전송</Term>이라고 불러요.

기다리는 시간(RTO)은 왕복 시간을 재며 정해요. 표준은 아직 재지 못했을 때 1초로 시작하고, 재전송할 때마다 두 배로 늘리라고 해요. 그래서 같은 패킷이 몇 번 사라지면 응답이 몇 초씩 늦어질 수 있어요.

## 연결 실패 두 가지

연결을 못 맺는 경우는 크게 둘로 나뉘어요. 두 오류는 원인이 달라서 구별해서 봐야 해요.

## 연결의 상태

TCP 연결은 여러 상태를 거쳐요. 리눅스에서는 `ss` 명령으로 상태별 연결을 세어 볼 수 있어요.

| 상태 | 뜻 |
| --- | --- |
| LISTEN | 서버가 연결 요청을 기다려요 |
| SYN-SENT | 클라이언트가 SYN을 보내고 답을 기다려요 |
| ESTABLISHED | 연결이 열려 데이터를 주고받아요 |
| CLOSE-WAIT | 상대가 연결을 닫았고, 이쪽 앱이 닫기를 기다려요 |
| TIME-WAIT | 먼저 닫은 쪽이 마지막 확인이 닿도록 잠시 기다려요 |

CLOSE-WAIT는 이쪽 앱이 연결을 닫아 줘야 끝나요. 그래서 CLOSE-WAIT가 계속 쌓이면 앱이 다 쓴 연결을 닫지 않는 거예요.

TIME-WAIT는 정상적인 상태예요. 표준은 최대 세그먼트 수명(MSL)을 2분으로 잡고, 이 상태에서 그 두 배까지 기다리게 해요. 짧은 연결을 아주 많이 맺고 끊는 쪽에 TIME-WAIT가 많이 쌓여요.

<Deeper>
  ### 재전송 타이머의 규칙

  RFC 6298은 왕복 시간을 아직 재지 못했으면 RTO를 1초로 두라고 해요. 타이머가 만료되면 RTO를 두 배로 늘리고(back off), 최댓값을 둔다면 60초 이상이어야 해요.

  ### 시간 초과가 길어지는 경우

  connect 매뉴얼은 시간 초과를 서버가 너무 바빠 새 연결을 받지 못하는 경우로 설명해요. 서버의 SYN 쿠키 설정에 따라 이 기다림이 아주 길어질 수도 있어요.

  ### 순서 번호

  TCP는 보내는 데이터의 바이트마다 순서 번호를 붙여요. 받는 쪽은 이 번호로 빠진 부분을 알아채고, 순서가 뒤바뀐 데이터도 제자리에 맞춰요.
</Deeper>
