## 왜 층으로 나눌까요

통신에는 풀 문제가 여러 개예요. 선 위로 신호를 보내고, 옆 장비에 건네고, 먼 네트워크까지 길을 찾고, 받을 프로그램을 찾아야 해요. 이 일을 층으로 나눠 맡기면, 한 층을 바꿔도 다른 층은 그대로 써요.

노트북이 유선에서 와이파이로 바뀌어도 웹 브라우저의 HTTP는 그대로예요. 아래층만 바뀌었기 때문이에요.

## 번호가 4에서 7로 뛰는 이유

L1부터 L7까지의 번호는 <Term term="network/osi-model">OSI 모델</Term>에서 왔어요. ITU-T와 ISO가 정한 참조 모델로, 통신을 일곱 층으로 나눠요.

인터넷에서 실제로 쓰는 TCP/IP는 층을 넷으로 나눠요. 링크, 인터넷, 전송, 응용이에요. 그래도 현장에서는 OSI 번호로 불러서 L2, L3, L4, L7이라고 해요.

## 보낼 때 층마다 감싸요

앱이 HTTP 요청을 보내면, 아래층으로 내려가며 층마다 자기 머리표(헤더)를 앞에 붙여요. 이렇게 감싸는 일을 <Term term="network/encapsulation">캡슐화</Term>라고 해요. 맨 위 계단 그림의 파란 칸이 층마다 붙는 머리표예요.

선 위를 지나는 이더넷 프레임은 그 계단의 맨 아래 줄이에요. MAC 머리, IP 머리, TCP 머리, HTTP 요청, 꼬리가 차례로 이어져요.

받는 쪽은 거꾸로 아래층부터 머리표를 하나씩 벗기며 위층에 넘겨요. 각 층은 자기 머리표만 읽어요.

층마다 덩어리를 부르는 이름도 달라요. L2는 프레임, L3는 패킷, L4의 TCP는 세그먼트라고 해요. 흔히 모두 뭉뚱그려 패킷이라고도 불러요.

## 머리표만큼 실을 자리가 줄어요

이더넷이 한 번에 실어 보내는 IP 패킷의 최대 크기를 <Term term="network/mtu">MTU</Term>라고 해요. 보통 1,500바이트예요.

옵션 없는 IPv4 머리가 20바이트, TCP 머리가 20바이트예요. 그래서 앱 데이터는 패킷 하나에 1,460바이트까지 실어요. 이 크기를 MSS(Maximum Segment Size)라고 하고, 큰 응답은 이 크기로 잘려 나눠 가요.

## 라우터를 지나면 맨 바깥 이름표만 바뀌어요

L2 머리표의 MAC 주소는 같은 네트워크 안에서만 써요. 그래서 라우터는 패킷을 다음 네트워크로 넘길 때 L2 머리표를 떼고 새로 붙여요. 안쪽의 IP 주소는 그대로예요.

## 장비 이름의 숫자는 읽는 층이에요

- **L2 스위치**: MAC까지 읽고, 같은 네트워크 안의 포트로 넘겨요.
- **L3 스위치와 라우터**: IP까지 읽고, 네트워크 사이로 길을 골라요.
- **L4 로드 밸런서**: IP와 포트까지 읽고, 연결 단위로 나눠요. AWS의 Network Load Balancer가 여기예요.
- **L7 로드 밸런서**: HTTP 요청까지 읽고, 주소나 헤더로 나눠요. AWS의 Application Load Balancer가 여기예요.

장비는 자기가 읽는 층보다 위의 내용을 몰라요. 그래서 L4 로드 밸런서는 HTTP 상태 코드를 모르고, 5xx 같은 지표도 내지 않아요. 로드 밸런서는 <Term slug="cloud/load-balancers">로드 밸런서</Term>에서 다뤄요.

<Deeper>
  ### OSI의 5·6층

  OSI의 세션층(5)은 대화를 열고 닫는 일을, 표현층(6)은 데이터 형식을 맞추는 일을 맡아요. 실제 프로토콜은 이 경계에 딱 맞지 않아서, TLS를 몇 층에 둘지는 설명마다 달라요.

  ### MSS는 연결을 맺을 때 알려요

  TCP는 연결을 맺는 SYN에 자기가 받을 수 있는 MSS를 실어 보내요. 상대가 알려 주지 않으면 IPv4에서는 536바이트로 여겨요. 576바이트에서 IP·TCP 머리 40바이트를 뺀 값이에요.

  ### 1,500바이트는 IP 패킷 크기예요

  RFC 894는 이더넷으로 보내는 IP 패킷의 최대 길이를 1,500바이트로 정해요. 선 위의 이더넷 프레임에는 여기에 이더넷 머리와 꼬리가 더 붙어요.
</Deeper>
