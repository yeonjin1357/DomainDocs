## 터널은 무엇인가요

<Term term="network/tunnel">터널</Term>은 패킷을 다른 패킷 안에 넣어 보내는 방법이에요. 바깥 패킷에는 터널 양 끝 장비의 주소가 붙어요. 중간 장비는 안쪽 패킷이 무엇인지 몰라도 바깥 주소만 보고 날라요.

<Figure caption="지사의 원래 패킷을 터널 입구가 바깥 주소로 감싸 인터넷 너머로 보내고, 출구가 벗겨 본사에 넘겨요. 감싼 동안 중간 장비에는 파란 칸의 바깥 주소만 보여요.">
  <TunVpn aria-label="지사 PC의 원래 패킷(안쪽 IP, 데이터)을 터널 입구가 바깥 IP와 터널 머리로 감싸 인터넷 위의 터널로 보내고, 본사의 출구가 벗겨 원래 패킷을 서버에 넘기는 그림" />
</Figure>

감싸는 방식을 일컫는 말이 셋 있어요.

- **VPN**: 지사와 본사처럼 떨어진 두 네트워크를 인터넷 너머로 잇는 터널이에요. IPsec처럼 안쪽 패킷을 암호화해요.
- **GRE**: 암호화 없이 감싸기만 하는 단순한 터널이에요. 기본 머리표는 4바이트이고, 바깥 IP 머리 20바이트가 더 붙어요.
- **VXLAN**: 이더넷 프레임을 통째로 UDP에 넣어, 떨어진 서버들을 한 네트워크처럼 묶어요. 클라우드와 쿠버네티스 <Term slug="kubernetes/pod-network">파드 네트워크</Term>의 오버레이가 이 방식을 많이 써요.

<Term term="network/overlay">오버레이</Term>는 이렇게 실제 네트워크(언더레이) 위에 터널로 엮은 가상 네트워크를 말해요.

## 감싼 만큼 실을 자리가 줄어요

선이 한 번에 실을 수 있는 IP 패킷의 크기(<Term term="network/mtu">MTU</Term>)는 터널을 써도 그대로예요. 그래서 머리표를 더 붙인 만큼 안쪽 패킷이 작아야 해요.

## 큰 패킷만 사라질 때

보내는 쪽은 보통 패킷에 '쪼개지 말 것(DF)' 표시를 붙여 보내요. 길 중간에 그보다 작은 MTU를 만나면, 그 장비가 패킷을 버리고 "너무 커요"라는 ICMP 메시지를 돌려보내요.

보내는 쪽은 이 메시지를 보고 크기를 줄여요. 이걸 경로 MTU 찾기(PMTUD)라고 해요.

문제는 방화벽이 ICMP를 모두 막을 때예요. 보내는 쪽은 "너무 커요"를 못 받아서, 같은 크기로 계속 다시 보내요. 큰 패킷만 소리 없이 사라지는 <Term term="network/mtu-black-hole">MTU 블랙홀</Term>이에요.

<Figure caption="응답이 1,500바이트라 터널 입구에서 버려져요. 입구가 보낸 ICMP '너무 커요'는 방화벽에 막혀 서버에 닿지 않아서, 서버는 같은 크기로 다시 보내요.">
  <TunPmtud aria-label="서버, 방화벽, 터널 입구, 클라이언트 순으로 놓인 그림. 클라이언트의 작은 요청은 서버에 닿고, 서버의 1,500바이트 응답은 터널 입구에서 버려져요. 입구가 보낸 ICMP 너무 커요는 방화벽에 막히고, 서버는 다시 1,500바이트로 보내 또 버려져요" />
</Figure>

그래서 연결은 맺어지고 작은 요청도 오가는데, 큰 응답이나 큰 인증서가 오가는 TLS 연결 맺기에서만 멈춰요. 연결이 끊기지 않고 그냥 멈춰 있어서, 시간 초과로만 보여요.

고치는 길은 셋이에요.

- 터널 구간에서 ICMP의 "너무 커요" 메시지를 허락해요.
- 터널 안쪽의 MTU를 감싼 만큼 줄여요.
- 터널 입구에서 TCP 연결을 맺을 때 MSS를 줄여 적어요. 이걸 MSS 고정(MSS clamping)이라고 해요.

MSS는 <Term slug="network/layers">네트워크 계층</Term>에서 본 앱 데이터 최대 크기예요.

## 모니터링에서는

길에서 실을 수 있는 크기는 `ping`으로 재요. 리눅스에서 `-M do`는 쪼개지 말라는 표시를 붙여요. `-s`는 데이터 크기라, IP 머리 20바이트와 ICMP 머리 8바이트를 더한 값이 패킷 크기예요.

```bash
ping -M do -s 1472 -c 1 대상
ping -M do -s 1422 -c 1 대상
```

1472는 1,500바이트, 1422는 1,450바이트 패킷이에요. 1472는 응답이 없고 1422는 온다면, 길 어딘가의 MTU가 1,500보다 작아요. 내 서버의 MTU보다 크게 보내면 "message too long, mtu=1500"이 바로 나와요.

모니터링 화면에서는 VPN 터널의 상태(up·down)와 터널 인터페이스의 트래픽을 다른 인터페이스처럼 봐요. 터널이 살아 있는데 큰 요청만 실패한다면, 위의 MTU 블랙홀을 먼저 떠올려요.

<Checkpoints>
  <Check>VPN이나 오버레이 너머로 작은 요청은 되는데 큰 응답만 시간 초과로 끝난다면, 터널 구간의 MTU와 ICMP 차단을 먼저 보세요.</Check>
  <Check>방화벽에서 ICMP를 모두 막는 규칙이라면 다시 보세요. IPv4의 fragmentation needed, IPv6의 Packet Too Big은 경로 MTU 찾기에 필요해요.</Check>
  <Check>오버레이를 새로 깔면서 파드나 VM의 MTU를 선과 같은 1,500으로 둔 설정이라면, 감싼 머리표만큼 줄였는지 보세요.</Check>
  <Check>ping으로 장비가 살아 있는 걸 확인했다면, 작은 ping만 보낸 건 아닌지 보세요. MTU 문제는 큰 패킷에서만 보여요.</Check>
</Checkpoints>

<Deeper>
  ### VXLAN의 50바이트

  VXLAN 패킷은 바깥 IP(20바이트), UDP(8바이트), VXLAN 머리(8바이트) 안에 안쪽 이더넷 프레임을 넣어요. 안쪽 이더넷 머리(14바이트)까지 더하면 안쪽 IP 패킷보다 50바이트 커요. 바깥 IP가 IPv6면 머리가 40바이트라 70바이트가 돼요.

  ### VTEP은 쪼개지 않아요

  RFC 7348은 터널 끝 장비(VTEP)가 VXLAN 패킷을 쪼개지 않아야 한다고 정해요. 중간 라우터가 쪼갠 조각은 받는 쪽이 조용히 버려도 돼요. 그래서 선의 MTU를 감싼 크기에 맞추라고 권해요.

  ### MSS 고정의 계산

  리눅스 iptables의 `--clamp-mss-to-pmtu`는 MSS를 줄여 적어요. 경로 MTU에서 IPv4는 40, IPv6는 60을 뺀 값이에요. 연결을 맺는 SYN 패킷에만 걸어요.
</Deeper>
