  </Point>
  <Point title="어디까지 읽었는지 커밋해요">
    파티션마다 다음에 읽을 오프셋 하나만 기록해 두면 돼요. 다시 시작하면 거기서부터 읽어요.
  </Point>
  <Point title="그룹은 파티션을 나눠 맡아요">

  </Point>

  게시판의 칸을 팀원들이 나눠 맡아 읽는 것과 같아요. 각자 맡은 칸에서 어디까지 읽었는지 책갈피(커밋)를 꽂아 둬요. 팀원이 자리를 비우면 그 칸은 다른 팀원이 책갈피부터 이어 읽어요.

## 가져가는 방식

<Term term="messaging/consumer">컨슈머</Term>는 파티션의 리더 브로커에 "이 오프셋부터 주세요"라고 요청해서 이벤트를 가져가요. 브로커가 밀어주지 않고 컨슈머가 당겨 가는 방식(pull)이에요.

그래서 컨슈머가 느려도 브로커가 컨슈머를 덮치지 않아요. Kafka 문서는 당겨 가는 방식의 장점을 컨슈머가 "뒤처졌다가 따라잡을 수 있다"는 점으로 설명해요. 컨슈머가 원하면 예전 오프셋으로 되돌아가 다시 읽을 수도 있어요.

## 오프셋 커밋

컨슈머의 위치는 파티션마다 숫자 하나예요. 다음에 읽을 이벤트의 오프셋이에요. 이 위치를 Kafka에 안전하게 저장하는 걸 <Term term="messaging/offset-commit">커밋</Term>이라고 해요.

컨슈머가 죽었다 다시 뜨면, 커밋된 위치부터 읽어요. 그래서 언제 커밋하느냐가 "한 번은 처리했는가"를 정해요.

<Figure caption="처리한 뒤에 커밋하면, 커밋 직전에 죽었을 때 그 이벤트를 다시 처리해요. 커밋한 뒤에 처리하면, 처리 중에 죽었을 때 그 이벤트를 놓쳐요.">
  <Compare
    columns={['처리 → 커밋', '커밋 → 처리']}
    rows={[
      { label: '사이에 죽으면', values: ['같은 이벤트를 다시 처리해요', '그 이벤트를 놓쳐요'] },
      { label: '결과', values: ['중복은 있어도 잃지 않아요', '중복은 없어도 잃을 수 있어요'] },
      { label: '부르는 말', values: ['최소 한 번', '최대 한 번'] },

기본 설정에서는 자동 커밋이 켜져 있고, 5초마다 커밋해요. 자동 커밋으로도 "최소 한 번"을 지킬 수 있어요. 다만 한 번 가져온 이벤트를 다음에 가져가기 전에 모두 처리해야 해요.

처리를 끝낸 시점에 직접 커밋하려면 자동 커밋을 끄고 커밋 함수를 불러요. 전달 보장은 <Term slug="messaging/delivery-guarantees">전달 보장</Term>에서 더 자세히 다뤄요.

## 처음 읽을 때는 어디부터?

새 컨슈머 그룹은 커밋된 위치가 없어요. 이때 어디서 시작할지는 `auto.offset.reset`이 정해요. 커밋된 위치의 이벤트가 보관 기간이 지나 지워졌을 때도 이 설정을 따라요.

| 값 | 시작 위치 |
| --- | --- |
| latest | 지금부터 새로 들어오는 이벤트. 기본값이에요 |
| earliest | 남아 있는 가장 오래된 이벤트 |
| none | 시작하지 않고 에러를 내요 |

## 리밸런스

그룹 구성원이 바뀌면 파티션을 다시 나눠요. 이걸 <Term term="messaging/rebalance">리밸런스</Term>라고 해요. 컨슈머가 죽거나 새로 들어오거나, 구독한 토픽에 파티션이 늘면 일어나요.

컨슈머가 살아 있는지는 두 가지로 판단해요.

| 기준 | 기본값 | 넘으면 |
| --- | --- | --- |
| `session.timeout.ms` | 45초 | 하트비트가 이 시간 동안 없으면 그룹에서 빼요 |
| `max.poll.interval.ms` | 5분 | 다음 이벤트를 이 시간 안에 가져가지 않으면 그룹을 떠나요 |

두 번째 기준이 자주 문제가 돼요. 하트비트는 잘 보내는데 처리 하나가 너무 오래 걸리면, 컨슈머가 그룹에서 빠지고 리밸런스가 일어나요. 이때 커밋도 실패해서 같은 이벤트를 다른 컨슈머가 다시 처리해요.

## 모니터링에서는

컨슈머 그룹에서 가장 먼저 보는 숫자는 지연(lag)이에요. 파티션 끝의 오프셋과 컨슈머가 읽은 위치의 차이예요. 읽는 법은 <Term slug="apm/consumer-lag">메시지 큐 지연</Term>에서 다뤄요.

| 지표 | 뜻 |
| --- | --- |
| records-lag-max | 이 컨슈머가 맡은 파티션 중 가장 큰 지연(이벤트 수) |
| rebalance-rate-per-hour | 한 시간에 참여한 리밸런스 수 |
| commit-latency-avg | 커밋 요청의 평균 시간 |
| last-poll-seconds-ago | 마지막으로 이벤트를 가져간 뒤 지난 초 |

<Checkpoints>
  <Check>지연을 줄이려고 컨슈머를 파티션 수보다 많이 늘렸다면 다시 보세요. 남는 컨슈머는 놀아요. 파티션 수를 함께 봐요.</Check>
  <Check>리밸런스가 자주 일어나면, 이벤트 하나를 처리하는 시간이 max.poll.interval.ms에 가까운지 보세요.</Check>
  <Check>새 컨슈머 그룹을 띄웠는데 예전 이벤트를 하나도 안 읽는다면, auto.offset.reset이 기본값 latest인지 보세요.</Check>
  <Check>장애 뒤 같은 이벤트가 두 번 처리됐다면, 처리 후 커밋 전에 죽은 경우예요. 최소 한 번 방식에선 정상이라, 받는 쪽이 중복을 견디게 만들어요.</Check>
</Checkpoints>
