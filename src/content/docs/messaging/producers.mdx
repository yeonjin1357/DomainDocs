## 어디로 보내나

<Term term="messaging/producer">프로듀서</Term>는 이벤트를 쓸 파티션을 먼저 정해요. 키가 있으면 키로, 없으면 프로듀서가 골라요. 파티션 고르는 법은 <Term slug="messaging/topics-and-partitions">토픽과 파티션</Term>에서 다뤄요.

파티션마다 리더 역할을 하는 브로커가 하나 있어요. 프로듀서는 중간 단계 없이 그 리더 브로커로 직접 보내요. 어느 브로커가 리더인지는 Kafka 서버 아무 곳에나 물어 알아내요.

## 모아서 보내기

프로듀서는 이벤트를 메모리에 잠깐 모았다가, 파티션별로 묶어 한 번에 보내요. 요청 수가 줄고 브로커도 큰 덩어리로 디스크에 쓸 수 있어서 효율이 좋아요.

| 설정 | 기본값 | 뜻 |
| --- | --- | --- |
| `batch.size` | 16,384바이트 | 파티션 하나에 모을 최대 크기 |
| `linger.ms` | 5ms | 묶음을 채우려고 기다리는 최대 시간 |

기다리는 시간을 늘리면 더 크게 모여 처리량이 늘지만, 이벤트 하나가 도착하는 시간은 그만큼 늦어져요. 반대로 줄이면 빨리 보내지만 요청이 많아져요.

## acks: 어디까지 확인받나

`acks`는 프로듀서가 "보냈다"고 믿기 전에 받을 확인의 정도예요. 리더와 그 복제본(팔로워)의 관계는 메시지가 여러 브로커에 복사되는 방식에서 나와요.

<Figure caption="acks=all일 때의 흐름이에요. 팔로워들이 리더에게서 이벤트를 복제해 가고, 동기화된 복제본이 모두 받으면 리더가 확인을 보내요.">
  <Sequence
    ariaLabel="프로듀서가 리더에게 배치를 보내고, 팔로워 1과 팔로워 2가 리더에게서 복제해 간 뒤, 리더가 프로듀서에게 확인을 보내는 순서"
    participants={['프로듀서', '리더', '팔로워 1', '팔로워 2']}
    messages={[
      { from: '프로듀서', to: '리더', label: '배치 보내기', tone: 'accent' },

      { from: '팔로워 2', to: '리더', label: '복제해 가기', dashed: true },
      { from: '리더', to: '프로듀서', label: '확인', tone: 'accent' },
    ]}
  />
</Figure>

| acks | 기다리는 것 | 잃을 수 있는 경우 |
| --- | --- | --- |
| 0 | 아무것도 기다리지 않아요 | 브로커가 받았는지조차 몰라요 |
| 1 | 리더가 자기 로그에 쓸 때까지 | 리더가 확인한 직후, 복제 전에 죽으면 잃어요 |
| all | 동기화된 복제본 모두가 받을 때까지 | 동기화된 복제본이 하나라도 살아 있으면 잃지 않아요. 기본값이에요 |

acks=all은 "동기화된 복제본 모두"를 기다려요. 그런데 복제본이 줄어 리더 혼자 남아도 "모두"가 될 수 있어요. 그래서 토픽에 `min.insync.replicas`를 함께 걸어요.

흔한 조합은 복제본 3개에 최소 2개, 그리고 acks=all이에요.

## 다시 보내기와 중복 막기

보내다 실패하면 프로듀서는 알아서 다시 보내요. 기본 설정에서는 재시도 횟수를 사실상 끝없이 두고, 대신 `delivery.timeout.ms`(기본 2분) 안에 성공하지 못하면 실패로 끝내요.

다시 보내다 보면 중복이 생길 수 있어요. 첫 요청이 사실은 성공했는데 응답만 늦어 다시 보낸 경우예요. 그래서 Kafka 프로듀서는 <Term term="messaging/idempotent-producer">멱등성</Term>을 지원해요.

브로커가 프로듀서마다 ID를 주고, 이벤트마다 붙은 순번으로 같은 이벤트를 걸러내요. 지금은 기본으로 켜져 있어요.

재시도와 멱등성의 일반 원리는 <Term slug="apm/timeouts-and-retries">타임아웃과 재시도</Term>에서 다뤄요.

## 모니터링에서는

프로듀서는 앱 안에서 도는 라이브러리라서, 지표도 앱에서 나와요. Kafka 클라이언트가 내놓는 프로듀서 지표 중 자주 보는 건 이래요.

| 지표 | 뜻 |
| --- | --- |
| record-send-rate | 초당 보낸 이벤트 수 |
| record-error-rate | 초당 실패로 끝난 전송 수 |
| record-retry-rate | 초당 다시 보낸 수 |
| request-latency-avg | 브로커 요청의 평균 지연(ms) |
| batch-size-avg | 요청마다 파티션별로 보낸 평균 바이트 |

재시도가 늘면 브로커 쪽에 문제가 생기고 있다는 신호예요. 오류율이 0이어도 재시도율이 오르고 있다면 브로커 상태를 먼저 봐요.

<Checkpoints>
  <Check>속도 때문에 acks=1이나 0으로 바꿨다면 다시 보세요. 리더가 복제 전에 죽으면 확인받은 이벤트도 사라질 수 있어요.</Check>
  <Check>acks=all인데 min.insync.replicas가 1이라면 다시 보세요. 복제본이 리더 하나로 줄어도 쓰기가 성공해서, 그 리더가 죽으면 잃어요.</Check>
  <Check>이벤트 하나하나가 늦게 도착한다는 불만이 있다면, linger.ms와 batch.size를 보세요. 모으는 동안 기다리는 시간이 있어요.</Check>
  <Check>오류는 없는데 record-retry-rate가 오르고 있다면, 브로커와 네트워크부터 보세요. 재시도가 문제를 잠시 가리고 있을 수 있어요.</Check>
</Checkpoints>

<Deeper>
  ### 멱등성과 acks

  멱등성을 켜려면 acks가 all이어야 해요. 두 설정은 함께 이벤트가 빠지지도 겹치지도 않게 보내는 데 쓰여요.

  ### 트랜잭션

  Kafka 프로듀서는 여러 파티션에 쓰는 이벤트를 한꺼번에 반영하거나 한꺼번에 취소하는 트랜잭션도 지원해요. "읽고, 처리하고, 쓰기"를 정확히 한 번 하도록 만들 때 써요.
</Deeper>
