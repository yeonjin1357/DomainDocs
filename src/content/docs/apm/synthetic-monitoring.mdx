DNS가 늘었다면 이름 풀이, 연결이 늘었다면 네트워크나 서버의 연결 받기, 서버 처리가 늘었다면 앱이 느린 거예요. 브라우저가 페이지를 띄우는 순서와 같아서, <Term slug="apm/page-load">브라우저에서 페이지가 뜨기까지</Term>의 앞부분과 겹쳐요.

## 무엇을 성공으로 볼까요

blackbox_exporter의 HTTP 점검은 기본으로 2xx 응답이면 성공이에요. 리다이렉트는 기본으로 따라가서 마지막 응답으로 판정해요.

그런데 앱이 오류 화면을 200으로 돌려주면 성공으로 나와요. 그래서 응답 본문에 꼭 있어야 하는 글자(예: '주문하기' 버튼)나 없어야 하는 글자('Error')를 함께 검사해요. blackbox_exporter의 `fail_if_body_not_matches_regexp`가 그 설정이에요.

HTTPS 주소라면 같은 점검으로 인증서 만료일도 함께 받아요. 만료 감시는 <Term slug="network/tls-certificates">TLS 인증서와 만료</Term>에서 다뤘어요.

## 어디서, 얼마나 자주

점검 한 번은 한 위치에서 한 사용자가 연 것과 같아요. 그래서 사용자가 있는 지역마다 위치를 둬요. 회사 안에서만 열리는 주소는 안쪽에 둔 점검 위치(private probe)에서 재요.

간격을 1분으로 하면 하루 1,440번 열어요. 짧을수록 빨리 알지만, 점검 요청이 그만큼 서버의 요청 수와 로그에 섞여요.

한 번 점검이 기다리는 시간(타임아웃)도 정해요. blackbox_exporter는 Prometheus의 수집 타임아웃보다 조금 짧게 잡고, 둘 다 없으면 120초를 기다려요.

## 실제 사용자 감시와 함께 봐요

외부 감시는 같은 조건에서 되풀이해 재서 변화를 견주기 좋아요. 대신 정해 둔 위치와 주소만 재요. 느린 휴대폰, 먼 지역, 로그인한 뒤의 화면은 실제 사용자 감시(RUM)가 보여 줘요.

둘을 함께 두면 서로를 메워요. 외부 감시는 사용자가 없을 때 장애를 먼저 알리고, RUM은 감시가 못 가는 곳의 느림을 알려요.

## 모니터링에서는

blackbox_exporter는 점검마다 성공 여부와 걸린 시간을 내요. `probe_success`는 성공 1, 실패 0이고, `probe_duration_seconds`는 걸린 시간이에요. 구간별 시간은 `probe_http_duration_seconds`의 `phase` 레이블로 나뉘어요.

알림은 한 번의 실패가 아니라 여러 위치, 일정 시간으로 걸어요. 아래 식은 위치마다 5분 성공률을 구하고, 80%가 안 되는 위치가 두 곳 이상일 때 참이에요.

```text
count by (instance) (
  avg_over_time(
    probe_success[5m]
  ) < 0.8
) >= 2
```

세 위치의 성공률을 평균 내 90%와 견주는 식은 한 곳만 막혀도 66.7%가 되어 울려요. 위치를 따로 세는 쪽이 감시 쪽 문제를 더 잘 걸러요.

<Deeper>
  ### IPv6를 먼저 골라요

  이름이 IPv4와 IPv6 주소를 모두 가지면, blackbox_exporter는 기본으로 IPv6를 골라요. `preferred_ip_protocol`의 기본값이 `ip6`이에요. 한쪽 주소만 있으면 그쪽으로 이어요.

  점검 위치에서 IPv6가 막혀 있다면 `ip4`로 바꿔요.

  ### 타임아웃의 비율

  README는 `probe_duration_seconds / probe_timeout_seconds`로 타임아웃을 얼마나 썼는지 보라고 해요. 이 비율이 1에 가까워지면 곧 시간 초과로 실패하기 시작해요.

  ### 다른 도구의 기본 규칙

  Grafana Cloud 합성 모니터링의 예전 기본 알림은 세 규칙이었어요. 점검의 성공률이 5분 동안 95%, 90%, 75% 아래로 머물면 울려요. 지금은 점검마다 실패 횟수, 평균 지연, 인증서 만료 기준을 따로 정해요.
</Deeper>
