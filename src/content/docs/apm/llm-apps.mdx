<KeyPoints>
  <Point title="LLM 호출은 토큰으로 재요">
    LLM은 입력 토큰을 읽고 출력 토큰을 하나씩 만들어요. 지연도, 비용도, 호출 한도도 토큰 수를 따라가요.
  </Point>
  <Point title="첫 토큰까지와 그 뒤를 나눠 봐요">
    첫 토큰까지의 시간은 입력 길이와 대기열이, 그 뒤는 출력 길이가 정해요. 응답시간 하나로는 어느 쪽인지 안 갈려요.
  </Point>
  <Point title="에이전트는 호출 여러 번의 묶음이에요">
    질문 하나에 LLM 호출과 도구 실행이 번갈아 돌아요. 단계마다 트레이스로 나누고, 단계마다 늘어나는 토큰을 세요.
  </Point>
</KeyPoints>

<Analogy limit="실제 모델은 단어가 아니라 토큰이라는 조각으로 읽고 써요. 앞에서 읽은 원고를 기억해 두면(캐시) 다시 읽는 시간이 거의 들지 않아요.">
  LLM은 원고를 끝까지 읽은 뒤 답을 한 단어씩 쓰는 번역가와 같아요. 읽은 단어와 쓴 단어 수로 요금을 매기고, 원고가 길수록 첫 단어가 늦게 나와요.
</Analogy>

## LLM 호출 하나는 이렇게 생겼어요

앱은 LLM에 HTTP로 요청을 보내요. 요청에는 대화(시스템 지시, 사용자 말)와 모델 이름, 출력 토큰 상한(`max_tokens`)이 들어가요. 응답에는 만든 글과 끝난 까닭, 쓴 토큰 수가 와요.

<Term term="apm/llm-token">토큰</Term>은 모델이 글을 자르는 단위예요. 단어 하나가 토큰 하나일 때도, 여러 개일 때도 있어요. 자르는 법은 모델마다 달라요.

응답은 보통 스트리밍으로 와요. 토큰이 만들어지는 대로 조각조각 보내서, 사용자는 끝까지 기다리지 않고 첫 글자부터 봐요.

응답의 사용량에는 캐시에서 읽은 토큰 수가 따로 와요. 이 서버는 `cached_tokens`로, Anthropic API는 `cache_read_input_tokens`로 알려 줘요. 입력 중 캐시 몫이 줄면 TTFT와 비용이 함께 늘어요.

캐시는 앞에서부터 같은 만큼만 맞아요. 시스템 지시 맨 앞에 현재 시각처럼 매번 바뀌는 값을 넣으면 그 뒤가 모두 새로 읽혀요.

## 비용과 호출 한도

비용은 토큰 수에 가격을 곱한 값이에요. 입력과 출력의 가격이 달라요. Anthropic 가격표에서는 출력 토큰이 입력 토큰의 5배이고, 캐시에서 읽은 입력은 기본 입력 가격의 0.1배 이하예요.

예를 들어 입력 100만 토큰에 2달러, 출력 100만 토큰에 10달러인 모델이라고 쳐요. 입력 460토큰, 출력 57토큰인 질문 하나는 약 0.0015달러예요. 하루 10만 번이면 하루 149달러예요.

호출 한도도 토큰으로 걸려요. Anthropic API는 분당 요청 수(RPM)와 분당 입력 토큰(ITPM), 분당 출력 토큰(OTPM)을 따로 재요. 어느 하나라도 넘으면 429 `rate_limit_error`가 와요.

요청 수가 적어도 입력이 길면 토큰 한도에 먼저 닿아요. 공급자 쪽이 붐빌 때는 다른 에러가 와요. Anthropic은 529 `overloaded_error`로 알려요.

둘 다 다시 보내면 토큰을 또 쓰니, 재시도도 비용으로 세요.

## 에이전트는 호출 여러 번의 묶음이에요

<Term term="apm/ai-agent">AI 에이전트</Term>는 LLM이 도구를 골라 부르며 일을 나눠 하는 앱이에요. LLM이 "주문 조회 도구를 이 값으로 불러"라고 답하면, 앱이 도구를 실행하고 결과를 대화에 붙여 LLM을 다시 불러요.

같은 서버로 주문 조회 도구 하나를 가진 에이전트를 돌려 봤어요. "주문 A-1042는 어디 있나요?"라는 질문 하나에 이렇게 돌았어요. 도구는 0.3초 걸리는 DB 조회를 흉내 냈어요.

<Figure caption="질문 하나가 LLM 호출 두 번과 도구 실행 한 번이 됐어요. 첫 호출은 도구를 고르고(finish_reason: tool_calls), 둘째 호출이 도구 결과로 답을 썼어요.">

둘째 호출의 입력은 191토큰에서 269토큰으로 늘었어요. LLM은 앞의 대화를 기억하지 않아서, 앱이 첫 질문과 도구 호출, 도구 결과를 모두 다시 보내요. 단계가 늘수록 입력 토큰이 쌓여요.

에이전트는 몇 단계를 돌지 미리 정해지지 않아요. 같은 도구를 되풀이하거나 끝내지 못하고 돌면, 응답은 늦고 토큰은 계속 늘어요. 그래서 실행 한 번에 LLM을 몇 번, 도구를 몇 번 불렀는지를 세요.

## 200인데 틀린 답

LLM 앱의 실패는 상태 코드에 다 안 잡혀요. 상한에 닿아 잘린 답, 모델이 답을 거절한 응답, 그럴듯하지만 틀린 답이 모두 200이에요.

- **잘린 답**: `finish_reason`이 `length`예요. Anthropic API에서는 `stop_reason`이 `max_tokens`예요.
- **거절**: Anthropic API는 `stop_reason`을 `refusal`로 알려요.
- **틀린 답**: 응답만 봐서는 몰라요. 사용자 평가(좋아요·싫어요)를 모으거나, 일부 응답을 뽑아 다른 모델이나 사람이 채점해요.

입력도 위험해요. 사용자 글이나 도구가 가져온 웹 페이지에 "앞의 지시를 무시해" 같은 문장이 섞여 모델을 조종하는 걸 <Term term="apm/prompt-injection">프롬프트 인젝션</Term>이라고 해요. 에이전트가 무슨 도구를 어떤 인자로 불렀는지 남겨 두면, 이상한 호출을 찾아낼 수 있어요.

## 모니터링에서는

OpenTelemetry는 생성형 AI 호출을 기록하는 이름을 정하고 있어요. 아직 개발(Development) 단계라 이름이 바뀌는 중이에요. 지금 규약으로는 위 첫 호출이 이런 span이 돼요.

```text
span: chat qwen
gen_ai.operation.name
  = chat
gen_ai.request.model
  = qwen
gen_ai.usage.input_tokens
  = 191
gen_ai.usage.output_tokens
  = 27
gen_ai.response.finish_reasons
  = ["tool_calls"]
```

span 이름은 하는 일과 모델 이름을 이어 붙여요. 도구 실행은 `execute_tool`, 에이전트 전체는 `invoke_agent`로 시작해요.

프롬프트와 응답 본문은 규약에서도 따로 켜야(Opt-In) 남겨요. 사용자가 쓴 글에는 개인정보가 섞이기 쉬워서예요. 남겨야 하면 <Term slug="logs/sensitive-data">민감 정보를 가리고</Term>, 일부만 뽑아 남겨요.

  실험 조건이에요. 서버는 llama.cpp b12099, 모델은 Qwen2.5-0.5B-Instruct Q4_K_M이에요. CPU 스레드 4개, temperature 0으로 WSL에서 돌렸어요.

  숫자는 이 조건의 것이에요. 큰 모델이나 GPU 서버에서는 몇 배씩 달라요. 그래도 입력이 길수록 TTFT가, 출력이 길수록 전체 시간이 는다는 모양은 같아요.

  이 서버는 OpenAI 호환 형식으로 사용량을 알려요. 입력은 `prompt_tokens`, 출력은 `completion_tokens`예요. 캐시에서 읽은 입력은 `prompt_tokens_details.cached_tokens`예요.

  Anthropic API는 입력을 `input_tokens`, 출력을 `output_tokens`로 알려요. 캐시 쪽은 읽은 `cache_read_input_tokens`와 새로 적은 `cache_creation_input_tokens`로 나눠요.

  Anthropic API의 `stop_reason`에는 이런 값이 있어요.

  - `end_turn`: 답을 다 썼어요.
  - `max_tokens`: 상한에 닿아 잘렸어요.
  - `tool_use`: 도구를 불러 달래요.
  - `refusal`: 답을 거절했어요.
  - `stop_sequence`, `pause_turn`: 정한 멈춤 글자를 만났거나, 긴 작업을 잠시 멈췄어요.

  스트리밍은 `message_start`로 시작해 글 조각(`content_block_delta`)이 이어져요. 끝에는 `message_delta`에 끝난 까닭과 출력 토큰 수가 오고, `message_stop`으로 끝나요.

  Anthropic의 호출 한도는 토큰 버킷 방식이라 정해진 시각에 한꺼번에 차지 않고 계속 조금씩 차요. 분당 60번이라도 1초에 1번처럼 짧게 나눠 재기도 해서, 짧은 몰림에도 429가 날 수 있어요. 대부분 모델에서 캐시에서 읽은 입력 토큰은 ITPM에 세지 않아요.

  OpenTelemetry의 생성형 AI 규약은 의미 규약 1.42.0부터 별도 저장소로 옮겨졌어요. 저장소 이름은 semantic-conventions-genai예요.

  지금 규약에는 TTFT를 담는 속성 `gen_ai.response.time_to_first_chunk`가 있어요. 에이전트 한 번의 LLM 호출 수를 세는 지표 `gen_ai.invoke_agent.inference_calls`도 있어요. 개발 단계라 이름이 바뀔 수 있으니, 쓰는 SDK의 버전과 함께 확인해요.
