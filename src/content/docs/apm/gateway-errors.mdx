<Situation>
  주문 API에서 502와 504가 섞여 늘었어요. 그런데 WAS 로그에는 그 시각의 에러가 거의 없어요.

  502와 504는 앞단의 웹 서버(nginx 같은 리버스 프록시)가 만든 응답이에요. 그래서 WAS는 모를 수 있어요.

  웹 서버의 에러 로그에서 원인을 가르고, 그 뒤 WAS 쪽을 따라가요. 예시는 nginx 기준이에요.
</Situation>

## 1. 누가 만든 응답인지 가르세요

WAS가 일부러 502나 504를 돌려줄 수도 있어요. 웹 서버가 WAS에서 응답을 못 받아 스스로 만든 것인지부터 가려요.

**확인 방법**: 웹 서버 접근 로그에 `$upstream_status`와 `$upstream_response_time`을 함께 남겨요. 앞은 WAS에서 받은 코드, 뒤는 WAS 응답을 받기까지 걸린 시간이에요.

웹 서버가 시간 초과로 만든 504라면, 걸린 시간이 시간 제한(기본 60초) 근처이고 에러 로그에 시간 초과 문구가 남아요. WAS가 직접 돌려준 504라면 WAS 로그에도 남아요. 웹 서버가 보낼 WAS를 고르지도 못했다면 `$upstream_status`에는 502가 들어가요.

## 2. 에러 로그 문구로 갈래를 나누세요

nginx는 502·504를 만들 때마다 에러 로그에 이유를 남겨요. 문구가 곧 원인의 갈래예요.

| 에러 로그 문구 | 응답 | 뜻 |
| --- | --- | --- |
| `upstream timed out ... while reading response header` | 504 | WAS가 시간 안에 답하지 않았어요 |
| `connect() failed (111: Connection refused)` | 502 | WAS 포트에 받는 프로그램이 없어요 |
| `upstream prematurely closed connection` | 502 | WAS가 응답 도중 연결을 끊었어요 |
| `no live upstreams` | 502 | 모든 WAS가 실패로 빠져 있어요 |

**확인 방법**: 문제 시각의 에러 로그에서 위 문구별로 줄 수를 세요. 한 문구가 대부분이라면 아래 단계 중 그 갈래로 가요.

## 3. 504라면 느린 요청을 찾으세요

nginx는 WAS의 응답을 기본으로 60초 기다려요. 설정 이름은 `proxy_read_timeout`이에요.

이 시간은 전체 응답 시간이 아니라, 두 번 읽는 사이에 아무것도 오지 않은 시간이에요. 60초 동안 한 바이트도 오지 않으면 연결을 끊고 504를 줘요.

**확인 방법**: 같은 시각 WAS의 느린 트랜잭션을 찾아요. DB나 외부 API를 기다리다 늦은 경우가 흔해요. 순서는 <Term slug="apm/slow-response">응답이 느려졌을 때 어디부터 볼까</Term>에 있어요.

시간 제한은 겹겹이 있어요. 브라우저, 로드 밸런서, 웹 서버, WAS, DB마다 따로예요.

WAS의 제한이 웹 서버보다 길면, 사용자는 이미 504를 받았는데 WAS는 계속 일해요. 맞추는 법은 <Term slug="apm/timeouts-and-retries">타임아웃과 재시도</Term>에서 다뤄요.

## 4. 다음 서버로 다시 보내는지 보세요

nginx는 기본으로 연결 에러나 시간 초과가 나면 같은 요청을 다음 WAS로 다시 보내요. 기본값이 `proxy_next_upstream error timeout`이에요. 그래서 느린 GET 요청 하나가 60초를 두 번 기다리고, WAS 두 대가 같은 일을 해요.

POST처럼 멱등이 아닌 요청은 nginx 1.9.13부터 기본으로 다시 보내지 않아요. 응답을 사용자에게 보내기 시작한 뒤에도 다시 보내지 않아요.

또 WAS와 한 번만 통신에 실패해도 그 WAS를 10초 동안 빼요. `max_fails`의 기본값이 1, `fail_timeout`의 기본값이 10초예요. 느려진 WAS가 차례로 빠지면, 남은 WAS가 없어져 `no live upstreams`와 함께 502가 쏟아져요.

## 5. 502가 꾸준히 조금씩 난다면 keep-alive를 보세요

웹 서버와 WAS 사이의 연결을 재사용하면, 쉬는 연결을 양쪽이 각자 정한 시간 뒤에 닫아요. nginx의 `upstream` 블록에서 `keepalive`를 켜면 쉬는 연결을 기본 60초 동안 들고 있어요. 그런데 Node.js 서버는 기본으로 5초 쉬면 연결을 닫아요.

WAS가 막 닫은 연결에 웹 서버가 요청을 보내면, 그 요청은 502가 돼요. 에러 로그에는 `upstream prematurely closed connection` 같은 문구가 남아요. 트래픽에 상관없이 낮은 비율로 꾸준히 나는 게 특징이에요.

## 6. 전부 502라면 WAS가 살아 있는지 보세요

`connect() failed (111: Connection refused)`가 대부분이라면 WAS 포트에 받는 프로그램이 없는 거예요. WAS가 죽었거나, 배포 중 다시 시작하는 사이이거나, 다른 포트로 떠 있어요.

**확인 방법**: WAS 프로세스와 포트가 살아 있는지, 같은 시각에 배포나 재시작이 있었는지 봐요. 배포 중에만 잠깐 몰렸다면, 새 WAS가 준비된 뒤에 요청을 받게 하는 순서를 봐요.
