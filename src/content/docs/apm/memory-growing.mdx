## 1. 어떻게 끝났는지 보세요

메모리가 모자라 끝나는 길은 두 가지예요. 남는 흔적이 달라요.

| 끝난 방식 | 누가 | 흔적 |
| --- | --- | --- |
| `OutOfMemoryError` | JVM | 앱 로그에 에러와 스택 트레이스가 남아요 |
| OOMKilled | 리눅스 커널 | 앱 로그에는 없고, 파드의 종료 이유와 종료 코드 137에 남아요 |

<Term term="apm/out-of-memory-error">OutOfMemoryError</Term>는 JVM 안의 어느 메모리 칸이 모자랐다는 뜻이에요. 에러 뒤의 문구가 그 칸을 알려 줘요.

OOMKilled는 프로세스 전체가 컨테이너 메모리 한도를 넘어 커널이 죽인 거예요. 힙은 여유가 있어도, 힙 밖 메모리까지 더한 크기가 한도를 넘으면 이렇게 끝나요. 파드 쪽에서 보는 법은 <Term slug="kubernetes/pod-restarting">파드가 계속 재시작될 때</Term>에 있어요.

## 2. 힙인지 힙 밖인지 가르세요

JVM이 내는 힙 사용량과, 서버가 보는 프로세스 메모리(RSS)를 같은 시간축에 놓아요.

- 힙의 GC 직후 바닥이 함께 오르면 힙 안에 쌓이는 거예요. 3·4단계로 가요.
- 힙 바닥은 평평한데 프로세스 메모리만 오르면 힙 밖이에요. 5단계로 가요.

## 3. 힙이라면 GC 직후 바닥을 보세요

힙은 객체가 쌓이면 오르고 GC가 치우면 내려가요. 누수가 있으면 GC가 치운 뒤에도 남는 양, 곧 바닥이 계속 올라가요.

<Figure caption="최대 힙 64MB인 자바 프로그램이 요청마다 1MB를 캐시에 넣고 지우지 않게 해서 GC 기록을 본 결과예요. GC 직후 바닥이 7MB에서 61MB까지 오르고, 마지막엔 치워도 줄지 않아 OutOfMemoryError로 끝났어요.">
  <MiniLineChart
    ariaLabel="GC 직전 힙은 29MB에서 61MB로, GC 직후 힙은 7MB에서 61MB로 올라 두 선이 점점 붙는 그래프"
    yMax={64}
    series={[
      { label: 'GC 직전', values: [29, 37, 47, 55, 56, 59, 59, 61], tone: 'sub', value: '61MB' },
      { label: 'GC 직후', values: [7, 31, 41, 51, 55, 59, 59, 61], tone: 'warn', value: '7 → 61MB' },
    ]}
  />
</Figure>

두 선이 붙는다는 건 GC가 치울 게 거의 없다는 뜻이에요. 이때 GC는 점점 자주 돌고, 끝에는 힙 전체를 치우는 Full GC가 이어져요.

실험에서도 마지막 Full GC 두 번은 61MB를 하나도 줄이지 못했어요. 바로 뒤에 `OutOfMemoryError: Java heap space`가 났어요.

바닥이 오르다 일정한 높이에서 멈춘다면 누수가 아닐 수 있어요. 캐시처럼 정해진 크기까지 채우는 객체가 다 찬 거예요. 이때는 힙이 앱에 비해 작은지를 봐요.

**확인 방법**: GC 기록(`-Xlog:gc`)의 `29M->7M(64M)` 같은 줄에서 화살표 뒤 숫자가 GC 직후 크기예요. APM의 힙 그래프에서는 톱니의 아랫점을 이어 봐요.

## 4. 힙 덤프로 무엇이 쌓였는지 보세요

<Term term="apm/heap-dump">힙 덤프</Term>는 그 순간 힙에 있던 객체를 모두 파일로 쏟아 낸 거예요. 자바 문서는 메모리 누수를 찾는 데 가장 중요한 자료로 꼽아요.

| 방법 | 언제 |
| --- | --- |
| `jcmd <PID> GC.heap_dump 파일이름` | 지금 바로 떠요 |
| `-XX:+HeapDumpOnOutOfMemoryError` | OutOfMemoryError가 날 때 저절로 떠요 |

`jcmd`로 뜨면 먼저 Full GC를 해서 살아 있는 객체만 남겨요. 그래서 앱이 잠깐 멈추고, 문서도 부하를 '높음'으로 적어요. 운영 중이라면 트래픽을 뺀 인스턴스에서 떠요.

덤프 파일을 분석 도구로 열어, 가장 많은 메모리를 붙잡고 있는 객체를 찾아요. 흔한 범인은 크기 제한 없이 커지는 캐시나 정적 컬렉션이에요. 캐시에 크기 한도와 만료를 두는 법은 <Term slug="apm/cache">캐시와 적중률</Term>에서 다뤄요.

덤프에는 메모리에 있던 데이터가 그대로 담겨요. 개인정보나 비밀번호가 들어 있을 수 있어서, 보관하고 옮기는 곳을 정해 둬요.

## 5. 힙 밖이라면 칸을 나눠 보세요

힙 밖에서 늘 수 있는 곳은 주로 세 군데예요.

- **메타스페이스**: 클래스 정보예요. 클래스를 계속 새로 만들거나 불러오면 늘어요.
- **다이렉트 버퍼**: 네트워크·파일 입출력용으로 힙 밖에 잡는 메모리예요. 최대 크기를 정하지 않으면 JVM이 정해요.
- **스레드 스택**: 스레드마다 하나씩이라, 스레드 수가 늘면 같이 늘어요.

다이렉트 버퍼가 바닥나면 에러 문구가 이렇게 달라요. 자바 17에서 한도 32MB로 재현한 결과예요.

```text
OutOfMemoryError: Cannot reserve
1048576 bytes of direct buffer
memory (allocated: 33554432,
limit: 33554432)
```

어느 칸이 느는지 모르겠다면 NMT(Native Memory Tracking, JVM의 칸별 메모리 기록)를 켜요. 앱을 `-XX:NativeMemoryTracking=summary`로 띄워요. 그다음 `jcmd <PID> VM.native_memory summary`로 칸별 크기를 봐요.

기준점(`baseline`)을 찍고 나중에 차이(`summary.diff`)를 보면 어느 칸이 늘었는지 바로 보여요.

NMT를 켜면 성능이 5~10% 떨어진다고 문서에 적혀 있어요. 원인을 찾는 동안에만 켜요.
