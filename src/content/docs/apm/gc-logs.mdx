## 켜는 법

JDK 9부터 <Term term="apm/gc-log">GC 로그</Term>는 통합 로깅 옵션 `-Xlog`로 켜요. 짧게는 `-Xlog:gc`, 자세히는 `-Xlog:gc*`예요.

```text
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=10m
```

위 옵션은 gc.log 파일에 쓰고, 10MB마다 새 파일로 넘겨 5개까지 남겨요. 꾸밈 항목을 빼면 기본은 uptime, level, tags예요. 파일 돌려쓰기의 기본값은 5개, 20MB예요.

JDK 8의 옵션을 그대로 옮기면 안 돼요. JDK 21에서 직접 돌려 본 결과예요.

| JDK 8 옵션 | JDK 21에서 |
| --- | --- |
| `-XX:+PrintGCDetails` | 경고를 내고 `-Xlog:gc*`로 바꿔 실행해요 |
| `-Xloggc:파일` | 경고를 내고 `-Xlog:gc:파일`로 바꿔 실행해요 |
| `-XX:+UseGCLogFileRotation` | `Unrecognized VM option`으로 JVM이 뜨지 않아요 |

마지막 줄처럼 JVM이 아예 뜨지 않을 수 있어서, JDK를 올릴 때는 GC 옵션부터 확인해요.

## 한 줄 읽기

```text
[0.458s][info][gc] GC(3) Pause Young (Normal) (G1 Evacuation Pause) 83M->67M(128M) 3.486ms
```

| 부분 | 뜻 |
| --- | --- |
| `[0.458s]` | JVM이 뜬 뒤 지난 시간 |
| `GC(3)` | 몇 번째 GC인지. 같은 번호의 줄은 한 GC의 단계예요 |
| `Pause Young (Normal)` | GC 종류. 앱을 멈추고 새 객체 영역을 치웠어요 |
| `(G1 Evacuation Pause)` | 시작한 이유. young 영역이 찼어요 |
| `83M->67M(128M)` | GC 전 → GC 후 힙 사용량, 괄호 안은 지금 힙 크기 |
| `3.486ms` | 앱이 멈춘 시간 |

화살표 뒤 숫자가 GC 직후에도 살아남은 양이에요. 이 값이 GC마다 조금씩 오르면 <Term term="apm/memory-leak">메모리 누수</Term>를 의심해요. 확인 순서는 <Term slug="apm/memory-growing">메모리가 계속 늘 때</Term>에 있어요.

## G1에서 나오는 GC 종류

128MB 힙에서 쉬지 않고 할당하는 프로그램을 JDK 21로 돌려, 아래 종류가 모두 찍히는 걸 확인했어요.

| 종류 | 뜻 |
| --- | --- |
| `Pause Young (Normal)` | 새 객체 영역만 치워요. 가장 흔해요 |
| `Pause Young (Concurrent Start)` | young 수집을 하면서 old 영역의 표시(marking)를 시작해요 |
| `Concurrent Mark Cycle` | 앱과 함께 돌며 old 영역의 살아 있는 객체를 표시해요 |
| `Pause Remark`, `Pause Cleanup` | 표시를 마무리하는 짧은 멈춤이에요 |
| `Pause Young (Prepare Mixed)`, `(Mixed)` | young과 함께 old 영역 일부도 치워요 |
| `Pause Full (G1 Compaction Pause)` | 힙 전체를 압축해요. 가장 오래 멈춰요 |

<Term term="apm/young-gc">young 수집</Term>이 이어지다 old 영역이 어느 정도 차면 표시를 시작해요. 표시가 끝나면 <Term term="apm/mixed-gc">mixed 수집</Term>으로 old 영역을 조금씩 치워요.

`Concurrent Mark Cycle`은 앱을 멈추지 않아요. 그 줄의 시간을 멈춤 합계에 더하면 안 돼요.

## 경고 신호: Evacuation Failure와 Full GC

```text
GC(11) Pause Young (Mixed) (G1 Evacuation Pause) (Evacuation Failure) 126M->126M(128M) 0.515ms
GC(12) Pause Young (Mixed) (G1 Evacuation Pause) (Evacuation Failure) 127M->127M(128M) 0.517ms
GC(13) Pause Full (G1 Compaction Pause) 127M->53M(128M) 7.268ms
```

G1은 살아 있는 객체를 빈 영역으로 옮기며 치워요. 옮길 자리가 모자라면 <Term term="apm/evacuation-failure">Evacuation Failure</Term>가 찍혀요. Oracle 문서는 이 상태가 이어지면 G1이 결국 힙 전체를 압축하는 Full GC를 한다고 해요.

Full GC의 이유가 `System.gc()`라면 코드나 라이브러리가 직접 부른 거예요. 실험에서는 `Pause Full (System.gc())`로 따로 찍혔어요.

## 멈춤 비율 계산

GC로 멈춘 시간의 합을 같은 구간의 전체 시간으로 나누면 멈춤 비율이에요. 1분 동안 멈춤 합계가 3초라면 5%예요. 그 시간만큼 모든 요청이 기다렸어요.

합계를 낼 때는 `Pause`가 들어간 줄의 시간만 더해요. 실험 프로그램은 0.8초 동안 70번 멈췄고, 합계 100ms로 약 12%였어요. 일부러 힙을 몰아붙인 경우라 실제 서비스보다 훨씬 높아요.

## 컨테이너에서는 GC가 바뀌어요

JVM은 서버급 기계에서만 G1을 기본으로 골라요. JDK 소스의 기준은 CPU 2개 이상, 메모리 1792MB 이상이에요. 2GB에서 256MB 여유를 뺀 값이에요.

컨테이너 한도를 바꿔 가며 JDK 21을 돌려 봤어요. CPU 2개일 때 메모리 1791MB까지는 Serial GC를, 1792MB부터 G1을 골랐어요. CPU가 1개면 메모리 1GB에서도 Serial이었어요.

<Deeper>
  ### 실험 조건

  eclipse-temurin:21-jdk 이미지(OpenJDK 21.0.12)에서 `-Xmx128m -Xlog:gc`로 돌렸어요. 프로그램은 64KB 쓰레기를 계속 만들고, 5번마다 256KB를 붙잡아 두다가 절반씩 놓아요. 중간에 4MB 배열 하나를 만들고, `System.gc()`도 한 번 불러요.

  ### 자세한 로그의 영역 수

  `-Xlog:gc*`로 켜면 GC마다 영역 수가 함께 나와요. 실험의 GC(1)에서는 이렇게 찍혔어요.

  ```text
  Eden regions: 43->0(39)
  Survivor regions: 3->6(6)
  Old regions: 2->23
  Humongous regions: 0->0
  ```

  Eden은 새 객체 영역, Survivor는 한두 번 살아남은 객체 영역, Old는 오래 산 객체 영역이에요. Humongous는 영역 크기의 절반 이상인 큰 객체를 담는 영역이에요.

  ### 같은 번호의 여러 줄

  `Concurrent Mark Cycle`은 시작과 끝이 다른 줄에 찍혀요. 그 사이에 다른 번호의 young 수집이 끼어들 수 있어요. 실험에서도 GC(5)의 표시가 도는 동안 GC(6), GC(7)이 먼저 끝났어요.
</Deeper>
