## 런타임마다 요청을 나눠 받는 법이 달라요

Java는 <Term term="apm/thread-pool">스레드 풀</Term>의 스레드가 요청을 하나씩 맡아요. Node.js, Python, Go는 방식이 달라서, 느릴 때 먼저 볼 숫자도 달라요.

- **Java**: 스레드 풀의 스레드가 요청을 맡아요. 스레드 상태와 힙, GC를 먼저 봐요.
- **Node.js**: 이벤트 루프 하나가 모든 요청을 돌려요. 이벤트 루프 지연을 먼저 봐요.
- **Python**: 워커 프로세스 여러 개가 나눠 받아요. 워커 수와 프로세스마다의 지표를 봐요.
- **Go**: 요청마다 고루틴을 띄워요. 고루틴 수를 먼저 봐요.

## Node.js: 이벤트 루프 하나가 모두를 돌려요

Node.js의 JavaScript 코드는 <Term term="apm/event-loop">이벤트 루프</Term>(event loop)라는 스레드 하나에서 돌아요. DB나 다른 서비스의 답을 기다리는 동안 다른 요청의 일을 처리해서, 스레드 하나로도 많은 요청을 받아요.

대신 한 요청이 CPU를 오래 쓰면 그동안 다른 요청이 모두 멈춰요. 큰 JSON을 한 번에 파싱하거나, 긴 배열을 정렬하거나, 동기 함수로 암호화하는 코드가 그래요.

## Python: 한 번에 한 스레드만 계산해요

가장 널리 쓰는 Python인 CPython에는 <Term term="apm/gil">GIL</Term>(global interpreter lock)이 있어요. 한 프로세스 안에서는 한 번에 한 스레드만 Python 코드를 실행해요. 스레드를 늘려도 계산은 빨라지지 않아요.

그래서 Python 웹 서버는 워커 프로세스를 여러 개 띄워요. Gunicorn은 워커 수의 출발점으로 (2 × CPU 코어 수) + 1을 권해요. 기본 sync 워커는 한 번에 요청 하나만 처리해요.

## Go: 고루틴을 스레드 몇 개에 나눠 돌려요

<Term term="apm/goroutine">고루틴</Term>(goroutine)은 Go 런타임이 관리하는 가벼운 실행 단위예요. 처음 받는 스택이 몇 KB뿐이라 수십만 개도 띄울 수 있어요. 리눅스에서 10만 개를 띄워 보니 하나에 2KB, 모두 약 196MB였어요.

Go 런타임은 고루틴을 OS 스레드 몇 개에 나눠 돌려요. 한순간에 Go 코드를 돌리는 스레드 수가 <Term term="apm/gomaxprocs">GOMAXPROCS</Term>예요. 기본은 CPU 수이고, Go 1.25부터 리눅스에서는 컨테이너의 CPU 제한(쿠버네티스 CPU limit)도 따라요.

## 모니터링에서는

런타임마다 먼저 볼 지표가 달라요. Prometheus 클라이언트 라이브러리가 기본으로 내보내는 이름은 이래요.

```text
# Node.js(prom-client)
nodejs_eventloop_lag_p99_seconds
nodejs_eventloop_lag_max_seconds
# Go(client_golang)
go_goroutines
go_sched_gomaxprocs_threads
```

Node.js의 두 지표는 이벤트 루프 지연의 p99와 최댓값이에요. 평소 0.01초 안팎이 바닥이에요. Go의 두 지표는 고루틴 수와 GOMAXPROCS예요.

Python은 지표가 워커 프로세스마다 따로 생겨요. 그래서 워커의 값을 합쳐 보는 설정(client_python의 multiprocess 모드)이 필요해요.

Node.js에서 모든 API가 함께 느려지고 이벤트 루프 지연도 같이 오르면, 어딘가에서 CPU를 오래 쓰는 코드예요. 한 API만 느리면 그 API가 기다리는 DB나 서비스부터 봐요.

<Deeper>
  ### 이벤트 루프 지연을 재는 법

  Node.js의 `monitorEventLoopDelay()`는 정해진 간격의 타이머를 걸어요. 그리고 그 타이머가 실제로 불린 간격을 히스토그램으로 모아요. prom-client는 이 간격을 10ms로 두고, 수집할 때마다 히스토그램을 비워요.

  Node.js 22에서 막힘 없이 재면 간격 1ms에선 p50 1.1ms, 10ms에선 10.1ms, 20ms에선 20.1ms였어요. 그래서 평소 값은 간격과 비교해 읽어요.

  1초에 한 번 100ms씩 막히게 하고 5초를 재면 p99는 10.6ms, max는 110ms였어요. 10ms마다 하나씩 잰 값 중 막힌 순간은 1%쯤이라, p99에는 잘 안 잡혀요. 짧고 드문 막힘은 max로 봐요.

  ### libuv 스레드 풀 크기

  libuv 스레드 풀은 기본 4개이고, 프로세스가 뜰 때 `UV_THREADPOOL_SIZE` 환경 변수로 바꿔요. 최대 1024개까지예요.

  앞의 pbkdf2 실험에서 8로 늘리니 8개가 모두 32~38ms에 끝났어요. 파일과 DNS 조회가 많은 서비스가 CPU는 낮은데 느리다면 이 줄을 의심해요.

  ### Python의 asyncio

  FastAPI처럼 asyncio로 도는 앱은 Node.js처럼 이벤트 루프 하나로 요청을 돌려요. Python 문서도 1초 걸리는 계산을 그대로 부르면 모든 작업이 1초씩 늦는다고 해요. 그래서 async 함수 안의 오래 걸리는 계산은 따로 떼어 내요.

  GIL을 끈 빌드는 Python 3.14 기준으로 한 스레드만 쓰는 코드가 5~10% 느려요. 확인은 `sys._is_gil_enabled()`로 해요.

  ### Go의 GOMAXPROCS를 직접 정하면

  `GOMAXPROCS` 환경 변수나 `runtime.GOMAXPROCS()`로 직접 정하면, Go 1.25의 자동 맞춤이 꺼져요. 리눅스에서 CPU를 2개로 제한한 cgroup 안에서 Go 1.27 프로그램을 띄우니 GOMAXPROCS가 2였어요. 같은 프로그램을 제한 없이 띄우면 16이었어요.

  Go 1.25부터는 CPU 제한이 바뀌어도 GOMAXPROCS를 다시 맞춰요. 쿠버네티스의 CPU request는 보지 않고 CPU limit만 봐요.
