<KeyPoints>
  <Point title="코드를 고치지 않고 감싸서 재요">
    에이전트는 클래스를 메모리에 올릴 때 메서드 앞뒤에 시작·끝 기록을 끼워 넣어요. 소스 코드는 그대로예요.
  </Point>
  <Point title="끼운 곳만 보여요">
    HTTP, DB 드라이버 같은 흔한 라이브러리는 저절로 재요. 직접 쓴 메서드는 따로 정해야 이름이 보여요.
  </Point>
  <Point title="에이전트도 앱의 자원을 써요">
    에이전트는 앱과 같은 JVM에서 돌아요. 기록이 많을수록 CPU와 메모리를 더 써요.
  </Point>
</KeyPoints>

<Analogy limit="출퇴근 기록기는 공장 밖에 따로 서 있지만, 에이전트는 앱과 같은 JVM 안에서 돌아요. 그래서 앱이 쓸 CPU와 메모리를 함께 나눠 써요.">
  공장 라인 곳곳에 출퇴근 기록기를 다는 것과 비슷해요. 물건이 기록기를 지날 때마다 시각을 찍으니, 어느 구간에서 오래 걸렸는지 보여요.
</Analogy>

## 에이전트는 언제 붙나요

<Term term="apm/java-agent">자바 에이전트</Term>는 JVM이 시작할 때 함께 띄우는 작은 프로그램이에요. 실행 명령에 `-javaagent` 옵션으로 에이전트 파일(JAR)을 적어요.

<Figure caption="JVM은 앱보다 에이전트를 먼저 띄워요. 그 뒤 클래스를 메모리에 올릴 때마다 에이전트가 끼어들어 바이트코드를 고쳐요.">
  <Triage
    ariaLabel="1단계 JVM이 -javaagent 옵션을 읽고, 2단계 앱의 main보다 먼저 에이전트를 띄우고, 3단계 클래스를 올릴 때마다 에이전트가 바이트코드를 고치고, 4단계 고친 메서드가 요청을 처리하며 시작과 끝을 기록하고, 5단계 모은 기록을 수집 서버로 보내는 순서"

      { label: '클래스 올리기', note: '그때마다 바이트코드를 고쳐요', tone: 'accent' },

```bash
java -javaagent:otel-agent.jar \
  -jar order-api.jar
```

옵션을 실행 명령에 넣기 어려우면 `JAVA_TOOL_OPTIONS` 환경 변수에 넣기도 해요. 그래서 컨테이너에서는 이미지는 그대로 두고 환경 변수만 더해 붙여요.

## 메서드를 감싸요

자바 코드는 실행 전에 <Term term="apm/bytecode">바이트코드</Term>(JVM이 읽는 명령)로 바뀌어 있어요. 에이전트는 이 바이트코드를 고쳐, 메서드가 시작할 때와 끝날 때 기록을 남기게 해요.

<Figure caption="에이전트가 고친 뒤의 메서드예요. 원래 코드 앞뒤에 시작·끝 기록이 붙어요(파란 칸). 디스크의 파일은 그대로이고, 메모리에 올린 클래스만 바뀌어요.">

시작 기록은 시각과 요청을 이을 번호(trace id)를 적어요. 끝 기록은 걸린 시간과 에러가 났는지를 적어요. 이 한 쌍이 span(요청 한 구간의 기록) 하나가 되고, span들이 모여 워터폴이 돼요.

## 끼운 곳만 보여요

에이전트는 흔히 쓰는 라이브러리를 미리 알고 있어요. HTTP 요청을 받는 곳, DB 드라이버(JDBC), 다른 서비스를 부르는 HTTP 클라이언트, Kafka 같은 곳은 저절로 감싸요.

직접 쓴 메서드는 감싸지 않아요. 그 메서드가 오래 걸려도 워터폴에는 이름 없는 빈칸으로 보여요.

<Figure caption="900ms 요청의 예시예요. 에이전트가 감싼 맨 앞 질의와 맨 뒤 결제 호출은 span이 있어요. 그 사이 720ms는 직접 쓴 코드가 돈 시간이라, 워터폴에서는 막대 없는 빈칸이에요.">

빈칸을 채우려면 그 메서드도 감싸라고 알려 줘요. OpenTelemetry 에이전트라면 메서드에 `@WithSpan`을 붙여요. 빈칸 안에서 무엇이 CPU를 썼는지는 <Term slug="apm/continuous-profiling">지속 프로파일링</Term>으로도 봐요.

## 다른 스레드로 넘어가면 끊길 수 있어요

에이전트는 지금 처리 중인 요청의 번호를 스레드에 붙여 들고 다녀요. 일을 다른 스레드에 넘길 때도 이 번호를 같이 넘겨야 같은 트레이스로 이어져요.

에이전트가 아는 스레드 풀은 번호를 저절로 넘겨요. 직접 만든 방식으로 넘기면 번호가 빠져, 뒤의 기록이 새 트레이스로 끊겨요. 끊긴 트레이스는 <Term slug="apm/broken-traces">트레이스가 끊겼을 때</Term>에서 다뤄요.

## 에이전트도 자원을 써요

에이전트는 앱과 같은 JVM에서 돌아서 CPU, 메모리, 네트워크를 함께 써요. 이 몫을 <Term term="apm/agent-overhead">에이전트 부하</Term>(오버헤드)라고 해요.

부하는 span 수에 따라 커져요. 그래서 OpenTelemetry는 샘플링으로 span을 줄이고, 필요 없는 계측을 끄라고 권해요. JDBC처럼 span을 많이 만드는 계측은 `-Dotel.instrumentation.jdbc.enabled=false`처럼 끌 수 있어요.

모든 메서드에 `@WithSpan`을 붙이면 span이 크게 늘어요. 부하가 커지고, 쓸모없는 기록도 늘어요. 감쌀 곳은 오래 걸릴 만한 곳으로 골라요.

<Deeper>
  ### 실행 중인 JVM에 붙이기

  에이전트는 이미 도는 JVM에 나중에 붙일 수도 있어요. 이때는 에이전트 JAR의 `Agent-Class`와 `agentmain`을 써요.

  JDK 21부터는 실행 중에 에이전트를 붙이면 경고를 남겨요. JEP 451로 들어온 변화로, 앞으로 기본으로 막을 준비예요. 시작할 때 `-javaagent`로 붙이면 경고가 없어요.

  ### 고친 클래스는 메모리에만 있어요

  에이전트는 클래스 파일을 읽어 들이는 순간 바이트코드를 바꿔서 JVM에 넘겨요. 디스크의 JAR 파일은 그대로라, 에이전트를 빼고 다시 시작하면 원래 코드로 돌아가요.

  ### 다른 언어

  다른 언어의 APM 에이전트도 흔한 라이브러리의 함수를 감싸서 재는 방식은 같아요. 감싸는 방법만 언어마다 달라요. 그래서 어떤 라이브러리를 저절로 재는지는 에이전트 문서의 지원 목록에서 확인해요.
</Deeper>
