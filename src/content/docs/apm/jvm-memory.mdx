<KeyPoints>
  <Point title="객체는 힙에 담겨요">
    자바 코드가 만든 객체는 JVM의 힙에 담겨요. 힙의 최대 크기는 `-Xmx`로 정해요.
  </Point>
  <Point title="GC가 안 쓰는 객체를 치워요">
    더는 쓰지 않는 객체는 GC가 치워 자리를 만들어요. 치우는 동안 앱 스레드를 잠깐 멈추기도 해요.
  </Point>
  <Point title="JVM 메모리는 힙보다 커요">
    클래스 정보, 스레드 스택 같은 힙 밖 메모리도 써요. 그래서 프로세스 메모리는 `-Xmx`보다 커요.
  </Point>
</KeyPoints>

<Analogy limit="은행의 서류 정리 담당은 일하는 사이사이 조용히 치우지만, GC는 치우는 동안 앱 스레드를 잠깐 멈추게 하기도 해요.">
  힙은 지점의 서류 보관실이에요. 새 서류는 오늘 들어온 서류함(young)에 두고, 오래 남은 서류는 장기 보관함(old)으로 옮겨요. 정리 담당(GC)이 더는 찾지 않는 서류를 치워요.
</Analogy>

<Term term="apm/jvm">JVM</Term>은 자바 코드를 실행하는 프로그램이에요. 서버 입장에서는 프로세스 하나예요.

<Term term="apm/heap">힙</Term>은 자바 코드가 만든 객체가 담기는 곳이에요. `-Xmx`가 힙의 최대 크기를, `-Xms`가 처음 크기를 정해요.

힙 밖에도 메모리를 써요. 클래스 정보는 <Term term="apm/metaspace">메타스페이스</Term>에 담기는데, 기본으로 크기 제한이 없어요. 스레드마다 스택이 하나씩 있어서, 스레드가 많으면 스택 메모리도 그만큼 늘어요.

## 힙과 GC

자바 코드는 객체를 직접 지우지 않아요. 더는 아무도 가리키지 않는 객체는 <Term term="apm/gc">GC</Term>(가비지 컬렉터)가 찾아 치워요.

요즘 기본 GC인 G1은 힙을 young과 old 두 세대로 나눠요. 새 객체는 young에 담기고, young을 치울 때 살아남은 객체는 old로 옮겨요. G1은 힙을 같은 크기의 영역(region) 여러 개로 나눠 관리해요.

GC는 치우는 동안 앱 스레드를 잠깐 멈추는 구간(stop-the-world)이 있어요. 이 멈춤이 응답시간에 주는 영향은 <Term slug="apm/gc-pause">GC 멈춤</Term>에서 다뤄요.

## 힙이 모자라면

GC가 치워도 새 객체를 담을 자리가 없으면 `OutOfMemoryError: Java heap space`가 나요. 자바 문서는 이 오류가 꼭 메모리 누수를 뜻하지는 않는다고 해요. 앱에 비해 힙 크기를 작게 잡은 설정 문제일 수도 있어요.

메타스페이스가 바닥나면 `OutOfMemoryError: Metaspace`가 나요. 오류 뒤의 이름을 보면 어느 메모리가 모자랐는지 알 수 있어요.

힙 사용량은 객체가 쌓이면 오르고 GC가 치우면 내려가는 톱니 모양이 정상이에요. 봐야 할 것은 GC 직후에 남는 양이에요. 이 바닥이 계속 올라가면 치울 수 없는 객체가 쌓이고 있는 거예요.

서버나 컨테이너의 메모리 숫자와 힙 숫자는 달라요. 서버가 보는 프로세스 메모리(RSS)에는 힙 밖의 메모리까지 들어가요. RSS는 서버·OS의 <Term slug="server/memory">메모리</Term>에서 다뤄요.

<Deeper>
  ### 힙 크기 옵션

  `-Xmx`는 힙의 최대 크기, `-Xms`는 힙의 최소이자 처음 크기, `-Xss`는 스레드 스택 크기를 정해요. `-XX:MaxMetaspaceSize`는 클래스 정보에 쓸 네이티브 메모리의 최대치이고, 정하지 않으면 제한이 없어요.

  ### G1의 young 수집

  G1의 young 전용 단계는 보통 young 수집 몇 번으로 시작해요. 이때 살아남은 객체를 old 세대로 옮기는데, 이를 승격(promote)이라고 불러요.

  ### 힙 정보 보기

  `jcmd <PID> GC.heap_info`로 실행 중인 JVM의 힙 정보를 볼 수 있어요. 운영 중에 쓸 때는 문서가 적은 부하(Impact)를 확인해요.
</Deeper>
