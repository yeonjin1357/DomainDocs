## 세 방식은 HTTP를 다르게 써요

셋 다 HTTP 위에서 시작하지만, <Term slug="apm/http-basics">HTTP 요청과 응답</Term>에서 본 'URL 하나에 상태 코드 하나'와 쓰는 법이 달라요. 그래서 HTTP 상태 코드와 URL로 짠 화면은 셋을 제대로 못 보여 줘요.

| 방식 | 겉의 HTTP | 실패가 적히는 곳 |
| --- | --- | --- |
| gRPC | POST, 늘 200 | 끝의 grpc-status |
| GraphQL | POST /graphql, 흔히 200 | 본문의 errors |
| WebSocket | 처음에 101 한 번 | 닫힘 코드 |

WSL에 세 가지 서버를 띄우고 Envoy 1.40을 앞에 두어, 접근 로그에 무엇이 찍히는지 봤어요.

## gRPC: 실패도 200이에요

<Term term="apm/grpc">gRPC</Term>는 다른 서비스의 함수를 부르듯 호출하는 틀이에요. HTTP/2 위에서 `POST /shop.Orders/Get`처럼 서비스와 메서드 이름을 경로로 보내요. 메시지는 사람이 읽을 수 없는 이진 형식(protobuf)이에요.

결과는 HTTP 상태가 아니라 응답 맨 끝의 트레일러(trailer, 본문 뒤에 붙는 머리말)에 적혀요. 이 값이 <Term term="apm/grpc-status">grpc-status</Term>예요. 0이 성공이고, 실패해도 HTTP 상태는 200이에요.

Python grpcio 1.85 서버를 Envoy 뒤에 두고 여러 결과를 만들어 봤어요. Envoy 접근 로그의 HTTP 상태와 grpc-status예요.

| 호출 | HTTP | grpc-status |
| --- | --- | --- |
| 정상 | 200 | 0 OK |
| 없는 주문 | 200 | 5 NOT_FOUND |
| 처리 안 된 예외 | 200 | 2 UNKNOWN |
| 서버가 꺼짐 | 200 | 14 UNAVAILABLE |

서버가 꺼졌을 때도 200이에요. Envoy가 뒤쪽에 붙지 못하자 gRPC 꼴의 답(grpc-status 14)을 직접 만들어 보냈어요. HTTP 상태로 에러율을 세면 이 넷이 모두 성공이에요.

부르는 쪽 스팬은 OK가 아니면 모두 에러로 쳐요. 그래서 같은 호출이 클라이언트 화면에서는 에러, 서버 화면에서는 정상으로 보일 수 있어요.

gRPC는 기본으로 마감 시각(deadline)이 없어서, 부르는 쪽이 정해야 해요. 마감 0.3초로 1초 걸리는 메서드를 불렀더니 클라이언트는 0.3초에 DEADLINE_EXCEEDED(4)로 끝냈어요. 마감은 <Term slug="apm/timeouts-and-retries">타임아웃과 재시도</Term>에서 다뤄요.

### 스트리밍 호출은 길어요

gRPC는 응답을 여러 번 나눠 흘려보내는 스트리밍 호출도 있어요. 1초마다 하나씩 다섯 번 보내는 호출은 Envoy 로그에 5,002ms로 찍혔어요. 이 시간은 느린 게 아니라 스트림이 열려 있던 시간이에요.

## GraphQL: 한 주소로 모든 요청이 와요

<Term term="apm/graphql">GraphQL</Term>은 클라이언트가 필요한 필드를 질의로 적어 보내는 API 방식이에요. 질의는 모두 한 주소(보통 `POST /graphql`)로 가요. 무엇을 하는지는 본문의 질의와 operation 이름(`query GetOrder`의 `GetOrder`)에 적혀요.

그래서 URL로 트랜잭션을 묶으면 모든 요청이 `POST /graphql` 하나로 뭉쳐요. 주문 조회와 결제가 같은 이름이라, 무엇이 느린지 알 수 없어요. operation 이름으로 나눠야 해요.

### 필드 하나가 실패해도 200이에요

GraphQL은 필드마다 값을 따로 구해요. 하나가 실패하면 그 필드만 `null`로 두고, 실패 내용을 `errors`에 적어 함께 보내요. 이것을 부분 성공이라고 해요.

graphql-http 1.23으로 띄운 서버에서 가격 필드만 실패하게 했어요. HTTP 200과 함께 이런 본문이 왔어요.

```json
{
  "errors": [{
    "message":
      "price service timeout",
    "path": ["order", "price"]
  }],
  "data": {
    "order": {
      "id": "A-2",
      "price": null
    }
  }
}
```

없는 필드를 묻는 잘못된 질의는 요청의 `Accept` 머리말에 따라 달랐어요. `application/json`이면 200, 새 형식인 `application/graphql-response+json`이면 400이었어요. 상태 코드 규칙을 정하는 GraphQL over HTTP 명세가 아직 작업 초안이라, 라이브러리마다 따르는 판이 달라요.

결국 GraphQL의 에러율은 HTTP 상태가 아니라 응답 본문에 `errors`가 있는지로 세야 해요. 한 질의가 필드마다 DB를 따로 부르면 <Term slug="apm/n-plus-one">N+1</Term>이 생기기 쉬워서, 필드별 시간도 함께 봐요.

## WebSocket: 연결이 계속 열려 있어요

<Term term="apm/websocket">WebSocket</Term>은 HTTP로 시작해서, 같은 연결을 양쪽이 아무 때나 메시지를 보내는 통로로 바꿔 쓰는 방식이에요. 채팅, 실시간 알림, 실시간 대시보드가 써요. 처음 한 번만 HTTP 요청이고, 서버가 101(Switching Protocols)로 답하면 그 뒤로는 HTTP가 아니에요.

1초마다 메시지를 보내는 서버에 5초 동안 붙어 있다가 닫았어요. Envoy 접근 로그에는 `GET /live 101 5009ms`가 남았어요. 요청 하나가 5초 걸린 것처럼 보이지만, 이 시간은 연결이 열려 있던 시간이에요.

이런 줄을 HTTP 응답시간과 함께 모으면 <Term slug="foundations/percentiles">p99</Term>가 크게 부풀어요. WebSocket과 스트리밍은 응답시간 계산에서 빼고 따로 봐요.

### 어떻게 닫혔는지가 실패의 표시예요

WebSocket은 닫을 때 닫힘 코드를 주고받아요. 1000은 정상 종료예요. 1006은 닫힘 신호 없이 연결이 끊겼다는 뜻으로, 실제로 오가는 코드가 아니라 받는 쪽이 스스로 붙이는 값이에요.

같은 실험에서 3초 뒤에 서버 프로세스를 끄자, 클라이언트는 닫힘 코드 1006을 받았어요. 1006이 갑자기 늘면 서버가 죽었거나, 중간 장비가 연결을 끊은 것이에요.

중간 프록시는 오래 조용한 연결을 끊어요. nginx는 기본으로 60초 동안 뒤쪽에서 아무 데이터가 없으면 연결을 닫아요. 그래서 WebSocket 서버는 보통 주기적으로 ping 메시지를 보내 연결을 살려 둬요.
