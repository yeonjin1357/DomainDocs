<Situation>
  주문 API의 트레이스를 열었는데, 결제 API를 부른 구간 아래가 비어 있어요. 결제 API 쪽에는 같은 시각에 따로 시작한 트레이스가 보여요.

  트레이스가 끊기는 원인은 몇 갈래로 나뉘어요. 끊긴 모양으로 갈래를 정한 뒤, 헤더, 스레드, 샘플링 순서로 봐요.

## 1. 끊긴 모양부터 보세요

뒷단 서비스에 같은 시각의 새 트레이스가 있다면, trace id가 넘어가지 않은 거예요. 뒷단은 부모를 모른 채 새 트레이스를 시작했어요. 이때는 2단계와 3단계를 봐요.

뒷단 span이 어느 트레이스에도 없다면, 뒷단이 계측되지 않았거나 샘플링에서 빠졌어요. 이때는 4단계를 봐요.

**확인 방법**: <Term slug="apm/service-map">서비스 맵</Term>에서 `user` → 내부 서비스로 가는 선을 찾아요. Tempo와 OpenTelemetry Collector는 부른 쪽 span 없이 시작한 SERVER span의 부른 쪽을 `user`로 그려요. 내부 서비스끼리 부르는 자리에 `user`가 있다면 전파가 끊긴 거예요.

## 2. 헤더가 넘어가는지 보세요

trace id는 HTTP 헤더에 실려 다음 서비스로 넘어가요. OpenTelemetry는 기본으로 W3C 표준 `traceparent` 헤더를 써요. 사이에 있는 프록시, 게이트웨이, 직접 만든 HTTP 클라이언트가 이 헤더를 빼먹으면 트레이스가 끊겨요.

전파 형식도 맞아야 해요. SDK가 쓸 형식은 `OTEL_PROPAGATORS` 환경 변수로 정하고, 기본값은 `tracecontext,baggage`예요. 한쪽이 `b3`(Zipkin 형식)만 쓰면 다른 쪽은 헤더를 알아듣지 못해요.

**확인 방법**: 받는 쪽에서 들어온 요청의 `traceparent` 헤더를 잠시 로그로 남겨요. 값은 아래처럼 버전, trace id(32자), 부모 span id(16자), 플래그를 `-`로 이은 꼴이에요.

```text
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
```

헤더가 없다면 부른 쪽 클라이언트나 사이의 프록시가 헤더를 빼먹은 거예요. 헤더는 있는데 받는 쪽 span의 trace id가 헤더와 다르다면, 받는 쪽이 헤더를 읽지 않은 거예요.

## 3. 스레드를 넘는 곳을 보세요

같은 서비스 안에서 끊긴다면, 작업을 다른 스레드로 넘긴 곳을 봐요. OpenTelemetry Java는 지금의 컨텍스트(trace id가 든 실행 정보)를 기본으로 스레드 로컬에 둬요. 그래서 스레드 풀이나 비동기로 넘긴 작업에는 컨텍스트가 따라가지 않을 수 있어요.

이럴 땐 넘길 때 컨텍스트를 함께 넘겨요. Java라면 `Context.current().wrap(executorService)`처럼 스레드 풀을 감싸요. 메시지 큐를 거친다면 메시지에 컨텍스트를 실어 보내는지 봐요.

**확인 방법**: 끊긴 뒤쪽 span이 어느 스레드에서 시작했는지, 그 작업을 어디서 넘겼는지 코드를 따라가요.

## 4. 샘플링 결정을 보세요

head 샘플링에서는 시작한 서비스가 남길지를 정하고, 뒤 서비스는 그 결정을 따라야 해요. OpenTelemetry SDK의 기본 샘플러(`parentbased_always_on`)는 부모의 결정을 따라요. 뒤 서비스가 따로 비율을 정하면, 앞은 남고 뒤는 빠진 트레이스가 생겨요.

<Term slug="apm/sampling">tail 샘플링</Term>이라면 한 트레이스의 span이 모두 같은 Collector 인스턴스로 와야 해요. Collector를 여러 대 둔다면, 앞에 load balancing exporter를 두고 `routing_key`를 `traceID`로 정해요.

**확인 방법**: 서비스마다 `OTEL_TRACES_SAMPLER` 설정을 견줘 봐요. 고친 뒤에는 1단계의 `user` 선이 사라지는지 확인해요.

<Checkpoints>
  <Check>새 서비스를 붙인 뒤 트레이스가 끊겼다면, 그 서비스의 전파 형식과 샘플러 설정을 다른 서비스와 견줘 보세요. 환경 변수로는 `OTEL_PROPAGATORS`와 `OTEL_TRACES_SAMPLER`예요.</Check>
  <Check>`user` 선이 모두 끊김은 아니에요. 계측되지 않은 스케줄러, 프런트엔드, curl로 보낸 요청도 `user`로 나와요. 내부 서비스끼리 부르는 자리에 있을 때만 의심하세요.</Check>
  <Check>바깥에서 온 `traceparent`를 그대로 이어받는 공개 서비스라면 다시 보세요. 바깥 요청이 우리 트레이스의 시작과 샘플링 결정을 정할 수 있어요. Elastic은 이럴 때 새 트레이스를 시작하는 restart 전략을 권해요.</Check>
</Checkpoints>
