## 에러는 세 갈래로 와요

| 갈래 | 잡는 곳 | 예 |
| --- | --- | --- |
| 실행 중 에러 | `error` 이벤트, `window.onerror` | undefined의 속성을 읽음 |
| 처리하지 않은 Promise 거부 | `unhandledrejection` 이벤트 | await한 요청의 실패를 잡지 않음 |
| 자원 불러오기 실패 | 캡처 단계로 등록한 `error` 리스너 | 이미지·스크립트 404 |

앞의 두 갈래와 `Script error.`는 <Term slug="apm/rum">실제 사용자 모니터링(RUM)</Term>에서 다뤘어요. 여기서는 놓치기 쉬운 자원 실패와 fetch부터 봐요.

<Term term="apm/resource-error">자원 불러오기 실패</Term>는 그 요소(img, script)에서 일어나요. MDN에 따르면 이 이벤트는 위로 퍼지지(bubble) 않아요. 그래서 window.onerror에는 오지 않고, window에 캡처 단계로 등록한 리스너에서 잡혀요.

```js
window.addEventListener('error', (e) => {
  if (e.target !== window) report(e.target.src);
}, true);
```

Chromium, Firefox, WebKit에서 이미지 404를 만들어 봤어요. 세 엔진 모두 window.onerror에는 오지 않고 캡처 리스너에서만 잡혔어요.

MDN에 따르면 fetch의 Promise는 주소가 잘못됐거나 네트워크가 실패할 때만 거부돼요. 서버가 404나 504를 돌려줘도 정상 응답으로 끝나요. 세 엔진에서 돌려 봐도 404 응답은 `ok: false`, `status: 404`로 정상 반환됐어요.

그래서 에러 화면에 API 실패가 없다고 API가 멀쩡한 건 아니에요. 응답의 ok나 status를 확인해서 따로 보내야 화면에 남아요.

네트워크가 끊긴 실패는 TypeError로 거부되는데, 문구가 엔진마다 달라요.

| 엔진 | 네트워크 실패 문구 |
| --- | --- |
| Chromium | `Failed to fetch` |
| Firefox | `NetworkError when attempting to fetch resource.` |
| WebKit | `Load failed` |

## 같은 버그, 다른 문구

undefined인 `user`의 `name`을 읽는 같은 코드를 세 엔진에서 돌려 봤어요. 에러 문구가 모두 달라요.

| 엔진 | 에러 문구 |
| --- | --- |
| Chromium 156 | `Cannot read properties of undefined (reading 'name')` |
| Firefox 157 | `can't access property "name", user is undefined` |
| WebKit 27.2 | `undefined is not an object (evaluating 'user.name')` |

문구로만 묶으면 버그 하나가 세 묶음으로 갈라져요. 그래서 에러 도구는 문구보다 <Term term="apm/stack-trace">스택 트레이스</Term>의 위치로 먼저 묶어요. Sentry는 스택이 있으면 스택으로, 없으면 에러 종류와 값으로, 그것도 없으면 메시지로 묶어요.

스택의 형식도 달라요. Chromium은 `at readName (…:20:41)`처럼, Firefox와 WebKit은 `readName@…:20:29`처럼 써요. 같은 위치인데 열 번호도 41, 29, 40으로 달랐어요.

줄인 코드에서는 함수 이름과 위치가 배포마다 바뀌어서 묶음이 흐트러져요. Sentry 문서도 줄인 코드가 묶기를 크게 망친다고 경고해요. <Term term="apm/source-map">소스 맵</Term>으로 원래 위치를 되살린 뒤 묶어야 해요.

## 소음 거르기

고칠 수 없거나 해가 없는 에러도 함께 들어와요. 대표적인 것이 `ResizeObserver loop completed with undelivered notifications.`예요.

MDN에 따르면 크기 감시 콜백이 크기를 다시 바꿔서, 한 프레임에 알림을 다 전하지 못했다는 뜻이에요. 브라우저가 멈추지 않게 막은 것이라 화면이 잠깐 흔들릴 수 있어요. 세 엔진 모두 스택 없이 들어와서 위치를 알 수 없었어요.

콜백이 크기를 계속 바꾸게 두자, Chromium에서 0.8초 동안 이 에러가 50번 넘게 쌓였어요. 페이지 보기 한 번이 에러 수를 크게 부풀릴 수 있어요.

문자열로 거부한 Promise도 위치를 알 수 없어요. `Promise.reject('plain string')`은 세 엔진 모두 reason이 문자열이었고 스택이 없었어요. Error 객체로 거부해야 위치가 남아요.

## 화면에서 읽는 법

에러 수, 묶음 수, 겪은 사용자 수는 서로 다른 질문에 답해요. 에러 수는 사용자 한 명이 수백 번 낼 수 있어서 부풀기 쉬워요. 고칠 순서는 <Term term="apm/error-grouping">에러 묶음</Term>마다 겪은 사용자 수로 정해요.

비율로 볼 때는 분모를 밝혀요. "페이지 보기 중 에러가 난 비율"과 "사용자 중 에러를 겪은 비율"은 같은 데이터로도 값이 달라요.

배포 버전을 함께 보내면 새 버전에서 처음 나온 묶음을 따로 볼 수 있어요. 배포 직후에 새 묶음이 생기면 그 배포를 먼저 의심해요.

<Checkpoints>
  <Check>이미지나 스크립트 404가 에러 화면에 없다면, 캡처 단계로 등록한 error 리스너가 있는지 보세요. window.onerror로는 안 잡혀요.</Check>
  <Check>API 실패를 fetch의 catch에서만 보내고 있다면 다시 보세요. 404와 500 응답은 catch로 가지 않아요.</Check>
  <Check>에러를 문구로만 묶고 있다면 다시 보세요. 같은 버그가 브라우저마다 다른 묶음으로 갈라져요.</Check>
  <Check>에러 수 순서로 고칠 순서를 정했다면, 겪은 사용자 수로도 정렬해 보세요.</Check>
  <Check>ResizeObserver 경고가 상위를 차지한다면, 걸러 낼지와 실제로 화면이 흔들리는지를 따로 판단하세요.</Check>
</Checkpoints>

<Deeper>
  ### 실험 조건

  Playwright로 Chromium 156, Firefox 157, WebKit 27.2에서 같은 페이지를 열었어요. 페이지는 undefined의 속성 읽기, 문자열로 Promise 거부, 404 이미지를 차례로 일으켜요. 이어서 404 API, 끊긴 API, ResizeObserver 크기 변경도 일으켜요.

  ### onerror의 문구

  Chromium에서는 window.onerror가 받은 문구 앞에 `Uncaught`가 붙었어요. 같은 에러의 error.message에는 붙지 않아요. 어느 쪽을 보내느냐에 따라 묶음이 갈릴 수 있어요.

  ### MDN과 다른 문구

  MDN은 Firefox의 문구를 `"x" is undefined`로 소개해요. 그런데 실험한 Firefox 157은 `can't access property "name", user is undefined`로 보였어요. 같은 엔진도 버전마다 문구가 달라요.
</Deeper>
