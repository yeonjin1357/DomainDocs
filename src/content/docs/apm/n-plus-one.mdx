<Situation>
  주문 목록 API가 1.2초씩 걸려요. 그런데 Top SQL에 보이는 SQL은 모두 한 번에 2ms 안쪽이에요.

  빠른 SQL도 요청마다 수백 번 부르면 느려져요. 목록을 한 번 가져온 뒤, 항목마다 SQL을 하나씩 더 보내는 모양을 <Term term="apm/n-plus-one">N+1</Term>이라고 해요. 목록 1번에 항목 N번이라 N+1이에요.
</Situation>

## 1. 트레이스에서 같은 막대를 세세요

느린 요청의 <Term slug="apm/trace-waterfall">트레이스 워터폴</Term>을 열어요. N+1이라면 목록 SQL 하나 뒤에 같은 SQL 막대가 계단처럼 길게 이어져요.

막대 하나는 짧아서 눈에 안 띄어요. 막대 수와 합계 시간을 봐요. 하나에 2ms여도 500번이면 1초예요.

**확인 방법**: 트레이스에서 같은 SQL의 구간 수를 세어요. 구간 수에 상한을 두는 도구도 있어서 뒷부분이 잘려 보일 수 있어요. 예를 들어 Elastic APM 자바 에이전트는 트랜잭션 하나에 구간을 기본 500개까지만 남겨요.

## 2. Top SQL에서 호출 수를 보세요

DB 쪽에서는 한 번은 빠른데 호출 수가 유난히 많은 SQL로 보여요. PostgreSQL의 `pg_stat_statements`라면 `calls`가 크고 `mean_exec_time`이 작은 SQL이에요.

호출 수를 같은 시간의 요청 수로 나눠 봐요. 주문 목록 요청이 1만 번인데 고객 조회 SQL이 100만 번 불렸다면, 요청 하나에 100번씩 부른 거예요. 읽는 법은 <Term slug="database/top-sql">Top SQL</Term>에 있어요.

## 3. 무엇이 부르는지 찾으세요

N+1은 손으로 짠 코드에서도 생기지만, ORM에서 특히 잘 숨어요. Hibernate 문서는 자바 데이터 접근 코드가 느린 가장 흔한 원인으로 N+1을 꼽아요.

흔한 모양은 이래요. 주문 목록을 가져온 뒤 목록을 돌며 `order.getCustomer().getName()`을 읽어요. 고객 정보가 아직 안 불려 있으면, 읽는 순간마다 SQL이 하나씩 나가요.

이렇게 필요할 때 가져오는 방식을 <Term term="apm/lazy-loading">지연 로딩</Term>(LAZY)이라고 해요. JPA 3.2의 기본값은 연관 종류마다 달라요.

| 연관 | 기본 로딩 |
| --- | --- |
| `@ManyToOne`, `@OneToOne` | 바로 가져와요(EAGER) |
| `@OneToMany`, `@ManyToMany` | 필요할 때 가져와요(LAZY) |

그래서 코드에 SQL이 안 보여도, 목록을 도는 반복문 안에서 연관 객체를 읽는 곳이 범인이에요. 화면 템플릿이 목록을 그리며 연관 객체를 읽어도 같아요.

## 4. 한 번에 가져오게 고치세요

실제 DB는 네트워크 너머에 있어서, SQL마다 왕복 시간이 더 붙어요. 왕복이 1ms라면 N+1은 101ms가 더 붙고, 조인은 1ms만 더 붙어요.

고치는 길은 두 가지예요.

- **조인으로 함께 가져오기**: 목록 SQL에서 고객을 조인해 한 번에 가져와요. JPA라면 `join fetch`를 써요. Hibernate 문서는 거의 언제나 이 방법을 쓰라고 해요.
- **묶어서 가져오기**: 목록의 고객 번호를 모아 `IN`이나 배열 조건으로 한 번에 가져와요. Hibernate의 배치 가져오기(`hibernate.default_batch_fetch_size`, `@BatchSize`)가 이 방식이에요.

```sql
-- N+1: 주문마다 한 번씩
select name from customers
 where id = ?

-- 묶어서: 한 번에
select id, name from customers
 where id = any(?)
```

Hibernate 문서는 배치 가져오기가 N+1을 줄여 줄 뿐 없애지는 못한다고 해요. 조인하면 결과가 너무 커지는 드문 경우에만 배치를 고르라고 권해요.

## 5. 요청당 SQL 수로 지켜보세요

N+1은 데이터가 적은 개발 환경에서는 빨라서 놓치기 쉬워요. 주문이 10건이면 SQL 11번이지만, 운영에서 1,000건이면 1,001번이에요.

그래서 요청 하나가 부르는 SQL 수를 지표로 봐요. 시험 코드에서 요청마다 SQL 수를 세어 두면, 늘어나는 순간 바로 알아요. Sentry 같은 도구는 트레이스에서 이 모양을 자동으로 찾아 주기도 해요.
