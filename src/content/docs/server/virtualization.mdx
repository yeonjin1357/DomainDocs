## 가상화는 무엇인가요

가상화는 물리 서버 한 대에서 운영체제 여러 개를 따로 돌리는 기술이에요. <Term term="server/hypervisor">하이퍼바이저</Term>가 CPU, 메모리, 디스크를 나눠 주고, 나눠 받은 단위를 가상 머신(VM)이라고 불러요. VM 안의 운영체제를 게스트(guest), 바깥의 물리 서버를 호스트(host)라고 해요.

서버에서는 하드웨어 바로 위에 하이퍼바이저를 깔아요. VMware ESXi, 리눅스의 KVM, Windows의 Hyper-V가 그렇게 써요. PC의 VirtualBox처럼 운영체제 위에 프로그램으로 까는 하이퍼바이저도 있어요.

클라우드의 <Term slug="cloud/virtual-machines">가상 머신</Term>도 클라우드 회사의 하이퍼바이저 위에서 돌아요. 다만 호스트 쪽 숫자는 클라우드 회사만 봐요. 회사 안에 VMware 같은 하이퍼바이저를 두면, 호스트 숫자까지 직접 볼 수 있어요.

<Term slug="kubernetes/containers">컨테이너</Term>와는 나누는 높이가 달라요. 컨테이너는 커널 하나를 여럿이 나눠 쓰고, VM은 커널까지 따로 가져요.

## CPU는 시간으로 나눠 써요

<Term term="server/vcpu">vCPU</Term>(가상 CPU)는 물리 코어를 빌려 쓰는 자리예요. 하이퍼바이저가 vCPU들을 물리 코어에 번갈아 앉혀요. VM에 준 vCPU의 합이 물리 코어보다 많은 것을 <Term term="server/overcommit">오버커밋</Term>(overcommit)이라고 해요.

오버커밋은 흔하고, 그 자체로 나쁘지 않아요. VM들이 한꺼번에 바쁘지 않으면 코어가 노는 시간을 줄여 줘요. 한꺼번에 바빠지면 vCPU가 차례를 기다려요.

### 게스트가 기다림을 못 볼 때도 있어요

steal은 하이퍼바이저가 알려 줘야 보여요. WSL 2는 Windows의 Hyper-V 위에서 도는 VM이에요. Windows 쪽에 CPU 부하를 걸자 WSL 안의 같은 계산이 14.4초에서 20.2초로 늘었는데, steal은 0%였어요.

리눅스 커널의 Hyper-V 코드에는 steal을 받는 부분이 없어요. VMware 위의 리눅스는 호스트가 지원한다고 답할 때만 steal을 세요. 그래서 VM이 느린데 게스트 숫자가 멀쩡하면 호스트를 봐야 해요.

## 메모리는 되가져갈 수 있어요

VM에 준 메모리를 더하면 호스트 메모리보다 많을 수 있어요. 게스트가 받은 메모리를 다 쓰지 않으면 문제가 없어요. 여러 VM이 한꺼번에 많이 쓰면 호스트가 VM의 메모리를 되가져가요.

VMware는 호스트의 빈 메모리가 줄면 먼저 풍선을 부풀려요. 풍선으로 모자라거나 더 빨리 줄면 호스트 스왑을 함께 써요.

### 풍선은 게스트 안에서 메모리를 잡아 둬요

<Term term="server/memory-balloon">풍선</Term>(balloon)은 게스트 안에 깔린 드라이버예요. VMware는 VMware Tools에 들어 있어서, Tools가 없으면 풍선도 없어요. 호스트가 신호를 주면 드라이버가 게스트 메모리를 잡아 두고, 그만큼의 실제 메모리를 호스트에 돌려줘요.

게스트에 빈 메모리가 넉넉하면 빈 곳을 내줘서 성능에 영향이 없어요. 넉넉하지 않으면 게스트가 덜 쓰는 페이지를 골라 자기 스왑으로 내보내요. 무엇을 내보낼지 게스트가 고르는 게 풍선의 장점이에요.

같은 KVM VM으로 실험해 봤어요. 메모리 1GB인 VM에서 호스트가 풍선으로 512MiB를 되가져가게 하고, 게스트의 `/proc/meminfo`를 봤어요.

VMware의 리눅스 풍선 드라이버는 아래쪽처럼 메모리를 잡아 두기만 하고 전체를 줄이지 않아요. 그래서 게스트 안에서는 쓰는 프로세스 없이 사용량이 오른 것처럼 보여요. 프로세스마다 쓰는 메모리(RSS)를 더해도 사용량에 한참 못 미치면 풍선을 의심해요.

### 호스트 스왑은 게스트 모르게 내보내요

풍선으로 모자라면 호스트가 VM의 메모리를 자기 디스크로 내보내요. 이것을 호스트 스왑이라고 해요. 게스트는 이 일을 몰라요.

그래서 게스트가 절대 내보내지 않을 커널 페이지나 자주 쓰는 페이지도 나갈 수 있어요. 그 메모리에 닿을 때마다 디스크를 기다려서 VM 전체가 크게 느려져요. 게스트 안의 스왑 숫자는 0인데 느릴 수 있어요.

### 메모리 한도가 있으면 호스트가 넉넉해도 되가져가요

VM에 메모리 한도(limit)를 걸면, 호스트가 넉넉해도 한도를 넘는 만큼 풍선과 스왑이 일어나요. 게스트에는 16GB로 보이는데 한도가 8GB라면, 8GB를 넘게 쓰는 순간부터 되가져가요. 게스트 안에서는 한도가 보이지 않아서 찾기 어려워요.

## 디스크와 스냅숏

VM의 디스크는 보통 여러 호스트가 함께 쓰는 저장소 위의 파일이에요. VMware는 이 저장소를 데이터스토어라고 불러요. 같은 데이터스토어의 다른 VM이 디스크를 많이 쓰면, 내 VM의 <Term term="server/io-latency">입출력 지연</Term>도 늘어요.

스냅숏(snapshot)은 VM의 한 시점을 남겨 두는 기능이에요. 그 뒤로 바뀐 내용은 따로 쌓여서, 오래 둘수록 파일이 커져요. VMware는 스냅숏 하나를 72시간 넘게 두지 말고, 백업으로 쓰지 말라고 권해요.

실행 중인 VM을 다른 호스트로 옮길 수도 있어요. VMware는 이것을 vMotion이라고 불러요.

옮기고 나면 이웃이 바뀌어요. 그래서 숫자가 바뀐 시점에 VM이 어느 호스트에 있었는지도 남겨야 해요.

호스트 쪽에서 볼 숫자는 이래요.

- CPU Ready: vCPU가 코어를 기다린 시간이에요. 같은 호스트의 다른 VM들과 함께 봐요.
- 풍선: 풍선 드라이버가 잡아 둔 메모리의 양이에요. 0이 아니면 호스트 메모리가 모자랐다는 뜻이에요.
- 호스트 스왑: 호스트가 디스크로 내보낸 VM 메모리의 양과 속도예요.
- 데이터스토어 지연: 같은 저장소를 쓰는 VM들이 함께 겪는 입출력 지연이에요.

vCenter의 CPU Ready는 차트 간격 동안 기다린 시간을 밀리초로 더한 값이에요. 실시간 차트는 20초 간격이라, 합계를 200으로 나누면 %가 돼요. 이 값은 vCPU를 모두 더한 것이라, vCPU 4개인 VM의 합계 4,000ms는 20%이고 vCPU 하나로는 5%예요.

<Deeper>
  CPU Ready 합계를 %로 바꾸는 식은 합계 ÷ (차트 간격 초 × 1000) × 100이에요. Broadcom KB 306576이 드는 나눌 수는 실시간 200, 하루 3,000, 한 주 18,000이에요. 한 달은 72,000, 한 해는 864,000이에요.

  vCPU별 지표는 기본으로 실시간에서만 모아요.

  KVM의 steal은 vCPU가 일하려 했는데 돌지 못한 시간이에요. vCPU가 쉬던(idle) 시간은 steal로 세지 않아요. 그래서 위 실험에서 일꾼을 하나만 돌리면 vCPU 둘이 코어 하나를 나눠도 steal이 4%에 그쳤어요.

  KVM의 virtio 풍선은 `deflate-on-oom`을 켜지 않으면 되가져간 만큼 MemTotal을 줄여요. 켜면 MemTotal은 그대로 두고, 게스트가 메모리 부족에 빠지면 풍선을 먼저 줄여요. 리눅스의 VMware 풍선 드라이버(vmw_balloon)는 MemTotal을 줄이지 않아요.

  실험 환경은 WSL 2(커널 6.18, Hyper-V 위)예요. 그 안에서 QEMU와 KVM으로 Ubuntu 커널 6.8 게스트를 busybox만으로 띄웠어요. `taskset`으로 QEMU를 CPU 하나에 묶고, 셸에서 덧셈 400만 번을 돌렸어요.

  VMware의 메모리 되가져가기는 버전마다 단계 이름과 문턱값이 달라졌어요. 숫자 기준은 쓰는 버전의 문서로 확인해요.
</Deeper>
