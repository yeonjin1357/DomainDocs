## 무엇인가요

<Term term="network/ebpf">eBPF</Term>는 리눅스 커널 안에서 작은 프로그램을 돌리는 기능이에요. 커널 소스를 고치거나 커널 모듈을 올리지 않아요. 프로그램은 정해진 지점(훅)에 붙어, 그 지점을 지날 때마다 돌아요.

커널 안에서 도는 코드가 잘못되면 서버 전체가 멈출 수 있어요. 그래서 프로그램은 올리기 전에 검사를 받아요.

<Figure caption="에이전트가 올린 프로그램은 검사기를 통과해야 훅에 붙어요. 붙은 뒤에는 이벤트마다 돌며 맵에 적고, 에이전트가 맵을 읽어 가요.">
  <EbpfLoad aria-label="사용자 공간의 에이전트가 1 bpf() 시스템 콜로 프로그램을 커널에 올리면, 2 검사기가 반드시 끝나는지와 안전한지 보고 아니면 거절해요. 통과하면 3 기계어로 바꿔 훅에 붙고, 4 시스템 콜이나 패킷 같은 이벤트마다 돌며 맵에 적어요. 5 에이전트가 맵을 읽어 모니터링 서버로 보내요" />
</Figure>

<Term term="server/ebpf-verifier">검사기</Term>(verifier)는 프로그램이 지나갈 수 있는 길을 모두 따라가 봐요. 끝나지 않을 수 있는 반복이 있거나, 허락 안 된 메모리를 읽으면 거절해요. 직접 끝없는 반복을 넣어 봤더니 `infinite loop detected`로 거절했어요.

맵(map)은 커널 안의 프로그램과 바깥의 에이전트가 함께 쓰는 저장소예요. 프로그램이 이벤트마다 맵에 숫자를 더하고, 에이전트는 몇 초마다 맵을 읽어 가요. 이벤트를 하나하나 바깥으로 보내지 않아서 가벼워요.

## 어디에 붙이나요

붙이는 곳에 따라 보이는 것이 달라요. 앱 쪽에 가까울수록 뜻이 담긴 데이터가, 커널 아래로 갈수록 바이트와 패킷이 보여요.

<Figure caption="앱은 라이브러리에, 라이브러리는 시스템 콜에, 시스템 콜은 커널 네트워크 처리에 기대요. 층마다 붙이는 방법과 보이는 것이 달라요.">
  <EbpfHooks aria-label="위에서부터 사용자 공간의 앱 코드는 uprobe로 함수 호출을, TLS 라이브러리는 uprobe로 암호화 전 평문을 봐요. 커널 쪽 시스템 콜은 tracepoint로 주고받는 바이트를, 커널 TCP/IP는 kprobe로 연결·재전송·RTT를, 네트워크 카드는 XDP로 들어온 패킷을 봐요" />
</Figure>

- **<Term term="server/tracepoint">tracepoint</Term>**: 커널 개발자가 미리 박아 둔 지점이에요. 커널 버전이 바뀌어도 잘 유지돼요.
- **<Term term="server/kprobe">kprobe</Term>**: 커널 함수 아무 곳에나 붙여요. 함수 이름이나 인자가 바뀌면 깨질 수 있어요.
- **<Term term="server/uprobe">uprobe</Term>**: 사용자 프로그램이나 라이브러리의 함수에 붙여요. 함수 이름을 알아야 해요.

네트워크 성능 모니터링이 연결마다 재전송과 RTT를 모으는 곳이 커널 TCP/IP 층이에요. 그 이야기는 <Term slug="network/network-performance">네트워크 성능</Term>에서 다뤄요. 이 글은 그 위, 요청 단위로 보는 법을 다뤄요.

## 앱을 고치지 않고 HTTP 보기

직접 해 봤어요. WSL(리눅스 커널 6.18)에서 Python으로 만든 작은 HTTP 서버를 띄웠어요. 서버 코드는 한 줄도 고치지 않고, bpftrace(eBPF 프로그램을 짧은 글로 쓰는 도구)로 아래 몇 줄을 올렸어요.

```text
t:syscalls:sys_enter_sendto
/comm == "python3"/
{
  printf("%s\n",
    str(args->buff, 15));
}
```

`t:`는 tracepoint의 줄임이에요. python3 프로세스가 `sendto` 시스템 콜로 보내는 데이터의 앞 15바이트를 찍어요. 요청 하나에 이렇게 나왔어요.

```text
HTTP/1.0 200 OK
ok
```

첫 줄은 응답의 상태 줄, 둘째 줄은 본문이에요. 앱이 커널에 넘긴 바이트라서, 앱 밖에서도 그대로 보여요.

<Figure caption="요청을 읽은 시스템 콜과 응답을 보낸 시스템 콜에 붙으면, 둘 사이가 서버 안의 처리 시간이에요. /slow는 일부러 0.2초를 쉬게 만든 경로예요.">
  <EbpfHttp aria-label="클라이언트가 GET /slow를 보내면 앱이 recvfrom 시스템 콜로 요청을 읽고, 0.2초 쉰 뒤 sendto 시스템 콜로 200 OK를 보내요. eBPF가 두 시스템 콜의 시각을 적어, 그 차이 0.2초가 서버 안 처리 시간이에요" />
</Figure>

요청을 읽은 `recvfrom`과 응답을 보낸 `sendto`의 시각을 짝지으니 지연도 나왔어요.

```text
REQ  GET /fast HTTP/1
RESP HTTP/1.0 200 OK  0 ms
REQ  GET /slow HTTP/1
RESP HTTP/1.0 200 OK  200 ms
```

eBPF로 계측 없이 서비스 지표를 만드는 제품도 이 원리예요. 지나가는 요청과 응답을 읽어 요청 수, 에러 수, 지연(RED)을 서비스마다 세요.

## 암호화되면 어디에 붙이나요

HTTPS로 바꾸면 시스템 콜에는 암호문만 지나가요. 같은 서버를 TLS로 띄우고 `write` 시스템 콜을 봤더니 첫 바이트가 `\x17\x03\x03`이었어요. TLS 레코드의 머리표이고, 뒤는 읽을 수 없는 암호문이에요.

그래서 암호화하기 전, TLS 라이브러리 함수에 uprobe를 붙여요. Python은 OpenSSL의 libssl을 써서, `SSL_write_ex` 함수에 붙이자 평문이 보였어요.

```text
SSL_write_ex HTTP/1.0 200 OK
write   \x17\x03\x03\x00\x80n
```

<Figure caption="같은 응답이 libssl 함수에서는 평문이고, write 시스템 콜에서는 TLS 레코드로 감싼 암호문이에요.">
  <EbpfTls aria-label="앱이 부른 libssl 함수 SSL_write_ex에 uprobe를 붙이면 평문 HTTP/1.0 200 OK가 보여요. libssl이 암호화한 뒤 write 시스템 콜에 tracepoint를 붙이면 TLS 레코드 머리표 17 03 03 뒤에 암호문뿐이에요" />
</Figure>

붙일 함수는 라이브러리와 버전마다 달라요. Python 3.12는 `SSL_write`가 아니라 `SSL_write_ex`를 불렀어요. 앞의 것에만 붙였다면 아무것도 안 잡혔을 거예요.

libssl을 쓰지 않는 언어도 있어요. Go는 TLS를 언어 안의 `crypto/tls`로 직접 해요. Go로 만든 HTTPS 서버는 libssl 훅에 한 번도 걸리지 않았고, `write`에는 암호문만 지나갔어요.

자바의 기본 TLS(JSSE)도 순수 자바로 만들어져 있어요. 그래서 libssl 훅만으로는 Go나 자바 서비스의 HTTPS 내용이 보이지 않아요. Datadog 문서도 OpenSSL을 쓰는 HTTPS는 지원하고, Go의 TLS는 미리보기라고 적어요.

## 권한과 부담

eBPF 프로그램을 올리려면 권한이 커야 해요. root이거나, 리눅스 5.8부터 생긴 `CAP_BPF` 같은 권한이 있어야 해요. 일반 사용자로 `bpf()` 시스템 콜을 부르자 `Operation not permitted`가 났어요.

실험한 WSL 커널은 `unprivileged_bpf_disabled`가 2라서 일반 사용자의 `bpf()`를 막아요. 그래서 eBPF 에이전트는 대개 높은 권한으로 돌아요. 쿠버네티스라면 노드마다 특권 컨테이너로 띄워요.

부담은 이벤트마다 붙어요. 프로그램이 붙은 지점을 지날 때마다 돌기 때문이에요. 1바이트씩 100만 번 쓰는 시간을 재 봤어요.

<Figure caption="WSL(커널 6.18, 논리 CPU 16개)에서 dd로 1바이트씩 100만 번 쓴 시간이에요. 쓰기마다 세기만 해도 약 30ns, 일을 더 하면 약 80ns씩 늘었어요.">

쓰기 한 번에 수십 ns라 작아 보여요. 하지만 초당 수십만 번 지나가는 길목이면 그만큼 CPU를 써요. 그래서 모든 시스템 콜이나 모든 패킷에 붙는 프로그램은 하는 일을 줄이고, 맵에 모아 두었다가 가끔 읽어요.

## 모니터링에서는

eBPF는 SDK 계측을 없애 주는 게 아니라, 계측이 닿지 않는 곳을 메워요. 둘은 보는 높이가 달라요.

<Figure caption="SDK는 앱 안에서 뜻을 담아 기록하고, eBPF는 앱 밖에서 지나가는 것을 봐요. 계측하지 않은 서비스와 서드파티 프로그램은 eBPF로, 함수와 사용자 단위는 SDK로 봐요.">
  <EbpfVsSdk aria-label="SDK·APM 에이전트는 주문 앱과 결제 앱 안에 SDK로 들어가 함수·사용자 속성을 보고, traceparent로 서비스 사이를 이으며, 암호화와 상관없지만 앱마다 고쳐야 해요. eBPF는 앱은 그대로 두고 커널에서 지나가는 요청·연결·지연을 보지만, 암호화는 라이브러리 훅이 필요하고, 서비스 사이를 잇기 어렵고, 높은 권한이 필요해요" />
</Figure>

eBPF로 만든 지표는 화면에서 "계측하지 않은 서비스"로도 보여요. 서비스 맵에 SDK 없는 서비스가 나타나거나, 서비스마다 요청 수와 지연이 생겨요. 다만 함수 단위 트레이스와 사용자 정보는 없어요.

<Deeper>
  검사기는 프로그램이 지날 수 있는 길을 모두 따라가요. 끝없는 반복을 넣어 봤더니 `infinite loop detected at insn 27`로 거절했어요.

  같은 기록에 `processed 40 insns (limit 1000000)`도 나왔어요. 따라갈 수 있는 명령 수에 한도가 있다는 뜻이에요.

  `unprivileged_bpf_disabled`는 0, 1, 2 중 하나예요. 0은 일반 사용자도 `bpf()`를 부를 수 있고, 1과 2는 막아요. 1은 켜진 커널에서 다시 풀 수 없고, 2는 관리자가 나중에 바꿀 수 있어요.

  `CAP_BPF`와 `CAP_PERFMON`은 리눅스 5.8에서 생겼어요. 그 전에는 넓은 권한인 `CAP_SYS_ADMIN`에 들어 있었어요. 커널 소스의 설명에 따르면 추적용 프로그램을 올릴 때는 두 권한이 함께 필요해요.

  커널 자료 구조는 버전마다 달라요. BTF가 있으면 한 번 만든 프로그램이 여러 커널에서 자리를 맞춰 돌아요. 이 PC의 WSL 커널 6.18에는 `/sys/kernel/btf/vmlinux`가 있었어요.

  Datadog의 무계측 서비스 모니터링은 리눅스 커널 4.14 이상을 요구해요. 설정 예시에는 `/lib/modules`, `/usr/src`와 함께 커널 헤더를 받는 폴더, 그 자리에서 컴파일한 결과를 두는 폴더가 있어요. BTF로 못 맞출 때를 위한 거예요.

  WSL에서 실험할 때 처음에는 셸이 알려 준 PID로 걸렀다가 아무것도 안 잡혔어요. WSL 배포판은 PID 네임스페이스가 따로라, 커널이 보는 PID와 달랐어요. 프로세스 이름으로 거르자 잡혔어요.
