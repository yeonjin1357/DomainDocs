  <Point title="세 숫자로 봐요">
    초당 몇 번 읽고 썼는지(IOPS), 얼마나 많이 옮겼는지(처리량), 한 번에 얼마나 걸렸는지(지연)예요.
  </Point>
  <Point title="처리량은 횟수 × 한 번의 크기예요">
    작은 요청이 많으면 횟수가, 큰 요청이 많으면 처리량이 먼저 한계에 닿아요.
  </Point>
  <Point title="%util 100%가 꽉 찼다는 뜻은 아니에요">
    %util은 요청이 하나라도 있던 시간의 비율이에요. 여러 요청을 함께 처리하는 SSD에서는 아직 여유가 있을 수 있어요.
  </Point>
</KeyPoints>

<Analogy limit="%util은 '창구가 바빴던 시간'이에요. 요즘 SSD는 창구가 여러 개라, 한 창구가 늘 바빠도 다른 창구는 비어 있을 수 있어요.">
  캐비닛 앞의 서류 창구를 떠올려 봐요. 하루에 몇 번 서류를 꺼내 줬는지(IOPS), 서류를 몇 상자 옮겼는지(처리량), 요청부터 받기까지 얼마나 기다렸는지(지연)를 세요.
</Analogy>

## 세 숫자

| 숫자 | `iostat` 이름 | 뜻 |
| --- | --- | --- |
| IOPS | r/s, w/s | 초당 끝낸 읽기·쓰기 요청 수 |
| 처리량 | rkB/s, wkB/s | 초당 읽고 쓴 양 |
| 지연 | r_await, w_await | 요청 하나가 끝나기까지 걸린 평균 시간(ms) |
| 줄 길이 | aqu-sz | 디스크에 걸려 있던 요청 수의 평균 |
| 사용률 | %util | 요청이 하나라도 걸려 있던 시간의 비율 |

<Term term="server/iops">IOPS</Term>와 처리량은 디스크가 얼마나 일했는지, <Term term="server/io-latency">지연</Term>은 앱이 얼마나 기다렸는지를 보여 줘요. 앱 입장에서 가장 먼저 느끼는 건 지연이에요.

## 처리량은 횟수 × 한 번의 크기

같은 디스크라도 요청 하나의 크기에 따라 먼저 닿는 한계가 달라요.

그래서 처리량만 보면 작은 요청이 몰리는 DB 서버의 한계를 놓쳐요. 처리량이 4MB/초로 낮아 보여도, 디스크는 초당 횟수 한계에 닿아 있을 수 있어요.

## 지연에는 줄 선 시간도 들어가요

`iostat`의 await는 요청이 디스크에서 처리된 시간만이 아니에요. 줄에서 기다린 시간까지 더한 값이에요. 디스크가 감당하는 것보다 요청이 많이 오면 줄(aqu-sz)이 길어지고, await도 함께 커져요.

디스크를 기다리는 프로세스는 D 상태로 잠들어요. 그래서 디스크가 느려지면 CPU는 한가한데 <Term slug="server/cpu-usage">부하</Term>가 올라가요.

## %util의 함정

%util은 디스크에 요청이 하나라도 걸려 있던 시간의 비율이에요. 요청을 하나씩 차례로 처리하는 디스크라면 100%에 가까울 때 꽉 찬 거예요.

요즘 SSD나 RAID처럼 여러 요청을 한꺼번에 처리하는 장치는 달라요. 요청이 늘 하나 이상 걸려 있으면 100%가 되지만, 아직 더 받을 여유가 있을 수 있어요. 매뉴얼도 이런 장치에서는 이 숫자가 성능 한계를 보여 주지 않는다고 해요.

<Deeper>
  ### /proc/diskstats의 칸

  커널은 디스크마다 끝낸 읽기 수, 읽기에 쓴 시간(ms), 지금 처리 중인 요청 수, 입출력에 쓴 시간(ms) 같은 칸을 내놓아요. 지금 처리 중인 요청 수만 빼고 모두 늘어나기만 하는 누적값이에요.

  %util은 "입출력에 쓴 시간"의 증가분을 경과 시간으로 나눈 값이에요. 이 칸은 처리 중인 요청이 하나라도 있으면 늘어나서, 요청이 몇 개든 같은 속도로 늘어요.

  ### 합쳐진 요청

  `iostat`의 r/s, w/s는 합친 뒤의 요청 수예요. 커널은 디스크의 붙어 있는 자리를 읽는 요청 여러 개를 하나로 합치기도 해요.
</Deeper>
