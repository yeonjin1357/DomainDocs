<Situation>
  주문 서비스의 파드 하나가 재시작 횟수 47회에 상태는 CrashLoopBackOff예요. 같은 Deployment의 다른 파드도 하나둘 재시작하기 시작했어요.

  CrashLoopBackOff는 "계속 죽고 있다"는 표시일 뿐 원인이 아니에요. 마지막으로 어떻게 끝났는지부터 보고, 그 갈래를 따라 원인을 좁혀요.
</Situation>

## 1. 마지막 종료 이유를 보세요

지금 상태가 아니라 직전 실행이 어떻게 끝났는지가 실마리예요. `kubectl describe pod`의 Last State에 종료 이유(Reason)와 종료 코드(Exit Code)가 남아요.

| 종료 이유 | 뜻 | 다음에 볼 곳 |
| --- | --- | --- |
| OOMKilled | 메모리 한도를 넘어 커널이 프로세스를 끝냈어요 | 2단계 |
| Error | 앱이 0이 아닌 코드로 스스로 끝났어요 | 3단계 |
| Completed | 앱이 0으로 정상 종료했어요. 계속 도는 앱이라면 이상해요 | 3단계 |

**확인 방법**: `kubectl describe pod 파드이름`에서 Last State 칸과 Restart Count를 봐요. 상태 이름의 뜻은 <Term slug="kubernetes/pod-status">파드 상태와 재시작</Term>에 있어요.

## 2. OOMKilled라면 메모리 한도와 사용량을 견주세요

OOMKilled는 컨테이너가 메모리 한도보다 더 쓰려 해서 끝난 거예요. 쿠버네티스 문서의 예에서는 이때 종료 코드가 137이에요. 137은 흔히 128에 강제 종료 신호 번호 9를 더한 값으로 읽어요.

- **매번 같은 크기에서 끊긴다면**: 앱이 원래 그만큼 필요해요. 한도를 늘리거나 앱의 메모리 설정을 줄여요.
- **실행할수록 바닥이 높아진다면**: 메모리 누수를 의심해요.

자바라면 컨테이너 한도를 힙 크기(`-Xmx`)와 같게 잡지 않았는지 봐요. JVM은 힙 밖에서도 메모리를 써요.

자세한 건 <Term slug="apm/jvm-memory">JVM과 힙 메모리</Term>에 있어요. 한도의 뜻은 <Term slug="kubernetes/requests-and-limits">요청과 한도</Term>에서 다뤄요.

## 3. Error라면 이전 실행의 로그를 보세요

앱이 스스로 끝났다면 그 이유는 앱 로그에 있어요. 그런데 지금 컨테이너는 새로 뜬 것이라, 그냥 로그를 보면 방금 시작한 로그만 보여요.

**확인 방법**: `kubectl logs 파드이름 --previous`로 직전에 끝난 컨테이너의 로그를 봐요. 시작하자마자 죽는다면 맨 끝의 몇 줄에 원인이 있는 경우가 많아요.

흔한 원인은 이래요.

- 환경 변수나 설정 파일이 빠졌거나 틀렸어요. ConfigMap·Secret을 바꾼 뒤라면 그 변경부터 봐요.
- 시작할 때 붙어야 하는 DB나 다른 서비스에 닿지 못해 앱이 포기했어요.
- 새로 배포한 이미지에 버그가 있어요. 배포 시각과 재시작이 시작된 시각을 맞춰 봐요.

## 4. 프로브가 죽였는지 보세요

앱은 멀쩡한데 liveness 프로브가 실패해서 kubelet이 다시 시작시키는 경우도 있어요. 이때 이벤트에 프로브 실패(Unhealthy)가 남아요.

- 시작이 느린 앱이라면 liveness가 시작을 기다려 주지 않았을 수 있어요. startup 프로브나 첫 검사 지연을 둬요.
- liveness가 DB 같은 바깥 의존성까지 확인한다면, 바깥이 잠깐 느려져도 멀쩡한 파드가 다시 시작돼요.

**확인 방법**: `kubectl describe pod`의 Events에서 Unhealthy와 Killing 기록을 찾아요.
