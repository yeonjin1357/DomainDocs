## 1. 서비스가 있고 이름이 풀리는지 보세요

먼저 부르는 쪽과 같은 네임스페이스에 그 이름의 서비스가 있는지 봐요. 다른 네임스페이스라면 `pay.결제네임스페이스`처럼 네임스페이스까지 붙여 불러야 해요.

이름이 클러스터 IP로 풀리지 않는다면 DNS 쪽이에요. 다른 서비스 이름도 안 풀린다면 클러스터 DNS 자체를 봐요. 이름 풀이는 <Term slug="network/dns">DNS</Term>와 <Term slug="kubernetes/services-and-ingress">서비스와 인그레스</Term>에서 다뤄요.

**확인 방법**: 부르는 쪽 파드 안에서 `nslookup pay`로 이름이 풀리는지 봐요.

## 2. 서비스가 파드를 잡았는지 보세요

이름은 풀리는데 연결이 안 된다면, 서비스 뒤에 실제 파드가 잡혀 있는지 봐요. 서비스가 고른 파드의 IP는 EndpointSlice에 적혀요.

<Figure caption="서비스 셀렉터는 app=pay인데, 파드 레이블은 app=payment예요. 값이 조금만 달라도 대상 파드가 0개가 돼요.">
  <Compare
    columns={['서비스 셀렉터', '파드 레이블']}
    rows={[
      { label: '값', values: ['app=pay', 'app=payment'] },

목록이 비어 있다면 두 가지를 봐요.

- **셀렉터와 레이블이 다르다면**: 쿠버네티스 문서도 오타를 가장 흔한 실수로 꼽아요. 서비스의 셀렉터와 파드의 레이블을 글자 그대로 견줘요.
- **파드가 준비되지 않았다면**: readiness 프로브가 실패한 파드는 대상에서 빠져요. 파드의 READY 칸을 봐요.

**확인 방법**: 아래 명령으로 대상 파드의 IP 목록을 봐요. ENDPOINTS가 비어 있다면 위 두 가지를 봐요.

```text
kubectl get endpointslices \
  -l kubernetes.io/service-name=pay
```

## 3. 포트가 맞는지 보세요

서비스의 port는 서비스가 받는 포트이고, targetPort는 파드로 넘길 때 쓰는 포트예요. targetPort가 파드에서 앱이 실제로 듣는 포트와 다르면, 요청이 파드에 닿아도 받을 곳이 없어요.

**확인 방법**: `kubectl get service pay -o yaml`에서 port와 targetPort를 봐요. 이 값을 파드의 containerPort, 앱 설정의 포트와 견줘요. 이름 붙은 포트를 쓴다면 파드에도 같은 이름의 포트가 있는지 봐요.

## 4. 그래도 안 되면 길을 막는 규칙을 보세요

여기까지 맞는데도 안 된다면, 길 위의 규칙과 구성 요소를 봐요.

- 네트워크 정책(NetworkPolicy)이 대상 파드로 들어오는 트래픽을 막고 있을 수 있어요.
- 노드마다 서비스 규칙을 까는 kube-proxy가 멈췄을 수 있어요.

**확인 방법**: 대상 파드 IP와 포트로 직접 요청해 봐요. 직접은 되고 서비스 IP로는 안 된다면, 서비스 규칙(kube-proxy) 쪽이에요.
