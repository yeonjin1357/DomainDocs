<KeyPoints>
  <Point title="할당량은 요청 합계를 막아요">
    ResourceQuota는 한 네임스페이스에 있는 파드들의 요청·한도 합계와 객체 수를 제한해요. 넘으면 만들기 요청이 거부돼요.
  </Point>
  <Point title="배포는 성공해도 파드가 모자라요">
    거부는 파드를 만들 때 일어나요. 그래서 배포 명령은 성공하고, 파드만 원하는 수보다 적게 떠요.
  </Point>
  <Point title="LimitRange가 빈칸을 채워요">
    요청·한도를 안 적은 컨테이너에 기본값을 넣고, 파드 하나가 정한 범위를 벗어나지 않게 막아요.
  </Point>
</KeyPoints>

<Analogy limit="카드 한도는 실제로 쓴 금액을 세지만, 할당량은 실제 사용량이 아니라 파드에 적어 둔 요청·한도의 합계를 세요.">
  부서마다 법인카드 월 한도가 있고, 한 번에 결제할 수 있는 금액도 정해진 것과 같아요. 월 한도가 ResourceQuota, 한 번 결제 한도가 LimitRange예요.
</Analogy>

## 네임스페이스마다 합계를 정해요

<Term term="kubernetes/k8s-namespace">네임스페이스</Term>는 한 클러스터를 팀이나 환경별로 나눈 이름 공간이에요. 한 팀이 클러스터 자원을 다 차지하지 않게, 관리자는 네임스페이스마다 <Term term="kubernetes/resource-quota">ResourceQuota</Term>를 둬요.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a
  namespace: team-a
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.memory: 16Gi
    pods: "20"
```

이 설정에서 `team-a` 네임스페이스의 파드는 CPU 요청을 모두 더해 4코어까지, 메모리 요청은 8Gi까지 쓸 수 있어요. 파드는 20개까지 만들 수 있어요.

| 항목 | 막는 것 |
| --- | --- |
| `requests.cpu`, `requests.memory` | 파드들의 CPU·메모리 요청 합계 |
| `limits.cpu`, `limits.memory` | 파드들의 CPU·메모리 한도 합계 |
| `pods` | 파드 수 |
| `requests.storage` | PVC들의 저장소 요청 합계 |
| `count/deployments.apps` 같은 `count/…` | 그 종류의 객체 수 |

합계에는 끝난 파드가 빠져요. 상태가 Succeeded나 Failed인 파드는 세지 않아요.

## 실제 사용량이 아니라 적어 둔 값을 세요

할당량이 세는 건 파드에 적어 둔 요청과 한도예요. 원리는 <Term slug="kubernetes/requests-and-limits">요청과 한도</Term>와 같아요.

그래서 여기에 요청 1.5코어짜리 파드를 더 만들면 거부돼요. 요청 합계가 4.5코어가 되기 때문이에요. 노드가 한가해 보여도 할당량에는 자리가 없을 수 있어요.

## 넘으면 만들 때 거부해요

새 객체를 만들어 할당량을 넘게 되면, API 서버가 그 요청을 `403 Forbidden`으로 거부해요. 메시지에 무엇을 얼마나 요청했고, 얼마를 쓰고 있고, 한도가 얼마인지 나와요.

```text
pods "web-7d9-x2k" is forbidden:
exceeded quota: team-a,
requested: requests.memory=2Gi,
used: requests.memory=7Gi,
limited: requests.memory=8Gi
```

파드를 직접 만들 때는 이 오류가 바로 보여요. 하지만 보통은 Deployment를 만들고, 파드는 컨트롤러가 대신 만들어요.

이때 거부된 파드는 아예 만들어지지 않아요. Pending 파드도 남지 않아서, 파드 목록만 보면 이유가 안 보여요. 흔적은 ReplicaSet의 FailedCreate 이벤트에 `Error creating: … exceeded quota`로 남아요.

할당량을 바꿔도 이미 만든 객체에는 영향이 없어요. 할당량을 줄여도 떠 있는 파드는 그대로이고, 새로 만들 때부터 걸려요.

## 요청을 안 적으면 거부될 수 있어요

할당량에 CPU나 메모리 항목이 있으면, 새 파드는 그 자원의 요청이나 한도를 적어야 해요. 안 적으면 `must specify` 메시지와 함께 만들기가 거부될 수 있어요.

매번 적기 번거로우니, 보통 LimitRange로 기본값을 채워요.

## LimitRange: 파드 하나의 범위와 기본값

<Term term="kubernetes/limit-range">LimitRange</Term>는 네임스페이스 안 컨테이너 하나, 파드 하나, PVC 하나가 가질 수 있는 범위를 정해요. 요청·한도를 안 적은 컨테이너에는 기본값을 넣어 줘요.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: 250m
        memory: 256Mi
      default:
        cpu: "1"
        memory: 512Mi
      max:
        memory: 2Gi
```

| 항목 | 하는 일 |
| --- | --- |
| `defaultRequest` | 요청을 안 적은 컨테이너에 넣을 요청값 |
| `default` | 한도를 안 적은 컨테이너에 넣을 한도값 |
| `min`, `max` | 적은 값이 이 범위를 벗어나면 거부 |

LimitRange도 파드를 만들 때만 검사해요. 새로 만들거나 고쳐도, 이미 떠 있는 파드는 그대로예요.

기본값끼리 맞는지는 검사하지 않아요. 위 설정에서 CPU 요청만 `1500m`으로 적으면, 기본 한도 `1`이 붙어 요청이 한도보다 커져요. 이 파드는 `must be less than or equal to cpu limit` 오류로 만들어지지 않아요.

할당량 화면은 사용률이 아니라 '적어 둔 값의 합계 대 할당량'을 보여 줘요. 이 값이 거의 찼다면, 다음 배포나 자동 확장이 막힐 수 있어요.

롤링 업데이트는 바꿔 끼우는 동안 파드를 잠깐 더 띄워요. 할당량이 꽉 차 있으면 그 새 파드를 못 만들어 배포가 멈춰요. <Term slug="kubernetes/hpa-not-scaling">HPA가 파드를 늘리지 않을 때</Term>도 할당량이 원인일 수 있어요.

<Deeper>
  ### 저장소 할당량

  `requests.storage`는 PVC 요청 합계를, `persistentvolumeclaims`는 PVC 개수를 막아요. `gold.storageclass.storage.k8s.io/`처럼 앞에 등급 이름을 붙이면, 그 등급만 따로 막아요.

  ### 할당량의 범위

  할당량에 범위(scope)를 붙이면 일부 파드에만 걸 수 있어요. 예를 들어 BestEffort 파드에만, 또는 특정 우선순위 클래스의 파드에만 거는 식이에요.

  ### LimitRange가 둘 이상이면

  한 네임스페이스에 LimitRange가 둘 이상 있으면, 어느 기본값이 붙을지 정해져 있지 않아요. 기본값을 주는 LimitRange는 하나만 두는 게 안전해요.
</Deeper>
