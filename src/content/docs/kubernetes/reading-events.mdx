<Situation>
  어젯밤 2시에 결제 서비스 파드들이 줄줄이 다시 시작됐다는 걸 아침에 알았어요. `kubectl describe`로 이벤트를 보려 했는데, 이벤트가 하나도 없어요.

  이벤트는 쿠버네티스가 "무슨 일이 왜 일어났는지"를 남기는 짧은 기록이에요. 무엇을 담는지, 언제 사라지는지 알면 장애 원인을 훨씬 빨리 찾아요.
</Situation>

## 1. 이벤트가 무엇을 담는지 알아 두세요

<Term term="kubernetes/k8s-event">이벤트</Term>는 클러스터 어딘가에서 일어난 일을 알리는 기록이에요. 파드가 노드에 놓였다, 이미지를 받았다, 프로브가 실패했다 같은 일이 하나씩 남아요.

| 칸 | 뜻 | 예 |
| --- | --- | --- |
| 종류(type) | 정상(Normal)인지 경고(Warning)인지 | Warning |
| 이유(reason) | 왜 일어났는지 짧은 이름 | FailedScheduling |
| 대상 | 어느 객체에 대한 일인지 | Pod/payment-7d9f |
| 메시지 | 사람이 읽는 설명 | 0/42 nodes available |

쿠버네티스 문서는 이벤트를 "참고용, 최선을 다할 뿐인 보조 자료"로 다루라고 해요. 같은 이유의 이벤트가 늘 같은 원인에서 나온다고 믿지 말라는 뜻이에요.

## 2. 경고만 골라 보세요

이벤트 대부분은 정상 기록이에요. 원인을 찾을 때는 Warning만 골라, 시간 순서로 봐요.

**확인 방법**: `kubectl events --types=Warning`으로 경고만 봐요. 특정 객체만 보려면 `kubectl events --for pod/파드이름`을 써요. 파드 하나라면 `kubectl describe pod`의 Events 칸에도 나와요.

## 3. 이유로 갈래를 정하세요

자주 보는 경고 이유와 다음에 볼 글이에요.

| 이유 | 뜻 | 다음에 볼 곳 |
| --- | --- | --- |
| FailedScheduling | 파드를 놓을 노드를 못 찾았어요 | <Term slug="kubernetes/pod-pending">파드가 Pending에 머물 때</Term> |
| BackOff | 컨테이너가 죽어 다시 띄우기를 미루고 있어요 | <Term slug="kubernetes/pod-restarting">파드가 계속 재시작될 때</Term> |
| Unhealthy | 프로브가 실패했어요 | <Term slug="kubernetes/pod-status">파드 상태와 재시작</Term> |
| FailedMount | 볼륨을 붙이지 못했어요 | <Term slug="kubernetes/config-and-storage">설정과 저장소</Term> |
| Failed(이미지) | 이미지를 받지 못했어요 | 이미지 이름·태그와 인증 정보 |

같은 시각에 여러 객체에서 같은 이유가 쏟아진다면, 파드 하나보다 공통 원인을 먼저 봐요. 예를 들어 여러 노드의 파드가 동시에 Unhealthy라면 그 파드들이 함께 기대는 DB나 네트워크를 봐요.

## 4. 사라지기 전에 모아 두세요

이벤트는 오래 남지 않아요. API 서버의 `--event-ttl` 기본값은 1시간이라, 1시간이 지난 이벤트는 지워져요. 그래서 새벽 장애의 이벤트를 아침에 찾으면 이미 없어요.
