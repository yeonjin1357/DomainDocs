<Situation>
  새 버전을 배포했는데 20분째 끝나지 않아요. 파드 4개 중 새 버전은 1개뿐이고, 그마저 준비되지 않았어요. 옛 버전 파드 3개가 아직 요청을 받고 있어요.

  롤링 업데이트는 새 파드가 준비돼야 다음으로 넘어가요. 그래서 새 파드가 준비되지 못하면 배포가 그 자리에 멈춰요. 서비스는 아직 옛 버전으로 버티고 있어요.
</Situation>

<FirstLook>
  <Item title="멈췄다고 표시됐나">Progressing 조건이 False인지 봐요.</Item>
  <Item title="새 파드는 어떤 상태인가">Pending, 재시작, 준비 실패 중 무엇인지 봐요.</Item>
  <Item title="되돌릴지 정하기">급하면 이전 버전으로 돌려요.</Item>
</FirstLook>

## 1. 멈췄다고 표시됐는지 보세요

Deployment는 정해 둔 시간(`progressDeadlineSeconds`, 기본 600초) 동안 진전이 없으면 멈췄다고 표시해요. 상태 조건 Progressing이 False가 되고, 이유가 ProgressDeadlineExceeded로 바뀌어요.

쿠버네티스는 멈춘 배포에 대해 이 표시 말고는 아무것도 하지 않아요. 저절로 되돌리지도 않아요. 컨트롤러는 계속 다시 시도할 뿐이에요.

**확인 방법**: `kubectl rollout status deployment/이름`으로 진행 상황을 봐요. `kubectl describe deployment 이름`의 Conditions에서 Progressing의 값과 이유를 봐요.

## 2. 새 파드가 왜 준비되지 못하는지 보세요

쿠버네티스 문서는 배포가 멈추는 흔한 이유를 이렇게 꼽아요. 새 파드의 상태가 어느 쪽인지 보면 갈래가 정해져요.

| 새 파드 상태 | 흔한 이유 | 다음에 볼 곳 |
| --- | --- | --- |
| Pending | 자원·할당량이 모자라요 | <Term slug="kubernetes/pod-pending">파드가 Pending에 머물 때</Term> |
| ImagePullBackOff | 이미지를 받지 못해요 | 이미지 이름·태그, 저장소 인증 |
| CrashLoopBackOff | 새 버전이 시작하자마자 죽어요 | <Term slug="kubernetes/pod-restarting">파드가 계속 재시작될 때</Term> |
| Running인데 준비 안 됨 | readiness 프로브가 실패해요 | 4단계 |

권한이 모자라거나(서비스 계정), 네임스페이스의 자원 범위 설정에 걸리는 경우도 있어요.

## 3. 급하면 먼저 되돌리세요

원인을 찾는 동안 사용자 영향을 줄이고 싶다면 이전 버전으로 되돌려요. 되돌리기도 롤링 업데이트라서, 준비된 옛 파드를 늘리고 새 파드를 줄여요.

**확인 방법**: `kubectl rollout undo deployment/이름`으로 바로 이전 버전으로 돌려요. 되돌린 뒤 원인을 찾아 고친 버전을 다시 배포해요.

## 4. 준비 실패라면 readiness 프로브를 보세요

새 파드가 Running인데 READY가 0/1이라면, readiness 프로브가 실패하고 있어요. 이 파드는 서비스 요청을 받지 않고, Deployment도 다음 파드로 넘어가지 않아요.

- 새 버전의 상태 확인 경로나 포트가 바뀌었는데 프로브 설정은 그대로예요.
- 새 버전이 시작할 때 붙어야 하는 DB나 설정을 찾지 못해요.
- 시작이 오래 걸리는데 프로브가 너무 일찍, 너무 짧게 확인해요.

**확인 방법**: `kubectl describe pod 새파드`의 Events에서 Unhealthy 기록과 프로브 실패 메시지를 봐요.
