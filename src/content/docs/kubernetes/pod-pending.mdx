## 1. 스케줄러가 남긴 이유를 읽으세요

스케줄러는 파드를 놓을 노드를 찾지 못할 때마다 FailedScheduling 이벤트를 남겨요. 메시지에 노드 몇 개 중 몇 개가 왜 안 되는지 적혀 있어요.

```text
Type:    Warning
Reason:  FailedScheduling
From:    default-scheduler
Message: 0/42 nodes available:
         insufficient cpu
```

쿠버네티스 문서의 예시예요. 노드 42개 모두 이 파드의 CPU 요청을 받아 줄 자리가 없다는 뜻이에요.

**확인 방법**: `kubectl describe pod 파드이름`의 Events를 봐요. 메시지에 나온 이유에 따라 아래 단계를 골라요.

## 2. 자리가 없다면 요청 합계를 보세요

메시지가 insufficient cpu나 insufficient memory라면, 노드마다 요청 합계에 남은 자리가 없는 거예요. 스케줄러는 실제 사용량이 아니라 요청으로 자리를 따져요. 그래서 노드가 한가해 보여도 파드가 못 들어가요.

원리는 <Term slug="kubernetes/requests-and-limits">요청과 한도</Term>에 있어요.

쿠버네티스 문서가 권하는 길은 세 가지예요.

- 필요 없는 파드를 지워 자리를 만들어요.
- 파드의 요청을 실제 사용량에 맞게 줄여요.
- 노드를 늘려요. 노드 자동 확장이 켜져 있다면 새 노드가 붙을 때까지 기다려요.

**확인 방법**: `kubectl describe node 노드이름`의 Allocated resources에서 노드마다 요청 합계를 봐요.

## 3. 자리는 있는데 못 간다면 조건을 보세요

자리가 남는데도 못 간다면, 파드와 노드의 조건이 맞지 않는 거예요.

- **taint**: 노드에 taint가 있으면, 그에 맞는 toleration이 없는 파드는 그 노드에 놓이지 않아요. 전용 노드나 장애가 난 노드에 흔해요.
- **nodeSelector와 affinity**: 파드가 특정 레이블의 노드만 원하면, 그 레이블이 있는 노드에만 놓여요. 레이블 오타 하나로 갈 곳이 없어지기도 해요.
- **hostPort**: 파드가 노드의 포트를 직접 쓰면, 그 포트가 빈 노드에만 놓일 수 있어요.

**확인 방법**: `kubectl describe node`의 Taints와 Labels를 봐요. 그걸 파드 명세의 tolerations, nodeSelector와 견줘요.

## 4. 저장소를 기다리는지 보세요

파드가 PVC를 쓰는데 그 PVC가 아직 PV에 묶이지 않았다면, 파드도 기다려요. 쿠버네티스 문서는 맞는 볼륨이 없으면 PVC가 계속 묶이지 않은 채로 남는다고 해요. 예를 들어 100Gi를 요청했는데 50Gi짜리 PV만 있으면 묶이지 않아요.

**확인 방법**: `kubectl get pvc`에서 STATUS가 Bound가 아니라 Pending인지 봐요. 저장소는 <Term slug="kubernetes/config-and-storage">설정과 저장소</Term>에서 다뤄요.

## 노드에는 놓였는데 시작을 못 한다면

노드가 정해졌는데도 컨테이너가 Waiting이라면, 쿠버네티스 문서는 가장 흔한 원인으로 이미지 받기 실패를 꼽아요. 이미지 이름과 태그가 맞는지, 레지스트리에 이미지가 올라가 있는지, 사설 레지스트리라면 인증 정보가 있는지 봐요.
