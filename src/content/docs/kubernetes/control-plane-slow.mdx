## 1. API 서버 응답시간을 요청 종류별로 보세요

API 서버는 요청마다 걸린 시간을 히스토그램으로 남겨요. 요청 종류(`verb`)와 자원(`resource`)으로 나눠 보면, 어떤 요청이 느린지 좁혀져요.

```promql
histogram_quantile(0.99,
  sum by (verb, le) (rate(
    apiserver_request_duration_seconds_bucket[5m]
  ))
)
```

GET은 빠른데 LIST만 느리다면, 누군가 큰 목록을 자주 읽는 거예요. 클러스터의 파드 수천 개를 몇 초마다 통째로 LIST하는 에이전트나 스크립트가 흔한 원인이에요.

**확인 방법**: `apiserver_request_total`을 `verb`, `resource`로 나눠, 요청 수가 갑자기 는 쪽을 찾아요. API 서버의 감사 로그(audit log)가 켜져 있다면 사용자 이름으로 누가 불렀는지 봐요.

## 2. 429 거절이 늘었는지 보세요

API 서버는 한꺼번에 받을 수 있는 요청 수에 한도가 있어요. APF(API Priority and Fairness)가 요청을 줄 세워요. 줄까지 넘치면 HTTP 429(Too Many Requests)로 거절해요.

**확인 방법**: `apiserver_flowcontrol_rejected_requests_total`이 늘었는지 봐요. 늘었다면 1단계에서 찾은, 많이 부르는 쪽을 줄여요. 같은 정보를 계속 받아야 한다면 LIST를 되풀이하지 말고 watch로 바뀐 것만 받게 해요.

## 3. 웹훅이 느린지 보세요

API 서버는 객체를 만들거나 바꾸기 전에 어드미션 웹훅(admission webhook)에 물어볼 수 있어요. 정책 검사나 기본값 넣기 같은 일을 하는 바깥 서버예요. 웹훅이 느리면 그 객체를 바꾸는 요청이 모두 함께 느려져요.

**확인 방법**: 웹훅마다 걸린 시간은 `apiserver_admission_webhook_admission_duration_seconds`에 있어요. 웹훅 이름(`name`)으로 나눠 봐요. 웹훅 서버가 죽었다면, 설정의 실패 정책(failurePolicy)에 따라 요청이 거절되거나 검사 없이 지나가요.

## 4. etcd의 디스크 쓰기가 느린지 보세요

etcd는 모든 쓰기를 디스크에 확정한 뒤에 응답해요. 그래서 디스크가 느리면 API 서버의 쓰기가 모두 느려져요. etcd 문서는 WAL fsync의 p99가 10ms 아래, 백엔드 커밋의 p99가 25ms 아래여야 디스크가 충분히 빠르다고 해요.

**확인 방법**: 두 값의 p99를 봐요. 지표 이름은 이래요.

- `etcd_disk_wal_fsync_duration_seconds`: WAL을 디스크에 확정하는 시간이에요.
- `etcd_disk_backend_commit_duration_seconds`: 백엔드에 커밋하는 시간이에요.

느리다면 etcd에 전용 디스크나 더 빠른 디스크를 줘요. `etcd_server_has_leader`가 0이면 리더가 없어 쓰기를 못 받는 상태예요.

## 5. etcd 크기가 한도에 가까운지 보세요

etcd의 기본 저장 한도는 2GiB예요. 한도를 넘으면 클러스터 전체에 NOSPACE 경보를 띄우고, 읽기와 지우기만 받아요. 그때부터 API 서버에는 "database space exceeded" 에러가 나고, 새 객체를 못 만들어요.

**확인 방법**: `etcd_mvcc_db_total_size_in_bytes`를 한도와 견줘 봐요. 지운 데이터의 자리는 조각 모으기(defragment)를 해야 디스크에서 돌아와요. 이벤트나 오래된 Job처럼 쌓이기만 하는 객체가 많지 않은지도 봐요.
