  </Point>
  <Point title="metrics-server는 저장용이 아니에요">

  </Point>

<Analogy limit="배의 선원은 사람이 직접 세지만, kubelet은 리눅스가 컨테이너마다 묶어 둔 cgroup의 값을 읽어요. 그래서 운영체제마다 세는 방식이 조금씩 달라요.">
  항구에 빗대면, 배마다 있는 선원(kubelet)은 컨테이너가 실제로 쓴 연료를 재요. 관제탑의 장부를 베끼는 사람(kube-state-metrics)은 배를 몇 척 띄우기로 했는지, 몇 번 다시 띄웠는지를 적어요.
</Analogy>

## 세 출처

| 출처 | 무엇을 | 예 |
| --- | --- | --- |
| kubelet(cAdvisor) | 컨테이너가 쓴 CPU·메모리·네트워크 | `container_cpu_usage_seconds_total` |
| kube-state-metrics | API 서버에 적힌 객체의 상태 | `kube_pod_status_phase` |
| metrics-server | 자동 확장용 최근 사용량 | `kubectl top`, HPA |

사용량을 재는 곳은 노드마다 있는 kubelet이에요. kubelet 안의 cAdvisor가 리눅스 cgroup에서 컨테이너별 값을 읽어요. kubelet은 이 값을 `/metrics/cadvisor`와 `/metrics/resource`로 내보내요.

kube-state-metrics는 API 서버를 지켜보며 객체의 상태를 지표로 바꿔요. 원하는 복제 수, 실제로 준비된 수, 파드의 단계(phase), 재시작 수, 요청과 한도 같은 값이에요. 노드의 자원 사용량은 재지 않아요.

## 사용량: 메모리는 working set

cAdvisor는 메모리를 여러 이름으로 내요. `container_memory_usage_bytes`는 쓰는 모든 메모리를 세서 파일 캐시까지 들어가요. `container_memory_working_set_bytes`는 쉽게 비울 수 없는 메모리에 가까운 값이에요.

쿠버네티스 문서는 자원 지표의 메모리를 working set으로 보고한다고 해요. `kubectl top`과 자동 확장이 이 값을 써요. 그래서 메모리 화면과 알림도 working set으로 맞춰야 서로 같은 숫자를 봐요.

## 사용량과 요청을 함께 보기

사용량만으로는 많은지 적은지 알 수 없어요. 파드가 잡아 둔 <Term term="kubernetes/resource-request">요청</Term>과 견줘야 해요. 먼저 아래 식으로 파드마다 메모리 사용량을 더해요.

```text
sum by (namespace, pod) (
container_memory_working_set_bytes
  {image!=""}
)
```

요청은 kube-state-metrics의 `kube_pod_container_resource_requests`에 있어요. `resource="memory"`인 줄을 같은 방식으로 파드마다 더하고, 위 값을 이 값으로 나눠요.

그러면 요청 대비 사용률이 나와요. 1에 가까울수록 요청만큼 다 쓰고 있어요.

`image!=""`는 이미지가 없는 줄을 빼요. cAdvisor 지표에는 컨테이너 줄 말고도 파드 전체를 합친 줄 같은 것이 함께 있어서, 거르지 않고 더하면 두 번 세요. 널리 쓰는 kubernetes-mixin 규칙도 이렇게 걸러요.

## 모니터링에서는

모니터링 제품이 쿠버네티스를 보려면 두 곳을 모두 모아야 해요. 노드마다 kubelet에서 사용량을, kube-state-metrics 하나에서 객체의 상태를 가져와요.

둘 다 권한이 있어야 읽혀서, 수집기에 맞는 역할을 줘야 해요. 역할은 <Term slug="kubernetes/rbac">권한과 서비스 계정</Term>에서 다뤘어요.

파드가 왜 다시 시작했는지, 왜 Pending인지는 사용량이 아니라 상태 지표와 이벤트에서 찾아요. 읽는 법은 <Term slug="kubernetes/pod-status">파드 상태와 재시작</Term>에 있어요.

</Checkpoints>

<Deeper>
  ### working set도 근삿값이에요

  쿠버네티스 문서는 working set을 '압박이 와도 비울 수 없는 메모리'에 가까운 값이라고 설명해요. 다만 운영체제마다 계산이 다르고 어림을 많이 쓰며, 보통 파일 캐시 일부도 들어간다고 해요.

  ### 요청 지표는 스케줄러 쪽이 더 정확해요

  kube-state-metrics 문서는 요청 지표로 kube-scheduler가 내는 `kube_pod_resource_request`를 권해요. 자기 `kube_pod_container_resource_requests`보다 더 정확하다고 해요.

  ### kube-state-metrics는 값을 가공하지 않아요

  kube-state-metrics는 API 서버에 적힌 값을 거의 그대로 내놓아요. 그래서 `kubectl`이 보여 주는 요약 상태와 다를 수 있어요. 예를 들어 파드의 단계와 컨테이너의 대기 이유(CrashLoopBackOff)는 서로 다른 지표예요.
</Deeper>
