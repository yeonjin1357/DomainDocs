## 워크로드가 하는 일

<Term term="kubernetes/workload">워크로드</Term>는 파드보다 한 단계 위에서, 파드를 어떻게 몇 개 띄울지 적어 둔 객체예요. 파드의 설계도(파드 템플릿)와 원하는 개수 같은 걸 적어요. 그러면 컨트롤 플레인이 그 내용대로 파드를 대신 만들고 관리해요.

파드가 죽거나 노드가 사라지면, 워크로드가 원하는 개수에 맞춰 새 파드를 다시 띄워요. 그래서 운영 앱은 파드를 직접 만들지 않고 워크로드로 만들어요.

## 일에 맞는 다섯 가지

| 워크로드 | 이럴 때 써요 | 예 |
| --- | --- | --- |
| Deployment | 파드끼리 바꿔 써도 되는, 상태 없는 앱 | 웹 서버, API 서버 |
| StatefulSet | 파드마다 고유한 이름과 저장소가 필요한 앱 | 데이터베이스, 메시지 큐 |
| DaemonSet | 노드마다 하나씩 돌아야 하는 것 | 로그 수집, 노드 모니터링 에이전트 |
| Job | 끝까지 돌고 멈추는 한 번짜리 일 | 데이터 이관, 일괄 처리 |
| CronJob | 정해진 일정마다 반복하는 일 | 백업, 리포트 만들기 |

## Deployment와 ReplicaSet

가장 흔한 워크로드는 <Term term="kubernetes/deployment">Deployment</Term>예요. Deployment는 직접 파드를 만들지 않고, 그 아래의 ReplicaSet을 만들어요. ReplicaSet은 정해 둔 개수의 파드가 언제나 떠 있도록 지키는 일만 해요.

그럼 Deployment는 왜 따로 있을까요? 버전을 바꿀 때 쓰기 위해서예요. 새 이미지로 바꾸면 Deployment가 새 ReplicaSet을 만들고, 새 쪽은 늘리고 옛 쪽은 줄여요.

## 롤링 업데이트

이렇게 조금씩 바꿔 끼우는 방식을 <Term term="kubernetes/rolling-update">롤링 업데이트</Term>라고 해요. 기본 설정에서는 원하는 개수의 75% 이상이 늘 떠 있게 하고, 125%를 넘게 띄우지 않아요.

새 버전 파드가 준비되지 않으면, Deployment는 정해 둔 범위를 넘어서까지 옛 파드를 내리지 않아요. 그래서 잘못된 버전을 배포해도 앱 전체가 한꺼번에 멈추지는 않아요. 문제가 있으면 이전 버전으로 되돌릴 수도 있어요.

## 노드마다 하나: DaemonSet

<Term term="kubernetes/daemonset">DaemonSet</Term>은 모든 노드(또는 고른 노드)에 파드를 하나씩 띄워요. 노드가 클러스터에 들어오면 그 노드에도 파드가 생기고, 노드가 빠지면 그 파드도 정리돼요.

그래서 노드마다 꼭 하나씩 있어야 하는 일에 써요. 노드의 로그를 모으는 수집기나, 노드를 재는 모니터링 에이전트가 대표적이에요.

## 이름이 고정된 파드: StatefulSet

<Term term="kubernetes/statefulset">StatefulSet</Term>은 파드마다 고유한 정체성이 필요할 때 써요. Deployment의 파드는 서로 바꿔 써도 되지만, 데이터베이스는 파드마다 자기 데이터가 달라요.

StatefulSet의 파드는 `db-0`, `db-1`처럼 번호가 붙은 이름을 받아요. 파드가 다시 떠도 같은 이름과 같은 저장소를 이어받아요. 기본 설정에서는 띄우고 늘릴 때도 번호 순서대로 하나씩 해요.

## 끝나는 일: Job과 CronJob

<Term term="kubernetes/job">Job</Term>은 끝까지 돌고 멈추는 일을 맡아요. 정해 둔 개수의 파드가 성공할 때까지 파드를 다시 실행해요. 기본 설정에서는 6번까지 다시 시도한 뒤 실패로 봐요.

CronJob은 정해진 일정마다 Job을 만들어요. 리눅스의 crontab 한 줄과 같아서, "매일 새벽 2시에 백업"처럼 적어요.

쿠버네티스 화면은 워크로드마다 원하는 파드 수와 실제로 준비된 파드 수를 함께 보여 줘요. 두 숫자가 계속 다르면, 어떤 파드가 뜨지 못하고 있는 거예요.

파드는 자주 바뀌니까, 문제를 볼 때도 워크로드 단위로 먼저 봐요. 같은 워크로드의 파드가 모두 아픈지, 한두 개만 아픈지가 첫 갈림길이에요.

<Checkpoints>
  <Check>롤링 업데이트 중에 파드 수가 원하는 수와 잠깐 다르다고 알림이 울린다면 다시 보세요. 바꿔 끼우는 동안 잠깐 많거나 적은 건 정상이에요.</Check>
  <Check>DaemonSet 파드 수가 노드 수보다 적다면 확인해 보세요. 일부 노드만 고른 설정일 수도, 어떤 노드에서 파드가 뜨지 못한 것일 수도 있어요.</Check>
  <Check>데이터베이스를 Deployment로 띄웠다면 다시 보세요. 파드가 다시 뜰 때 이름과 저장소가 이어지지 않을 수 있어요.</Check>
  <Check>CronJob이 정상이라는 이유로 일도 성공했다고 판단했다면 다시 보세요. 일정마다 만들어진 Job이 성공했는지는 따로 봐야 해요.</Check>
</Checkpoints>

<Deeper>
  ### Deployment가 지키는 범위

  쿠버네티스 문서는 기본값을 "25% max unavailable, 25% max surge"로 설명해요. 원하는 수의 25%까지는 잠깐 모자라도 되고, 25%까지는 더 띄워도 된다는 뜻이에요.

  ### Job의 재시도 횟수

  Job이 실패로 보기 전까지 다시 시도하는 횟수는 `.spec.backoffLimit`으로 정해요. 적지 않으면 6이에요.
</Deeper>
