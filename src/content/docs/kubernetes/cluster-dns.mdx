  </Point>

  </Point>
  <Point title="바깥 이름은 질의가 여러 번 나가요">

  </Point>
</KeyPoints>

## 파드의 DNS 설정

파드 안의 `/etc/resolv.conf`는 kubelet이 만들어 넣어요. `shop` 네임스페이스의 파드라면 대략 이렇게 생겨요.

| 줄 | 값 | 뜻 |
| --- | --- | --- |
| `nameserver` | `10.96.0.10` | 물어볼 DNS 서버. 클러스터 DNS 서비스의 IP예요 |
| `search` | `shop.svc.cluster.local` 외 2개 | 짧은 이름에 차례로 붙여 볼 도메인 |
| `options` | `ndots:5` | 점이 5개보다 적으면 검색 도메인부터 붙여 봐요 |

검색 도메인의 첫째는 자기 네임스페이스의 `shop.svc.cluster.local`이에요. 그다음이 `svc.cluster.local`, 마지막이 `cluster.local`이에요. `cluster.local`은 클러스터 도메인의 흔한 기본값이에요.

`nameserver`가 가리키는 건 클러스터 DNS 서비스예요. 요즘 클러스터는 대부분 <Term term="kubernetes/coredns">CoreDNS</Term>를 쓰지만, 서비스 이름은 예전 이름 그대로 `kube-system`의 `kube-dns`예요.

## 서비스 이름을 찾는 순서

<Term slug="kubernetes/services-and-ingress">서비스</Term>는 `서비스.네임스페이스.svc.cluster.local` 꼴의 이름을 받아요. 같은 네임스페이스라면 짧은 이름만 써도 돼요.

`shop` 네임스페이스의 파드가 `pay`를 찾으면, 리졸버는 첫 검색 도메인을 붙여 `pay.shop.svc.cluster.local`을 물어요. 여기서 답을 받으면 바로 끝나요.

다른 네임스페이스의 서비스는 짧은 이름으로 못 찾아요. `billing` 네임스페이스의 `pay`라면 `pay.billing`처럼 네임스페이스까지 적어요.

## 바깥 이름은 왜 여러 번 묻나요

`options ndots:5`는 이름에 점이 5개보다 적으면 검색 도메인부터 붙여 보라는 뜻이에요. 리눅스 기본값은 1인데, 쿠버네티스 파드는 5로 받아요. 그래서 `pay.billing`처럼 점이 있는 줄인 이름도 검색 도메인을 붙여 풀려요.

그런데 `api.example.com`도 점이 2개라 5보다 적어요. 그래서 바깥 이름인데도 검색 도메인을 차례로 붙여 본 뒤에야 원래 이름을 물어요.

1. `api.example.com.shop.svc.cluster.local`: 없다는 답이 와요.
2. `api.example.com.svc.cluster.local`: 없다는 답이 와요.
3. `api.example.com.cluster.local`: 없다는 답이 와요.
4. `api.example.com`: 그제야 주소가 와요.

이름 끝에 점을 붙이면 '이미 완전한 이름'이라는 뜻이라, 검색 도메인을 붙이지 않아요. 바깥 API를 자주 부르는 파드라면 `dnsConfig`로 그 파드의 `ndots`를 낮추는 방법도 있어요. 둘 다 쿠버네티스 문서가 다루는 방법이에요.

## DNS 정책

파드가 어느 DNS 설정을 받을지는 `dnsPolicy`로 정해요.

| 정책 | 받는 설정 |
| --- | --- |
| `ClusterFirst` | 클러스터 DNS를 먼저 써요. 적지 않으면 이게 기본값이에요 |
| `Default` | 파드가 뜬 노드의 DNS 설정을 그대로 받아요 |
| `ClusterFirstWithHostNet` | 노드 네트워크를 쓰는 파드가 클러스터 DNS를 쓰게 해요 |
| `None` | `dnsConfig`에 적은 값만 써요 |

이름과 달리 `Default`는 기본값이 아니에요. 또 노드 네트워크(`hostNetwork`)를 쓰는 파드는 `ClusterFirstWithHostNet`을 적어야 서비스 이름을 찾아요. 그냥 두면 `Default`처럼 동작해요.

CoreDNS는 이런 지표를 내요.

- `coredns_dns_requests_total`: 질의 수예요.
- `coredns_dns_responses_total`: 응답 코드(`rcode` 레이블)별 응답 수예요.
- `coredns_dns_request_duration_seconds`: 질의 하나를 처리한 시간이에요.
- `coredns_cache_hits_total`: 캐시에서 바로 답한 수예요.

NXDOMAIN(그런 이름이 없음)이 많다고 바로 장애는 아니에요. 바깥 이름 하나에 8번 중 6번이 NXDOMAIN이었어요. 더 볼 것은 SERVFAIL(서버가 답을 못 함)과 처리 시간이 느는지예요.

앱이 바깥을 부르는 시간에는 이름을 찾는 시간도 들어 있어요. 바깥 API 호출이 느려졌는데 상대 서버는 멀쩡하다면, CoreDNS 처리 시간도 함께 봐요.

<Deeper>
  ### 헤드리스 서비스와 파드 이름

  클러스터 IP가 없는 헤드리스 서비스의 이름은 대상 파드들의 IP 목록으로 풀려요. StatefulSet 파드는 `db-0.db.shop.svc.cluster.local`처럼 파드마다 이름을 받을 수 있어요.

  ### CoreDNS의 바깥 질의

  쿠버네티스 문서의 기본 CoreDNS 설정은 클러스터 도메인이 아닌 이름을 바깥 서버로 넘겨요. `forward . /etc/resolv.conf` 줄이 노드의 DNS 설정에 있는 서버로 넘기라는 뜻이에요. `cache 30` 줄 때문에 답은 30초 동안 캐시해요.

  ### 오래된 이미지의 DNS 문제

  쿠버네티스 문서는 Alpine 3.17 이하 이미지에서 DNS가 제대로 안 될 수 있다고 해요. 그 버전의 C 라이브러리(musl)는 512바이트가 넘는 응답을 TCP로 다시 받지 못해요. 3.18 이상으로 올리라고 권해요.
</Deeper>
