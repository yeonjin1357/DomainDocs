## 1. PVC가 Bound인지 보세요

PVC가 아직 묶이지 않았다면 상태가 Pending이에요. 이벤트로 이유를 가려요.

| 이벤트 | 뜻 |
| --- | --- |
| waiting for first consumer to be created before binding | 이 PVC를 쓰는 파드가 생길 때까지 일부러 기다려요 |
| no persistent volumes available for this claim and no storage class is set | 저장소 등급이 없고, 미리 만든 맞는 PV도 없어요 |
| ProvisioningFailed | 저장소를 새로 만들다 실패했어요 |

첫 번째는 정상이에요. <Term term="kubernetes/storage-class">StorageClass</Term>의 `volumeBindingMode`가 `WaitForFirstConsumer`이면 파드의 노드가 정해진 뒤 디스크를 만들어요. 파드가 없으면 계속 Pending이에요.

두 번째는 PVC에 등급 이름이 없고 기본 StorageClass도 없을 때 나와요. 등급 이름을 빈 문자열(`""`)로 적은 PVC는 기본 등급도 쓰지 않아, 미리 만든 PV만 기다려요. 크기나 접근 모드가 맞는 PV가 없으면 계속 묶이지 않아요.

**확인 방법**: `kubectl get pvc`의 STATUS를 보고, `kubectl describe pvc PVC이름`의 Events를 봐요.

## 2. 디스크와 노드의 영역이 맞는지 보세요

클라우드 블록 디스크는 가용 영역 하나에 속해요. 다른 영역의 노드에는 붙일 수 없어요. 그래서 디스크가 a 영역에 있으면, 그 파드는 a 영역의 노드에만 놓일 수 있어요.

`volumeBindingMode`를 적지 않으면 기본값은 `Immediate`예요. 이때는 PVC를 만들자마자 디스크를 만들어서, 파드가 놓일 수 없는 영역에 디스크가 생길 수 있어요. 쿠버네티스 문서는 이런 저장소에 `WaitForFirstConsumer`를 권해요.

이 경우 파드는 Pending이고, 스케줄러 메시지에 노드가 PV의 영역 조건과 맞지 않는다고 나와요. 문구는 버전마다 달라요.

| 버전 | FailedScheduling 메시지 |
| --- | --- |
| 1.32까지 | node(s) had volume node affinity conflict |
| 1.33부터 | node(s) didn't match PersistentVolume's node affinity |

노드 점검으로 a 영역 노드가 모두 빠지면, a 영역 디스크를 쓰는 StatefulSet 파드는 갈 곳이 없어요. 디스크가 있는 영역에 노드가 남아 있는지 봐요.

**확인 방법**: `kubectl describe pv PV이름`의 Node Affinity에서 영역을 봐요. 그 영역을 노드의 `topology.kubernetes.io/zone` 레이블과 견줘요.

## 3. 다른 노드에 붙어 있지 않은지 보세요

접근 모드가 ReadWriteOnce인 볼륨은 한 번에 노드 하나에만 붙어요. 옛 노드에서 떼어지기 전에 새 노드의 파드가 붙이려 하면 FailedAttachVolume 이벤트가 나요. 메시지의 앞부분은 버전마다 달라요.

| 버전 | FailedAttachVolume 메시지 |
| --- | --- |
| 1.34까지 | Multi-Attach error for volume … |
| 1.35부터 | Waiting for detach for volume … |

메시지 뒷부분을 읽으면 무엇이 잡고 있는지 알 수 있어요. 'already used by pod(s)' 뒤에 파드 이름이 나오면, 다른 노드의 그 파드가 아직 볼륨을 쓰고 있는 거예요. 'already exclusively attached'라면 쓰는 파드는 없지만 디스크가 아직 옛 노드에 붙어 있는 거예요.

옛 파드가 끝나 디스크가 떼어지면 저절로 풀려요. 계속 남는다면 옛 노드가 살아 있는지, 디스크를 떼는 데 실패하고 있지 않은지 봐요.

이 에러는 설정 실수로도 자주 나요. ReadWriteOnce PVC 하나를 Deployment 파드 여럿이 쓰거나, 롤링 업데이트로 새 파드가 다른 노드에 먼저 뜬 경우예요. 이럴 땐 파드마다 PVC를 따로 받는 StatefulSet을 쓰거나, 옛 파드를 먼저 내리는 `Recreate` 배포 방식을 써요.

## 4. 연결 단계에서 멈췄는지 보세요

디스크는 노드에 붙었는데 파드 안에 연결하지 못하면 FailedMount 이벤트가 나요. 이 일은 그 노드의 kubelet과 저장소 드라이버가 해요.

CSI(쿠버네티스가 저장소 드라이버를 붙이는 표준) 드라이버는 보통 노드마다 파드 하나를 띄워 일해요. 그 노드에서 드라이버 파드가 돌고 있는지부터 봐요.

**확인 방법**: `kubectl describe pod 파드이름`의 Events에서 FailedMount 메시지를 봐요. 같은 노드에 뜬 드라이버 파드의 상태도 봐요.

## 5. 가득 찼다면 늘리세요

볼륨이 가득 차면 쿠버네티스 이벤트는 남지 않아요. 앱이 쓰기에 실패하고, 로그에 `No space left on device` 같은 에러가 남아요.

StorageClass의 `allowVolumeExpansion`이 true라면 PVC의 크기를 키울 수 있어요. 줄이는 건 안 돼요. 파일 시스템이 있는 볼륨은 XFS, Ext3, Ext4일 때 파일 시스템까지 함께 늘어나요.

사용량은 kubelet이 PVC마다 내는 지표로 지켜봐요. 남은 바이트는 `kubelet_volume_stats_available_bytes`로 내요. 전체 바이트는 `kubelet_volume_stats_capacity_bytes`예요.

남은 바이트를 전체 바이트로 나눈 값이 0.1 아래면 알리는 식이에요. 두 지표에는 `namespace`와 `persistentvolumeclaim` 레이블이 붙어요.
