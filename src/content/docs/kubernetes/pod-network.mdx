## 파드마다 IP가 하나예요

쿠버네티스의 네트워크 규칙은 셋이에요.

- 파드마다 클러스터 안에서 하나뿐인 IP를 받아요.
- 모든 파드는 노드가 달라도 NAT 없이 서로 닿아요.
- 노드의 에이전트(kubelet 등)는 그 노드의 파드에 모두 닿아요.

파드 안의 컨테이너들은 같은 네트워크 공간을 써서 서로 `localhost`로 불러요. 파드 하나는 <Term slug="kubernetes/pods-and-nodes">파드와 노드</Term>에서 다뤄요.

노드마다 파드 IP 범위를 나눠 주는 방식이 흔해요. 컨트롤러 매니저가 나눠 줄 때 기본 크기는 /24라, 노드 하나에 주소가 256개예요. kubelet이 노드 하나에 띄우는 파드는 기본 110개까지라 범위가 넉넉해요.

## 길은 CNI 플러그인이 깔아요

<Term term="kubernetes/cni">CNI</Term>(Container Network Interface)는 파드 네트워크를 만드는 플러그인과 쿠버네티스 사이의 약속이에요. 파드가 뜰 때 컨테이너 런타임이 CNI 플러그인을 불러 IP를 주고 길을 이어요.

노드를 넘는 길은 플러그인마다 두 방식 중 하나를 써요. 파드 패킷을 노드 주소로 한 번 더 감싸 보내는 오버레이와, 바깥 네트워크에 파드 범위로 가는 길을 알려 주는 라우팅이에요.

Flannel의 VXLAN은 머리표가 50바이트라, 선의 MTU가 1,500바이트면 파드 쪽 MTU를 1,450바이트로 잡아요. 감싸기와 MTU, 큰 패킷만 사라지는 문제는 <Term slug="network/tunnels">터널과 오버레이</Term>에서 다뤄요.

AWS의 VPC CNI처럼 파드에 VPC의 실제 IP를 나눠 주는 플러그인도 있어요. 감싸지 않아서 빠르지만, 노드가 가질 수 있는 IP 수만큼만 파드를 띄울 수 있어요.

## 파드 IP는 바뀌어요

파드가 죽고 다시 만들어지면 새 IP를 받아요. 배포 때마다 파드가 바뀌니, 파드 IP를 설정에 적어 두면 금방 틀려요.

그래서 다른 파드를 부를 때는 고정 주소를 가진 <Term slug="kubernetes/services-and-ingress">서비스</Term>를 써요. 서비스 이름을 IP로 바꾸는 일은 <Term slug="kubernetes/cluster-dns">클러스터 안의 DNS</Term>가 해요.

## 막는 규칙: NetworkPolicy

기본으로 모든 파드는 모든 파드와 통신할 수 있어요. <Term term="kubernetes/network-policy">NetworkPolicy</Term>는 이 길을 막는 규칙이에요. 파드가 한 정책에라도 걸리면, 그 정책이 허락한 통신만 들어올 수 있어요.

## 모니터링에서는

파드마다 네트워크로 주고받은 양은 kubelet 안의 cAdvisor가 세요. 바이트 카운터라 rate로 초당 양을 봐요.

- `container_network_receive_bytes_total`: 파드가 받은 바이트예요.
- `container_network_transmit_bytes_total`: 파드가 보낸 바이트예요.
- `container_network_receive_packets_dropped_total`: 받다가 버린 패킷이에요.

파드끼리 통신이 안 될 때는 CNI 플러그인 자체의 파드부터 봐요. 플러그인은 보통 노드마다 하나씩 DaemonSet으로 떠요. 그 파드가 죽은 노드에서는 새 파드가 IP를 받지 못해 ContainerCreating에 머물러요.

  <Check>다른 서비스의 파드 IP를 설정 파일에 적어 둔 코드라면 다시 보세요. 파드가 다시 만들어지면 IP가 바뀌어요. 서비스 이름으로 불러요.</Check>
  <Check>NetworkPolicy를 만들었는데 막히지 않는다면, 쓰는 CNI 플러그인이 정책을 지원하는지 보세요. 지원하지 않으면 정책은 아무 효과가 없어요.</Check>
  <Check>오버레이 네트워크에서 작은 요청은 되는데 큰 응답만 멈춘다면 MTU를 의심하세요. 감싼 머리표만큼 실을 자리가 줄어요.</Check>
  <Check>노드에 CPU와 메모리가 남는데 새 파드가 ContainerCreating에 머문다면, CNI 플러그인 파드와 남은 IP 수를 보세요.</Check>

<Deeper>
  ### 파드 안의 네트워크 장치

  리눅스에서 파드는 자기만의 네트워크 공간(network namespace)을 가져요. CNI 플러그인은 보통 가상 이더넷 한 쌍(veth)을 만들어 한쪽은 파드 안에, 다른 쪽은 노드에 둬요. 노드는 이 장치로 파드와 패킷을 주고받아요.

  ### VPC CNI의 파드 수 한도

  AWS VPC CNI는 인스턴스의 네트워크 카드(ENI)마다 IP를 붙여 파드에 나눠 줘요. 그래서 노드의 파드 수 한도는 ENI 수와 ENI당 IP 수로 정해져요. README는 max-pods를 (ENI 수 × (ENI당 IP 수 − 1)) + 2로 잡으라고 권해요.

  ### 서비스와 kube-proxy

  서비스 IP로 온 요청을 파드 IP로 바꾸는 일은 kube-proxy가 해요. 다만 Cilium처럼 이 일을 플러그인이 직접 하는 경우도 있어요.
</Deeper>
