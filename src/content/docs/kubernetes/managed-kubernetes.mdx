## 누가 무엇을 맡나요

## 컨트롤 플레인은 덜 보여요

컨트롤 플레인 서버에는 들어갈 수 없어요. 그래서 etcd나 스케줄러의 지표를 직접 모으지 못하고, 클라우드가 열어 준 길로만 봐요.

기본으로 꺼져 있어서, 장애가 난 뒤에 켜면 그 전 기록은 없어요. 켜면 CloudWatch Logs의 저장 비용이 따로 들어요.

컨트롤 플레인이 느릴 때 무엇부터 볼지는 <Term slug="kubernetes/control-plane-slow">컨트롤 플레인이 느릴 때</Term>에서 다뤄요.

## 버전은 정해진 때 올려요

쿠버네티스는 넉 달쯤마다 새 마이너 버전이 나와요. 관리형 서비스는 버전마다 지원 기간을 두고, 기간이 끝나면 올리라고 해요.

다른 클라우드도 방식은 달라도 같은 문제를 다뤄요. AKS는 최신 버전과 그 앞의 두 버전, 세 개를 지원해요. GKE는 릴리스 채널(Rapid, Regular, Stable, Extended)을 고르면 그 채널에 맞춰 클러스터를 올려요.

컨트롤 플레인만 올라가고 노드는 남는 경우가 많아요. EKS의 관리형 노드 그룹도 컨트롤 플레인을 올릴 때 함께 올라가지 않아요. 쿠버네티스는 노드의 kubelet이 API 서버보다 세 마이너 버전까지 낮아도 되게 하지만, 높으면 안 돼요.

## 클라우드와 이어지는 곳

관리형 클러스터는 클라우드의 다른 서비스와 맞물려 돌아요. 문제도 그 이음새에서 자주 나요.

- **파드 IP**: EKS의 기본 CNI(VPC CNI)는 파드에 VPC의 실제 IP를 줘요. 서브넷의 IP가 바닥나면 노드가 있어도 새 파드가 뜨지 않아요. 자세한 건 <Term slug="kubernetes/pod-network">파드 네트워크(CNI)</Term>에 있어요.
- **로드 밸런서**: `type: LoadBalancer`인 Service를 만들면 클라우드의 로드 밸런서가 생겨요. 그 비용과 상태도 클라우드 쪽에서 봐요.
- **권한**: 파드가 클라우드 API를 부를 때는 클라우드의 권한 체계(IAM)와 이어 줘요. EKS Pod Identity, GKE Workload Identity 같은 기능이에요.

## 모니터링에서는

노드와 파드는 직접 운영할 때처럼 모아요. kubelet, kube-state-metrics, 노드 에이전트는 그대로예요. 다른 점은 컨트롤 플레인과, 클라우드와 이어진 곳이에요.

- **컨트롤 플레인**: API 서버 지표는 직접 모으고, 나머지는 클라우드의 지표와 로그를 끌어와요. 로그는 미리 켜 둬요.
- **버전과 지원 기간**: 클러스터마다 버전과 지원이 끝나는 날을 보여 줘요. 연장 지원에 들어간 EKS 클러스터는 비용이 여섯 배가 돼요.
- **IP와 할당량**: 서브넷의 남은 IP, 노드 그룹의 최대 크기처럼 클라우드 쪽 한도가 파드를 막을 수 있어요.
