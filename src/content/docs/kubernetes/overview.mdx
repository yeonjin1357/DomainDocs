<Analogy limit="항구 관제탑은 사람이 지시를 내리지만, 쿠버네티스는 사람이 '원하는 모습'만 적어 두면 지금 모습과의 차이를 스스로 계속 메워요.">
  쿠버네티스는 큰 항구와 비슷해요. 화주는 "컨테이너 세 개를 실어 줘"라고 원하는 상태만 적어 내요. 관제탑(컨트롤 플레인)이 어느 배(노드)에 실을지 정하고, 배마다 있는 선원(kubelet)이 실제로 싣고 지켜요.
</Analogy>

## 원하는 상태를 적으면 맞춰 줘요

쿠버네티스에 무언가를 맡길 때는 "이렇게 되어 있으면 좋겠다"는 <Term term="kubernetes/desired-state">원하는 상태</Term>를 적어 내요. 예를 들어 "이 이미지로 파드 3개를 띄워 둬"예요.

쿠버네티스의 객체는 대부분 원하는 상태(spec)와 지금 상태(status)를 함께 가져요. <Term term="kubernetes/control-plane">컨트롤 플레인</Term>은 지금 상태가 원하는 상태와 같아지도록 계속 맞춰요. 파드 하나가 죽으면, 원하는 수에 맞추려고 새 파드를 다시 띄워요.

## 클러스터의 구성

쿠버네티스 <Term term="kubernetes/cluster">클러스터</Term>는 컨트롤 플레인과 일하는 <Term term="kubernetes/node">노드</Term> 여러 대로 이뤄져요.

| 구성 요소 | 있는 곳 | 하는 일 |
| --- | --- | --- |
| API 서버 | 컨트롤 플레인 | 쿠버네티스 API를 내놓는 중심 서버예요 |
| etcd | 컨트롤 플레인 | API 서버의 모든 데이터를 담는 저장소예요 |
| 스케줄러 | 컨트롤 플레인 | 아직 노드가 없는 파드에 알맞은 노드를 정해요 |
| 컨트롤러 매니저 | 컨트롤 플레인 | 원하는 상태를 맞추는 컨트롤러들을 돌려요 |
| kubelet | 노드마다 | 파드와 그 컨테이너가 돌고 있는지 지켜요 |
| kube-proxy | 노드마다 | 서비스를 위한 네트워크 규칙을 유지해요 |
| 컨테이너 런타임 | 노드마다 | 컨테이너를 실제로 실행해요 |

구성 요소들은 서로 직접 부르기보다 API 서버를 거쳐 움직여요. 그래서 API 서버가 멈추면 새 배포나 변경이 모두 멈춰요. 이미 떠 있는 파드는 그대로 돌아요.

## 단계를 하나씩 확대해 봐요

- 쿠버네티스가 다루는 기본 단위는 <Term slug="kubernetes/containers">컨테이너</Term>에서 다뤄요.
- 컨테이너를 묶어 노드에 띄우는 단위는 <Term slug="kubernetes/pods-and-nodes">파드와 노드</Term>에서 다뤄요.

노드는 결국 리눅스 서버이고, 파드끼리는 네트워크로 이어져요. 그래서 <Term slug="server/overview">서버·OS</Term>와 <Term slug="network/overview">네트워크</Term> 기초를 함께 알면 쿠버네티스가 훨씬 잘 읽혀요.
