## 파드의 다섯 단계

<Term term="kubernetes/pod-phase">파드 단계</Term>(phase)는 파드가 생애의 어디쯤 있는지 짧게 보여 줘요.

| 단계 | 뜻 |
| --- | --- |
| Pending | 클러스터가 파드를 받았지만, 컨테이너가 아직 돌 준비가 안 됐어요. 노드 배정을 기다리거나 이미지를 받는 중이에요 |
| Running | 노드에 배정됐고 컨테이너가 다 만들어졌어요. 하나 이상이 돌고 있거나, 시작 또는 재시작 중이에요 |
| Succeeded | 모든 컨테이너가 성공으로 끝났고, 다시 시작하지 않아요 |
| Failed | 모든 컨테이너가 끝났고, 하나 이상이 실패로 끝났어요 |
| Unknown | 파드 상태를 알 수 없어요. 보통 파드가 있는 노드와 연락이 안 될 때예요 |

Running에는 "재시작 중"도 들어 있어요. 그래서 컨테이너가 계속 죽었다 살아나도 단계만 보면 Running일 수 있어요.

## 컨테이너의 세 상태

파드 안의 컨테이너마다 상태가 따로 있어요. Waiting은 시작에 필요한 일을 하는 중이에요. Running은 문제없이 도는 중이고, Terminated는 끝까지 돌았거나 실패로 끝난 거예요.

Waiting과 Terminated 상태에는 이유(reason)가 함께 붙어요. Terminated에는 종료 코드와 시작·종료 시각도 붙어요. 문제를 찾을 때는 이 이유부터 봐요.

## 재시작과 늘어나는 간격

컨테이너가 끝나면 kubelet은 파드의 재시작 정책(restartPolicy)을 따라요. 기본값 Always는 어떻게 끝나든 다시 시작해요. OnFailure는 실패로 끝났을 때만, Never는 다시 시작하지 않아요.

Deployment의 파드는 Always만 쓸 수 있어요. Job은 보통 OnFailure나 Never를 써요. 재시작은 같은 노드, 같은 파드 안에서 컨테이너만 새로 띄우는 거예요.

## CrashLoopBackOff

<Term term="kubernetes/crashloopbackoff">CrashLoopBackOff</Term>는 컨테이너가 죽고 다시 뜨기를 되풀이해서, 기다리는 시간이 걸려 있는 상태예요. 그 자체가 원인은 아니고, "계속 죽고 있다"는 표시예요.

쿠버네티스 문서는 흔한 원인으로 이런 것들을 꼽아요.

- 앱이 오류로 스스로 끝나요.
- 환경 변수가 틀렸거나 설정 파일이 없어요.
- 시작하기에 메모리나 CPU가 모자라요.
- 정해 둔 시간 안에 앱이 준비되지 않아 상태 검사에 실패해요.

원인은 컨테이너 로그에 있는 경우가 많아요. 이미 죽은 컨테이너의 로그는 `kubectl logs --previous`로 이전 실행분을 봐요.

## 자주 보는 이유

| 이유 | 뜻 | 먼저 볼 것 |
| --- | --- | --- |
| Pending이 오래감 | 파드를 놓을 노드를 못 찾았어요 | 스케줄러 메시지, 노드의 요청 합계 |
| ImagePullBackOff | 이미지를 받지 못해 컨테이너를 시작 못 해요 | 이미지 이름·태그, 사설 저장소 인증 |
| CrashLoopBackOff | 컨테이너가 계속 죽고 다시 떠요 | 이전 실행의 로그, 종료 코드 |
| OOMKilled | 메모리 한도를 넘어 프로세스가 끝났어요 | 메모리 한도, 앱의 메모리 누수 |

ImagePullBackOff도 같은 식으로 다시 시도해요. 이미지 받기를 계속 시도하면서 간격을 늘리고, 최대 5분까지 늘어나요. 요청과 한도는 <Term slug="kubernetes/requests-and-limits">요청과 한도</Term>에서 다뤄요.

## 프로브: 살았나, 받을 준비가 됐나

<Term term="kubernetes/probe">프로브</Term>는 kubelet이 컨테이너를 주기적으로 찔러 보는 검사예요. 컨테이너 안에서 명령을 실행하거나, HTTP·TCP 같은 네트워크 요청을 보내요.

| 프로브 | 묻는 것 | 실패하면 |
| --- | --- | --- |
| startup | 앱이 시작을 마쳤나요 | 컨테이너를 끝내고 재시작 정책을 따라요. 성공 전에는 다른 프로브를 하지 않아요 |
| liveness | 앱이 살아서 일하고 있나요 | 정해 둔 횟수를 넘게 실패하면 컨테이너를 다시 시작해요 |
| readiness | 요청을 받을 준비가 됐나요 | 서비스가 그 파드로 요청을 보내지 않아요. 다시 시작하지는 않아요 |

liveness는 앱이 떠 있지만 멈춰 버린 상태를 잡으려고 써요. 서로 기다리느라 아무것도 못 하는 교착 상태(deadlock)가 대표적이에요. readiness는 시작이 오래 걸리거나 잠깐 과부하일 때, 요청을 잠시 다른 파드로 돌리는 데 써요.

쿠버네티스 화면은 파드마다 단계와 재시작 횟수, 마지막 종료 이유를 보여 줘요. 재시작 횟수가 오르는 파드가 있으면, 단계가 Running이어도 종료 이유부터 봐요.

준비 상태(Ready)도 따로 봐요. Running인데 Ready가 아니면, 그 파드는 지금 서비스 요청을 받지 않고 있어요.

  <Check>파드 단계가 Running이라는 이유로 정상이라고 판단했다면 다시 보세요. 재시작 중인 컨테이너도 Running에 들어가요. 재시작 횟수와 Ready를 함께 보세요.</Check>
  <Check>liveness 프로브가 데이터베이스 같은 바깥 의존성까지 확인한다면 다시 보세요. 바깥이 잠깐 아프면 멀쩡한 파드까지 한꺼번에 다시 시작돼요.</Check>
  <Check>시작이 느린 앱에 liveness만 걸었다면 다시 보세요. liveness는 다른 프로브를 기다리지 않아서, 시작을 마치기 전에 실패로 보고 다시 시작할 수 있어요. startup 프로브나 첫 검사 지연(`initialDelaySeconds`)을 두세요.</Check>
  <Check>CrashLoopBackOff 알림만 보고 재시작을 기다리고 있다면, 이전 실행의 로그부터 보세요. 원인을 고치기 전까지는 계속 죽어요.</Check>
</Checkpoints>

<Deeper>
  ### 연쇄 장애를 부르는 liveness

  쿠버네티스 문서는 liveness 프로브를 잘못 만들면 연쇄 장애로 이어질 수 있다고 경고해요. 부하가 높을 때 컨테이너가 다시 시작되고, 남은 파드에 일이 더 몰려요.

  문서는 바깥 서비스에 기대는 앱이라면 둘을 나누라고 해요. liveness는 앱 자신이 건강한지만 보고, readiness가 필요한 바깥 서비스까지 확인해요.

  ### 기다리는 시간의 최대값

  최대 대기 5분은 기본값이에요. 쿠버네티스 최근 버전에는 노드마다 이 최대값을 바꾸는 설정이 있어요.
</Deeper>
