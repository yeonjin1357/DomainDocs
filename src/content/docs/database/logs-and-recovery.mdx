  </Point>

## 왜 로그에 먼저 적나요

커밋할 때마다 바뀐 데이터 파일을 모두 디스크에 쓰면 느려요. 바뀐 블록이 파일 여기저기에 흩어져 있기 때문이에요. 그래서 DB는 바뀐 내용을 <Term term="database/wal">로그</Term>에만 확실히 적고, 데이터 파일은 나중에 써요.

이 원칙을 로그 선행 기록(write-ahead logging)이라고 불러요. 데이터 파일의 변경은 그 변경을 적은 로그가 디스크에 닿은 뒤에만 쓸 수 있어요.

| DB | 로그 이름 |
| --- | --- |
| PostgreSQL | WAL |
| Oracle | 리두 로그(redo log) |
| MySQL InnoDB | 리두 로그(redo log) |
| SQL Server | 트랜잭션 로그 |

DB를 다시 켜면 먼저 마지막 <Term term="database/checkpoint">체크포인트</Term>를 찾아요. 그 뒤로 로그에 적힌 변경을 차례로 다시 적용해서, 데이터 파일에 미처 못 쓴 변경을 채워요.

커밋하지 못하고 끊긴 트랜잭션도 있어요. SQL Server 문서는 복구 때 이런 트랜잭션의 변경을 모두 되돌린다고 해요. MySQL InnoDB는 이 복구를 마친 뒤에야 연결을 받아요.

## 로그는 비워 줘야 해요

체크포인트가 지나면 그 앞의 로그는 장애 복구에 더는 필요 없어요. DB는 이 부분을 지우거나 새 로그로 다시 써요. 그런데 아직 다른 일에 필요한 로그는 지우지 못해요.

- 아직 끝나지 않은 트랜잭션의 로그예요. 오래 열린 트랜잭션이 하나 있으면, 그 시작점 뒤의 로그를 모두 남겨 둬야 해요.
- 백업이나 보관이 아직 안 된 로그예요. PostgreSQL은 보관 명령이 계속 실패하면 옛 WAL이 쌓여요. SQL Server는 전체 복구 모델에서 로그 백업을 해야 로그를 비워요.
- 복제 서버가 아직 받지 못한 로그예요. 복제가 밀리면 보낼 로그가 남아요.

이 중 하나라도 걸리면 로그가 계속 커지고, 끝내 디스크를 채워요. SQL Server는 로그를 더 늘릴 수 없으면 9002 에러를 내요.

커밋은 로그가 디스크에 닿을 때까지 기다려요. 그래서 로그 디스크가 느리면 모든 커밋이 함께 느려져요. Oracle에서는 이 기다림이 `log file sync` 대기 이벤트로 보여요.

로그 디스크 사용량이 계속 오르면 위의 세 가지 원인을 봐요. 오래 열린 트랜잭션은 <Term slug="database/transactions">트랜잭션과 커밋</Term>에서, 밀린 복제는 <Term slug="database/replication-lag">복제 지연</Term>에서 찾는 법을 봐요.

<Deeper>
  ### 백업과 로그로 원하는 시점까지

  로그를 보관해 두면 장애 복구보다 더 많은 일을 할 수 있어요. 예전 백업을 복원하고, 보관한 로그를 원하는 시각까지만 다시 적용하면 그 시점의 데이터로 돌아가요. PostgreSQL은 이를 시점 복구(PITR)라고 불러요.

  SQL Server는 끊기지 않은 로그 백업의 연결(log chain)이 있어야 장애 시점까지 복원할 수 있어요.

  ### MySQL의 두 로그

  MySQL에는 로그가 두 가지 있어요. InnoDB 리두 로그는 장애 복구용이에요. 바이너리 로그(binlog)는 데이터 변경 이벤트를 담아 복제와 시점 복구에 써요.

  ### Oracle의 커밋

  Oracle에서 커밋하면 세션이 LGWR(로그를 쓰는 백그라운드 프로세스)에 리두 기록을 부탁해요. LGWR이 다 쓰면 세션에 알려 주고, 그동안 세션은 `log file sync`로 기다려요.

  ### SQL Server의 로그가 비워지는 때

  단순 복구 모델에서는 체크포인트 뒤에 로그를 비워요. 전체 복구 모델에서는 로그 백업 뒤에 비워요. 어느 쪽이든 아직 끝나지 않은 트랜잭션의 로그는 남겨 둬요.
</Deeper>
