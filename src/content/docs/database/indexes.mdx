  </Point>
  <Point title="인덱스는 공짜가 아니에요">
    행을 넣고 고칠 때마다 인덱스도 함께 고쳐야 해요. 인덱스가 많을수록 쓰기가 느려지고 공간도 더 써요.
  </Point>
  <Point title="있어도 안 쓰일 때가 있어요">

  </Point>
</KeyPoints>

## 인덱스는 이렇게 생겼어요

대부분의 DB에서 기본 인덱스는 <Term term="database/b-tree">B-tree</Term>예요. 값을 정렬해 나무 모양으로 쌓은 구조라, 위에서부터 범위를 좁혀 내려가면 원하는 값에 닿아요.

인덱스는 테이블과 따로 저장돼요. 인덱스에는 정렬한 값과 그 값이 든 행의 위치만 있어서, 테이블보다 훨씬 작고 빨리 훑을 수 있어요.

## 쓰기에는 비용이 들어요

인덱스를 만들면 DB는 테이블이 바뀔 때마다 인덱스도 맞춰 고쳐요. 인덱스가 5개인 테이블에 행 하나를 넣으면, 테이블과 인덱스 5개에 모두 적어야 해요.

그래서 PostgreSQL 문서도 거의 쓰이지 않는 인덱스는 지우라고 해요. 찾기에 도움이 되지 않으면서 쓰기만 느리게 하기 때문이에요.

## 있어도 안 쓰일 때가 있어요

인덱스를 쓸지는 <Term term="database/optimizer">옵티마이저</Term>가 비용을 어림해 정해요. 이런 경우에는 인덱스가 있어도 쓰지 않거나, 써도 효과가 작아요.

- 가져올 행이 많을 때예요. 테이블의 행 대부분을 가져온다면 처음부터 다 읽는 편이 더 싸요.
- 열에 함수를 씌운 조건이에요. `WHERE lower(email) = …`은 `email` 순서로 정렬한 인덱스와 모양이 달라요. `lower(email)`로 만든 인덱스가 따로 있어야 써요.
- 여러 열을 묶은 <Term term="database/composite-index">복합 인덱스</Term>에서 앞 열 조건이 없을 때예요. `(고객, 주문일)` 인덱스는 고객으로 먼저 정렬돼 있어서, 주문일만으로 찾으면 효율이 크게 떨어져요. 계획으로 확인하고 고치는 순서는 <Term slug="database/index-not-used">인덱스가 있는데도 안 쓰일 때</Term>에 있어요.

인덱스 문제는 <Term slug="database/execution-plans">실행 계획</Term>에서 드러나요. 읽은 행이 돌려준 행보다 훨씬 많다면, 인덱스가 없거나 쓰이지 않는지 봐요. 그런 SQL은 <Term slug="database/top-sql">SQL별 부하 순위</Term> 위쪽에 자주 올라와요.

반대로 쓰이지 않는 인덱스도 찾아요. PostgreSQL은 인덱스마다 쓰인 횟수(`idx_scan`)를 세어요. 오래 0이라면 지울 후보예요.

<Deeper>
  ### 테이블을 인덱스 순서로 저장하는 DB

  PostgreSQL과 Oracle의 테이블은 기본으로 힙(heap)이에요. 행을 특별한 순서 없이 빈자리에 저장하고, 인덱스는 따로 둬요.

  MySQL InnoDB는 테이블마다 클러스터형 인덱스가 있고, 행 데이터가 그 안에 저장돼요. 보통 기본 키가 클러스터형 인덱스예요.

  InnoDB의 보조 인덱스에는 행 위치 대신 기본 키 값이 들어 있어요. 그래서 보조 인덱스로 찾으면, 얻은 기본 키로 클러스터형 인덱스를 한 번 더 찾아요.

  SQL Server도 클러스터형 인덱스가 있으면 행을 그 키 순서로 저장해요. 행은 한 가지 순서로만 저장할 수 있어서, 클러스터형 인덱스는 테이블마다 하나예요.

  ### 기본 키와 유니크 제약

  SQL Server는 기본 키나 유니크 제약을 정의하면 인덱스를 자동으로 만들어요. 이 인덱스는 같은 값이 두 번 들어오지 않게 막는 데 쓰여요.
</Deeper>
