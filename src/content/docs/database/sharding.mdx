<KeyPoints>
  <Point title="여러 서버에 나눠 담아요">
    한 서버가 감당하지 못하는 데이터와 쓰기를 여러 DB 서버(샤드)로 나눠요. 행마다 갈 샤드는 샤드 키가 정해요.
  </Point>
  <Point title="샤드 키가 거의 모든 걸 정해요">
    고르게 나뉘는지, 질의가 한 샤드에서 끝나는지가 키에 달려요. 나중에 바꾸기도 어려워요.
  </Point>
  <Point title="샤드를 넘는 일은 비싸요">
    샤드 키 없는 질의는 모든 샤드로 가요. 샤드를 넘는 조인과 트랜잭션은 느리고 복잡해요.
  </Point>
</KeyPoints>

<Analogy limit="분관은 책이 늘면 새로 하나 지으면 되지만, 샤드를 늘리면 이미 있는 데이터를 새 샤드로 옮겨야 해요. 옮기는 동안 서버들이 바빠져요.">
  책이 너무 많아 도서관 한 곳에 다 못 둘 때, 분관 여러 곳에 나눠 두는 것과 같아요. 저자 이름처럼 정한 기준으로 어느 분관에 둘지 정해요.
</Analogy>

## 파티셔닝과 무엇이 다른가요

<Term slug="database/partitioning">테이블 파티셔닝</Term>은 한 DB 서버 안에서 큰 표를 칸으로 나눠요. 샤딩은 데이터를 아예 여러 DB 서버에 나눠 담아요. 한 서버의 CPU, 메모리, 디스크, 쓰기 속도로는 감당하지 못할 때 써요.

## 샤드 키로 갈 곳을 정해요

<Term term="database/shard">샤드</Term>는 데이터의 한 몫을 맡은 DB 서버(보통은 복제까지 갖춘 묶음)예요. 앱과 샤드 사이에는 라우터가 있어서, 행의 <Term term="database/shard-key">샤드 키</Term> 값을 보고 어느 샤드로 보낼지 정해요. MongoDB에서는 mongos가, Citus에서는 코디네이터 노드가 이 일을 해요.

나누는 방법은 크게 둘이에요. 범위(range)는 키 값의 구간마다 샤드를 정해요. 해시(hash)는 키 값을 해시해서 나온 수로 샤드를 정해요.

## 계속 커지는 키는 한 샤드에 몰려요

주문 번호나 시각처럼 계속 커지는 값을 범위로 나누면, 새 행은 모두 마지막 구간으로 가요. 쓰기가 샤드 하나에 몰리고 나머지는 놀아요. MongoDB 문서도 이렇게 계속 커지는 키는 새 쓰기를 한 곳에 몰리게 한다고 해요.

<Figure caption="주문 10만 건으로 경계를 정한 샤드 4개에 새 주문 1만 건을 넣는 계산이에요. 범위로 나누면 모두 샤드 4로 가고, 주문 번호를 해시하면 네 샤드에 고르게 가요.">
  <Strip
    ariaLabel="새 주문 1만 건이 간 샤드의 몫. 범위로 나누면 샤드 1, 2, 3은 0%, 샤드 4는 100%. 해시로 나누면 25.3%, 24.7%, 25.2%, 24.9%"
    rows={[
      { label: '범위(주문 번호 구간)', heads: ['샤드 1', '샤드 2', '샤드 3', '샤드 4'], cells: [{ label: '0%', heat: 0 }, { label: '0%', heat: 0 }, { label: '0%', heat: 0 }, { label: '100%', heat: 1, tone: 'warn' }] },
      { label: '해시(주문 번호)', heads: ['샤드 1', '샤드 2', '샤드 3', '샤드 4'], cells: [{ label: '25.3%', heat: 0.25 }, { label: '24.7%', heat: 0.25 }, { label: '25.2%', heat: 0.25 }, { label: '24.9%', heat: 0.25 }] },
    ]}
  />
</Figure>

해시가 늘 좋은 건 아니에요. 가까운 값이 여러 샤드에 흩어져서, 범위로 찾는 질의는 모든 샤드로 가야 해요. 같은 계산에서 주문 번호 1000~1100을 찾으면 범위 샤딩은 샤드 1개에서, 해시 샤딩은 샤드 4개 모두에서 찾았어요.

값의 종류가 적은 키도 몰려요. 나라 코드를 키로 두면 큰 나라 하나가 샤드 하나를 다 채워요. 이렇게 한 샤드에 몰리는 걸 <Term term="database/hot-partition">핫 파티션</Term>과 같은 뜻으로 핫 샤드라고 불러요.

## 샤드를 넘는 질의는 비싸요

샤드 키가 조건에 있으면 라우터는 그 샤드에만 보내요. 키가 없으면 모든 샤드에 보내고 결과를 모아 합쳐요. MongoDB는 앞의 것을 targeted, 뒤의 것을 broadcast라고 불러요.

<Figure caption="같은 주문 표에 두 질의를 보낸 순서예요. 샤드 키(user_id)가 있으면 한 샤드에서 끝나고, 없으면 모든 샤드에 묻고 가장 늦은 샤드를 기다려요.">
  <Sequence
    ariaLabel="user_id로 찾는 질의는 라우터가 샤드 A에만 보내 답을 받고, status로 찾는 질의는 라우터가 샤드 A와 샤드 B 모두에 보내 둘의 답을 모으는 순서"
    participants={['앱', '라우터', '샤드 A', '샤드 B']}
    messages={[
      { from: '앱', to: '라우터', label: 'user_id = 7', tone: 'accent' },
      { from: '라우터', to: '샤드 A', label: '샤드 A에만', tone: 'accent' },
      { from: '샤드 A', to: '라우터', label: '결과', dashed: true },
      { from: '앱', to: '라우터', label: 'status = 실패', tone: 'warn' },
      { from: '라우터', to: '샤드 A', label: '모두에게', tone: 'warn' },
      { from: '라우터', to: '샤드 B', label: '모두에게', tone: 'warn' },
      { from: '샤드 B', to: '라우터', label: '결과(늦음)', dashed: true },
    ]}
  />
</Figure>

모든 샤드에 묻는 질의는 가장 느린 샤드만큼 느려요. 샤드가 늘수록 묻는 곳도 늘어요. 그래서 자주 쓰는 질의에 샤드 키가 들어가도록 키를 골라요.

샤드를 넘는 조인과 트랜잭션도 비싸요. 함께 쓰는 표를 같은 키로 나눠 같은 샤드에 두는 방법이 흔해요.

Citus는 이걸 co-location이라고 불러요. 예를 들어 주문과 주문 상품을 모두 user_id로 나누면, 한 사용자의 조인은 한 샤드에서 끝나요.

## 키는 바꾸기 어려워요

샤드 키를 바꾸면 거의 모든 데이터를 다른 샤드로 옮겨야 해요. MongoDB는 5.0부터 `reshardCollection`으로 키를 바꿀 수 있지만, 그동안 디스크와 네트워크를 많이 써요. 그래서 처음에 질의 모양과 쓰기 분포를 보고 신중히 골라요.

샤딩한 DB는 샤드별로 나눠 봐요. 데이터 크기, 초당 질의·쓰기, CPU가 한 샤드만 튀면 키가 몰리고 있다는 신호예요. 클러스터 합계나 평균만 보는 화면은 쏠림을 가려요.

모든 샤드로 가는 질의의 비율도 봐요. 늘고 있다면 새로 생긴 질의가 샤드 키를 쓰지 않는 거예요. 샤드끼리 데이터를 옮기는 일(MongoDB의 balancer)이 도는 동안에는 디스크와 네트워크가 바빠지니, 그 시각도 함께 표시해요.
