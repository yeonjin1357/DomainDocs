<KeyPoints>
  <Point title="잠금은 동시에 바꾸는 것을 막아요">
    행을 바꾸는 트랜잭션은 그 행에 잠금을 걸고, 보통 트랜잭션이 끝날 때까지 쥐어요. 같은 행을 바꾸려는 다른 트랜잭션은 그동안 기다려요.

    PostgreSQL에서는 읽기와 쓰기가 서로 막지 않아요. 행의 여러 버전을 두는 방식(MVCC)이라, 평범한 SELECT는 쓰는 중인 행도 기다리지 않고 읽어요.
  </Point>
  <Point title="기다리는 잠금도 뒤를 막아요">
    `ALTER TABLE`의 여러 형태는 표 전체를 잠그는 ACCESS EXCLUSIVE 잠금을 써요. 이 잠금은 다른 모든 잠금과 충돌해서, 평범한 SELECT도 막아요.

    그래서 앞 트랜잭션 때문에 `ALTER TABLE`이 기다리는 동안, 그 뒤에 온 SELECT도 `ALTER TABLE` 뒤에 줄을 서요. `pg_blocking_pids`는 이렇게 대기 줄에서 앞에 선 세션이 막는 것을 soft block이라 불러요.
  </Point>
  <Point title="교착은 DB가 하나를 끊어 풀어요">
    두 트랜잭션이 서로의 잠금을 기다리면 둘 다 끝나지 않아요. 이를 교착(deadlock)이라고 해요. PostgreSQL은 교착을 찾아내 한쪽 트랜잭션을 에러로 끝내고, 나머지를 진행시켜요.
  </Point>
</KeyPoints>

<Checkpoints>
  <Check>운영 중에 `ALTER TABLE` 같은 DDL을 돌린다면 `lock_timeout`을 짧게 두세요. 정한 시간 안에 잠금을 얻지 못하면 더 기다리지 않고 실패해서, 뒤의 쿼리를 오래 줄 세우지 않아요.</Check>

<Deeper>
  ### 표 잠금 모드

  - ACCESS SHARE: SELECT가 읽는 표에 걸어요. ACCESS EXCLUSIVE하고만 충돌해요.
  - ROW EXCLUSIVE: `INSERT`, `UPDATE`, `DELETE`가 걸어요.
  - ACCESS EXCLUSIVE: `DROP TABLE`, `TRUNCATE`, `VACUUM FULL`과 많은 `ALTER TABLE`이 걸어요. 모든 모드와 충돌해요.

  PostgreSQL 문서는 FOR UPDATE·SHARE 없는 SELECT를 막는 건 ACCESS EXCLUSIVE뿐이라고 정리해요.

  ### 기다리는 잠금 보기

  `pg_locks`에서 `granted`가 거짓인 줄이 아직 얻지 못하고 기다리는 잠금이에요.

  ```text
  -- 얻지 못하고 기다리는 잠금
  SELECT pid, locktype, relation::regclass, mode, granted
  FROM pg_locks
  WHERE NOT granted;
  ```

  ### 교착 검사와 대기 로그

  PostgreSQL은 잠금을 `deadlock_timeout`(기본 1초)만큼 기다린 뒤에 교착인지 검사해요. 검사가 비싸서 잠금을 기다릴 때마다 하지는 않아요.

  `log_lock_waits`(기본 꺼짐)를 켜면, `deadlock_timeout`보다 오래 잠금을 기다린 세션을 로그에 남겨요. 잠금 대기가 성능을 떨어뜨리는지 볼 때 써요.
</Deeper>
