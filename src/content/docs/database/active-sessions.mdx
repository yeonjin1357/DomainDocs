<KeyPoints>
  <Point title="액티브 세션은 일하거나 기다리는 세션이에요">
    DB에 붙은 세션 대부분은 다음 명령을 기다리며 쉬어요. 액티브 세션은 그중 쿼리를 실행하고 있는 세션이에요. PostgreSQL에서는 `pg_stat_activity`의 `state`가 `active`인 세션이에요.

    액티브 세션 수는 DB가 동시에 처리하는 일의 양이에요. Oracle은 이 수의 평균을 평균 액티브 세션(AAS)이라 부르고, 세션들이 쓴 시간의 합(DB time)을 경과 시간으로 나눠 구해요.
  </Point>
  <Point title="대기 이벤트가 무엇을 기다리는지 알려 줘요">
    액티브 세션은 CPU에서 실행 중이거나, 무언가를 기다려요. PostgreSQL은 기다리는 대상을 `wait_event_type`으로 나눠요. 잠금은 Lock, 디스크 읽기·쓰기는 IO, 공유 메모리 구조는 LWLock이에요.

    대기 종류로 나누면 원인의 갈래가 보여요. 그림처럼 Lock 대기만 늘었다면, 쿼리가 무거워진 게 아니라 서로의 잠금을 기다리는 거예요.
  </Point>
  <Point title="쉬는 대기는 빼고 봐요">
    대기 이벤트에는 할 일이 없어 쉬는 대기도 있어요. PostgreSQL의 `ClientRead`는 앱이 다음 데이터를 보내길 기다리는 대기예요. Oracle도 Idle 종류의 대기는 성능 문제를 볼 때 빼라고 해요.
  </Point>
</KeyPoints>

<Deeper>
  ### PostgreSQL에서 세어 보기

  `state`와 `wait_event`는 따로 움직여요. `active`이면서 `wait_event`가 있으면, 쿼리를 실행하다 어딘가에서 막혀 기다리는 중이에요. `wait_event`가 비어 있는 `active` 세션은 기다리지 않고 실행 중이라, 아래 질의는 그 몫을 CPU로 셌어요.

  ```text
  -- 지금 액티브 세션을 기다리는 대상별로 세기
  SELECT coalesce(wait_event_type, 'CPU') AS waiting_for, count(*)
  FROM pg_stat_activity
  WHERE state = 'active' AND backend_type = 'client backend'
  GROUP BY 1;
  ```

  주요 대기 종류는 아래와 같아요.

  - Lock: 표나 행 같은 잠금을 기다려요. `transactionid`는 다른 트랜잭션이 끝나길 기다리는 거예요.
  - LWLock: 공유 메모리 안의 자료 구조를 기다려요.
  - IO: 디스크 읽기·쓰기를 기다려요. `DataFileRead`는 표 데이터 파일 읽기예요.
  - Client: 앱 쪽 소켓을 기다려요. `ClientRead`가 여기에 들어요.
  - Activity: 할 일 없이 쉬는 서버 프로세스예요.

  ### Oracle의 DB time과 ASH

  DB time은 Idle이 아닌 사용자 세션들의 CPU 시간과 대기 시간을 모두 더한 값이에요. 세션 여럿의 합이라 경과 시간보다 클 수 있어요. 30분 동안 액티브 세션 4개가 일했다면 DB time은 약 120분이고, 평균 액티브 세션은 120 ÷ 30 = 4예요.

  ASH(Active Session History)는 Idle 대기가 아닌 세션을 1초마다 표본으로 떠서 메모리에 돌려 쓰며 담아요. 활성 세션만 담아서, 연결된 세션 수가 아니라 일의 양만큼 쌓여요.

  ### 쉬는 트랜잭션 끊기

  PostgreSQL의 `idle_in_transaction_session_timeout`은 트랜잭션을 연 채 오래 쉬는 세션을 끊어요. 기본값 0은 꺼져 있어요. 문서는 쉬는 세션이 잠금을 너무 오래 쥐지 않게 할 때 쓰라고 해요.
</Deeper>
