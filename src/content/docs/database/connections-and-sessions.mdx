    연결은 앱과 DB 서버를 잇는 통신 통로예요. 세션은 DB가 그 접속에 대해 기억하는 상태예요.
  </Point>
  <Point title="연결 하나를 맡는 방식은 DB마다 달라요">
    PostgreSQL은 연결마다 서버 프로세스를 하나씩 띄워요. MySQL은 연결마다 스레드를 하나씩 둬요.
  </Point>
  <Point title="쉬는 연결도 자리를 차지해요">
    일하지 않는 연결도 프로세스나 스레드, 메모리를 쥐고 있어요. 그래서 연결 수에는 한도가 있어요.
  </Point>
</KeyPoints>

<Analogy limit="식당은 손님이 떠나면 테이블이 비어요. 앱의 커넥션 풀은 손님(요청)이 없어도 테이블(연결)을 잡아 둬요.">
  DB를 식당이라고 해 봐요. 연결은 손님이 앉은 테이블이고, 세션은 그 테이블에 놓인 주문서예요. 주문서에는 손님이 누구인지, 지금 무엇을 주문해 기다리는지 적혀 있어요.
</Analogy>

## 연결은 어떻게 생기나요

앱이 DB에 SQL을 보내려면 먼저 <Term term="database/connection">연결</Term>을 맺어야 해요. 연결을 맺을 때 DB는 누가 접속했는지 확인하고, 이 접속을 맡을 준비를 해요.

연결을 맺는 데는 시간이 들어요. 네트워크를 몇 번 오가고, 인증을 하고, 서버 쪽 일꾼을 준비해야 하기 때문이에요. 그래서 앱은 <Term term="database/connection-pool">커넥션 풀</Term>로 연결을 미리 열어 두고 돌려 써요.

## 세션에는 무엇이 담기나요

<Term term="database/session">세션</Term>은 접속 하나에 대한 DB의 기억이에요. 같은 연결로 들어온 SQL은 같은 세션에서 처리돼요.

- 누가 접속했는지: 사용자 이름, 접속한 데이터베이스, 앱 이름이에요.
- 어떤 설정으로 일하는지: 시간대, 문자 인코딩 같은 세션 설정이에요.
- 지금 무엇을 하는지: 실행 중인 SQL, 열려 있는 트랜잭션, 기다리는 대상이에요.

PostgreSQL에서는 `pg_stat_activity`에서 세션마다 한 줄씩 볼 수 있어요. 상태 열 `state`가 `active`면 SQL을 실행하는 중이고, `idle`이면 다음 명령을 기다리며 쉬는 중이에요.

## 연결 하나를 누가 맡나요

DB 서버 안에서 연결의 일을 맡는 일꾼은 DB마다 달라요. 크게 연결마다 프로세스를 두는 쪽과, 스레드로 맡는 쪽으로 나뉘어요.

PostgreSQL은 연결 요청이 올 때마다 <Term term="database/server-process">서버 프로세스</Term>를 새로 띄워요. 이 프로세스는 연결이 끊길 때까지 그 연결만 맡아요.

MySQL은 연결마다 그 연결 전용 스레드를 붙여요. SQL Server는 <Term term="database/worker-thread">작업 스레드</Term> 풀(일꾼 묶음)을 두고, 실행할 요청이 생길 때 하나씩 맡겨요.

<Deeper>
  ### Oracle의 연결과 세션

  Oracle 문서는 둘을 따로 정의해요. 연결은 클라이언트 프로세스와 DB 인스턴스 사이의 물리적 통로예요. 세션은 로그인 하나의 상태를 담은 인스턴스 메모리 안의 논리적 존재예요.

  그래서 Oracle에서는 연결 하나에 세션이 0개, 1개, 또는 여러 개일 수 있어요. 세션끼리는 독립이라, 한 세션의 커밋이 다른 세션의 트랜잭션에 영향을 주지 않아요.

  Oracle 문서가 드는 예는 SQL*Plus의 `SET AUTOTRACE`예요. 실행 통계를 켜면 같은 연결 위에 세션이 하나 더 생겨요.

  ### 다른 DB는 보통 연결 하나에 세션 하나예요

  PostgreSQL은 연결마다 서버 프로세스를 딱 하나 띄우고, 그 프로세스가 세션을 맡아요. MySQL도 연결마다 전용 스레드 하나가 인증과 요청 처리를 맡아요. 그래서 둘 다 연결과 세션이 하나씩 짝을 이뤄요.

  SQL Server도 보통 하나씩 짝을 이뤄요. 다만 MARS(Multiple Active Result Sets)를 켜면 세션 하나에 논리 연결이 여럿 붙을 수 있어요. 시스템이 쓰는 내부 세션에는 연결이 없어요.

  ### Oracle의 전용 서버와 공유 서버

  전용 서버 방식에서는 클라이언트 연결 하나에 서버 프로세스가 딱 하나 붙어요. 클라이언트 20개면 서버 프로세스도 20개예요.

  공유 서버 방식에서는 클라이언트가 디스패처 프로세스에 붙어요. 디스패처가 요청을 큐에 넣고, 비어 있는 공유 서버 프로세스가 꺼내 처리해요.

  ### MySQL의 스레드 캐시

  MySQL은 연결이 끝나면 그 스레드를 버리지 않고 스레드 캐시에 돌려 둬요. 새 연결이 오면 캐시에서 먼저 꺼내 써요. 캐시 크기는 `thread_cache_size`이고, 기본값은 서버가 시작할 때 알아서 정해요.

  문서는 연결마다 스레드를 두는 이 방식이 연결이 아주 많아질 때 불리하다고 해요. 접속한 클라이언트 수만큼 스레드가 생기기 때문이에요.

  ### SQL Server의 요청·태스크·작업 스레드

  SQL Server에서 요청(request)은 쿼리나 배치 하나예요. 요청은 태스크로 나뉘고, 태스크마다 작업 스레드가 하나씩 붙어요. 작업 스레드는 CPU마다 하나씩 있는 스케줄러 위에서 돌아가요.

  쉬는 세션은 작업 스레드를 쥐지 않아요. 그래서 연결이 수백 개여도 스레드 수는 `max worker threads` 설정 안에서 움직여요.

  ### 세션 설정이 남는 범위

  PostgreSQL의 `SET`은 트랜잭션이 커밋되면 세션이 끝날 때까지 남아요. 트랜잭션 안에서만 바꾸려면 `SET LOCAL`을 써요. 트랜잭션이 끝나면 원래대로 돌아와요.
</Deeper>
