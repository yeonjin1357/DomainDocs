<KeyPoints>
  <Point title="순위는 총 시간으로 매겨요">
    SQL 하나가 DB를 쓴 시간은 호출 수 × 평균 시간이에요. 평균 순으로 줄 세우면 드물게 도는 무거운 SQL이 위에 와요. 총 시간 순으로 줄 세우면 DB를 가장 많이 쓰는 SQL이 위에 와요.

    DB 부하를 줄이려면 총 시간 위쪽부터 봐요. 그림의 SQL A는 2ms로 빠르지만, 100만 번 불려 DB 시간의 대부분을 써요.
  </Point>
  <Point title="값만 다른 SQL은 하나로 묶어요">
    `WHERE id = 1`과 `WHERE id = 2`는 같은 SQL이에요. PostgreSQL의 `pg_stat_statements`는 상수 값만 다른 SQL을 한 항목으로 묶고, 상수 자리를 `$1`처럼 바꿔 보여 줘요.

    묶지 않으면 같은 SQL이 값마다 흩어져, 순위에서 하나하나는 작아 보여요.
  </Point>
  <Point title="누적값이라 구간마다 차이를 봐요">
    `pg_stat_statements`의 호출 수와 시간은 마지막 초기화 뒤로 쌓인 누적값이에요. 그래서 최근 1시간을 보려면, 1시간 전과 지금 값의 차이를 써요. <Term slug="foundations/counters-and-rate">카운터</Term>를 읽는 방법과 같아요.
  </Point>
</KeyPoints>

<Checkpoints>
  <Check>평균 시간 순으로만 줄 세운 화면은 다시 보세요. 하루 한 번 도는 배치가 맨 위에 오고, 1초에 수백 번 도는 SQL이 묻혀요. 총 시간과 호출 수를 함께 두세요.</Check>
  <Check>누적값을 그대로 그린 그래프는 다시 보세요. 시간이 갈수록 오르기만 해서, 지금 무엇이 무거운지 보이지 않아요. 초기화되면 값이 갑자기 0으로 떨어지기도 해요.</Check>
  <Check>항목 수가 상한(`pg_stat_statements.max`, 기본 5,000)에 닿으면 적게 불린 SQL부터 버려져요. 버린 횟수가 `pg_stat_statements_info`에서 늘고 있다면 상한을 올리세요.</Check>

<Deeper>
  ### pg_stat_statements 읽기

  주요 열은 `calls`(실행 횟수)와 `total_exec_time`(실행 시간 합, ms)이에요. `mean_exec_time`은 평균(ms), `rows`는 가져오거나 바꾼 행 수예요. 계획 시간(planning)은 `pg_stat_statements.track_planning`을 켜야 따로 세요.

  ```text
  -- 실행 시간 합 상위 5개 SQL
  SELECT queryid, calls, total_exec_time, mean_exec_time, query
  FROM pg_stat_statements
  ORDER BY total_exec_time DESC
  LIMIT 5;
  ```

  `pg_stat_statements.track`의 기본값은 `top`이라, 앱이 직접 보낸 SQL만 세요. 함수 안에서 부른 SQL까지 세려면 `all`로 바꿔요.

  ### 묶는 기준

  묶음은 SQL 글자가 아니라 해석한 뒤의 구조로 정해요. 그래서 상수 값만 다르면 한 항목이 되고, 글자가 같아도 `search_path` 설정이 달라 뜻이 다르면 따로 잡힐 수 있어요. 상수 자리 바꾸기와 `queryid`는 `compute_query_id`가 켜져 있을 때의 설명이에요.

  항목이 상한을 넘어 자주 버려지면, 묶이지 않은 상수 값이 그대로 보이는 항목이 생길 수 있어요. 문서는 이때도 `pg_stat_statements.max`를 올리라고 해요.

  ### 숫자의 예

  그림의 SQL A는 2ms × 1,000,000 = 2,000초, SQL B는 5초 × 10 = 50초예요. SQL A를 1ms 줄이면 1ms × 1,000,000 = 1,000초가 줄어요. SQL B를 반으로 줄여도 25초예요.
</Deeper>
