  <Point title="전체 사본에 로그를 더해 되살려요">
    전체 백업으로 그 시각까지 돌아간 뒤, 보관해 둔 로그를 다시 적용해 원하는 시각까지 나아가요.
  </Point>
  <Point title="복제는 백업이 아니에요">
    실수로 지운 데이터는 복제 서버에서도 바로 지워져요. 지난 시각으로 돌아가려면 백업이 있어야 해요.
  </Point>
  <Point title="되살려 봐야 백업이에요">
    백업 작업이 성공으로 끝나도, 실제로 되살려 보기 전에는 쓸 수 있는지 몰라요.
  </Point>
</KeyPoints>

<Analogy limit="식당 장부는 한 장이 빠져도 기억을 더듬어 메울 수 있지만, DB는 보관한 로그가 하나만 빠져도 그 뒤 시각으로는 되돌리지 못해요.">
  식당이 밤마다 장부 전체를 복사해 금고에 넣고, 낮의 주문 장부도 몇 분마다 사본을 보낸다고 해 봐요. 불이 나면 어젯밤 사본에 오늘 주문을 차례로 다시 적어, 원하는 시각의 장부를 만들어요. 앞의 사본이 전체 백업, 뒤의 사본이 로그 보관이에요.
</Analogy>

<Term term="database/logical-backup">논리 백업</Term>은 데이터를 다시 만들 수 있는 SQL이나 행으로 내보내요. PostgreSQL의 `pg_dump`는 시작한 순간의 스냅숏을 담고, 도는 동안 다른 작업을 막지 않아요. 대신 큰 DB는 내보내고 다시 넣는 데 오래 걸려요.

물리 백업은 데이터 파일을 그대로 복사해요. 되살릴 때 SQL을 다시 실행하지 않아서 빨라요. 아래의 시점 복구도 물리 백업 위에서 해요.

## 전체, 차등, 증분

전체 백업은 매번 모든 데이터를 담아요. 크고 오래 걸려서, 사이사이에 바뀐 것만 담는 백업을 섞어요.

차등 백업은 마지막 전체 백업 뒤 바뀐 것을 담아요. SQL Server가 이 방식을 써요. 되살릴 때는 전체 백업과 마지막 차등 백업 둘만 있으면 돼요.

증분 백업은 바로 앞 백업 뒤 바뀐 것만 담아요. 한 번은 작지만, 되살릴 때는 전체 백업 뒤의 증분을 모두 차례로 써야 해요. PostgreSQL은 17부터 `pg_basebackup --incremental`로 증분 백업을 떠요.

## 시점 복구: 전체 사본 + 로그

DB는 바꾼 내용을 먼저 로그에 적어요. 이 로그를 버리지 않고 따로 보관해 두면, 전체 백업 뒤의 변경을 다시 적용할 수 있어요. 로그는 <Term slug="database/logs-and-recovery">로그와 복구</Term>에서 다뤘어요.

그래서 전체 백업을 되살린 뒤 원하는 시각까지만 로그를 다시 적용하면, 그 시각의 모습으로 돌아가요. 이걸 <Term term="database/pitr">시점 복구</Term>(PITR)라고 해요.

DB마다 보관하는 로그가 달라요. PostgreSQL은 WAL을 보관하고, MySQL은 바이너리 로그(binlog)로 전체 백업 뒤의 변경을 다시 적용해요. SQL Server는 로그 백업을 떠요.

SQL Server는 복구 모델에 따라 시점 복구가 되는지 갈려요. 단순(simple) 복구 모델은 로그 백업이 없어서, 마지막 백업을 뜬 시각으로만 돌아가요. 전체(full) 복구 모델이어야 원하는 시각으로 돌아가요.

## 얼마나 잃고, 얼마나 멈추나: RPO와 RTO

백업 계획은 두 목표에서 시작해요. <Term term="database/rpo">RPO</Term>는 잃어도 되는 데이터를 시간으로 정한 목표예요. <Term term="database/rto">RTO</Term>는 서비스가 멈춰도 되는 최대 시간이에요.

하루에 한 번 전체 백업만 뜨면, 백업 직전에 사고가 나면 하루치를 잃어요. 로그를 몇 분마다 보관하면 잃는 양이 몇 분으로 줄어요.

되살리는 시간은 백업 크기와 다시 적용할 로그 양에 달려요. 마지막 전체 백업이 오래될수록 다시 적용할 로그가 많아서 오래 걸려요.

## 복제는 백업이 아니에요

<Term slug="database/replication">복제</Term>는 주 서버의 변경을 복제 서버로 곧바로 옮겨요. 서버 한 대가 고장 나도 버티게 해 주지만, 실수로 지운 표도 그대로 옮겨요.

## 관리형 DB에서는

Amazon RDS는 자동 백업을 정한 보관 기간 동안 남겨요. 보관 기간은 0~35일이고, 0이면 자동 백업이 꺼져요. 트랜잭션 로그는 5분마다 올려서, 보관 기간 안의 시각으로 되돌릴 수 있어요.

시점 복구는 원래 DB를 바꾸지 않고 새 DB 인스턴스를 만들어요. 그래서 되살린 뒤에는 앱이 새 주소를 보게 바꾸는 일이 남아요. 관리형 DB는 <Term slug="cloud/managed-databases">관리형 데이터베이스</Term>에서 다뤄요.

백업은 실패 횟수보다 마지막으로 성공한 시각을 봐요. 백업 작업이 아예 돌지 않으면 실패 기록도 남지 않아서, 실패만 세면 놓쳐요.

PostgreSQL은 `pg_stat_archiver`에서 로그 보관 상태를 보여 줘요. 마지막으로 보관한 시각은 `last_archived_time`, 실패 횟수는 `failed_count`예요.

보관이 계속 실패하면 옛 WAL을 지우지 못해 디스크가 차요. 이 흐름은 <Term slug="database/storage-growing">DB 저장 공간이 계속 늘 때</Term>에서 다뤄요.

RDS는 되돌릴 수 있는 가장 늦은 시각을 `LatestRestorableTime`으로 보여 줘요. 이 값이 지금보다 크게 뒤처졌다면, 그 사이로는 되돌릴 수 없어요.

<Deeper>
  ### pg_dump는 DB 하나씩 찍어요

  `pg_dump`는 DB 하나를 시작한 순간의 스냅숏으로 담아요. 여러 DB를 하나씩 덤프하면 DB끼리는 시각이 맞지 않아요. 사용자 같은 클러스터 전체 정보는 `pg_dumpall --globals-only`로 따로 담아요.

  ### 증분 백업을 되살릴 때

  PostgreSQL의 증분 백업은 `--incremental`에 앞선 백업의 매니페스트(백업 목록 파일)를 넘겨 떠요. 되살릴 때는 `pg_combinebackup`으로 앞선 백업들과 합쳐요. 증분 백업도 전체 백업처럼 그 뒤의 WAL이 모두 있어야 해요.

  ### SQL Server의 기본 복구 모델

  SQL Server Enterprise와 Standard는 전체 복구 모델이, Express는 단순 복구 모델이 기본이에요. 단순 복구 모델은 로그 백업을 지원하지 않아요.

  ### RDS 보관 기간의 기본값

  RDS 보관 기간을 정하지 않으면 API나 CLI로 만든 DB는 1일, 콘솔로 만든 DB는 7일이에요.
</Deeper>
