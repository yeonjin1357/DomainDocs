## 적중률은 캐시에서 찾은 블록의 비율이에요

DB는 데이터를 블록(PostgreSQL은 보통 8kB) 단위로 읽어요. 읽으려는 블록이 메모리의 버퍼 캐시에 있으면 적중이고, 없으면 디스크 쪽에서 가져와요. 적중률은 읽은 블록 중 캐시에서 찾은 블록의 비율이에요.

## 같은 블록을 많이 읽을수록 비율이 올라가요

나쁜 실행 계획은 같은 인덱스와 표 블록을 몇 번이고 다시 읽어요. 다시 읽는 블록은 대부분 캐시에 있어서, 일을 많이 할수록 적중률은 오히려 올라가요. 맨 위 예에서는 60배 많은 블록을 읽고도 적중률이 99.9%였어요.

## 캐시 밖 읽기도 디스크 읽기가 아닐 수 있어요

PostgreSQL의 적중은 자기 버퍼 캐시(`shared_buffers`)에서 찾은 것만 세요. 캐시에 없어 읽은 블록도 운영체제의 파일 캐시에서 나왔을 수 있어요. PostgreSQL은 운영체제 캐시에도 기대는 구조라서, 문서도 전용 서버의 `shared_buffers`를 메모리의 25%쯤에서 시작하라고 해요.

<Deeper>
  ### 그림의 숫자

  앞 글 「실행 계획 읽기」의 상황을 PostgreSQL 18.6(PGlite)에서 재현한 값이에요. `EXPLAIN (ANALYZE, BUFFERS)`로 쟀어요.

  낡은 통계의 Nested Loop는 `shared hit=84253 read=71`이었어요. 통계를 다시 모은 Hash Join은 `shared hit=1406`이었어요.

  적중률은 84,253 ÷ (84,253 + 71) = 99.92%와 1,406 ÷ 1,406 = 100%예요. 읽은 블록은 84,324 ÷ 1,406 ≈ 60배 차이예요.

  ### PostgreSQL에서 재기

  `pg_stat_database`의 `blks_hit`은 버퍼 캐시에서 찾은 횟수, `blks_read`는 캐시에 없어 읽은 블록 수예요. 둘 다 누적값이에요.

  ```text
  -- DB별 버퍼 캐시 적중률(누적값)
  SELECT datname, blks_hit, blks_read,
         round(blks_hit * 100.0
               / nullif(blks_hit + blks_read, 0), 2) AS hit_pct
  FROM pg_stat_database
  WHERE datname IS NOT NULL;
  ```

  SQL 하나의 블록 읽기는 `EXPLAIN (ANALYZE, BUFFERS)`가 노드마다 `shared hit`과 `read`로 보여 줘요. 누적으로는 `pg_stat_statements`의 `shared_blks_hit`, `shared_blks_read`가 같은 값이에요.

  ### shared_buffers

  기본값은 보통 128MB예요. 문서는 1GB 넘는 전용 DB 서버라면 메모리의 25%를 출발점으로 들어요. 운영체제 캐시에도 기대서, 40%를 넘게 주면 더 나아지기 어렵다고 해요.

  Oracle도 물리적 읽기(physical read)가 파일 시스템 캐시에서 채워질 수 있어서, 디스크 읽기와 같지 않다고 해요.
</Deeper>
