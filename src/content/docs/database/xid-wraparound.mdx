<Situation>
  PostgreSQL 로그에 아래 경고가 찍혀요: `must be vacuumed within 29999999 transactions`. 그대로 두면 이 숫자가 줄다가 쓰기가 막혀요.

  PostgreSQL은 트랜잭션마다 번호(XID)를 붙이는데, 이 번호는 32비트라 한 바퀴 돌아요. 오래된 행을 미리 얼려(freeze) 두지 않으면, 번호가 한 바퀴 돌 즈음 그 행이 미래의 것으로 보여요. PostgreSQL은 그 전에 쓰기를 막아 데이터를 지켜요.
</Situation>

<FirstLook>
  <Item title="얼마나 남았나">데이터베이스와 표의 XID 나이를 봐요.</Item>
  <Item title="무엇이 얼리기를 막나">오래 열린 트랜잭션, 준비된 트랜잭션, 복제 슬롯을 봐요.</Item>
  <Item title="VACUUM이 끝나나">막는 것을 치운 뒤 VACUUM을 끝까지 돌려요.</Item>
</FirstLook>

## 1. 왜 바닥나는지 알아 두세요

XID는 32비트라 약 42억 개를 쓰면 0으로 돌아와요. 그래서 PostgreSQL은 어느 순간이든 지금 번호에서 반 바퀴, 약 21억 개를 과거로 보고 나머지 반 바퀴를 미래로 봐요.

<Figure caption="XID는 고리처럼 돌아요. 지금 번호가 늘어나면 경계도 함께 돌아서, 얼리지 않은 오래된 행은 언젠가 경계를 넘어 미래의 것으로 보여요.">
  <XidRing aria-label="XID 고리. 위쪽 지금 XID에서 왼쪽 반 바퀴는 과거 약 21억, 오른쪽 반 바퀴는 미래 약 21억이고, 아래쪽 경계 바로 앞에 얼리지 않은 오래된 행이 있으며, 번호는 시계 방향으로 늘어나는 그림" />
</Figure>

<Term term="database/vacuum">VACUUM</Term>은 충분히 오래된 행을 얼려요. 얼린 행은 번호와 상관없이 늘 과거의 것으로 보여서 경계를 넘어도 괜찮아요. 그래서 XID 고갈은 결국 VACUUM이 얼리지 못해서 생겨요.

PostgreSQL은 단계마다 손을 써요. 아래는 가장 오래 얼리지 못한 XID의 나이(age) 기준이에요.

강제 autovacuum은 autovacuum을 꺼 두어도 돌아요. failsafe가 켜지면 VACUUM은 인덱스 정리 같은 일을 건너뛰고 속도 제한도 풀어, 얼리는 일부터 끝내요.

## 2. 얼마나 남았는지 보세요

데이터베이스마다 가장 오래 얼리지 못한 XID의 나이를 봐요. 21억(정확히는 2,147,483,648)에 가까울수록 위험해요.

```sql
SELECT datname,
  age(datfrozenxid)
FROM pg_database
ORDER BY 2 DESC;
```

나이가 많은 데이터베이스에 접속해서, 어느 표가 오래됐는지 봐요. 큰 표가 위에 있다면 VACUUM에 오래 걸려요.

```sql
SELECT c.oid::regclass AS tbl,
  age(c.relfrozenxid)
FROM pg_class c
WHERE c.relkind IN ('r', 'm')
ORDER BY 2 DESC
LIMIT 5;
```

**확인 방법**: `pg_stat_activity`에서 강제 autovacuum을 찾아요. 질의 칸 끝에 `(to prevent wraparound)`가 붙어요. 이 autovacuum은 잠금이 겹쳐도 저절로 멈추지 않으니, 끊지 말고 끝나기를 기다려요.

## 3. 얼리기를 막는 것을 찾으세요

VACUUM은 아직 누군가 볼 수 있는 행은 얼리지 못해요. 그래서 가장 오래된 열린 스냅숏이 얼릴 수 있는 선을 정해요. 이 선이 오래 멈춰 있으면 VACUUM을 아무리 돌려도 나이가 줄지 않아요.

선을 붙잡는 것은 대개 셋이에요. PostgreSQL 16에서 셋을 일부러 만들어 아래 질의로 모두 찾아냈어요.

- **오래 열린 트랜잭션**: 커밋하지 않고 쉬는 세션이에요.
- **준비된 트랜잭션**: 2단계 커밋(PREPARE TRANSACTION)을 하다 마무리되지 않은 것이에요.
- **버려진 복제 슬롯**: 없어진 복제 서버나 멈춘 CDC 도구가 쓰던 슬롯이에요.

```sql
SELECT pid, state,
  age(backend_xid) AS xid_age,
  age(backend_xmin) AS xmin_age
FROM pg_stat_activity
ORDER BY 4 DESC NULLS LAST;

SELECT gid, prepared,
  age(transaction)
FROM pg_prepared_xacts;

SELECT slot_name, active,
  age(xmin), age(catalog_xmin)
FROM pg_replication_slots;
```

나이가 큰 줄이 범인이에요. 질의를 돌리는 내 세션도 목록에 보이니 빼고 봐요.

열린 트랜잭션은 끝내거나 세션을 끊어요(`pg_terminate_backend`). 준비된 트랜잭션은 `COMMIT PREPARED`나 `ROLLBACK PREPARED`로 마무리해요. 버려진 슬롯은 지워요.

다만 아직 쓰는 복제 서버의 슬롯을 지우면 그 서버를 다시 만들어야 할 수 있어요.

**확인 방법**: `VACUUM (VERBOSE) 표이름`을 돌려 `removable cutoff` 줄을 봐요. `which was 302 XIDs old`처럼 얼릴 수 있는 선이 몇 XID 뒤처졌는지 나와요. 이 숫자가 계속 크다면 아직 선을 붙잡는 것이 있어요.

## 4. VACUUM으로 얼리세요

막는 것을 치운 뒤, 경고에 나온 데이터베이스에서 VACUUM을 돌려요. 시스템 카탈로그까지 얼리려면 슈퍼유저로 돌려야 해요. 나이가 많은 큰 표부터 하나씩 돌리면 진행을 보기 쉬워요.

가능하면 쓰기가 적은 시간에 돌려요. VACUUM도 디스크를 많이 읽고 써요. 다만 경고가 나온 뒤라면 시간을 고를 여유가 없어요.

## 5. 쓰기가 막혔다면

한계까지 3백만 개가 남으면 PostgreSQL은 새 XID가 필요한 명령을 거부해요. 이미 도는 트랜잭션은 이어 가고, 읽기 전용 질의는 돼요.

```text
ERROR:  database is not accepting
  commands to avoid wraparound
  data loss in database "shop"
HINT:  Stop the postmaster and
  vacuum that database in
  single-user mode.
```

PostgreSQL 16에서 실제로 띄운 메시지예요. 실제로는 ERROR와 HINT가 각각 한 줄이에요.

PostgreSQL 17부터는 ERROR 문구가 조금 바뀌었어요. HINT도 서버를 내리라는 대신 데이터베이스 전체 VACUUM을 권해요.

푸는 순서는 2~4단계와 같아요. 막는 것을 치우고, 일반 접속으로 VACUUM을 돌려요. PostgreSQL 16에서 이 상태를 만든 뒤 데이터베이스마다 VACUUM을 돌리니, 나이가 0으로 돌아오고 쓰기가 다시 됐어요.

16까지의 HINT는 single-user 모드를 권하지만, 지금 문서는 될 수 있으면 피하라고 해요. 서버를 내려야 하고, 고갈을 막는 안전장치도 꺼지기 때문이에요.

## 6. 미리 알림을 걸어 두세요

경고는 한계의 98%쯤에서야 나와요. 그래서 나이를 지표로 모아, 훨씬 앞에서 알려요. 예를 들어 한계의 절반(약 10억)을 넘으면 알리는 식으로 여유를 둬요.

강제 autovacuum 기준인 2억을 넘는 것 자체는 흔한 일이에요. 넘은 뒤에도 나이가 내려오지 않고 계속 오르는지가 신호예요. Amazon RDS에서는 `MaximumUsedTransactionIDs` 지표로 같은 값을 봐요.
