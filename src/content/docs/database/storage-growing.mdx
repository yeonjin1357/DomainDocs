<Situation>
  주문 DB의 디스크 사용량이 한 달 사이 60%에서 85%가 됐어요. 그런데 주문 수는 거의 그대로예요.

  DB 공간은 표의 데이터만 쓰지 않아요. 인덱스, 지운 행이 남긴 자리, 로그(WAL)도 함께 써요.

  무엇이 커졌는지 먼저 나누고, 정리를 막는 것을 찾아요. 예시는 PostgreSQL 기준이에요.
</Situation>

## 1. 무엇이 커졌는지 나눠 보세요

디스크가 차는 속도만 봐서는 원인을 알 수 없어요. 표마다 크기를 재고, 표 데이터와 인덱스를 나눠 봐요. `pg_total_relation_size`는 표와 그 인덱스를 합친 크기예요.

**확인 방법**: 아래 질의로 크기가 큰 표 10개를 봐요. 몇 시간 간격으로 두 번 돌려, 어느 표가 늘고 있는지 견줘요.

```text
-- 크기가 큰 표 10개(인덱스 포함)
SELECT relname,
  pg_size_pretty(
    pg_total_relation_size(relid)
  ) AS total,
  pg_size_pretty(
    pg_indexes_size(relid)
  ) AS indexes
FROM pg_stat_user_tables
ORDER BY
  pg_total_relation_size(relid)
  DESC
LIMIT 10;
```

- **표가 커졌다면**: 행 수가 그대로인지 보고 2단계로 가요.
- **표 밖에서 늘었다면**: 데이터 디렉터리의 `pg_wal`을 봐요. 4단계로 가요.
- **인덱스만 크다면**: 5단계로 가요.

## 2. 죽은 행이 쌓였는지 보세요

PostgreSQL은 행을 바꾸거나 지워도 옛 버전을 바로 지우지 않아요. 다른 트랜잭션이 아직 볼 수 있기 때문이에요. 원리는 <Term slug="database/concurrency">동시에 읽고 쓰기</Term>에 있어요.

이 죽은 행은 VACUUM이 치우고, 보통은 자동 VACUUM(autovacuum)이 알아서 돌아요.

기본 설정에서는 표 행 수의 20%에 50을 더한 만큼 행이 바뀌거나 지워지면 돌아요. 그래서 큰 표는 죽은 행이 꽤 쌓인 뒤에야 정리돼요. PostgreSQL 18부터는 이 기준에 1억 행이라는 상한이 붙어요.

**확인 방법**: 아래 질의로 죽은 행이 많은 표와 마지막 자동 VACUUM 시각을 봐요. 죽은 행이 살아 있는 행만큼 많은데 자동 VACUUM이 오래전이라면 3단계로 가요.

```text
-- 죽은 행이 많은 표 10개
SELECT relname, n_live_tup,
  n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```

## 3. 정리를 막는 것을 찾으세요

VACUUM은 아직 누군가 볼 수 있는 옛 행을 지우지 못해요. 그래서 오래 열린 트랜잭션 하나가 DB 전체의 정리를 붙잡을 수 있어요. PostgreSQL 문서는 이런 트랜잭션을 `pg_stat_activity`에서 `age(backend_xmin)`이 큰 줄로 찾으라고 해요.

복제 슬롯도 정리를 붙잡아요. 복제본이 오래 멈췄거나 이미 없어졌는데 슬롯이 남아 있으면, 그 슬롯이 옛 행과 로그를 계속 잡아 둬요.

**확인 방법**: 아래 두 질의를 돌려요. 첫째는 오래 열린 트랜잭션, 둘째는 쓰이지 않는(`active`가 false인) 복제 슬롯을 찾아요.

```text
-- 오래 열린 트랜잭션
SELECT pid, state, xact_start,
  age(backend_xmin) AS xmin_age
FROM pg_stat_activity
WHERE backend_xmin IS NOT NULL
ORDER BY xact_start
LIMIT 5;
-- 복제 슬롯
SELECT slot_name, active,
  wal_status,
  age(xmin) AS xmin_age
FROM pg_replication_slots;
```

`state`가 `idle in transaction`인 세션이 몇 시간째라면, 앱이 트랜잭션을 연 채 쉬고 있어요. 이 경우는 <Term slug="database/slow-database">DB가 느려졌을 때 어디부터 볼까</Term>의 잠금 단계에서도 다뤄요.

## 4. WAL이 쌓인다면 보내지 못한 곳을 보세요

`pg_wal` 디렉터리가 커진다면, 아직 지우지 못하는 로그가 쌓인 거예요. 로그가 왜 남는지는 <Term slug="database/logs-and-recovery">로그와 복구</Term>에서 다뤄요.

흔한 원인은 복제 슬롯이에요. 슬롯은 복제본이 받기 전까지 WAL을 지우지 못하게 잡아 둬요. `max_slot_wal_keep_size`의 기본값은 -1이라 한도가 없어서, 멈춘 슬롯 하나가 디스크를 채울 수 있어요.

**확인 방법**: 3단계의 복제 슬롯 질의에서 `active`가 false인 슬롯을 찾아요. 그 슬롯을 쓰던 복제본이 아직 필요한지 확인한 뒤, 필요 없다면 슬롯을 지워요. 복제가 밀리는 경우는 <Term slug="database/replication-lag">복제 지연</Term>에 있어요.

## 5. 쓰지 않는 인덱스를 보세요

인덱스도 공간을 쓰고, 행을 바꿀 때마다 함께 고쳐야 해요. 한 번도 쓰이지 않는 인덱스는 공간만 차지해요. 인덱스의 쓰임새는 <Term slug="database/indexes">인덱스</Term>에서 다뤄요.

**확인 방법**: 아래 질의로 통계를 초기화한 뒤 한 번도 쓰이지 않은 인덱스를 찾아요. 고유 제약을 지키는 인덱스는 조회에 안 쓰여도 필요하니 남겨요.

```text
-- 한 번도 쓰이지 않은 인덱스
SELECT relname, indexrelname,
  pg_size_pretty(
    pg_relation_size(indexrelid)
  ) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

보통의 VACUUM은 죽은 행 자리를 다시 쓸 수 있게 표시할 뿐, 대개 디스크에 돌려주지 않아요. 표 맨 끝의 페이지가 통째로 비었을 때만 예외로 줄어요. 그래서 큰 DELETE 뒤에도 디스크 사용량이 그대로인 게 정상이에요.

공간을 꼭 돌려받아야 하면 VACUUM FULL로 표를 새로 써요. 대신 그동안 표 전체에 ACCESS EXCLUSIVE 잠금이 걸려서 읽기도 막혀요. 새 표를 다 쓸 때까지 옛 표도 남아서, 표 크기만큼의 빈 공간도 더 필요해요.

## 다른 DB에서는

MySQL InnoDB도 지운 행의 자리를 표 파일 안에서 다시 써서, 파일 크기는 바로 줄지 않아요. 표마다 따로 파일을 쓰는 설정(`innodb_file_per_table`)이라면 `OPTIMIZE TABLE`을 써요. 표와 인덱스를 다시 정리해 공간을 운영체제에 돌려줘요.

SQL Server에서 로그 파일이 계속 커진다면 복구 모델과 로그 백업을 봐요. <Term slug="database/logs-and-recovery">로그와 복구</Term>에서 다뤘어요.
