## 실행 계획은 노드를 쌓은 나무예요

## 예상과 실제 행 수가 다른 곳을 찾아요

`EXPLAIN ANALYZE`는 SQL을 실제로 실행해, 노드마다 걸린 시간과 실제 행 수를 함께 보여 줘요. PostgreSQL 문서는 예상 행 수가 실제와 가까운지가 보통 가장 중요하다고 해요.

예상이 크게 빗나가면 그 자리에 맞지 않는 방법을 고르기 쉬워요. 앞 그림처럼 8건을 예상하고 고른 Nested Loop는, 12,000건 앞에서 안쪽 찾기를 12,000번 돌려요. 통계를 다시 모으자 예상이 11,978건이 되고, DB는 Hash Join으로 바꿨어요.

## loops를 곱해야 그 노드의 전체 시간이에요

노드가 여러 번 실행되면, 표시된 시간과 행 수는 한 번 실행의 평균이에요. `loops` 값을 곱해야 그 노드에서 쓴 전체 시간이에요. 안쪽 찾기가 한 번에 0.1ms라도, 그림처럼 12,000번이면 1,200ms예요.

<Checkpoints>
  <Check>`UPDATE`나 `DELETE`를 `EXPLAIN ANALYZE`로 볼 때는 조심하세요. 실제로 실행되어 데이터가 바뀌어요. `BEGIN`과 `ROLLBACK` 사이에서 실행해요.</Check>
  <Check>`cost` 값을 밀리초로 읽는 화면이나 설명은 고치세요. `cost`는 디스크 페이지 하나를 차례로 읽는 비용을 1로 둔 임의 단위예요.</Check>
  <Check>SQL은 그대로인데 실행 시간이 갑자기 늘었다면, 큰 데이터 변경 뒤 통계를 다시 모았는지 보세요. 옵티마이저는 `ANALYZE`가 모은 통계로 행 수를 예상해서, 통계가 낡으면 계획이 나빠질 수 있어요. 순서는 <Term slug="database/plan-changed">실행 계획이 갑자기 바뀌었을 때</Term>에 있어요.</Check>
  <Check>운영 중 느렸던 실행의 계획을 보려면 `auto_explain`을 쓰세요. `auto_explain.log_min_duration`보다 오래 걸린 SQL의 계획을 로그에 남겨요. 기본값 -1은 꺼져 있어요.</Check>
</Checkpoints>

<Deeper>
  ### 출력 읽기

  PostgreSQL 문서의 예를 일부 줄여 옮겼어요. 들여 쓴 노드가 바로 위 노드에 행을 올려 줘요.

  ```text
  Nested Loop  (cost=4.65..118.50 rows=10 width=488) (actual time=0.017..0.051 rows=10.00 loops=1)
    ->  Bitmap Heap Scan on tenk1 t1  (… rows=10 …) (actual time=0.009..0.017 rows=10.00 loops=1)
    ->  Index Scan using tenk2_unique2 on tenk2 t2  (… rows=1 …) (actual time=0.003..0.003 rows=1.00 loops=10)
  ```

  괄호 안 앞쪽은 예상이에요. `cost=4.65..118.50`은 첫 행을 내기까지와 끝까지의 비용, `rows`는 예상 행 수, `width`는 행 하나의 평균 바이트예요. 뒤쪽 `actual time`은 첫 행과 마지막 행까지의 실제 밀리초예요.

  안쪽 Index Scan은 바깥 행마다 한 번씩, 10번 돌았어요. 그래서 0.003ms × 10 = 0.030ms가 이 노드에서 쓴 전체 시간이에요.

  ### cost 계산의 예

  옵티마이저는 관례로 차례 읽기 한 페이지(`seq_page_cost`)를 1.0, 행 하나 처리(`cpu_tuple_cost`)를 0.01로 둬요. 345페이지에 10,000행인 표를 전체 훑으면 (345 × 1.0) + (10,000 × 0.01) = 445예요.

  ### 실행 시간에 드는 것

  `EXPLAIN ANALYZE`의 Execution time에는 실행기 준비·정리와 트리거 시간이 들어요. 구문 분석, 재작성, 계획 세우기 시간은 빠져요.

  ### 통계

  옵티마이저 통계는 `pg_statistic`에 담기고, `ANALYZE`나 `VACUUM ANALYZE`가 갱신해요. 막 갱신해도 근삿값이에요. 문서는 통계가 정확하지 않으면 나쁜 계획을 골라 성능이 떨어질 수 있다고 해요.
</Deeper>
