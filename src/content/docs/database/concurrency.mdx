  <Point title="읽는 쪽은 커밋된 버전을 봐요">

  </Point>

## 같은 행을 바꾸면 기다려요

두 세션이 같은 주문의 상태를 동시에 바꾸려 한다고 해 봐요. 먼저 온 세션이 그 행에 <Term term="database/row-lock">행 잠금</Term>을 걸어요. 뒤에 온 세션은 앞 세션의 트랜잭션이 끝날 때까지 기다려요.

이 잠금은 같은 행을 바꾸려는 쪽만 막아요. 그 행을 읽기만 하는 쪽은 막지 않아요. 기다리는 세션이 줄줄이 이어지는 모습과 교착은 <Term slug="database/locks-and-blocking">잠금과 블로킹</Term>에서 다뤄요.

## 읽기는 커밋된 버전을 봐요

읽는 쪽까지 잠금을 기다리면, 쓰기가 많은 DB에서는 조회가 한참 멈춰요. 그래서 대부분의 DB는 한 행의 여러 버전을 함께 들고 있어요. 이 방식을 <Term term="database/mvcc">MVCC</Term>(다중 버전 동시성 제어)라고 불러요.

읽는 쪽은 자기가 시작한 시점에 커밋돼 있던 데이터만 봐요. 이렇게 한 시점에 고정된 데이터를 <Term term="database/snapshot">스냅숏</Term>이라고 불러요.

옛 버전을 어디에 두는지는 DB마다 달라요.

| DB | 옛 버전을 두는 곳 |
| --- | --- |
| PostgreSQL | 테이블 안에 옛 행을 그대로 남겨요 |
| Oracle | 언두(undo)에 옛 값을 따로 둬요 |
| MySQL InnoDB | 언두 로그에 옛 값을 따로 둬요 |
| SQL Server | 기본 설정에서는 버전을 쓰지 않아요 |

SQL Server는 기본 설정(`READ_COMMITTED_SNAPSHOT` 꺼짐)에서 읽기에도 공유 잠금을 써요. 그래서 바뀌는 중인 행을 읽으려면 쓰는 쪽이 끝날 때까지 기다려요. 이 설정을 켜면 다른 DB처럼 행 버전을 읽어요.

## 옛 버전은 나중에 치워요

PostgreSQL에서 행을 바꾸거나 지워도 옛 버전은 바로 사라지지 않아요. 다른 트랜잭션이 아직 볼 수 있기 때문이에요. 볼 트랜잭션이 없어지면 <Term term="database/vacuum">VACUUM</Term>이 그 자리를 치워 다시 쓰게 해요.

그런데 오래 열린 트랜잭션이 하나 있으면, 그 트랜잭션이 볼 수도 있는 옛 버전은 모두 남겨 둬야 해요. 그동안 테이블과 인덱스에 치우지 못한 옛 행이 쌓여 점점 커져요.

잠금 대기는 <Term slug="database/active-sessions">액티브 세션</Term>의 대기 종류로 보여요. PostgreSQL은 Lock, SQL Server와 Oracle은 잠금 관련 대기 이벤트로 나와요.

<Deeper>
  ### 스냅숏을 뜨는 시점

  PostgreSQL의 기본 격리 수준(READ COMMITTED)에서는 문장마다 그 문장이 시작할 때의 스냅숏을 봐요. 그래서 한 트랜잭션 안에서도 두 번째 SELECT는 그 사이 커밋된 변경을 볼 수 있어요.

  REPEATABLE READ에서는 트랜잭션의 첫 문장을 시작할 때 뜬 스냅숏을 끝까지 써요. 같은 SELECT를 여러 번 해도 결과가 같아요.

  ### 행 잠금과 조회

  PostgreSQL 문서는 행 잠금이 조회에 영향을 주지 않는다고 해요. 같은 행을 바꾸거나 잠그려는 쪽만 막아요. `SELECT … FOR UPDATE`는 읽은 행을 바꿀 때처럼 잠가서, 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 행을 바꾸지 못하게 해요.

  ### Oracle과 InnoDB의 언두

  Oracle은 언두 세그먼트에 커밋 전이거나 최근 커밋된 변경의 옛 값을 둬요. 쓰는 중인 행을 읽으면 이 언두로 일관된 옛 모습을 만들어 보여 줘요. 그래서 Oracle 문서는 읽기와 쓰기가 서로를 막지 않는다고 해요.

  MySQL InnoDB도 바뀐 행의 옛 정보를 언두 테이블스페이스의 롤백 세그먼트에 둬요. 이 정보로 롤백도 하고, 일관된 읽기를 위해 행의 옛 버전도 만들어요.
</Deeper>
