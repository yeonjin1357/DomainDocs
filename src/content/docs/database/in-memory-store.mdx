## 메모리에 둬서 빨라요

<Term term="database/in-memory-store">인메모리 저장소</Term>인 Redis는 키와 값을 서버 메모리에 둬요. 문자열, 목록, 해시, 집합 같은 자료 구조를 그대로 다뤄요. 그래서 <Term slug="apm/cache">캐시</Term>, 로그인 세션, 순위표, 작업 대기열에 자주 써요.

AWS의 ElastiCache는 Redis OSS와 Valkey 엔진을 관리형으로 띄워 줘요. ElastiCache 문서에 따르면 두 엔진의 지표는 같아요.

Redis는 명령을 실행하는 스레드가 하나예요. 명령이 짧아서 보통은 문제가 없지만, 오래 걸리는 명령 하나가 그동안 들어온 모든 명령을 기다리게 해요.

대표적인 것이 모든 키를 훑는 `KEYS`예요. Redis 문서는 키 100만 개를 훑는 데 보급형 노트북에서 40ms쯤 걸린다고 해요. 그리고 운영 코드에서 쓰지 말라고 경고해요.

키를 나눠 훑으려면 `SCAN`을 써요. 아주 큰 목록이나 집합을 통째로 읽는 명령도 같은 이유로 조심해요.

## 메모리 한도와 축출

`maxmemory`는 데이터에 쓸 메모리 한도예요. 64비트 서버의 기본값은 0이라 한도가 없어요. 한도를 두지 않으면 서버 메모리를 다 쓸 때까지 늘어요.

한도에 닿으면 `maxmemory-policy`대로 움직여요. 기본값 `noeviction`은 키를 지우지 않고, 새 데이터를 넣는 명령에 아래 에러를 돌려줘요. 읽기만 하는 명령은 그대로 돼요.

```text
OOM command not allowed when used memory > 'maxmemory'.
```

캐시로만 쓴다면 `allkeys-lru`처럼 덜 쓴 키를 지우는 정책을 골라요. 이렇게 지우는 일을 <Term term="apm/eviction">축출</Term>이라고 하고, 지운 키 수는 INFO의 `evicted_keys`로 세요.

## 디스크에 남기는 법

메모리의 데이터는 서버가 꺼지면 사라져요. 그래서 디스크에 남기는 방법을 골라요.

| 방식 | 하는 일 | 잃을 수 있는 것 |
| --- | --- | --- |
| RDB | 정한 간격마다 전체를 스냅숏 파일로 저장 | 마지막 스냅숏 뒤의 쓰기 |
| AOF | 쓰기 명령을 파일 끝에 계속 덧붙임 | 기본 설정이면 마지막 1초쯤 |
| 둘 다 끔 | 메모리에만 둬요 | 다시 뜨면 전부 |

<Term term="database/rdb">RDB</Term>는 저장할 때 프로세스를 복제(fork)해서 자식 프로세스가 파일을 써요. 데이터가 크면 fork 자체에 시간이 걸려 그동안 명령이 멈춰요. 문서는 데이터가 아주 크고 CPU가 느리면 1초까지도 멈출 수 있다고 해요.

<Term term="database/aof">AOF</Term>의 기본 fsync 정책은 1초마다예요. 그래서 갑자기 꺼지면 마지막 1초쯤의 쓰기를 잃을 수 있어요.

기본으로 보는 것은 메모리, 축출, 적중률, 연결 수예요. Redis INFO 필드와 ElastiCache 지표는 이렇게 짝지어져요.

| 보는 것 | INFO 필드 | ElastiCache 지표 |
| --- | --- | --- |
| 메모리 사용 | `used_memory` | BytesUsedForCache, DatabaseMemoryUsagePercentage |
| 지워진 키 | `evicted_keys` | Evictions |
| 적중률 | `keyspace_hits`, `keyspace_misses` | CacheHitRate |
| 연결 | `connected_clients` | CurrConnections |
| 명령 실행 스레드의 CPU | 없음 | EngineCPUUtilization |

명령을 실행하는 스레드가 하나라서, 서버 CPU 사용률이 낮아 보여도 그 스레드는 꽉 찼을 수 있어요. 4 vCPU 서버에서 스레드 하나가 꽉 차면 서버 전체로는 25%예요. ElastiCache는 그 스레드만 잰 EngineCPUUtilization을 따로 줘요.

느린 명령은 <Term term="database/slowlog">SLOWLOG</Term>로 찾아요. 기본으로 10ms(10000마이크로초)보다 오래 걸린 명령을 최근 128개까지 남겨요. 이 시간에는 클라이언트와 주고받은 시간이 빠지고 실행 시간만 들어요.

<Checkpoints>
  <Check>서버 CPU가 25%라서 여유 있다고 판단했다면 다시 보세요. 4 vCPU에서 명령 스레드 하나가 꽉 차도 25%로 보여요. EngineCPUUtilization을 보세요.</Check>
  <Check>쓰기가 OOM 에러로 실패한다면 maxmemory-policy가 noeviction인지 보세요. 캐시 용도라면 축출 정책을 골라야 해요.</Check>
  <Check>앱 코드나 운영 스크립트에 KEYS가 있다면 SCAN으로 바꾸세요. 키가 많으면 그동안 모든 명령이 멈춰요.</Check>
  <Check>SLOWLOG가 비어 있는데 응답이 느리다면 네트워크와 대기 시간을 의심하세요. SLOWLOG는 실행 시간만 재요.</Check>
  <Check>스냅숏을 뜨는 시각마다 지연이 튄다면 INFO의 `latest_fork_usec`을 보세요. fork에 걸린 시간만큼 멈췄을 수 있어요.</Check>
</Checkpoints>

<Deeper>
  ### 축출 정책의 종류

  `allkeys-`로 시작하는 정책은 모든 키에서 고르고, `volatile-`로 시작하는 정책은 만료 시간(TTL)이 있는 키에서만 골라요. 고르는 기준은 덜 최근에 쓴 것(lru), 덜 자주 쓴 것(lfu), 무작위(random) 등이에요. `volatile-ttl`은 남은 만료 시간이 가장 짧은 키를 골라요.

  `volatile-` 정책인데 만료 시간이 있는 키가 하나도 없으면, `noeviction`처럼 쓰기를 거절해요.

  ### 적중률 계산

  Redis 문서의 적중률은 `keyspace_hits / (keyspace_hits + keyspace_misses)`예요. 두 값은 서버가 뜬 뒤 계속 늘어나는 수라서, 구간 사이의 차이로 계산해야 지금의 적중률이 나와요.

  ### 네트워크 입출력 스레드

  redis.conf의 `io-threads`로 네트워크 입출력에 스레드를 더 쓸 수 있어요. 기본은 꺼져 있어요.
</Deeper>
