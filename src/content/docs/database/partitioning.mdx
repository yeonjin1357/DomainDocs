<KeyPoints>
  <Point title="큰 표를 기준으로 나눠 담아요">
    파티셔닝은 한 표를 날짜 같은 기준 열로 여러 칸(<Term term="database/partition">파티션</Term>)에 나눠 담는 거예요. 앱은 그대로 한 표처럼 써요.
  </Point>
  <Point title="조건에 맞는 칸만 읽어요">
    기준 열로 거르는 SQL은 맞는 칸만 읽어요. 이걸 파티션 가지치기라고 해요.
  </Point>
  <Point title="오래된 데이터는 칸째 지워요">
    지난 달 데이터를 DELETE로 한 줄씩 지우는 대신, 그 칸을 통째로 떼거나 지워요. 훨씬 빠르고 뒷정리도 없어요.
  </Point>
</KeyPoints>

<Analogy limit="캐비닛은 서랍이 많아도 관리할 게 늘지 않지만, 파티션은 칸마다 인덱스와 통계를 따로 가져요. 칸이 너무 많으면 계획을 세우는 데도 시간이 들어요.">
  서류를 달마다 서랍 하나에 넣는 캐비닛과 같아요. 3월 서류를 찾을 땐 3월 서랍만 열고, 보관 기간이 지난 서랍은 통째로 비워요.
</Analogy>

나누는 기준은 세 가지예요.

| 방식 | 나누는 법 | 흔한 예 |
| --- | --- | --- |
| 범위(range) | 값의 구간마다 한 칸 | 날짜별 로그, 주문 |
| 목록(list) | 정해 둔 값마다 한 칸 | 나라별, 지점별 |
| 해시(hash) | 값을 해시해 고르게 | 고객 번호를 고르게 나눌 때 |

PostgreSQL에서는 먼저 기준을 정한 빈 부모 표를 만들고, 칸을 하나씩 붙여요.

```sql
create table events (
  id bigint,
  created_at date not null,
  body text
) partition by range (created_at);

create table events_2026_03
  partition of events
  for values from ('2026-03-01')
             to ('2026-04-01');
```

범위의 끝값은 그 칸에 들어가지 않아요. 3월 칸은 3월 1일부터 4월 1일 직전까지예요.

## 조건에 맞는 칸만 읽어요

기준 열로 거르면, DB는 맞지 않는 칸을 아예 읽지 않아요. 이걸 <Term term="database/partition-pruning">파티션 가지치기</Term>(partition pruning)라고 해요.

<Figure caption="2026년 한 해를 달마다 12칸으로 나누고 120만 행을 넣어, PostgreSQL 18에서 계획을 본 결과예요.">
  <Compare
    columns={['기준 열로 거름', '기준 열 없이 거름']}
    rows={[
      { label: '조건', values: ['created_at이 3월', 'body = …'] },
      { label: '읽은 칸', values: ['3월 칸 1개', '12칸 모두'] },
    ]}
  />
</Figure>

값을 실행할 때에야 아는 경우도 가지치기가 돼요. 같은 SQL을 미리 준비해 두고 날짜만 바꿔 실행했더니, 계획에 `Subplans Removed: 11`이 찍혔어요. 12칸 중 11칸을 실행할 때 뺐다는 뜻이에요.

반대로 기준 열을 거르지 않는 SQL은 모든 칸을 읽어요. 칸마다 인덱스가 있어도 칸 수만큼 찾아야 해요. 그래서 기준 열은 가장 자주 거르는 열로 골라요.

## 오래된 데이터는 칸째 지워요

<Figure caption="같은 데이터를 나누지 않은 표와 나눈 표에 넣고, 1월 데이터 약 10만 행을 지운 시간이에요.">
  <StatTile label="DELETE로 지우기" value="135" unit="ms" tone="warn" note="죽은 행 10만 개 남음" />
  <StatTile label="1월 칸 DROP" value="6" unit="ms" note="뒷정리 없음" />
</Figure>

DELETE는 행을 하나씩 지우고, 지운 행은 VACUUM이 치울 때까지 자리를 차지해요. 칸을 `DROP TABLE`로 지우거나 `DETACH PARTITION`으로 떼면 이 뒷정리가 없어요. PostgreSQL 문서도 이 방법이 대량 DELETE보다 훨씬 빠르다고 해요.

그래서 보관 기간이 정해진 로그나 이벤트 표에 잘 맞아요. 지운 행이 쌓이는 문제는 <Term slug="database/storage-growing">DB 저장 공간이 계속 늘 때</Term>에서 다뤄요.

## 지켜야 할 제약

- **기본 키에 기준 열이 들어가야 해요**: 나눈 표의 기본 키나 고유 제약에는 기준 열이 모두 들어가야 해요. 빼고 만들면 에러가 나요.
- **칸이 없는 값은 못 넣어요**: 맞는 칸이 없는 행을 넣으면 에러가 나요. 다음 달 칸은 미리 만들어 둬요.
- **칸을 너무 많이 두지 않아요**: 문서는 가지치기로 대부분의 칸이 빠진다면 칸 수천 개까지는 무난하다고 해요. 칸이 많을수록 계획 시간과 메모리가 늘어요.

앞의 두 경우를 PostgreSQL 18에서 재현한 에러 문구예요.

```text
unique constraint on
partitioned table must include
all partitioning columns

no partition of relation
"events" found for row
```

크기와 행 수 같은 통계는 칸마다 따로 쌓여요. 표 단위 화면이라면 칸을 부모 표로 묶어 합계를 보여 줘야 해요.

다음 달 칸이 미리 만들어져 있는지도 지켜봐요. 월초에 칸이 없으면 그 시각부터 넣기가 모두 실패해요.

<Deeper>
  ### 기본 칸

  맞는 칸이 없는 행을 받아 줄 기본 칸(`DEFAULT`)을 둘 수 있어요. 다만 기본 칸에 이미 들어간 날짜로 새 칸을 만들려 하면, 기본 칸의 행이 새 칸 범위와 겹쳐 만들기가 실패해요. 재현에서는 'updated partition constraint for default partition'으로 시작하는 에러가 났어요.

  ### 다른 DB에서는

  MySQL, Oracle, SQL Server도 범위·목록·해시 같은 나누기를 지원해요. 문법과 제약은 DB마다 달라서, 쓰는 DB의 문서를 따로 봐요.
</Deeper>
