## 1. 교착 에러인지 확인하세요

DB는 교착을 스스로 찾아 한쪽 트랜잭션을 실패시키고 되돌려요. 남은 쪽은 잠금을 얻어 그대로 끝나요. 실패한 쪽이 받는 에러는 DB마다 달라요.

| DB | 에러 |
| --- | --- |
| PostgreSQL | `deadlock detected`, SQLSTATE 40P01 |
| MySQL | 1213 `ER_LOCK_DEADLOCK`, SQLSTATE 40001 |
| Oracle | ORA-00060 |
| SQL Server | 1205 |

PostgreSQL은 잠금을 `deadlock_timeout`(기본 1초)만큼 기다린 뒤에 교착인지 검사해요. 재현에서도 두 번째 트랜잭션이 엇갈린 지 1초 뒤에 한쪽이 에러를 받았어요.

## 2. 서버 로그에서 두 SQL을 찾으세요

앱이 받는 에러에는 어느 SQL끼리 엇갈렸는지가 다 나오지 않아요. PostgreSQL은 서버 로그에 두 프로세스와 각자의 SQL을 함께 남겨요.

```text
ERROR:  deadlock detected
DETAIL:  Process 645 waits for
  ShareLock on transaction 756;
  blocked by process 646.
  Process 646 waits for
  ShareLock on transaction 755;
  blocked by process 645.
  Process 645: update accounts
    set balance = balance + 10
    where id = 2
  Process 646: update accounts
    set balance = balance + 10
    where id = 1
```

PostgreSQL 18로 재현한 로그예요. 645번은 646번의 트랜잭션을, 646번은 645번의 트랜잭션을 기다려요. 그 아래 두 줄이 각자 막힌 SQL이에요.

다른 DB에서 보는 곳은 이래요.

- **MySQL**: `SHOW ENGINE INNODB STATUS`의 LATEST DETECTED DEADLOCK에 마지막 교착만 남아요. 모두 남기려면 `innodb_print_all_deadlocks`를 켜서 에러 로그에 써요.
- **Oracle**: 문서가 트레이스 파일에서 관련 트랜잭션과 자원을 보라고 해요.
- **SQL Server**: 기본으로 켜진 `system_health` 세션이 교착 그래프(`xml_deadlock_report`)를 남겨요.

PostgreSQL 문서는 교착을 막는 가장 좋은 방법으로 일관된 잠금 순서를 들어요. 이체라면 보내는 쪽·받는 쪽과 상관없이 계좌 번호가 작은 행부터 바꿔요. 그러면 두 트랜잭션이 같은 행에서 줄을 서고, 엇갈리지 않아요.

## 4. 다시 시도하게 하세요

순서를 맞춰도 교착을 모두 없애기는 어려워요. 그래서 앱은 교착 에러를 받으면 트랜잭션을 처음부터 다시 시도해야 해요. MySQL의 에러 문구도 'try restarting transaction'이에요.

다시 시도할 때는 실패한 SQL 하나가 아니라 트랜잭션 전체를 다시 해요. 실패한 쪽 트랜잭션은 이미 통째로 되돌려졌기 때문이에요. 몇 번까지 다시 할지와 사이 간격도 정해 둬요.

## 5. 얼마나 자주 나는지 세세요

PostgreSQL은 `pg_stat_database`의 `deadlocks`에 DB마다 교착 횟수를 쌓아요. 재현 뒤 이 값이 1 올랐어요. 계속 쌓이는 값이라, 하루에 몇 번 늘었는지로 봐요.

배포 뒤 이 값이 갑자기 는다면, 새 코드가 잠그는 순서를 바꾸지 않았는지 봐요.
