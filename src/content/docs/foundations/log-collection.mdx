## 로그가 지나는 길

앱은 로그를 파일에 쓰거나 표준 출력(stdout)으로 내보내요. 컨테이너가 표준 출력으로 낸 로그는 노드의 파일로 저장되고, 에이전트는 그 파일을 읽어요.

수집 에이전트는 Fluent Bit, OpenTelemetry Collector 같은 프로그램이에요. 서버마다 하나씩 돌며 정해 둔 경로의 파일을 따라 읽어요.

검색 화면에 로그가 보이려면 이 길을 모두 지나야 해요. 그래서 로그가 안 보이면 어느 구간에서 멈췄는지부터 가려요. 그 순서는 <Term slug="foundations/logs-missing">로그가 안 들어올 때</Term>에 있어요.

## 어디까지 읽었는지 기록해요

에이전트는 파일마다 마지막으로 읽은 위치(오프셋)를 기록해요. Fluent Bit은 이 기록을 `db` 설정으로 정한 파일에 두고, 다시 시작하면 그 위치부터 이어 읽어요.

위치 기록이 없으면, 시작할 때 이미 있던 파일을 어디부터 읽을지 기본값이 정해요. Fluent Bit tail과 OpenTelemetry Collector의 filelog는 기본으로 파일 끝부터 읽어요. 그래서 에이전트가 꺼져 있던 동안 쓴 줄은 다시 켜도 읽지 않아요.

갑자기 죽었을 때는 반대로 겹칠 수 있어요. Fluent Bit 문서는 이때 기록이 실제로 보낸 위치보다 조금 뒤처질 수 있다고 해요. 그래서 다시 시작하면 이미 보낸 줄을 조금 다시 보내요.

## 회전할 때 빠지거나 겹쳐요

로그 파일은 계속 커져서, 일정 크기나 기간마다 이름을 바꿔 보관하고 새 파일에 써요. 이 일을 로그 회전이라고 하고, 리눅스에서는 logrotate가 흔해요.

복사 후 비우기(copytruncate)는 앱이 파일을 다시 열지 못할 때 써요. logrotate 문서도 복사와 비우기 사이에 아주 짧은 틈이 있어 로그를 잃을 수 있다고 적어요.

이름을 바꾸는 방식이면, 에이전트는 이름이 바뀐 파일을 잠시 더 따라 읽어 남은 줄을 마저 가져가요. Fluent Bit은 기본으로 5초 동안 더 읽어요(`rotate_wait`).

쿠버네티스에서는 kubelet이 컨테이너 로그를 회전해요. 기본으로 10Mi마다 회전하고, 컨테이너마다 파일 5개까지 남겨요. 로그가 아주 빨리 쌓여 에이전트가 따라 읽기 전에 오래된 파일이 지워지면, 그 줄은 사라져요.

## 저장소가 막히면 쌓였다가 버려져요

에이전트는 읽은 로그를 묶음(chunk)으로 모아 보내요. 저장소가 느리거나 응답하지 않으면 묶음을 버퍼에 두고 다시 보내요.

Fluent Bit은 재시도 한도(`Retry_Limit`)를 넘긴 묶음을 버려요. 기본값이 1이라, 따로 정하지 않으면 한 번 다시 보내 실패한 묶음은 사라져요. 저장소 점검처럼 몇 분 멈추는 일이 있다면 한도를 넉넉히 잡아요.

메모리 버퍼에 한도(`mem_buf_limit`)를 걸면, 한도에 닿을 때 그 파일 읽기를 잠시 멈춰요. 멈춘 사이에 복사 후 비우기 회전이 일어나면, 아직 읽지 않은 줄을 잃을 수 있어요.

## 한 줄이 로그 하나예요

에이전트는 보통 줄바꿈 하나를 로그 하나로 봐요. 그래서 여러 줄짜리 스택 트레이스는 따로 묶지 않으면 줄마다 다른 로그로 쪼개져요. Fluent Bit tail과 OpenTelemetry filelog 모두 여러 줄을 하나로 묶는 설정이 있어요.

로그를 JSON 한 줄처럼 구조화해서 쓰면, 레벨이나 trace id 같은 값을 필드로 찾을 수 있어요. 글자 검색보다 정확하고, 알림도 필드 값으로 걸 수 있어요. trace id로 트레이스와 잇는 법은 <Term slug="foundations/logs-metrics-traces">로그, 메트릭, 트레이스</Term>에서 다뤄요.

아주 긴 한 줄도 조심해요. Fluent Bit tail은 한 줄이 버퍼 한도(`buffer_max_size`, 기본 32k)를 넘으면 그 파일을 더 따라 읽지 않아요. `skip_long_lines`를 켜면 긴 줄만 건너뛰고 계속 읽어요.

## 모니터링에서는

에이전트도 자기 지표를 내요. Fluent Bit은 HTTP 서버를 켜면 `/api/v2/metrics/prometheus`에서 지표를 내보내요.

| 지표 | 뜻 |
| --- | --- |
| `fluentbit_input_bytes_total` | 입력이 읽어 들인 바이트 |
| `fluentbit_output_proc_records_total` | 보내는 데 성공한 로그 수 |
| `fluentbit_output_retries_total` | 다시 보내기를 요청한 횟수 |
| `fluentbit_output_retries_failed_total` | 재시도 한도를 넘겨 버린 묶음 수 |
| `fluentbit_output_dropped_records_total` | 버린 로그 수 |

이 숫자들은 카운터라서 <Term slug="foundations/counters-and-rate">rate</Term>로 봐요. 버린 로그 수가 0보다 커지면, 그 시각의 로그는 검색해도 나오지 않아요.

<Deeper>
  ### 시작 뒤에 새로 생긴 파일

  Fluent Bit tail은 시작할 때 이미 있던 파일과, 그 뒤에 새로 찾은 파일을 다르게 다뤄요. 위치 기록이 없으면 앞의 것은 끝부터 읽어요. `read_from_head`의 기본값이 false이기 때문이에요.

  뒤의 것은 처음부터 읽어요. `read_newly_discovered_files_from_head`의 기본값이 true이기 때문이에요.

  새 파일은 파일 목록을 다시 훑을 때 찾아요. 기본 간격(`refresh_interval`)이 60초라, 새 파일은 최대 1분쯤 늦게 읽기 시작할 수 있어요.

  ### 회전한 파일을 다시 읽는 실수

  Fluent Bit 문서는 경로 패턴(`Path`)이 회전된 파일까지 고르면, 그 파일을 다시 읽어 로그가 겹친다고 경고해요. `app.log*`처럼 넓게 잡지 말고 `app.log`만 골라요.

  ### OpenTelemetry Collector의 위치 기록

  filelog 수신기는 저장소 확장(`storage`)을 정하지 않으면 위치를 메모리에만 둬요. 그래서 Collector를 다시 시작하면 위치를 잃고, `start_at` 기본값(end)대로 끝부터 읽어요.
</Deeper>
