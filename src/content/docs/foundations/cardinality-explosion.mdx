<Situation>
  배포하고 나서 Prometheus 메모리가 계속 오르고, 대시보드 질의가 느려져요. 전체 <Term slug="foundations/time-series-and-labels">시계열</Term> 수(`prometheus_tsdb_head_series`)를 그려 보면 배포 시각부터 가파르게 올라가 있어요.

  먼저 의심할 것은 값이 끝없이 늘어나는 레이블(label, 키와 값의 쌍) 하나예요. 새 값마다 시계열이 생기고, 시계열마다 메모리와 디스크를 써요. 그래서 늘어난 지표와 레이블을 찾아 계측 코드를 고치고, 다시 번지지 않게 수집 한도를 둬요.
</Situation>

## 1. 시계열이 많은 지표를 찾으세요

시계열이 많은 지표, 곧 <Term slug="foundations/time-series-and-labels">카디널리티</Term>(레이블 값 조합의 수)가 큰 지표부터 찾아요. Prometheus 3에선 Status 메뉴의 TSDB status(시계열 저장소 통계) 화면에서 바로 볼 수 있어요. 새 값을 모아 두는 메모리 영역(head block)의 시계열을 세서 보여 줘요.

맨 위 TSDB Head Status의 Number of Series가 head block의 시계열 총수예요. Top 10 series count by metric names 표에는 시계열이 많은 지표 10개가 나와요. 지표 하나 때문에 시계열이 두 배가 됐다면, 그 지표가 절반 이상을 차지해 맨 위에 와요.

화면을 열 수 없다면 배포한 서비스(`job`)를 골라 지표마다 세요. 아래 질의는 `api` 서비스에서 시계열이 많은 지표 10개를 보여 줘요. `__name__`은 지표 이름이 든 레이블이라, `count by (__name__)`가 지표마다 시계열을 세요.

```text
# api 서비스의 지표별 시계열 수, 많은 순 10개
topk(10, count by (__name__) ({job="api"}))
```

서비스를 고르지 않고 모든 지표를 세면, 모든 시계열을 읽어서 Prometheus에 부담을 줘요. 그래서 그래프 대신 Table 탭(한 시각의 값만 계산하는 화면)에서 실행해요.

이 질의는 지금 값이 들어오는 시계열만 세서, 화면 숫자보다 작을 수 있어요. 화면은 모든 서비스를 세고, 끝난 시계열도 head block에서 빠질 때까지 세요.

**확인 방법**: 아래 지표를 Graph 탭에서 지난 하루 범위로 그려요. 수집 대상(Prometheus가 값을 가져가는 서버)이 한 번에 내보낸 샘플(sample, 수집한 값 하나) 수예요. 시계열마다 샘플이 하나라 앱이 내보낸 시계열 수와 같고, 대상마다 한 줄이라 가벼워요.

```text
scrape_samples_scraped{job="api"}
```

늘기 시작한 시각이 배포 시각과 맞으면, 그 배포에서 바뀐 계측 코드가 원인 후보예요.

## 2. 값이 늘어나는 레이블을 찾으세요

지표를 찾았으면 레이블마다 값이 몇 개인지 세요. `method`나 `status`처럼 값이 몇 개로 정해진 레이블은 시계열을 끝없이 늘리지 못해요. 그래서 값이 다른 레이블보다 훨씬 많은 레이블이 원인이에요.

끝없이 늘어나는 값의 예는 실제 경로(`/users/123`), 사용자 ID·요청 ID, 에러 메시지 원문이에요. 요청이나 사용자마다 새 값이 나와서, 새 값마다 시계열이 생겨요. Prometheus 문서도 사용자 ID처럼 끝없는 값은 레이블로 쓰지 말라고 해요.

**확인 방법**: TSDB status 화면의 Top 10 label names with value count 표부터 봐요. 값이 수천 개인 레이블이 1단계 지표에 붙었는지는 아래 첫 질의로 Table 탭에서 확인해요. 화면이 없다면 `route` 자리에 레이블 이름을 바꿔 넣으며 실행해요.

```text
# route 값 개수. http_requests_total 자리엔 1단계에서 찾은 지표를 넣어요
count(count by (route) (http_requests_total{job="api"}))

# 시계열이 적은 route 값 10개
bottomk(10, count by (route) (http_requests_total{job="api"}))
```

첫 질의는 안쪽 `count by (route)`가 값마다 한 줄을 만들고, 바깥 `count`가 그 줄을 세요. 둘째 질의로 실제 값을 읽는데, 늘어난 값은 값마다 시계열이 적어서 적은 순으로 봐요. `/users/1`, `/users/2`처럼 ID가 든 값이 줄지어 있으면 실제 경로가 들어간 거예요.

## 3. 계측 코드를 고치세요

레이블에는 값이 몇 개로 정해진 것만 남겨요. 요청 경로는 라우터가 맞춘 경로 틀(`/users/:id`)로 바꿔요. OpenTelemetry(오픈소스 계측 도구) 규약도 경로(`http.route`)엔 경로 틀을 쓰고, 실제 경로로 대신할 수 없다고 해요.

사용자 ID·요청 ID는 지표에서 빼고 <Term slug="foundations/logs-metrics-traces">트레이스나 로그</Term>에 남겨요. 에러 메시지는 `timeout`처럼 몇 가지로 정한 에러 종류로 바꾸고, 원문은 로그에 남겨요. OpenTelemetry 규약도 에러 종류(`error.type`)는 값이 적어야 한다고 해요.

급하면 그 배포부터 되돌리고, 안 되면 `metric_relabel_configs`(저장 전에 시계열을 거르는 설정)로 그 지표를 버려요. 그 지표로 그린 대시보드가 비고, 그 지표에 건 Prometheus 알림 규칙도 <Term slug="foundations/no-data-vs-zero">결과가 비어</Term> 울리지 않아요. 그래서 코드를 고칠 때까지만 써요.

```yaml
scrape_configs:
  - job_name: api
    static_configs:
      - targets: ['api:8080']
    metric_relabel_configs:
      # 지표 이름(__name__)이
      - source_labels: [__name__]
        # 이 값과 통째로 같으면
        regex: http_requests_total
        # 저장하지 않고 버려요
        action: drop
```

늘어난 레이블만 지우는 `labeldrop`은 여기에 쓰지 않아요. 그 레이블만 달랐던 시계열이 같은 레이블 조합이 되면, 값 하나만 남고 나머지는 에러 없이 사라져요. 또 `metric_relabel_configs`는 수집한 뒤에 버리는 거라, 앱은 그 시계열을 계속 만들어 내보내요.

**확인 방법**: 고친 코드를 배포했으면 임시로 버리던 설정을 지우고, 2단계의 값 개수 질의를 다시 실행해요. `route` 값 개수가 경로 틀 개수만큼으로 줄면 돼요. TSDB status 화면의 Number of Series는 옛 시계열이 head block에서 정리될 때까지 몇 시간 높게 남을 수 있어요.

## 4. 수집 한도를 두세요

한 서비스의 실수가 Prometheus 전체를 흔들지 않게, 서비스마다 수집 한도를 둬요. 아래 한도는 모두 `metric_relabel_configs`로 거르고 남은 값에 걸려요. 하나라도 넘으면 그 수집 전체가 실패로 처리돼요.

`sample_limit`은 대상 하나를 한 번 수집할 때 남길 샘플 수의 상한이에요. `label_limit`은 샘플 하나의 레이블 수, `label_value_length_limit`은 레이블 값 하나의 길이(바이트) 상한이에요. 기본값은 모두 0이고, 0은 상한이 없다는 뜻이에요.

```yaml
scrape_configs:
  - job_name: api
    # 거르고 남은 샘플이 5만 개를 넘으면 수집 전체를 실패로 처리해요
    sample_limit: 50000
    # 샘플 하나에 레이블이 30개를 넘어도 실패로 처리해요
    label_limit: 30
    # 레이블 값 하나가 200바이트를 넘어도 실패로 처리해요
    label_value_length_limit: 200
    static_configs:
      - targets: ['api:8080']
```

한도를 넘으면 늘어난 시계열만이 아니라 그 대상의 <Term slug="foundations/empty-graph">새 값이 모두 끊기고</Term>, `up`(수집 성공 1, 실패 0)은 0이 돼요. 그래서 한도는 평소 값보다 넉넉하게 잡고, `up == 0` 알림과 함께 둬요. 평소 샘플 수는 `scrape_samples_post_metric_relabeling{job="api"}`(거르고 남은 샘플 수)로 봐요.

**확인 방법**: 설정을 적용한 뒤 `up{job="api"}`가 1로 남는지 봐요. 0이 됐다면 Status → Target health 화면의 에러에 `limit exceeded`가 있는지 봐요. 있다면 평소 값에 걸린 거라 한도를 올려요.

시계열 수가 갑자기 늘면 알림으로 받아요. Prometheus는 head block의 시계열 수를 `prometheus_tsdb_head_series`로 내보내요. 아래 규칙은 이 값이 하루 전의 1.5배를 넘은 채로 30분 이어지면 울려요.

```yaml
groups:
  - name: cardinality
    rules:
      - alert: HeadSeriesJump
        # 지금 시계열 수가 하루 전(offset 1d) 값의 1.5배를 넘고
        expr: |
          prometheus_tsdb_head_series{job="prometheus"}
            > 1.5 * prometheus_tsdb_head_series{job="prometheus"} offset 1d
        # 그 상태가 30분(for) 이어지면 울려요
        for: 30m
```

`job="prometheus"`는 Prometheus가 자기 지표를 수집하는 job 이름으로 바꿔요. 1.5배와 30분은 예시 값이에요. 이 알림은 Prometheus 전체를 보니, 울리면 1단계부터 서비스를 좁혀 가요.

OpenTelemetry 사양은 SDK가 지표마다 카디널리티 상한을 두라고 하고, 따로 정하지 않으면 2,000을 쓰라고 해요. 상한을 넘긴 조합의 값은 버리지 않고, overflow 시계열(상한을 넘친 측정값을 모으는 시계열) 하나로 모아요. 이 시계열이 보이면 그 지표가 상한에 걸린 적이 있다는 뜻이에요.

Prometheus에서는 보통 `otel_metric_overflow="true"` 레이블로 찾아요.

```text
# 상한에 걸린 적이 있는 api 서비스의 지표
count by (__name__) ({job="api", otel_metric_overflow="true"})
```
