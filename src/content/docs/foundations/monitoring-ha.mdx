## 모니터링 시스템도 장애가 나요

모니터링 시스템이 멈추면 다른 시스템의 장애도 못 봐요. 그래서 모니터링 시스템도 이중으로 두고, 한 대가 감당 못 할 만큼 커지면 나눠요. Prometheus 계열을 예로 들면 구성은 이래요.

<Figure caption="같은 대상을 Prometheus 두 대(수집 A, B)가 수집하고, 둘 다 중앙 저장소와 Alertmanager 두 대에 보내는 구성 예시예요.">
  <HaTopology aria-label="수집 대상을 Prometheus 수집 A(replica=a)와 수집 B(replica=b)가 함께 수집하고, 두 대 모두 중앙 저장소(Thanos·Mimir)로 보내며, 두 대 모두 Alertmanager 두 대에 알림을 보내는 그림" />
</Figure>

키우는 방법은 목적에 따라 네 가지예요.

- 이중화(HA 쌍): 같은 대상을 두 대가 똑같이 수집해요. 한 대가 죽어도 그래프에 빈칸이 없어요.
- 나누기(샤딩): 대상을 나눠 맡겨요. 시계열이 너무 많아 한 대의 메모리로 못 담을 때 써요.
- 모으기: 여러 곳의 숫자를 한 곳으로 보내요. remote write로 샘플을 그대로 보내거나, federation으로 다른 Prometheus의 값을 긁어 와요.
- 에이전트 모드: 수집해서 보내기만 하는 가벼운 Prometheus예요. 자기 안에서 질의하거나 알림 규칙을 돌리지는 못해요.

오래 담는 일은 Thanos나 Mimir 같은 장기 저장소가 맡아요. 저장 방식은 <Term slug="foundations/tsdb-storage">시계열 DB가 저장하는 법</Term>에서 다뤄요.

## HA 쌍은 값이 두 배가 돼요

Prometheus 3.15 세 대를 띄워 봤어요. A와 B가 같은 대상(1초에 주문 10건씩 느는 카운터)을 5초마다 긁고, 둘 다 저장소 C로 remote write를 보냈어요. A와 B는 `external_labels`로 `replica`를 a와 b로 달았어요.

C에는 같은 카운터가 replica만 다른 시계열 두 개로 쌓였어요. 화면에서 흔히 쓰는 `sum(rate(...))`는 두 배를 보여 줘요.

  <Bars
    ariaLabel="replica a 9.3, replica b 10, 그냥 더함 19.3, replica 중 큰 값 하나 9.5. 단위는 초당 주문 수"

a와 b의 값이 조금 다른 것은 긁은 시각이 어긋나서예요. 그래서 둘을 더하거나 평균 내지 말고, 하나를 골라 써야 해요. 이것을 중복 제거(deduplication)라고 해요.

중복 제거는 두 곳에서 해요.

- 질의할 때: Thanos의 질의 서버는 replica만 다른 시계열을 하나로 보여 줘요. 이 레이블 이름을 `--query.replica-label`로 알려 줘요.
- 받을 때: Mimir는 `cluster`와 `__replica__` 레이블을 보고, 한 쌍에서 리더로 뽑힌 쪽의 샘플만 받아요. 리더가 30초(기본값) 동안 안 보내면 다른 쪽으로 넘어가요.

이런 도구 없이 둘을 한 곳에 모았다면 질의에서 골라야 해요. `max without (replica) (rate(...))`처럼 replica를 빼고 하나만 남긴 뒤 더해요.

```promql
sum(
  max without (replica) (
    rate(orders_total[1m])
  )
)
```

## 저장소가 멈추면 그래프가 늦게 채워져요

remote write는 바로 보내지 않고, Prometheus의 WAL(먼저 적어 두는 기록)을 읽어 큐에 담아 보내요. 받는 쪽이 멈추면 실패한 묶음을 간격을 늘려 가며 다시 보내요. 그동안 보낼 샘플은 WAL에 남아 있어요.

실험에서 C를 60초 동안 껐다 켰어요. A의 `/metrics`에서 가장 최근 샘플 시각과 보내기를 마친 시각의 차이를 봤어요.

### 버퍼에는 한도가 있어요

Prometheus는 받는 쪽이 2시간 넘게 멈추면 보내지 못한 샘플을 잃어요. WAL이 2시간마다 정리되면서 오래된 기록이 지워지기 때문이에요. 에이전트 모드도 같은 2시간이에요.

OpenTelemetry Collector의 내보내기는 기본으로 메모리 큐에 1,000개 묶음까지 쌓아요. 큐가 차면 새 데이터를 버리고, Collector가 다시 뜨면 메모리 큐의 내용도 사라져요. `sending_queue.storage`로 디스크 큐를 켜면 재시작해도 이어서 보내요.

## 알림 경로도 이중으로 둬요

Alertmanager도 두 대 이상 띄우고 서로 알게 해 둬요. 이것을 클러스터로 묶는다고 해요.

같은 알림이 여러 대에 들어와도, 서로 누가 보냈는지 알려 한 번만 보내요. 그래서 Prometheus는 Alertmanager 목록 전체에 알림을 보내야 해요.

Prometheus와 Alertmanager 사이에 로드 밸런서를 두면 알림이 한 대에만 가요. 그 한 대가 죽으면 알림이 사라질 수 있어요. Alertmanager 문서도 로드 밸런서를 두지 말라고 적어요.

HA 쌍에는 함정이 하나 더 있어요. `external_labels`는 시계열뿐 아니라 알림에도 붙어요. 그대로 두면 A와 B의 알림이 replica만 다른 두 알림이 되어, 같은 장애로 알림이 두 번 와요.

```yaml
alerting:
  alert_relabel_configs:
    - action: labeldrop
      regex: replica
```

`alert_relabel_configs`로 알림에서만 replica를 떼면 두 대가 같은 알림을 보내고, Alertmanager가 하나로 묶어요. promtool 3.15로 설정을 검사했어요.

## 모니터링 시스템도 지켜봐요

수집 서버 자신의 숫자도 모아 둬요. Prometheus의 remote write라면 이런 지표가 있어요.

- `prometheus_remote_storage_samples_failed_total`: 끝내 보내지 못하고 버린 샘플 수예요. 늘면 데이터가 빠져요.
- `prometheus_remote_storage_samples_pending`: 아직 보내지 못하고 쌓인 샘플 수예요.
- 보내기 지연: 가장 최근 샘플 시각(`…_highest_timestamp_in_seconds`)에서 보내기를 마친 시각을 뺀 값이에요. 마친 시각은 `…_queue_highest_sent_timestamp_seconds`예요.

보내기 지연이 몇 분을 넘으면 알림을 받아 두면 좋아요. 2시간 한도에 닿기 전에 손쓸 수 있어요. 알림 경로 자체가 살아 있는지는 <Term slug="foundations/alerts-not-arriving">알림이 와야 하는데 안 올 때</Term>의 Watchdog 알림으로 지켜봐요.

<Deeper>
  실험은 Windows에서 Prometheus 3.15.1 세 대로 했어요. A와 B는 5초마다 긁고 remote write로 C(`--web.enable-remote-write-receiver`)에 보냈어요. replica a가 9.3으로 b보다 작은 것은 rate가 구간 끝을 외삽하는 방식과 긁은 시각의 어긋남 때문이에요.

  보내기를 다시 시도하는 간격은 `min_backoff`에서 시작해 실패할 때마다 두 배로 늘고, `max_backoff`에서 멈춰요. 받는 쪽이 돌아온 직후 여러 수집 서버가 한꺼번에 밀린 샘플을 보내서, 받는 쪽에 부하가 몰리기도 해요.

  federation은 다른 Prometheus의 `/federate`에서 고른 시계열을 긁어 와요. 모든 원본 시계열을 옮기기보다, 기록 규칙으로 줄인 값을 위로 모으는 데 맞아요.

  Mimir가 리더를 바꿀 때는 수집 한 번 정도의 데이터가 빠질 수 있어요. 그래서 Mimir 문서는 rate의 구간을 수집 주기의 네 배 이상으로 두라고 권해요.
</Deeper>
