## 1. 규칙이 firing까지 갔는지 보세요

알림 규칙은 조건이 참이 되면 바로 울리지 않아요. `for`로 정한 시간 동안 조건이 이어져야 pending에서 firing이 되고, 그때 Alertmanager로 보내요. 중간에 한 번이라도 거짓이 되면 pending은 처음부터 다시 세요.

<Figure caption="for: 5m 규칙의 예시예요. 처음에는 4분 만에 조건이 풀려 다시 셌고, 두 번째에 5분을 채운 10분에야 firing이 됐어요.">

장애가 짧게 끊겼다 이어지면, 조건이 `for`를 한 번도 채우지 못해 알림이 오지 않아요. 지속 시간을 정하는 법은 <Term slug="foundations/alert-conditions">알림 조건</Term>에서 다뤄요.

**확인 방법**: Prometheus의 Alerts 화면에서 규칙의 상태를 봐요. 지난 시각은 `ALERTS{alertname="규칙 이름"}`으로 질의하면 `alertstate`가 pending이었는지 firing이었는지 보여요.

## 2. 질의가 비어 있지 않은지 보세요

알림 질의의 결과가 비면 규칙은 아무것도 울리지 않아요. 값이 0인 것과 결과가 없는 것은 달라요. 배포로 레이블 이름이 바뀌면, 질의가 아무 시계열도 못 찾아 조용해져요.

데이터가 사라진 것 자체를 알리려면 `absent()`로 규칙을 따로 만들어요. 그 시계열이 하나도 없을 때 1을 돌려줘요.

```promql
absent(
  http_requests_total{job="orders"}
)
```

**확인 방법**: 알림 질의를 그대로 Explore 같은 질의 화면에서 돌려 봐요. 비어 있다면 <Term slug="foundations/empty-graph">그래프가 비어 있을 때</Term>의 순서로 찾아요.

## 3. Alertmanager까지 닿았는지 보세요

firing이 됐는데 Alertmanager 화면에 없다면, Prometheus가 보내지 못한 거예요. Prometheus는 보내다 실패해 버린 알림을 세어 둬요.

```promql
rate(
  prometheus_notifications_dropped_total[5m]
) > 0
```

**확인 방법**: 이 값이 0보다 크면 Prometheus 설정의 Alertmanager 주소와 그 사이 네트워크를 봐요. `prometheus_notifications_errors_total`도 함께 늘어요.

## 4. 잠재운 건 아닌지 보세요

Alertmanager에 알림이 있는데 안 왔다면, 일부러 잠재웠을 수 있어요. 사일런스, 억제(inhibition), 점검 시간(mute time interval)이 알림을 막아요.

<Term slug="foundations/alert-silencing">알림 잠재우기</Term>에서 본 것처럼, 점검 때 건 사일런스가 끝나지 않고 남아 있기도 해요. 억제는 큰 알림이 울리는 동안 레이블이 같은 작은 알림을 막아요.

**확인 방법**: Alertmanager 화면에서 그 알림이 silenced나 inhibited로 표시되는지 봐요. `alertmanager_notifications_suppressed_total`이 늘었다면 무언가가 막고 있어요.

## 5. 맞는 경로로 갔는지 보세요

Alertmanager는 레이블로 <Term slug="foundations/alert-routing">경로 나무</Term>를 내려가 받는 곳을 정해요. 레이블 값은 대소문자까지 똑같아야 맞아요. 맞는 경로가 없으면 맨 위 기본 경로로 가요.

**확인 방법**: `amtool`로 레이블만 넣어 어느 받는 곳으로 가는지 시험해요. 실제로 보내지 않아요. 위 나무에 `team=Payment`를 넣으면 `ops-chat`이 나와요.

```bash
amtool config routes test \
  --config.file=am.yml \
  team=Payment severity=critical
```

## 6. 보내기가 실패했는지 보세요

경로까지 맞았는데 안 왔다면, 채팅방이나 메일로 보내다 실패했을 수 있어요. 웹훅 주소가 바뀌었거나, 토큰이 만료됐거나, 받는 쪽이 에러를 돌려준 경우예요.

```promql
sum by (integration) (
  rate(alertmanager_notifications_failed_total[5m])
) > 0
```

**확인 방법**: 채널 종류(`integration`)마다 실패가 늘었는지 보고, Alertmanager 로그에서 그 채널의 에러 메시지를 읽어요.

## 7. 묶여서 기다리는지 보세요

Alertmanager는 같은 묶음의 알림을 모아 한 번에 보내려고 기다려요. 새 묶음은 `group_wait`(기본 30초), 이미 보낸 묶음의 새 알림은 `group_interval`(기본 5분)만큼 기다려요. 같은 알림을 다시 보내는 건 `repeat_interval`(기본 4시간)마다예요.

`group_wait`가 지나기 전에 풀린 알림은 아예 보내지 않아요. 그래서 20초쯤 튀었다 풀린 장애는 알림 없이 지나가요.
