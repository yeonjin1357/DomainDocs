## 이름표가 같아야 신호가 이어져요

모니터링 화면은 서비스 이름으로 데이터를 모아요. 에러 그래프에서 트레이스로 건너가면, 같은 서비스 이름과 같은 시간대의 트레이스를 찾아 보여 줘요. 로그로 건너갈 때도 같아요.

그런데 이름을 붙이는 쪽이 신호마다 달라요. 트레이스는 앱의 계측 설정에서, 로그는 수집 에이전트 설정에서 이름을 받기도 해요. 예를 들어 Datadog은 따로 정하지 않으면 로그의 서비스 이름을 컨테이너 이미지의 짧은 이름으로 정해요.

## 기본 이름표 셋: 서비스, 환경, 버전

업계는 이름표 세 개를 모든 신호에 붙이라고 권해요. OpenTelemetry는 이 값을 리소스 속성(resource, 데이터를 낸 쪽을 알리는 속성)으로 정해 뒀어요. Datadog은 `env`, `service`, `version`을 예약 태그로 둬요.

- **서비스**(`service.name`): 무엇인지예요. 같은 코드를 여러 개 띄워도 이름은 하나예요.
- **환경**(`deployment.environment.name`): 어디서 도는지예요. `production`, `staging`처럼 써요.
- **버전**(`service.version`): 어느 배포인지예요. 배포할 때마다 바뀌어야 해요.

같은 서비스를 띄운 하나하나는 인스턴스예요. `service.instance.id`로 구별해요. 서비스 여러 개를 한 시스템으로 묶을 때는 `service.namespace`를 써요.

<Figure caption="shop 묶음에 서비스 둘이 있고, checkout은 인스턴스 둘로 떠 있어요. 인스턴스가 몇 개든 서비스 이름은 하나예요.">

환경과 버전은 이 나무에 들어가지 않아요. OpenTelemetry 규약은 환경 이름이 달라도 `service.name`이 같으면 같은 서비스로 쳐요. 그래서 환경으로 나눠 보지 않으면 운영과 시험의 숫자가 한 서비스로 섞여요.

## 이름표는 여러 곳에서 붙어요

서비스, 환경, 버전은 배포하는 쪽만 알아요. 그래서 앱이 직접 붙여요. OpenTelemetry SDK는 환경 변수 두 개로 정해요.

```sh
export OTEL_SERVICE_NAME=checkout
export OTEL_RESOURCE_ATTRIBUTES=\
deployment.environment.name=\
production,service.version=1.4.2
```

줄 끝의 `\`는 줄을 이어 붙여요. 실제 값은 쉼표로 이은 한 줄이에요. 두 변수에 서비스 이름이 함께 있으면 `OTEL_SERVICE_NAME`이 이겨요.

앱 밖의 에이전트나 Collector는 어디서 도는지를 덧붙여요. 호스트 이름, 쿠버네티스의 파드·네임스페이스·노드 이름이에요. 앱은 자기가 어느 파드에서 도는지 모르니, 이건 수집 쪽이 맡아요.

<Figure caption="앱은 자기만 아는 서비스·버전·환경을 붙이고, 에이전트나 Collector는 어디서 도는지를 덧붙여요.">

앱이 서비스 이름을 정하지 않았다면 Collector가 쿠버네티스 정보로 채우게 할 수 있어요.

OpenTelemetry가 권하는 순서에서는 파드 애노테이션 `resource.opentelemetry.io/service.name`이 먼저예요. 그다음은 레이블 `app.kubernetes.io/instance`와 `app.kubernetes.io/name`이에요. 그래도 없으면 Deployment 이름, 파드 이름 순으로 내려가요.

이름을 정하는 곳이 여럿이면 이름이 갈려요. 앱 설정은 `checkout`인데 레이블이 `shop-checkout`이면, 어느 쪽이 붙었느냐에 따라 다른 서비스가 돼요. 그래서 이름은 배포 설정 한 곳에서 정해 앱 환경 변수와 레이블에 같이 넣어요.

## 환경 이름표가 빠지면 숫자가 섞여요

Prometheus는 OTLP(OpenTelemetry 전송 규약)로 받은 이름표를 자기 방식으로 바꿔요. `service.name`은 `job`이, `service.instance.id`는 `instance`가 돼요. `service.namespace`가 있으면 `shop/checkout`처럼 `job` 앞에 붙어요.

나머지 이름표는 기본으로 지표에 붙지 않아요. `target_info`라는 지표 하나에 따로 모여요. 환경과 버전도 여기로 가요.

직접 돌려 봤어요. Prometheus 3.15.1에서 OTLP 받기를 켜고 `checkout` 서비스의 지표를 보냈어요. 운영에서 주문 100건, 스테이징에서 7건이에요.

서비스별로 더하는 질의가 두 환경을 하나로 더했어요.

```promql
sum by (job) (orders_total)
```

고치는 길은 둘이에요. 첫째는 받을 때 레이블로 올리는 거예요. 설정의 `promote_resource_attributes`에 적은 속성은 모든 지표에 레이블로 붙어요.

```yaml
otlp:
  promote_resource_attributes:
    - deployment.environment.name
    - service.version
```

이렇게 바꾸자 지표마다 `deployment_environment_name` 레이블이 붙었어요. 점은 밑줄로 바뀌어요. 같은 질의를 환경까지 나눠 묶으면 운영 100, 스테이징 7로 갈라져요.

둘째는 질의에서 `target_info`를 이어 붙이는 거예요. 두 지표에 같이 있는 `job`과 `instance`를 열쇠로 써요.

```promql
sum by (
  job,
  deployment_environment_name
) (
  orders_total
  * on (job, instance)
  group_left (
    deployment_environment_name
  )
  target_info
)
```

이 질의도 운영 100, 스테이징 7로 나눴어요. 다만 질의마다 이 꼬리를 붙여야 해요. 늘 나눠 보는 환경과 버전은 레이블로 올려 두는 편이 편해요.

## 서비스 카탈로그: 이름표에 주인을 이어요

이름표가 맞으면 어느 서비스인지는 풀려요. 장애 때 다음 물음은 누구에게 연락하느냐예요. 서비스 카탈로그(service catalog)는 서비스마다 주인 팀과 연락처를 적은 목록이에요.

카탈로그에는 흔히 이런 걸 적어요.

- **주인 팀**: 고치고 결정하는 팀이에요. 한 팀만 둬요.
- **당직 연락처**: 알림을 받을 당직 일정이에요.
- **저장소와 런북**: 코드와 대응 절차가 있는 곳이에요.
- **의존**: 부르는 DB, 큐, 다른 서비스예요.
- **중요도**: 멈추면 매출이나 사용자에게 바로 닿는지예요.

Backstage(오픈소스 개발자 포털)는 서비스 저장소에 파일 하나로 적어요. 코드 옆에 있어서 코드와 함께 고쳐져요.

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: checkout
spec:
  type: service
  lifecycle: production
  owner: team-payments
  system: shop
  dependsOn:
    - resource:orders-db
```

`spec`의 `type`, `lifecycle`, `owner`는 꼭 적어야 해요. `owner`는 책임지는 단 하나의 주체로, 보통 팀이에요. `metadata.name`은 서비스 이름표와 같게 둬야 알림에서 바로 찾아요.

같은 서비스가 두 줄로 보이면 이름을 정하는 곳이 둘 이상이에요. `unknown_service`로 시작하는 줄은 앱이 이름을 정하지 않은 거예요. 이 PC의 윈도우에서 돌린 Python 앱은 `unknown_service:python.exe`로 들어왔어요.

환경 값도 봐요. 위 실험의 checkout-svc는 환경을 `prod`로 보냈어요. 환경을 `production`으로 거르면 이 서비스는 통째로 빠져요.

<Deeper>
  환경 속성의 이름은 바뀌었어요. 옛 이름 `deployment.environment`는 의미 규약 1.27.0에서 `deployment.environment.name`으로 옮겼어요. 새 이름은 1.41.0에서 안정(stable)이 됐어요.

  그래서 Prometheus가 권하는 올릴 속성 목록에는 둘이 다 있어요. 옛 SDK와 새 SDK가 섞여 있어도 환경 레이블이 붙어요.

  `service.instance.id`는 무작위 UUID로 만들라고 권해요. 파드 이름 같은 값은 드러내지 않을 정보로 다루라고 해요. Prometheus 안내도 인스턴스가 시작할 때마다 새 UUID를 만들라고 해요.

  Prometheus에는 `target_info`를 쉽게 잇는 `info()` 함수도 있어요. 아직 실험 기능이라 `--enable-feature=promql-experimental-functions`로 켜야 해요.

  `target_info`의 레이블이 바뀌면 옛 줄과 새 줄이 기본 5분 동안 겹쳐 조인이 실패할 수 있어요. `info()`는 가장 최근 줄을 골라 이 문제가 없어요.

  레이블로 올린 버전은 배포마다 새 값이에요. 배포할 때마다 시계열이 새로 생기고 옛 시계열은 끊겨요. 버전 수가 적어 보통은 괜찮지만, 배포가 아주 잦으면 시계열 수를 지켜봐요.

  Datadog은 쿠버네티스에서 `tags.datadoghq.com/env` 같은 레이블에 세 값을 넣으라고 안내해요. 레이블은 워크로드와 파드 템플릿 양쪽에 붙여요. 트레이스를 내는 앱에는 `DD_ENV`, `DD_SERVICE`, `DD_VERSION` 환경 변수에도 같은 값을 넣어요.

  OpenTelemetry 의미 규약에는 서비스의 중요도를 적는 `service.criticality`도 있어요. 값은 `critical`, `high`, `medium`, `low`이고, 아직 alpha 단계예요.
</Deeper>
