<KeyPoints>
  <Point title="서비스는 요청·에러·지연(RED)으로 봐요">
    요청을 받아 답하는 서비스는 RED로 봐요. Tom Wilkie가 만든 방법이에요. Rate는 초당 요청 수, Errors는 그중 실패하는 요청 수, Duration은 요청이 걸린 시간이에요.

    Duration은 평균 하나가 아니라 p99(요청의 99%가 이 시간 안에 끝나고, 느린 1%는 더 걸리는 값) 같은 <Term slug="foundations/percentiles">백분위수</Term>로 봐요. 세 숫자 모두 사용자가 직접 겪는 일이라, RED는 사용자 경험을 대신 보여 줘요.
  </Point>
  <Point title="원인은 자원의 사용률·포화·에러(USE)로 찾아요">
    CPU·메모리·디스크·네트워크 같은 자원은 Brendan Gregg가 만든 USE로 봐요. Utilization(사용률)은 자원이 일하느라 바빴던 시간의 비율이에요. Saturation(포화)은 처리하지 못하고 쌓아 둔 일의 양으로, CPU라면 실행 대기열(run queue) 길이예요.

    Errors는 디스크 I/O 에러처럼 자원이 낸 에러 횟수예요. USE는 문제의 원인을, RED는 사용자가 겪는 증상을 보여 줘요. 그래서 RED가 나빠지면 USE로 원인을 찾아요.
  </Point>
  <Point title="평균 사용률은 짧은 포화를 숨겨요">
    사용률은 구간 평균이라, 짧게 몰린 순간을 숨겨요. Gregg가 든 사례에서는 모니터링 도구의 CPU 사용률이 80%를 넘지 않았는데도, CPU 포화로 지연이 생겼어요. 도구는 5분 평균을 보여 줬고, 그 5분 안에 CPU는 몇 초씩 100%를 찍었어요.

    그래서 사용률 옆에 포화를 함께 둬요. Gregg는 포화가 조금이라도 있으면(0보다 크면) 문제가 될 수 있다고 봐요.
  </Point>
</KeyPoints>

<Checkpoints>
  <Check>서비스 대시보드 첫 화면이 CPU·메모리 사용률뿐이라면 다시 보세요. 서버가 바쁜지는 보여도, 사용자 요청이 실패하거나 느린지는 안 보여요. 첫 화면에는 RED를 두세요.</Check>
  <Check>에러를 초당 건수로만 보여 준다면 비율도 함께 보여 주세요. 에러율이 0.4% 그대로여도, 요청이 초당 1,200건에서 2,400건이 되면 에러는 4.8건에서 9.6건이 돼요. 건수만 보면 상황이 두 배로 나빠진 것처럼 보여요.</Check>
  <Check>지연을 평균으로만 보여 준다면 느린 요청이 숨어요. Google SRE Book은 평균 100ms인 웹 서비스에서도 요청 1%가 5초씩 걸릴 수 있다고 해요. p95·p99 같은 <Term slug="foundations/percentiles">백분위수</Term>를 함께 보여 주세요.</Check>
  <Check>자원 여유를 사용률 평균만 보고 판단했다면 다시 보세요. 앞의 사례처럼 5분 평균이 80%를 넘지 않아도, 그 안에 몇 초짜리 100%가 숨어 있을 수 있어요. CPU 실행 대기열, 디스크 대기열 같은 포화 지표를 함께 보세요.</Check>

<Deeper>
  ### 네 가지 골든 시그널

  Google SRE Book은 사용자를 상대하는 시스템에서 지표를 넷만 잴 수 있다면 이 넷을 재라고 해요. 지연(latency), 트래픽(traffic), 에러(errors), 포화(saturation)예요.

  지연·트래픽·에러는 RED의 Duration·Rate·Errors와 같아요. 그래서 Tom Wilkie는 골든 시그널을 RED에 포화를 더한 것으로 설명해요.

  골든 시그널의 포화는 서비스가 얼마나 찼는지로, 메모리처럼 가장 모자란 자원을 중심으로 봐요. 같은 책은 많은 시스템이 사용률 100% 전에 느려지니, 사용률 목표를 정해 두라고 해요.

  지연이 느는 게 포화의 앞선 신호일 때가 많아서, 1분 같은 짧은 구간의 p99로 일찍 알아챌 수 있다고도 해요.

  실패한 요청의 지연은 따로 봐요. DB 연결이 끊겨 곧바로 돌려준 500 에러는 빨라서, 전체 지연에 섞으면 지연이 실제보다 짧아 보여요. 느린 에러는 더 나빠서, 그림처럼 에러를 뺀 p99 옆에 실패한 요청의 p99도 따로 둬요.

  ### USE를 자원마다 적용하기

  먼저 자원 목록을 만들어요. Gregg의 서버용 목록은 CPU, 메모리, 네트워크 인터페이스, 저장 장치, 컨트롤러, 인터커넥트(CPU·메모리·I/O를 잇는 연결)예요. 에러는 보통 빨리 보고 해석하기 쉬워서, 사용률·포화보다 먼저 봐도 돼요.

  Gregg가 든 예시 지표예요.

  | 자원 | 사용률 | 포화 |
  | --- | --- | --- |
  | CPU | CPU가 바빴던 시간 비율(CPU별 또는 전체 평균) | 실행 대기열 길이 |
  | 메모리 | 남은 메모리(적을수록 사용률이 높아요) | 익명 페이징·스와핑(앱 메모리를 디스크로 내보냈다가 다시 읽는 일) |
  | 네트워크 | 송수신량 ÷ 최대 대역폭 | 패킷을 버리거나 받을 칸이 넘친 횟수(`dropped`·`overruns`) |
  | 디스크 | 장치가 바빴던 시간 비율 | 대기열 길이 |

  Gregg의 Linux 체크리스트는 CPU 포화를 `vmstat 1`(1초마다 CPU·메모리 상태를 찍는 명령)의 `r`로 봐요. `r`은 CPU에서 도는 스레드와 기다리는 스레드를 함께 세서, CPU 수를 넘은 만큼은 기다리는 스레드예요. 메모리 포화는 같은 명령의 `si`·`so`(스왑 입출력)로 봐요.

  load average(CPU를 쓰거나 기다리는 작업 수의 평균)는 Linux에서 디스크 I/O를 기다리는 작업도 세요. 그래서 이 체크리스트는 CPU 지표로 쓰지 않아요. Wilkie의 발표 자료가 CPU 포화로 쓰는 load average ÷ CPU 수는 디스크 I/O 대기로도 올라요.

  디스크 포화는 `iostat -x`(디스크마다 처리 통계를 찍는 명령)로 봐요. 체크리스트는 `aqu-sz`(옛 이름 `avgqu-sz`)가 1보다 크거나, `await`(대기를 포함한 요청당 평균 시간)가 높은지 봐요. `aqu-sz`는 장치에 보낸 요청의 평균 개수라서, 처리 중인 요청도 세요.

  SSD처럼 요청을 동시에 처리하는 장치는 `aqu-sz`가 1을 넘거나 `%util`(바빴던 시간 비율)이 100%여도 한계가 아닐 수 있어요.

  스레드 풀 같은 소프트웨어 자원도 USE로 봐요. 그 포화는 처리를 기다리는 요청 수예요.

  ### RED는 카운터의 rate로 구해요

  RED의 Rate와 Errors는 요청 수 카운터(counter, 계속 더하기만 하는 값)의 <Term slug="foundations/counters-and-rate">rate</Term>(초당 증가량)예요. Wilkie의 발표 자료처럼 요청 시간 히스토그램(요청 시간을 구간별로 센 지표) 하나로 RED 셋을 모두 구해요. Prometheus 클래식 히스토그램(기존 형식)의 `_count`가 요청 수를 세는 카운터라서예요.

  ```text
  Rate:     sum(rate(request_duration_seconds_count{job="order-api"}[5m]))
  Errors:   sum(rate(request_duration_seconds_count{job="order-api", status_code=~"5.."}[5m]))
  Duration: histogram_quantile(0.99, sum by (le) (rate(request_duration_seconds_bucket{job="order-api", status_code!~"5.."}[5m])))
  ```

  세 식은 `job="order-api"`로 주문 API만 골라요. `job` 조건을 빼면 모든 서비스의 요청이 한 숫자로 섞여요.

  응답 코드는 `status_code` <Term slug="foundations/time-series-and-labels">레이블</Term>로 골라요. 이 식은 5xx만 에러로 세고, 발표 자료는 2xx가 아닌 응답을 모두 에러로 세요. Google SRE Book은 1초 안에 답하기로 했다면 1초를 넘긴 요청도 에러로 칠 수 있다고 해요.

  그래서 무엇을 에러로 칠지 정하고, 식이 그 기준을 따르는지 확인해요.

  Duration 식은 버킷(`_bucket`) 카운터로 p99를 어림해요. 시계열마다 rate를 구하고 같은 `le`(버킷 경계)끼리 더한 뒤 계산하는 순서는 <Term slug="foundations/percentiles">여러 서버를 합친 p99</Term>와 같아요. 포화를 일찍 보려면 `[1m]`처럼 줄이되, <Term slug="foundations/collection-interval">수집 주기</Term>의 4배 이상(15초 수집이면 1분)으로 둬요.

  `le`만 남기고 더하면 응답 코드도 합쳐져서, 이 식은 `status_code!~"5.."`로 에러가 아닌 요청만 골라요. 실패한 요청의 지연은 `=~"5.."`로 따로 구해요.

  네이티브 히스토그램(Prometheus의 새 히스토그램 형식)에는 `_count`·`_bucket` 시계열이 없어요. 요청 수는 `histogram_count()`로 세고, p99는 `le` 없이 이렇게 구해요.

  ```text
  histogram_quantile(0.99, sum(rate(request_duration_seconds{job="order-api", status_code!~"5.."}[5m])))
  ```

  에러율은 Errors ÷ Rate예요.

  에러가 한 번도 안 난 서비스는 5xx 시계열이 없어, 이 비율이 0%가 아니라 <Term slug="foundations/no-data-vs-zero">빈 결과</Term>일 수 있어요.

  RED는 요청을 받아 답하는 서비스용이에요. Prometheus 문서도 배치 작업의 핵심 지표는 마지막 성공 시각이라고 해요.
</Deeper>
