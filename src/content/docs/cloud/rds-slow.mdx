## 1. CPU가 갑자기 올랐는지 보세요

CPUUtilization이 높다면 DB가 일을 많이 하고 있어요. 다만 AWS 문서는 높은 CPU가 목표한 처리량에 맞는 값이라면 괜찮을 수 있다고 해요. 평소와 견줘 갑자기 올랐는지가 중요해요.

db.t 같은 버스트형 클래스는 CPU 크레딧을 써요. 원리는 <Term slug="cloud/virtual-machines">가상 머신</Term>의 크레딧과 같아요. 다만 RDS의 db.t3·db.t4g는 Unlimited 모드로 설정돼 있어요.

그래서 크레딧(CPUCreditBalance)이 바닥나도 CPU가 기준선에 묶이지 않아요. 기준선을 넘게 쓴 몫은 CPUSurplusCreditBalance에 쌓여요. 이 값이 24시간 동안 벌 수 있는 크레딧을 넘으면, 넘은 몫에 요금이 붙어요.

그러니 크레딧은 느려짐보다 요금의 신호로 봐요. 요금이 붙은 몫은 CPUSurplusCreditsCharged로 보여요.

## 2. 메모리와 읽기 IOPS를 보세요

AWS 문서는 자주 쓰는 데이터와 인덱스(작업 집합)가 거의 다 메모리에 들어가게 하라고 권해요. 그렇지 않으면 같은 데이터를 디스크에서 자꾸 다시 읽어요.

**확인 방법**: 부하가 있을 때 ReadIOPS가 작고 안정적인지 봐요. AWS 문서는 더 큰 메모리 클래스로 올렸을 때 ReadIOPS가 크게 줄었다면, 작업 집합이 메모리에 다 들어가지 않았던 거라고 설명해요. 스왑 사용량(SwapUsage)이 늘었다면 메모리가 모자란 신호예요.

## 3. 디스크 지연과 한도를 보세요

ReadLatency와 WriteLatency는 디스크 읽기·쓰기 한 번에 걸린 평균 시간이에요. 지연이 늘었는데 IOPS가 볼륨이 낼 수 있는 한도에 붙어 있다면, 디스크가 모자란 거예요.

AWS 문서는 I/O가 모자랄 때 더 높은 I/O를 내는 클래스로 옮기거나, 저장소 종류를 바꾸거나, 더 많은 IOPS를 프로비저닝하라고 해요. 저장소의 IOPS·처리량 한도는 <Term slug="cloud/storage">블록·파일·오브젝트 저장소</Term>에서 다뤄요.

FreeStorageSpace도 함께 봐요. 남은 공간이 바닥에 가까우면 쓰기가 멈출 수 있어요.

## 4. 연결 수를 보세요

DatabaseConnections가 평소보다 크게 늘었다면, 앱 쪽에서 연결을 많이 열었거나 쿼리가 느려져 연결이 오래 붙잡혀 있어요. 연결이 한도에 닿으면 새 연결이 실패해요.

이때 어디부터 볼지는 <Term slug="database/too-many-connections">DB 연결이 한도에 닿았을 때 어디부터 볼까</Term>와 같아요.

## 5. 자원이 넉넉하다면 쿼리로 내려가세요

자원 지표가 모두 평소와 같다면 DB 안에서 일이 바뀐 거예요. 늘어난 SQL, 바뀐 실행 계획, 잠금 대기를 찾아요. 순서는 <Term slug="database/slow-database">DB가 느려졌을 때 어디부터 볼까</Term>와 같아요.

관리형 DB도 SQL로 DB 안을 들여다볼 수 있어요. PostgreSQL이라면 `pg_stat_activity`와 `pg_stat_statements`를 그대로 써요. OS 수준의 숫자가 필요하면 Enhanced Monitoring 같은 사업자 기능을 켜요.
