  IAM은 임대 빌딩의 출입증 제도와 비슷해요. 출입증마다 갈 수 있는 층과 할 일이 적혀 있는데, 이게 정책이에요. 정해진 일로 들르는 사람에게는 그날만 쓰는 방문증을 주는데, 이게 역할이에요.

## 보안 그룹과 IAM은 다른 문을 지켜요

## 정책 읽기

AWS의 <Term term="cloud/iam-policy">IAM 정책</Term>은 JSON 문서예요. 아래는 CloudWatch 지표를 읽게 허락하는 정책이에요.

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "cloudwatch:GetMetricData",
      "cloudwatch:ListMetrics"
    ],
    "Resource": "*"
  }]
}
```

`Effect`는 허락(`Allow`)인지 거부(`Deny`)인지예요. `Action`은 `서비스:동작` 꼴의 API 이름이고, `Resource`는 그 동작을 할 수 있는 자원이에요. `*`은 모든 자원을 뜻해요.

`Version`은 정책 문법의 버전이에요. 지금 버전은 `2012-10-17`이라, 날짜처럼 보여도 고치지 않고 그대로 적어요.

## 허락은 쌓이고, 거부가 이겨요

명시한 거부는 어떤 허락보다 앞서요. 그래서 한 정책이 S3 읽기를 허락해도, 다른 정책에 S3 읽기 `Deny`가 있으면 막혀요.

권한은 꼭 필요한 만큼만 줘요. AWS 문서도 이걸 최소 권한(least privilege)이라 부르며 권해요. 모니터링 수집기라면 읽기 동작만 있으면 돼요.

## 서버와 앱은 역할로 권한을 받아요

사람이나 프로그램이 API를 부르려면 자격 증명이 있어야 해요. 하나는 접근 키처럼 지울 때까지 쓰는 자격 증명이에요. 다른 하나는 <Term term="cloud/iam-role">역할</Term>(role)에서 받아 정해진 시간만 쓰는 임시 자격 증명이에요.

AWS 문서는 서버와 앱이 역할의 임시 자격 증명을 쓰라고 권해요. EC2 서버에 역할을 붙이면, 그 안의 앱은 서버의 메타데이터에서 임시 자격 증명을 받아 써요. Lambda 함수도 실행 역할로 권한을 받아요.

## 다른 계정에 맡길 때: 외부 ID

외부 모니터링 서비스가 내 계정의 지표를 읽게 하려면, 그 서비스가 맡을 역할을 내 계정에 만들어요. 이때 역할에 외부 ID를 함께 적어 두라고 AWS 문서가 권해요.

외부 ID는 그 서비스가 다른 고객의 부탁을 받고 내 역할을 잘못 맡는 일을 막아요. 이 문제를 혼동된 대리인(confused deputy)이라고 불러요. AWS는 외부 ID를 비밀로 다루지 않아서, 비밀번호처럼 숨기는 값은 아니에요.

## Azure에서는

Azure는 역할 할당으로 권한을 줘요. 역할 할당은 세 가지로 이뤄져요. 누구에게(보안 주체), 어떤 역할을(역할 정의), 어디에(범위)예요.

보안 주체는 사용자, 그룹, 서비스 주체, 관리 ID 가운데 하나예요. <Term term="cloud/managed-identity">관리 ID</Term>는 Azure 자원에 붙이는 ID라서, 앱이 자격 증명을 따로 두지 않고 토큰을 받아요. AWS에서 서버에 역할을 붙이는 것과 닮았어요.

지표와 로그를 읽기만 하는 역할로는 기본 역할인 Monitoring Reader가 있어요. 거부 할당(deny assignment)이 걸려 있으면, 역할 할당이 있어도 막혀요.

권한이 막히면 지표가 비어요. 에러는 수집기 로그에 AccessDenied로 남고, 화면에는 데이터 없음으로만 보여요. 비어 있는 지표를 찾는 순서는 <Term slug="cloud/cloud-metrics-missing">클라우드 지표가 비어 있을 때</Term>에 있어요.

AWS에서는 API 요청 기록인 CloudTrail에서 거부된 요청을 찾아요. 실패한 요청에는 `errorCode` 칸에 에러 이름이 남아요.

쿠버네티스도 같은 생각으로 권한을 다뤄요. 클러스터 안의 권한은 <Term slug="kubernetes/rbac">권한과 서비스 계정(RBAC)</Term>에서 다뤄요.

<Deeper>
  ### 루트 사용자는 예외예요

  AWS 계정을 만들 때 생기는 루트 사용자는 기본 거부의 예외라서 모든 권한을 가져요. 그래서 AWS 문서는 루트 사용자를 일상 작업에 쓰지 말고 따로 지키라고 해요.

  ### 판정 순서는 더 길어요

  그림은 한 계정 안의 정책만 줄여 그렸어요. 실제로는 조직 정책(SCP), 권한 경계, 세션 정책도 함께 따지고, 이들은 모두 허락해야 통과하는 교집합이에요. 어디서든 명시한 거부가 나오면 막혀요.

  ### 옛 정책 버전

  `Version`에는 `2008-10-17`이라는 옛 값도 있어요. 이 버전으로 쓰면 정책 변수 같은 새 기능을 쓰지 못해요.
</Deeper>
