## 두 가지 소식

클라우드 사업자는 장애와 점검을 두 갈래로 알려요. 하나는 모든 고객이 보는 공개 공지, 다른 하나는 내 계정에만 오는 공지예요.

<Figure caption="공개 상태판은 그 서비스를 쓰든 안 쓰든 모두에게 같은 공지를 보여 줘요. 내 계정 소식은 영향받는 내 자원의 ID까지 짚어 줘요.">
  <HealthScope aria-label="위 카드는 공개 상태판으로, 모든 고객에게 같은 공지를 보여 주며 예시는 us-east-1 EC2 API 지연이에요. 아래 카드는 내 계정 소식으로, 영향받는 내 자원까지 알려 주며 예시는 i-0a1b2c 서버의 11월 20일 퇴역 예정이에요" />
</Figure>

AWS에서는 AWS Health가 이 일을 해요. AWS Health의 공지 하나하나를 <Term term="cloud/health-event">상태 이벤트</Term>(Health event)라고 불러요.

- 공개 이벤트: 특정 계정과 상관없는 서비스 장애예요. 그 리전의 그 서비스를 안 써도 보여요.
- 계정 이벤트: 내 계정이나 조직의 자원에 관한 공지예요. 영향받는 자원(affected entities)의 ID가 함께 와요.

두 이벤트는 AWS Health Dashboard에서 봐요. 모든 고객이 추가 요금 없이 쓰고, 따로 설정할 것도 없어요. 로그인하지 않고도 공개 이벤트만 보는 Service health 페이지도 있어요.

이벤트는 종류가 셋이에요.

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| `issue` | 서비스나 자원에 생긴 뜻밖의 문제 | EC2 API 지연, EBS 볼륨 붙이기 문제 |
| `scheduledChange` | 앞으로 있을 변경과 점검 | 서버 퇴역 예정, RDS 버전 지원 종료 |
| `accountNotification` | 계정의 관리·보안 소식 | 공개된 S3 버킷 경고 |

이벤트는 열림(open), 예정(upcoming), 닫힘(closed) 상태를 가져요. 대시보드와 API에서 90일까지 볼 수 있어요.

Azure도 같은 갈래예요. 모두에게 같은 Azure status 페이지가 있고, 내 구독에 맞춘 Service Health가 있어요. 서버 같은 자원 하나의 상태는 <Term term="cloud/resource-health">Resource Health</Term>가 보여 줘요.

| Resource Health 상태 | 뜻 |
| --- | --- |
| Available | 자원에 영향을 주는 일이 없어요 |
| Unavailable | 플랫폼이나 사용자 쪽 일로 자원을 쓸 수 없어요 |
| Degraded | 쓸 수는 있지만 성능이 떨어졌어요 |
| Unknown | 10분 넘게 자원 소식이 없어요. 할당 해제한 VM에서 흔히 보여요 |

Unavailable은 원인을 둘로 나눠 보여 줘요. 하나는 계획된 점검이나 호스트 고장 같은 플랫폼 일(platform event)이에요. 다른 하나는 VM 멈추기 같은 사용자 쪽 일(non-platform event)이에요.

## 예정된 작업

사업자도 하드웨어를 고치고 바꿔요. 그때 그 위의 서버를 재부팅하거나 다른 호스트로 옮겨야 해서, <Term term="cloud/scheduled-event">예정 이벤트</Term>(scheduled event)로 미리 알려요.

EC2의 예정 이벤트는 다섯 가지예요.

| 이벤트 | 그 시각에 일어나는 일 |
| --- | --- |
| `instance-stop` | 서버가 멈춰요. 다시 켜면 새 호스트로 옮겨져요. EBS 루트 볼륨 서버만 해당돼요 |
| `instance-retirement` | EBS 루트 볼륨이면 멈추고, 인스턴스 스토어 루트면 지워져요 |
| `instance-reboot` | 같은 호스트에서 재부팅해요. 그동안 호스트를 점검해요 |
| `system-reboot` | 재부팅하면서 새 호스트로 옮겨요 |
| `system-maintenance` | 네트워크나 전원 점검으로 잠시 영향을 받을 수 있어요 |

AWS는 계정의 이메일로 시작·끝 시각을 미리 알리고, 같은 내용을 AWS Health 이벤트로도 보내요. 일부 이벤트는 날짜를 다시 잡을 수 있어요. 그래서 점검 시각을 내가 고른 한가한 시간으로 옮길 수 있어요.

서버가 <Term slug="cloud/auto-scaling">자동 확장 그룹</Term>에 들어 있으면 그룹이 알아서 처리해요. 예정 이벤트가 걸린 서버를 고장으로 보고 새 서버로 바꿔 끼워요.

서버 하나만 나쁘면 그 서버의 상태 검사와 안쪽을 봐요. 그 순서는 <Term slug="cloud/vm-status-check">가상 머신 상태 검사가 실패할 때</Term>에 있어요.

여러 자원이 함께 나쁘면 사업자 소식을 봐요. 공지가 없으면 우리 쪽 변경을 의심해요. 클라우드 설정을 누가 바꿨는지는 <Term slug="cloud/audit-logs">감사 로그</Term>에서 찾아요.

화면에서 자원을 AZ별로 묶어 보면 사업자 쪽 문제가 빨리 드러나요. 서로 다른 서비스가 같은 AZ에서 같은 시각에 함께 나빠지는 모양이에요. AZ가 무엇인지는 <Term slug="cloud/regions-and-zones">리전과 가용 영역</Term>에 있어요.

AWS Health 이벤트는 EventBridge로 받아 알림 채널로 보낼 수 있어요. 모든 고객이 추가 요금 없이 써요. 대시보드에 장애·점검 이벤트를 표시로 겹쳐 두면, 지표가 흔들린 이유를 바로 맞춰 볼 수 있어요.

AWS Health API로 이벤트를 가져오려면 Business Support+ 같은 상위 지원 플랜이 있어야 해요. 플랜이 없는 계정에서 부르면 `SubscriptionRequiredException`이 나요. 모니터링 제품이 이 API로 수집한다면, 고객 계정의 지원 플랜에 따라 데이터가 비어요.

<Deeper>
  ### 이벤트에 붙는 표시

  AWS Health 이벤트에는 대응이 필요한지 알려 주는 표시(actionability)가 붙기도 해요. 서비스 장애 이벤트에는 이 표시가 없어요.

  - `ACTION_REQUIRED`: 대응이 필요해요.
  - `ACTION_MAY_BE_REQUIRED`: 내 구성에 따라 대응이 필요할 수 있어요.
  - `INFORMATIONAL`: 알리기만 해요.

  ### 조직 전체를 한곳에서

  AWS Organizations를 쓰면 조직 보기(organizational view)를 켤 수 있어요. 그러면 모든 계정의 상태 이벤트를 관리 계정에서 한꺼번에 봐요.

  ### Azure의 원인 보고

  Azure는 플랫폼 때문에 생긴 VM 중단의 원인을 찾으면, 72시간 안에 Resource Health에 그 내용을 올려요. Resource Health는 포털에서 30일까지의 기록을 보여 줘요.
</Deeper>
